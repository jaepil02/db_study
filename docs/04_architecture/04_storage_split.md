이 문서는 **무엇이 어디로 왜 가는가**를 정한다. 어느 모듈이 어떤 순서로 가르는지(기전)는 [../06_pipeline/04_routing.md](../06_pipeline/04_routing.md)가 정한다. 정책과 기전을 가르는 이유는 기전이 바뀌어도 정책이 흔들리지 않게 하기 위해서다 — 최신값 갱신 주체가 Ingest에서 Collector로 옮겨 가도(ADR-10) "최신값은 Redis 휘발 사본이고 진실은 ClickHouse"라는 정책은 그대로다.

분기는 **"전부 큐를 태운다"가 아니라 "성격을 보고 경로를 고른다"**이다. 그리고 **경로를 고르지 않는 것도 분기의 결과다** — 업무 쓰기가 Stream을 타지 않는 것은 분기의 누락이 아니라 분기가 내린 판정이다(D-04 · REQ-GLB-12). 이 문서의 모든 행은 그 판정이 어느 성격에서 나왔는지, 다른 목적지로 보내면 무엇이 구체적으로 깨지는지를 함께 적는다.

**경계 — 저장 객체의 모양은 여기에 없다.** 테이블 · 컬럼 · 키 패턴의 정본은 [../05_data_stores](../05_data_stores/README.md)다. 이 문서는 루트 README 고정 기준에 있는 저장 객체 이름만 인용하고, 키는 영역 접두(stream · rt · alarm · cache · lock · rl · sess · auth · ch)로 가리킨다.

## 3계층 분기

루트 README 고정 기준과 같은 세 계층이다. 수치(계층 3)의 정본은 루트 README이고, 이 표는 각 계층이 **왜** 그 목적지인지를 고정한다.

| 계층 | 데이터 | 원천 경로 | 목적지 | 판정한 성격 | 다른 목적지로 보내면 |
|------|------|------|------|------|------|
| ① | 태그 원시값 | stream:plc:raw | **ClickHouse 전용**(tag_raw → 롤업) | 추가 전용 · 갱신 없음 · 시간 범위 집계 · 고빈도 | PostgreSQL에 넣으면 행 기반 저장이라 억 단위 행에서 범위 집계 스캔 비용이 급증하고 autovacuum · WAL 증폭이 업무 쓰기와 같은 디스크를 다툰다 — 그 꺾이는 지점을 재는 것이 대조군(SW-09)이다 |
| ② | 알람 판정 · 생산 카운터 | ①과 **같은 스트림** | **갈라진다** — 확정 이벤트 PostgreSQL · 판정 전수 ClickHouse · 핫 상태 Redis Hash | 같은 원천인데 **상태 갱신이 필요한 것과 불변 기록이 서로 다른 저장소를 요구**한다 | 한 저장소로 모으면 — ClickHouse는 확인 · 해제 UPDATE에 부적합하고, PostgreSQL은 판정 전수의 초당 수천 행을 못 받고, 둘 다 매 판정의 상태 왕복을 감당하지 못한다 |
| ③ | 회원 · 작업지시 · 감사 | API 직접(Stream 비경유) | **PostgreSQL 전용**(Redis는 캐시만) | 트랜잭션 · 강한 정합성 · read-your-writes | Stream에 올리면 커밋 응답 직후의 재조회가 아직 적재되지 않은 값을 보고, 재시도가 트랜잭션 밖에서 중복을 만든다(§업무 쓰기가 Stream을 타지 않는 이유) |

- 계층별 기전(어느 모듈이 어느 호출로 가르는가)은 [../06_pipeline/04_routing.md](../06_pipeline/04_routing.md) · ING가 계층별 쓰기 결과를 계측해 분기 대조표의 원천을 만든다(ING-10).

## 성격 판정 기준

새 데이터는 아래 순서로 판정한다. 판정 축은 넷 — **누가 쓰는가 · 갱신되는가 · 누가 즉시 읽는가 · 무엇이 진실인가**다.

```plain
새 데이터 종류
├─ 사람이 API로 쓰고 커밋 직후 다시 읽는가 ──────────────────────────── ③ PostgreSQL 전용
│  └─ 반복 조회가 잦은가 ─────────────────────────── + Redis 캐시 계열(TTL 필수)
└─ 설비 스트림에서 오는가
   ├─ 한 번 쓰고 갱신하지 않는 측정 사실인가 ────────────────────── ① ClickHouse 전용
   │  └─ 점조회가 초당 수백 회인가 ─────────────── + Redis 봉인 계열 휘발 사본(최신값만)
   └─ 측정 사실에서 파생되고 상태가 바뀌는가 ───────────────────── ② 목적별로 갈라짐
      ├─ 다음 판정이 즉시 읽는 핫 상태 ─────────────────────────── Redis 봉인 계열
      ├─ 갱신 없는 판정 전수(분석용) ───────────────────────────── ClickHouse
      └─ 확인 · 해제로 갱신되는 확정 사실 ──────────────────────── PostgreSQL
```

- **첫 분기는 저장소가 아니라 쓰는 주체다.** 사람이 쓰는 데이터는 트랜잭션 경계가 요청 하나와 같아야 해서 비동기 경로에 올릴 수 없다 — 성격 판정이 경로(Stream 경유 여부)부터 고른다.
- **Redis는 세 갈래 모두에 나타나지만 진실의 자리는 한 번도 아니다.** ③의 캐시 · ①의 최신값 사본 · ②의 핫 상태 셋 다 원천이 따로 있다. 핫 상태조차 부분 실패 시 진실은 PostgreSQL alarm_event다(REQ-GLB-13).
- **"+ Redis" 가지는 목적지가 아니라 사본이다.** 목적지는 각 가지의 끝 하나이고, 사본은 생존 정책(TTL 유무)이 다른 두 계열로 갈린다(ADR-05).

## 목적이 다른 세 쓰기

②계층의 알람 판정 한 건은 세 저장소에 쓰인다. **이것은 같은 데이터를 두 곳에 복제하는 dual-write가 아니라 목적이 다른 세 개의 쓰기다**(REQ-GLB-13 · 원본 data_flow.md §8.2).

| 쓰기 | 저장소 | 답하는 질문 | 갱신 | 빈도 | 실패하면 | 진실 여부 |
|------|------|------|------|------|------|------|
| 핫 상태 | Redis alarm 계열 | 다음 판정은 무엇인가(디바운스 진행 · 연속 위반 횟수) | 매 판정 덮어쓴다 | 판정마다 | 판정이 멈춘다 — 봉인 계열이라 실패를 그대로 던진다 | 아님 — PostgreSQL 쓰기 실패 시 되돌린다 |
| 판정 전수 | ClickHouse alarm_eval | 임계값은 적절했는가(오탐 분석) | 없음 — 추가 전용 | 판정마다 | 분석 데이터만 빈다 — 알람 발생 · 해제 · 통지는 정상 동작 | 아님 |
| 확정 이벤트 | PostgreSQL alarm_event | 누가 언제 확인했는가 · 언제 열리고 닫혔는가 | 확인 · 해제로 갱신 | 상태 전이 때만 | 알람이 확정되지 않은 것으로 보고 핫 상태를 되돌려 다음 주기에 재시도 | **진실** |

- 검산: 쓰기 = **3** — 진실 1 · 비진실 2
- **세 쓰기를 하나의 트랜잭션으로 묶지 않는다.** 묶으면 ClickHouse 중단이 알람 확정을 막아, 분석 데이터 하나 때문에 운영자가 알람을 받지 못한다.
- 상태 머신 5상태와 alarm_event 생애 값(ACTIVE · CLEARED)의 대응 정본은 [../11_glossary/03_enums_state_machines.md](../11_glossary/03_enums_state_machines.md)다.

### CDC로 맞추자는 제안에 대하여

**A형 — 통념**: 알람이 PostgreSQL과 ClickHouse 두 곳에 있으니 둘을 CDC(변경 데이터 캡처)로 동기화해야 정합성이 맞는다. **부정**: 두 곳에 있는 것은 같은 사실이 아니다. alarm_event 한 행은 "규칙 하나의 알람 생애 한 번"이고 alarm_eval 한 행은 "행 하나에 대한 판정 한 번"이다 — 생애 한 번에 판정이 수천 번 대응한다. CDC로 alarm_event를 ClickHouse에 복제하면 ClickHouse에 **생애 행의 UPDATE 이력이 mutation으로 쌓이고**, 반대 방향이면 PostgreSQL이 판정 전수 초당 수천 행을 받는다. **진짜 축**: 정합성의 단위가 "값의 일치"가 아니라 "질문별 진실의 자리"다 — 확인 이력의 진실은 alarm_event 하나이고 판정 분석의 원천은 alarm_eval 하나다. **대체 경로**: 둘의 대조가 필요하면 같은 구간의 판정 수(alarm_eval) · 확정 수(alarm_event) · 상태(alarm 계열)를 조회 시점에 대조한다(S7 합격 판정 ① — [../01_overview/05_priorities_roadmap.md](../01_overview/05_priorities_roadmap.md)).

## 업무 쓰기가 Stream을 타지 않는 이유

③계층의 쓰기(회원 · 마스터 · 작업지시 · 실적 · 감사)는 API가 PostgreSQL 트랜잭션으로 직접 커밋한다. Stream은 at-least-once 비동기 경로이고, 그 성질이 업무 쓰기의 두 보장을 깬다.

| 보장 | Stream 경로에서 깨지는 방식 | 구체적 실패 |
|------|------|------|
| read-your-writes | 커밋 응답이 적재 전에 나간다 | 작업지시 상태를 바꾸고 목록을 다시 열면 옛 상태가 보인다 — 사용자가 버튼을 다시 눌러 전이가 두 번 요청된다 |
| 트랜잭션 원자성 | 변경과 감사가 서로 다른 엔트리 · 다른 배치로 적재된다 | 변경은 반영됐는데 감사가 DLQ로 빠지는 창이 생긴다 — 감사 로그가 "누가 바꿨는가"에 답하지 못한다 |
| 제약 위반의 즉시 응답 | 유일 제약 위반이 소비 시점에야 드러난다 | 요청자는 200을 받았는데 행이 없다 — 오류를 돌려줄 요청이 이미 끝났다 |
| 재시도의 멱등 | at-least-once 재시도가 트랜잭션 밖에서 일어난다 | 결정적 토큰은 ClickHouse 파트 중복 제거용이라 PostgreSQL 삽입을 막지 못한다 — 재시도가 중복 작업지시를 만든다 |

- 검산: 깨지는 보장 = **4**
- **B형 — 업무 쓰기가 Stream을 타지 않는 것은 분기의 누락이 아니다.** 반대 시나리오: "모든 쓰기를 큐로 일원화"하면 위 네 실패가 전부 생기고, 그것을 막으려면 소비 측에 트랜잭션 조정 · 응답 대기 · 제약 사전 검사를 다시 지어야 한다 — 결국 동기 경로를 큐 위에 재구현한다. **파생 지침**: ING는 ③을 **받지 않는 것으로** 분기에 참여하며(ING-10), 업무 CRUD 부하 중 Stream 유입량이 CRUD와 무관하게 움직이는 것이 이 판정의 검증이다(REQ-GLB-12).
- ③의 캐시(cache 계열)는 커밋 **뒤에만** 삭제한다 — 무효화 체인의 정본은 [../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md)(ADR-12).

## 중복 저장의 유일한 예외

**중복 저장**은 같은 사실을 **수명 제한 없이** 두 저장소가 보유하는 것이다. 이 정의로 가르면 중복 저장은 하나뿐이다 — 태그 최신값(REQ-GLB-11 · 원본 architecture.md §5).

| 후보 | 같은 사실인가 | 수명 제한 | 판정 | 근거 |
|------|------|------|------|------|
| 태그 최신값(Redis rt 계열 ↔ ClickHouse tag_raw) | 같다 — 태그별 마지막 행 | **없다** — 봉인 계열 · 덮어쓰기 | **중복 저장 — 유일한 예외** | 초당 수백 회 점조회를 ClickHouse가 받지 못한다. 불일치 시 **ClickHouse가 진실**이고 argMax로 재구성한다 |
| 조회 결과 캐시(cache 계열) | 같다 — 집계 결과 | 있다 — TTL | 캐시 | TTL과 volatile-lru가 수명을 끊는다 |
| 마스터 캐시(cache 계열 · dict_tag) | 같다 — 태그 메타 | 있다 — TTL · 재적재 주기 | 캐시 | 원천은 PostgreSQL 하나 · 변경 시 무효화 체인 |
| 알람 핫 상태(alarm 계열) ↔ alarm_event | **다르다** — 판정 진행 대 이벤트 생애 | 없다 | 중복 아님 | §목적이 다른 세 쓰기 |
| 대조군 plc_tag_raw_control ↔ tag_raw | 같은 행 집합 | SW-09 on에서만 존재 | **중복 아님 — 계측물** | §대조군은 중복이 아니라 계측물 |
| 스풀 파일 ↔ Stream | 같은 엔트리 | 위험 단계 동안만 | 중복 아님 — 경로 | 둘 중 한쪽에만 있다 — 스풀은 Stream에 넣지 못한 것의 대기열이다 |

- 검산: 후보 = **6** — 중복 저장 1 · 캐시 2 · 중복 아님 3
- **최신값이 예외인 대가 — 갱신 경로가 ClickHouse에 묶인다.** 현행 잠정안은 삽입 성공 · XACK 뒤에 갱신하므로 ClickHouse가 멈추면 최신값도 멈춘다(ADR-10). 이 결합과 대안의 실측 비교는 [06_backpressure_failure.md](./06_backpressure_failure.md) §ClickHouse 중단 시 최신값 정지. 정책은 갱신 주체와 무관하다 — 누가 갱신하든 Redis는 사본이고 진실은 ClickHouse다.
- **Redis 자체가 중단되면 최신값은 ClickHouse로 폴백하지 않는다.** 키가 비어 있는 것(복원 대상)과 Redis에 접속할 수 없는 것(503)은 다르다 — 전 요청을 ClickHouse 점조회로 돌리면 적재까지 밀린다(REQ-GLB-09).

## 대조군은 중복이 아니라 계측물

**B형 — 대조군 plc_tag_raw_control은 원시값을 PostgreSQL에 두 번째로 저장하지만 "시계열은 ClickHouse 전용"의 위반이 아니다.** 대조군은 목적지가 아니라 **목표 ①의 실험 계측물**이다(D-05 · ADR-17). 기본 off이고 SW-09 on에서만 같은 배치를 양쪽에 싣는다. **반대 시나리오**: 대조군을 분기 목적지로 취급하면 ① 조회 API가 대조군을 원천으로 읽기 시작해 ClickHouse와 PostgreSQL 중 무엇이 진실인지 흐려지고 ② SW-09가 기본 on이 되어 모든 삽입 처리량에 대조군 비용이 섞여 목표 ②의 수치가 오염되며 ③ 대조군 삽입 실패가 XACK를 막아 계측물의 실패가 분기 경로를 멈춘다. **파생 지침**: 조회 표면은 대조군을 읽지 않는다 · SW-09 기본 off · 대조군 삽입 실패는 XACK를 막지 않는다(REQ-ING-15). 설계 정본은 [../05_data_stores/10_olap_vs_rdb_control.md](../05_data_stores/10_olap_vs_rdb_control.md)다.

- 대조군 삽입 의미론은 [../05_data_stores/10_olap_vs_rdb_control.md](../05_data_stores/10_olap_vs_rdb_control.md)가 판정했다 — ClickHouse 삽입 성공 뒤 배치당 COPY 1회 · 재시도 없음 · 재전달 중복은 구간 count 대조로 검출 · 실패 · 중복 구간은 대조 무효(ADR-17). 기전은 [../06_pipeline/04_routing.md](../06_pipeline/04_routing.md).
- **목표 ①과 ②는 비교 방향이 반대다.** ①은 데이터를 고정하고 저장소를 바꾸며(SW-09), ②는 저장소를 고정하고 역할을 바꾼다(SW-01~08 · SW-11). 두 축을 한 측정에 섞지 않는다([../02_features/13_switch_matrix.md](../02_features/13_switch_matrix.md) 조합 제약).

## ②계층 생산 카운터 판정

루트 README 고정 기준은 ②계층을 "알람 판정 · 생산 카운터"로 적었다. 알람 판정은 세 쓰기가 설계됐지만 생산 카운터는 원본에 기전이 없다. 같은 "생산 수량"이 ②와 ③에 나타나므로 **정책 수준에서 둘을 가르고 기전은 W4로 넘긴다.**

| 항목 | 분기 ②계층 생산 카운터 | ③계층 생산 실적(production_log) |
|------|------|------|
| 원천 | 설비 태그(COUNTER 프로파일 등)가 스트림으로 | 사람이 API로 입력(WRK-03) |
| 원시 표본의 목적지 | **① tag_raw** — 카운터 태그의 샘플은 다른 태그와 같은 측정 사실이다 | 해당 없음 |
| ②로 편입되는 부분 | 카운터 표본에서 **파생되고 상태 갱신이 필요한 사실**(예: 작업지시 목표 수량 도달) — **미설계** | 해당 없음 |
| 목적지 | 파생 사실의 목적지 **미정** — 현 스키마에 테이블이 없다 | PostgreSQL production_log |
| 금지 | production_log를 대신 쓰지 않는다 | 스트림 유래 값으로 자동 채우지 않는다 |

- **판정 ① — 생산 카운터의 원시 표본은 ①이다.** 카운터 값 자체는 추가 전용 측정 사실이라 성격 판정 기준의 ① 가지에 떨어진다. "생산"이라는 이름이 목적지를 바꾸지 않는다.
- **판정 ② — ②로 가는 것은 표본이 아니라 파생 사실이다.** 알람이 원시값이 아니라 원시값에 대한 판정을 ②로 보내듯, 생산 카운터도 표본에서 파생된 상태 전이만 ②가 될 수 있다.
- **판정 ③ — 파생 사실의 목적지를 정하기 전에 스키마에 올리지 않는다**([../CLAUDE.md](../CLAUDE.md) 고유 규칙). PostgreSQL 업무 테이블 수(14)는 이 판정으로 바뀌지 않으며, 파생 사실에 테이블이 필요해지면 이 표에 행을 먼저 두고 [../05_data_stores/01_postgresql_schema.md](../05_data_stores/01_postgresql_schema.md)의 채번과 루트 README 고정 기준을 같은 변경 단위에서 고친다.
- **판정 ④ — production_log는 ③ 전용이다.** 둘을 한 테이블로 합치면 스트림 유래 값이 업무 트랜잭션 경로에 섞여 ③의 "Stream을 타지 않는다"가 거짓이 된다(REQ-WRK-05).
- 기전(어느 판정이 파생 사실을 만드는가 · 알람과 같은 규칙 엔진을 쓰는가)의 정본은 [../06_pipeline/04_routing.md](../06_pipeline/04_routing.md)(W4)다.

## 스위치가 분기를 바꾸는가

스위치는 **경로**를 바꾸지만 **목적지 정책**을 바꾸지 않는다. 목적지가 바뀌어 보이는 스위치를 아래로 가른다.

| 스위치 | off일 때 보이는 것 | 목적지 정책이 바뀌는가 | 판정 |
|------|------|------|------|
| SW-01 | Collector가 Ingest를 프로세스 안 큐로 직접 부른다 | 아니다 — 원시값은 여전히 ClickHouse 전용 | 경로만 바뀐다 · 실험 전용 |
| SW-02 | 최신값 API가 ClickHouse argMax로 응답한다 | 아니다 — Redis 사본은 여전히 갱신된다 | 읽기 경로만 바뀐다 |
| SW-03 | 매 조회가 ClickHouse 집계 | 아니다 — 캐시는 목적지가 아니다 | 사본을 끌 뿐이다 |
| SW-09 | 대조군에 싣지 않는다(기본) · on이면 PostgreSQL에도 싣는다 | 아니다 — 대조군은 계측물이다 | 계측을 켜고 끈다 |

- 검산: 판정 행 = **4** — 나머지 스위치(SW-04~08 · SW-10 · SW-11)는 키 모양 · 락 · 팬아웃 · 병합 · 토큰 · 필터 · 최신값 사본의 갱신 주체를 바꿀 뿐 저장소를 고르지 않는다. 4 + 7 = **11**(스위치 채번 정본 [../02_features/13_switch_matrix.md](../02_features/13_switch_matrix.md))
