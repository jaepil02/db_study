## 성격 판정 기준

새 데이터는 아래 순서로 판정한다. 판정 축은 넷 — **누가 쓰는가 · 갱신되는가 · 누가 즉시 읽는가 · 무엇이 진실인가**다.

```plain
새 데이터 종류
├─ 사람이 API로 쓰고 커밋 직후 다시 읽는가 ──────────────────────────── ③ PostgreSQL 전용
│  └─ 반복 조회가 잦은가 ─────────────────────────── + Redis 캐시 계열(TTL 필수)
└─ 설비 스트림에서 오는가
   ├─ 한 번 쓰고 갱신하지 않는 측정 사실인가 ────────────────────── ① ClickHouse 전용
   │  └─ 점조회가 초당 수백 회인가 ─────────────── + Redis 봉인 계열 휘발 사본(최신값만)
   └─ 측정 사실에서 파생되고 상태가 바뀌는가 ───────────────────── 판정 보류 — 옛 ②(D-16 폐지)
                                                                      목적지를 정하기 전에 스키마에 올리지 않는다
```

- **첫 분기는 저장소가 아니라 쓰는 주체다.** 사람이 쓰는 데이터는 트랜잭션 경계가 요청 하나와 같아야 해서 **응답이 적재를 기다리지 않는 경로**에 올릴 수 없다 — 성격 판정이 적용 방식(배치 비동기 대 명령 동기)부터 고른다. 명령 스트림은 Redis를 지나지만 응답은 커밋 뒤라 이 조건을 지킨다.
- **Redis는 두 갈래 모두에 나타나지만 진실의 자리는 한 번도 아니다.** ③의 명령 버퍼 · 결과 · 캐시 · ①의 최신값 사본 모두 원천이 따로 있다 — 명령의 진실은 적용된 업무 행과 biz_command_log다.
- **"+ Redis" 가지는 목적지가 아니라 사본이다.** 목적지는 각 가지의 끝 하나이고, 사본은 생존 정책(TTL 유무)이 다른 두 계열로 갈린다(ADR-05).

## 업무 쓰기가 명령 스트림을 타는 방식

③계층의 쓰기(마스터 — 사이트 · 라인 · 설비 · 접속 설정 · 태그)는 api가 검증한 뒤 **stream:biz:cmd에 명령으로 싣고, 워커가 PostgreSQL 트랜잭션 하나로 적용하며, api는 커밋 결과를 받은 뒤에만 응답한다**(사용자 결정 2026-09-27 · D-04 · REQ-GLB-12). 옛 판정(Stream 비경유)은 Stream이 at-least-once 비동기 경로라 업무 쓰기의 네 보장을 깬다고 적었다. 판정은 뒤집혔지만 **그 근거는 버리지 않는다** — 새 기전이 네 보장을 각각 어떻게 지키는지가 이 절이다. 기전의 정본은 [../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) §업무 명령 경로다.

| 보장 | 옛 근거 — 비동기 스트림에서 깨지는 방식 | 새 기전이 지키는 방식 | 남는 잔여 |
|------|------|------|------|
| read-your-writes | 커밋 응답이 적재 전에 나간다 — 태그 이름을 바꾸고 목록을 다시 열면 옛 이름이 보여 같은 변경이 두 번 요청된다 | **api는 결과를 받아야 응답한다** — 워커는 커밋 → 캐시 삭제 · ch:cacheinv(체인 ②③) → biz:result SET → ch:bizreply 순으로만 결과를 내므로, 응답을 받은 화면의 재조회는 커밋된 값을 본다 | 대기 상한(현행 참고 5초)을 넘으면 202 pending — 이 응답은 성공이 아니므로 재조회 보장을 주장하지 않는다 · 명령 조회로 확인한다 |

| 재시도의 멱등 | at-least-once 재시도가 트랜잭션 밖에서 일어나고 결정적 토큰은 ClickHouse 파트 중복 제거용이라 PostgreSQL 삽입을 막지 못한다 — 재시도가 중복 설비 · 태그를 만든다 | **멱등 키 = cmdId · 원장 = PostgreSQL biz_command_log(cmd_id UNIQUE) · 같은 트랜잭션** — 재전달(XAUTOCLAIM · 워커 재기동)과 같은 cmdId 재요청은 원장 행을 보고 저장된 결과를 돌려준다 · 커밋과 원장이 한 트랜잭션이라 크래시 창이 없다 | 새 cmdId로 보낸 재시도(사람의 이중 제출)는 막지 못한다 · 같은 cmdId · 다른 본문은 첫 결과를 받는다([../05_data_stores/02_postgresql_constraints.md](../05_data_stores/02_postgresql_constraints.md) 한계 등재 #18 · #24) |

- 검산: 지키는 보장 = **4** — 옛 판정의 깨지는 보장 4행과 같은 순서
- **B형 — 업무 쓰기가 Redis를 거쳐도 "큐 위에 동기 경로를 재구현"한 것이 아니다.** 결론 — 명령 스트림은 적용을 한 주체(워커 · 소비자 1 · 직렬)로 모으고 응답만 동기로 둔다. 소비자 1은 **락 lock:biz:writer가 강제한다** — 쥔 워커만 소비하고, 쥔 워커가 죽으면 TTL 뒤 다른 워커가 이어받아 PEL부터 소진한다(키 [../05_data_stores/05_redis_keyspace.md](../05_data_stores/05_redis_keyspace.md)). 반대 시나리오 — 수집 스트림처럼 배치 · 다중 컨슈머 · 결정적 토큰으로 적용하면 위 네 실패가 전부 돌아오고, 응답을 기다리지 않으면 read-your-writes가, 원장을 트랜잭션 밖(Redis)에 두면 멱등이 깨진다. 파생 지침 — 업무 명령은 수집 스트림과 **키 · 그룹 · 소비자 · 멱등 수단을 공유하지 않는다.** ING는 여전히 ③을 받지 않고(ING-10), 업무 CRUD 부하 중 stream:plc:raw 유입량이 CRUD와 무관하게 움직이는 것이 이 분리의 검증이다(REQ-GLB-12).
- **새 대가 — Redis가 업무 쓰기의 가용성 경로에 들어온다.** Redis 불가면 업무 쓰기도 503(common.postgres_unavailable 재사용 — 원인은 biz_commands_total result 레이블이 가른다 · Redis 불가 = unavailable · PostgreSQL 불가 = failed)이다(옛 경로는 Redis 불가 중에도 커밋됐다). 읽기는 기존대로 PostgreSQL 직접(+ 캐시 degrade)이다. 옛 경로는 SW-12 direct로 남는다 — 두 경로의 지연 · 처리량 · 장애 가용성을 비교하던 EXP-46은 측정 도구 삭제로 폐지(D-16)됐다.
- ③의 캐시(cache 계열)는 커밋 **뒤에만** 삭제한다 — 무효화 체인의 정본은 [../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md)(ADR-12). 명령 경로에서 체인 ②③의 주체는 워커다.

## 중복 저장의 유일한 예외

**중복 저장**은 같은 사실을 **수명 제한 없이** 두 저장소가 보유하는 것이다. 이 정의로 가르면 중복 저장은 하나뿐이다 — 태그 최신값(REQ-GLB-11 · 원본 architecture.md §5).

| 후보 | 같은 사실인가 | 수명 제한 | 판정 | 근거 |
|------|------|------|------|------|
| 태그 최신값(Redis rt 계열 ↔ ClickHouse tag_raw) | 같다 — 태그별 마지막 행 | **없다** — 봉인 계열 · 덮어쓰기 | **중복 저장 — 유일한 예외** | 초당 수백 회 점조회를 ClickHouse가 받지 못한다. 불일치 시 **ClickHouse가 진실**이고 argMax로 재구성한다 |
| 조회 결과 캐시(cache 계열) | 같다 — 집계 결과 | 있다 — TTL | 캐시 | TTL과 volatile-lru가 수명을 끊는다 |
| 마스터 캐시(cache 계열 · dict_tag) | 같다 — 태그 메타 | 있다 — TTL · 재적재 주기 | 캐시 | 원천은 PostgreSQL 하나 · 변경 시 무효화 체인 |
| 대조군 plc_tag_raw_control ↔ tag_raw | 같은 행 집합 | SW-09 on · gated의 게이트 열림에서만 존재 | **중복 아님 — 계측물** | §대조군은 중복이 아니라 계측물 |
| 스풀 파일 ↔ Stream | 같은 엔트리 | 위험 단계 동안만 | 중복 아님 — 경로 | 둘 중 한쪽에만 있다 — 스풀은 Stream에 넣지 못한 것의 대기열이다 |
| 업무 명령 결과(biz:result ↔ biz_command_log.result) | 같다 — 명령 하나의 결과 | 있다 — 결과 키 TTL | 캐시 | 원천은 원장 하나 · 결과 키가 없으면 원장을 읽는다(명령 조회) |

- 검산: 후보 = **6** — 중복 저장 1 · 캐시 3 · 중복 아님 2 · 옛 알람 핫 상태 행은 D-16 삭제
- **최신값이 예외인 대가 — 갱신 경로가 ClickHouse에 묶인다.** 현행 잠정안은 삽입 성공 · XACK 뒤에 갱신하므로 ClickHouse가 멈추면 최신값도 멈춘다(ADR-10). 이 결합과 대안의 실측 비교는 [06_backpressure_failure.md](./06_backpressure_failure.md) §ClickHouse 중단 시 최신값 정지. 정책은 갱신 주체와 무관하다 — 누가 갱신하든 Redis는 사본이고 진실은 ClickHouse다.
- **Redis 자체가 중단되면 최신값은 ClickHouse로 폴백하지 않는다.** 키가 비어 있는 것(복원 대상)과 Redis에 접속할 수 없는 것(503)은 다르다 — 전 요청을 ClickHouse 점조회로 돌리면 적재까지 밀린다(REQ-GLB-09).

## 대조군은 중복이 아니라 계측물

**B형 — 대조군 plc_tag_raw_control은 원시값을 PostgreSQL에 두 번째로 저장하지만 "시계열은 ClickHouse 전용"의 위반이 아니다.** 대조군은 목적지가 아니라 **목표 ①의 실험 계측물**이다(D-05 · ADR-17). 기본 gated(옛 기본 off — D-16)이고 직접 비교 실행이 게이트를 연 동안(on이면 늘) 같은 배치를 양쪽에 싣는다. **반대 시나리오**: 대조군을 분기 목적지로 취급하면 ① 조회 API가 대조군을 원천으로 읽기 시작해 ClickHouse와 PostgreSQL 중 무엇이 진실인지 흐려지고 ② SW-09가 기본 on이 되어 모든 삽입 처리량에 대조군 비용이 섞여 목표 ②의 수치가 오염되며 ③ 대조군 삽입 실패가 XACK를 막아 계측물의 실패가 분기 경로를 멈춘다. **파생 지침**: 조회 표면은 대조군을 읽지 않는다 · SW-09 기본 off · 대조군 삽입 실패는 XACK를 막지 않는다(REQ-ING-15). 설계 정본은 [../05_data_stores/10_olap_vs_rdb_control.md](../05_data_stores/10_olap_vs_rdb_control.md)다.

- 대조군 삽입 의미론은 [../05_data_stores/10_olap_vs_rdb_control.md](../05_data_stores/10_olap_vs_rdb_control.md)가 판정했다 — ClickHouse 삽입 성공 뒤 배치당 COPY 1회 · 재시도 없음 · 재전달 중복은 구간 count 대조로 검출 · 실패 · 중복 구간은 대조 무효(ADR-17). 기전은 [../06_pipeline/04_routing.md](../06_pipeline/04_routing.md).
- **목표 ①과 ②는 비교 방향이 반대다.** ①은 데이터를 고정하고 저장소를 바꾸며(SW-09), ②는 저장소를 고정하고 역할을 바꾼다(SW-01~08 · SW-11). 두 축을 한 측정에 섞지 않는다([../02_features/13_switch_matrix.md](../02_features/13_switch_matrix.md) 조합 제약).

## 생산 카운터 판정

루트 README 고정 기준은 옛 ②계층을 "알람 판정 · 생산 카운터"로 적었다. D-16으로 ②가 폐지됐고 같은 "생산 수량"이 나타나던 ③의 생산 실적(production_log · 옛 WRK)도 함께 지워져, 남는 판정은 둘이다.

- **판정 ① — 생산 카운터의 원시 표본은 ①이다.** 카운터 값 자체는 추가 전용 측정 사실이라 성격 판정 기준의 ① 가지에 떨어진다. "생산"이라는 이름이 목적지를 바꾸지 않는다 — 구간 생산량은 조회 시점에 계산한다(기전 정본 [../06_pipeline/04_routing.md](../06_pipeline/04_routing.md)).
- **판정 ② — 파생 사실의 목적지를 정하기 전에 스키마에 올리지 않는다**([../CLAUDE.md](../CLAUDE.md) 고유 규칙). 카운터 표본에서 파생되고 상태 갱신이 필요한 사실(예: 목표 수량 도달)이 필요해지면 §성격 판정 기준에서 갈래를 먼저 정하고 §데이터 종류별 목적지에 행을 둔 뒤 [../05_data_stores/01_postgresql_schema.md](../05_data_stores/01_postgresql_schema.md)의 채번과 루트 README 고정 기준을 같은 변경 단위에서 고친다.

## 스위치가 분기를 바꾸는가

스위치는 **경로**를 바꾸지만 **목적지 정책**을 바꾸지 않는다. 목적지가 바뀌어 보이는 스위치를 아래로 가른다.

| 스위치 | off일 때 보이는 것 | 목적지 정책이 바뀌는가 | 판정 |
|------|------|------|------|
| SW-01 | Collector가 Ingest를 프로세스 안 큐로 직접 부른다 | 아니다 — 원시값은 여전히 ClickHouse 전용 | 경로만 바뀐다 · 실험 전용 |
| SW-02 | 최신값 API가 ClickHouse argMax로 응답한다 | 아니다 — Redis 사본은 여전히 갱신된다 | 읽기 경로만 바뀐다 |
| SW-03 | 매 조회가 ClickHouse 집계 | 아니다 — 캐시는 목적지가 아니다 | 사본을 끌 뿐이다 |
| SW-09 | off — 대조군에 싣지 않는다 · on — PostgreSQL에도 싣는다 · gated(기본 · D-16) — 직접 비교 실행이 게이트를 연 배치만 | 아니다 — 대조군은 계측물이다 | 계측을 켜고 끈다 |
| SW-12 | direct — api가 트랜잭션을 직접 커밋한다(명령 스트림 · 원장 · 결과 키 없음) | 아니다 — 업무 데이터는 여전히 PostgreSQL 전용 | 적용 경로만 바뀐다 · 비교 실험 EXP-46은 폐지(D-16) |

- 검산: 판정 행 = **5** — 나머지 스위치(SW-04~08 · SW-10 · SW-11)는 키 모양 · 락 · 팬아웃 · 병합 · 토큰 · 필터 · 최신값 사본의 갱신 주체를 바꿀 뿐 저장소를 고르지 않는다. 5 + 7 = **12**(스위치 채번 정본 [../02_features/13_switch_matrix.md](../02_features/13_switch_matrix.md))
