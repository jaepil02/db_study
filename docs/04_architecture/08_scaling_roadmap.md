> **개정일**: 2026-09-24 — W6 실험 채번 반영 — Stream 점유 메모리 메트릭 · EXP 번호(정본 10_observability/01 · 06)
> **개정일**: 2026-09-24 — W6 판정 반영 — 미확인 등재에 분산 추적(tempo) 진입 조건 행 신설

현재 구성은 **컨테이너 4개 — api 1 + 저장소 3**이다. 확장은 네 단계이며 **각 단계는 실측 진입 조건으로만 들어간다**(루트 README 고정 기준 · REQ-GLB-22). 추측으로 단계를 앞당기면 무엇이 병목이었는지 배울 수 없고, 분리 전 기준선이 없어 분리의 효과를 잴 수 없다. **진입 조건 값의 정본은 이 문서다.**

**머신이 하나라는 사실이 이 로드맵의 모양을 정한다.** 인스턴스를 늘려도 같은 CPU를 나눠 쓰므로 확장 실험의 목표는 처리량 향상이 아니라 **동작 검증**이다 — Pub/Sub이 인스턴스 경계를 넘는가 · 컨슈머 그룹이 컨테이너 워커로 그대로 늘어나는가 · 역할을 떼도 코드가 안 바뀌는가(원본 tech_stack.md §10.6). 검증할 수 없는 단계는 로드맵에서 뺐다(§삭제한 단계).

## 4단계

현재 구성에서 네 단계를 순서대로 밟는다. 앞 단계 없이 뒤 단계에 들어가지 않는다.

```plain
현재      컨테이너 4 — api(all) + postgres · clickhouse · redis
  ↓        진입: 이벤트 루프 지연 또는 조회 p95의 수집 부하 비례 악화
1단계     역할 분리 — 같은 이미지를 APP_ROLE로 api · worker · collector · datagen 컨테이너로
  ↓        진입: api 역할 컨테이너 CPU 지속 포화
2단계     api 다중 인스턴스 — api 역할 × N · Pub/Sub 팬아웃 · 무효화 전파 검증 · PgBouncer
  ↓        진입: 캐시 히트율과 Stream 점유 메모리의 역상관
3단계     Redis 분리 — stream 인스턴스(noeviction) · cache 인스턴스(allkeys-lru) · 컨슈머 워커 확장
  ↓        진입: Redis 메모리로 보존 기간 불가 · 재처리 요구
4단계     큐 교체 — Redis Streams → Kafka · ClickHouse Kafka 엔진으로 적재 워커 제거
```

- **1단계가 가장 싸다.** 데이터 평면 모듈이 처음부터 Redis Stream 경계로만 이어져 있어 기동 값만 바꾸면 분리가 끝난다 — 경계를 미리 지불한 값이 여기서 회수된다(ADR-06 · ADR-22).
- **2단계에 로드 밸런서를 두지 않는다.** 각 인스턴스에 직접 접속해 팬아웃과 캐시 무효화 전파를 확인한다 — 검증 대상은 부하 분산이 아니라 Pub/Sub이 인스턴스 경계를 넘어 동작하는가다.
- **3단계는 단일 인스턴스가 만든 학습 지점의 해소다.** 단일 인스턴스에서만 보이는 축출 연쇄를 관찰한 뒤에야 분리한다 — 먼저 나누면 그 연쇄를 영영 볼 수 없다(ADR-05).
- **4단계는 전환 실험이다.** Kafka는 로컬 메모리 예산에서 과다해 보류했고(ADR-04), 적재 소스를 포트로 추상화해 둔 것(PointSourcePort)이 전환 비용을 낮춘다.

## 진입 조건

원본 값은 4 vCPU급 가정의 **원본 목표**다. 이 머신은 병목 방향이 원본 가정과 반대라(CPU 과잉 · 메모리 부족) 현행 값은 **미확인 — 확정 전 임의 값 고정 금지**이며, S5 · S6 기준선 실측 뒤 이 표에 올린다.

| 단계 | 진입 지표 | 원본 목표(4 vCPU 가정) | 관측 창 | 현행 | 확인 자리 |
|------|------|------|------|------|------|
| 1 역할 분리 | api 이벤트 루프 지연 p95 · 또는 수집 pps 대비 조회 p95의 비례 악화 | p95 100 ms 초과 | 수집 부하 단계별 | 미확인 | REQ-NFR-15 · [05_latency_budget.md](./05_latency_budget.md) §단일 이벤트 루프 공유 |
| 2 api 다중 인스턴스 | api 역할 컨테이너 CPU 사용률 | 80% 지속 | 지속 구간(원본 미정) | 미확인 | 컨테이너 통계 |
| 3 Redis 분리 | 캐시 히트율 대 **Stream 점유 메모리**의 상관 · 히트율 절대값 | 역상관 · 히트율 50% 미만 | 원본 알림 규칙 10분 지속 | 미확인 | 키 접두별 메모리(REQ-OBS-04) · cache 접두 히트율 |
| 4 큐 교체 | Redis 메모리로 필요한 보존 기간을 감당할 수 있는가 · 재처리 요구 | 정성 조건 — 수치 없음 | 해당 없음 | 해당 없음 — 정성 | 요구 발생 기록 |

- 검산: 단계 = **4** — 수치 조건 3(1 · 2 · 3) + 정성 조건 1(4)
- **3단계의 상관 대상은 적체가 아니라 Stream 점유 메모리다.** 확인된 엔트리가 MAXLEN 트리밍 전까지 남아 Stream 메모리는 적체가 아니라 충전량을 따른다([06_backpressure_failure.md](./06_backpressure_failure.md) §MAXLEN과 maxmemory). 원본의 "캐시 히트율이 스트림 길이와 역상관"을 적체로 읽으면 정상 운전에서 상관이 나타나지 않아 진입 조건이 영영 충족되지 않는다.
- **1단계에는 수치 밖의 근거가 하나 더 있다 — 단일 실패점.** api 재빌드 · 크래시가 수집까지 멈추는 사실은 진입 조건이 아니라 상시 비용이며, 재기동 시간과 결측 구간 길이를 실측해 두는 것으로 1단계 진입 판단의 재료로 쓴다([06_backpressure_failure.md](./06_backpressure_failure.md) §단일 컨테이너의 대가).

### 진입 기록 계약

| 요소 | 규칙 | 없으면 |
|------|------|------|
| 진입 지표 실측값 | 진입 조건 지표의 값과 관측 창 | 추측 진입과 실측 진입을 가를 수 없다 |

## 단계별 교체 대상

각 단계가 무엇을 바꾸고 무엇이 그대로여야 하는지 고정한다. **그대로여야 하는 칸이 깨지면 그 단계는 경계 설계의 결함을 드러낸 것이다.**

| 단계 | 바뀌는 것 | 그대로인 것 | 전제 결정 | 그대로가 깨지면 |
|------|------|------|------|------|
| 1 역할 분리 | 컨테이너 수 · 각 컨테이너의 APP_ROLE · 컨테이너별 자원 배분 | **코드 · Stream 페이로드 계약 · 컨슈머 그룹 · 키 계열** | ADR-06 · ADR-22 | 역할 분리 커밋에 코드 diff가 생긴다 — 경계 밖 직접 호출이 남아 있었다는 뜻이다 |
| 2 api 다중 인스턴스 | api 역할 인스턴스 수 · PostgreSQL 커넥션 주체 수(→ PgBouncer) | 팬아웃 코드 · 무효화 코드 · 스위치 포트 | ADR-07 · ADR-19 | 인스턴스를 늘릴 때 팬아웃을 새로 써야 한다 — Pub/Sub 경계가 없던 경로가 있었다는 뜻이다 |
| 3 Redis 분리 | Redis 인스턴스 수 · 인스턴스별 축출 정책 · 접속 설정 | 키 이름 · 키 계열별 래퍼 · 실패 전략 | ADR-05 · ADR-13 | 키 계열을 인스턴스에 나눌 수 없다 — 한 접두에 두 생존 정책이 섞여 있었다는 뜻이다 |
| 4 큐 교체 | 버퍼 매체 · 적재 워커(ClickHouse Kafka 엔진이 대체) | 페이로드 계약 · 분기 정책 · 적재 대상 테이블 | ADR-04 · ADR-21 | 소스 포트 밖에서 Stream 명령을 직접 쓰던 코드가 전부 다시 쓰인다 |

- 검산: 단계 = **4**
- **2단계에서 PgBouncer를 도입하는 이유 — 커넥션 주체가 처음으로 여럿이 된다.** 단일 api 프로세스의 in-process 풀에서는 커넥션 폭발 조건이 성립하지 않았다(ADR-19). 인스턴스가 늘면 인스턴스마다 풀을 들어 조건이 생긴다.
- **4단계에서 백프레셔 1차 신호가 바뀐다.** Kafka는 디스크 보존이라 적체가 메모리 신호가 아니다 — 1차 신호(ADR-21)와 스풀의 의미를 그 단계에서 다시 판정한다.
- **역할 분리 시 동거 제약** — SIM과 GEN 모드 A는 collector와 한 컨테이너에 있어야 한다(루프백 · 프로세스 안 갱신). 배정의 정본은 [02_module_boundaries.md](./02_module_boundaries.md) §APP_ROLE 배정이다.

## 단계별 동작 검증

머신이 하나라 각 단계의 검증 대상은 처리량이 아니라 **동작**이다. 아래가 단계마다 "끝났다"를 판정하는 관찰이다.

| 단계 | 검증할 동작 | 관찰 방법 | 실패로 판정하는 관찰 |
|------|------|------|------|
| 1 | 역할 분리 뒤 수집 · 적재 · 조회가 코드 변경 없이 이어진다 · collector 재시작이 조회를 멈추지 않는다 | 역할 분리 커밋 diff · collector 재시작 중 조회 p95 | 커밋에 코드 diff가 있다 · collector 재시작 중 조회가 멈춘다 |
| 2 | 한 인스턴스의 발행을 다른 인스턴스의 WebSocket 소켓이 받는다 · 무효화가 인스턴스 경계를 넘는다 | 인스턴스별 직접 접속 · ch:cacheinv 구독자 수 | 다른 인스턴스 소켓이 값을 받지 못한다 |
| 3 | 스트림 인스턴스가 캐시를 밀어내지 않는다 · 키 계열이 인스턴스에 그대로 나뉜다 | 축출 연쇄 재현 조건에서 캐시 히트율 | 분리 뒤에도 Stream 충전에 따라 히트율이 떨어진다 |
| 4 | Kafka 소스로 바꿔도 페이로드 계약 · 분기가 그대로다 · 적재 워커 없이 적재된다 | 소스 포트 교체 diff · 행 수 대조 | 분기 정책 · 적재 대상 테이블이 바뀐다 |

- 검산: 단계 = **4**
- **처리량 향상은 판정에 쓰지 않는다.** 인스턴스를 늘려도 같은 CPU를 나눠 써 처리량이 늘지 않는 것이 정상이다 — 처리량이 줄지 않았는지만 기록한다([../10_observability/07_measurement_limits.md](../10_observability/07_measurement_limits.md)).

## 앞당기지 않는 규칙

**B형 — 기동이 all에 머물러 있는 것은 미완성이 아니다.** 코드는 처음부터 분리 가능하게 쓰되(Stream 경계 · Pub/Sub 경계 · 포트) 기동은 all로 둔다. **반대 시나리오**: 병목이 실측되기 전에 역할을 나누면 ① 분리 전 기준선이 없어 분리의 효과를 잴 수 없고 ② 컨테이너별 메모리를 떼어 주느라 측정 대상인 ClickHouse 몫이 줄며 ③ 이벤트 루프 지연이 실제 병목이었는지 끝내 모른다. **파생 지침**: 각 단계는 대시보드 수치를 근거로 진입하고 진입 전후 수치를 기록한다(§진입 기록 계약) — 이 기록이 없는 분리는 되돌린다.

| 앞당기는 시도 | 겉으로 보이는 이득 | 실제로 잃는 것 |
|------|------|------|
| 처음부터 역할 분리 기동 | 격리된 구성 | 단일 이벤트 루프 공유가 조회 p95를 끌어올리는 현상을 관찰하지 못한다 |
| 처음부터 Redis 두 인스턴스 | 인프라가 생존 정책을 강제 | 축출 연쇄(학습 정점)를 볼 수 없고, 키 계열별 래퍼가 강제하는 구분을 코드로 지켜 볼 기회가 사라진다 |
| 처음부터 Kafka | 재처리 자유 | 로컬 메모리 예산에서 ClickHouse 몫이 남지 않는다 |
| 처음부터 PgBouncer | 커넥션 관리 | 세션 모드와 동등한 in-process 풀의 prepared statement 자유를 잃는다 — 커넥션 폭발 조건이 없는데 제약만 얻는다 |

- 검산: 시도 = **4**

## 삭제한 단계

원본 초기 로드맵에 있던 단계 셋을 뺐다(원본 architecture.md §19). **머신이 하나라 검증할 방법이 없고, 검증할 수 없는 단계를 로드맵에 남겨 두면 진입 조건이 영영 충족되지 않는 장식이 된다.**

| 삭제한 단계 | 원래 내용 | 검증할 수 없는 이유 | 남기면 생기는 실패 |
|------|------|------|------|
| 저장소 분리 | DB 전용 인스턴스 · PostgreSQL 읽기 복제본 | 복제본이 같은 머신 · 같은 디스크에 있어 읽기 분산 효과가 측정되지 않는다 | 진입 조건 "읽기 부하 포화"가 복제본을 둬도 해소되지 않아 단계가 효과 없음으로 판정된다 — 그 판정이 복제의 무용이 아니라 단일 머신 때문이라는 사실이 가려진다 |
| ClickHouse 클러스터 | 샤딩 · 복제 | 샤드가 같은 CPU · 디스크를 나눠 써 병렬 이득이 없다 | 분산 쿼리 오버헤드만 측정되어 "클러스터가 느리다"는 거짓 결론이 남는다 |
| 관측 분리 | 관측 스택 전용 호스트 | 호스트가 하나다 — 대신 처음부터 선택 프로파일이다(ADR-20) | 진입 조건이 없는 단계가 로드맵에 남는다 |

- 검산: 삭제 단계 = **3**
- **배포 · 원격 접속 · TLS · 고가용성은 로드맵 단계가 아니라 범위 밖이다**(D-02). 단계를 늘려 범위를 넓히지 않는다.

## 로드맵 밖 조건부 분리

확장 단계와 별개로, 원본이 조건부로 열어 둔 분리가 하나 있다 — 데이터 평면의 Python 분리(원본 tech_stack.md §3.4). 확장 단계가 아니라 런타임 선택의 되돌림이라 이 로드맵에 번호를 두지 않는다.

| 조건(실측) | 분리 대상 | 그대로인 것 | 정본 |
|------|------|------|------|
| 생성기가 목표 pps의 3배를 내지 못함(S1) | 생성기만 Python으로 — 같은 Stream에 발행(모드 B) | Stream 페이로드 계약 | [../09_tech_stack/06_decisions_rationale.md](../09_tech_stack/06_decisions_rationale.md) |
| 시뮬레이터 기능 부족 | PlcSim만 별도 프로세스 — Collector는 접속 주소만 바꾼다 | Modbus 경계 | 상동 |
| 적재가 Arrow 직삽입을 요구 | Ingest만 별도 워커 — 같은 컨슈머 그룹 소비 | 컨슈머 그룹 · 페이로드 계약 | 상동 |

- 검산: 조건 = **3** · 어느 경우에도 제어 평면(API · 인증 · CRUD · WebSocket)은 NestJS에 남는다(ADR-01)
- **PlcSim을 별도 프로세스로 떼면 모드 A의 SIMULATED 판정 규칙(루프백 접속 대상)이 깨진다** — 접속 대상이 서비스명이 되기 때문이다. 그 시점에 [../02_features/03_collector.md](../02_features/03_collector.md) §모드 A의 SIMULATED 표지 판정을 재판정한다.
