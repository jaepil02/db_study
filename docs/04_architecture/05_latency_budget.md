지연 예산은 E2E 지연(ingested_at − ts) 하나를 **어느 구간이 얼마나 먹는가**로 쪼갠 것이다. 목표치의 정본은 [../03_requirements/13_nonfunctional.md](../03_requirements/13_nonfunctional.md)(REQ-NFR-04)이고 **전부 3계층 미확인**이다. 이 문서는 수치를 확정하지 않는 대신 수치가 성립할 **구조**를 고정한다 — 구간의 경계 시각 · 지배 구간이 무엇에 묶여 있는가 · 보정 결정이 구간을 어떻게 바꾸는가 · 어디서 재는가.

원본 값은 **원본 목표(4 vCPU 가정)**로만 인용한다. 이 머신은 CPU 과잉 · 메모리 부족으로 원본 가정과 병목 방향이 반대라(원본 implementation_plan.md §2.1), 원본 목표를 합격선으로 쓰면 다른 머신의 기준으로 이 머신을 판정하게 된다.

### 구간 경계 판정 — Stream 대기의 시작점

원본 측정식은 Stream 대기를 "XREADGROUP 수신 시각 − 엔트리 t0"로 적었다(원본 data_flow.md §15). **t0은 스캔 사이클의 기준 시각(폴링 시점)이라 이 식은 #2~#5를 Stream 대기에 함께 센다.** 판정 — **Stream 대기의 시작점은 엔트리 ID의 밀리초 부분(Redis가 XADD를 받은 시각)이다.** 컨테이너들이 호스트 시계를 공유하므로 Redis 시각과 api 시각을 같은 축에서 뺄 수 있다. 원본 식을 쓰면 Modbus 지연이 늘어난 실험에서 Stream 대기가 늘어난 것으로 보여 **플러시 주기를 줄이는 잘못된 튜닝**으로 이어진다. 히스토그램 이름의 정본은 [../10_observability/01_metrics_catalog.md](../10_observability/01_metrics_catalog.md)(W6)다. REQ-ING-18 · [../11_glossary/05_units_and_time.md](../11_glossary/05_units_and_time.md)의 옛 식(수신 − t0)은 W4에서 이 시작점으로 통일했다.

## 지배 구간 — Stream 대기와 플러시 주기

**지연 예산의 지배 구간은 Stream 대기다.** 원본 목표 400 ms는 배치 플러시 주기(현행 참고 시간 트리거 1,000 ms · 소유 [../06_pipeline/03_ingest_batch.md](../06_pipeline/03_ingest_batch.md))의 절반 근처다 — 엔트리가 배치 창의 아무 시점에나 도착하므로 평균 대기가 창의 절반에 수렴한다. 이 구간은 **처리량과 지연을 맞바꾸는 유일한 손잡이**다.

| 플러시 주기를 | E2E 지연 | 삽입 횟수 · 파트 생성률 | ClickHouse 부담 | 배치당 행 수(M 티어) |
|------|------|------|------|------|
| 줄인다 | 준다 — 대기가 창 절반을 따라 줄어든다 | 늘어난다 — 주기에 반비례 | 머지 부담 증가 · 활성 파트 증가 · too many parts 접근 | 줄어든다 |
| 늘린다 | 는다 | 줄어든다 | 머지 여유 | 늘어난다 — 행 수 · 페이로드 트리거가 먼저 걸릴 수 있다 |

- **원본 예시 — E2E를 500 ms로 줄이려면 플러시 주기를 200 ms로 낮춰야 하고 그러면 파트 생성률이 5배가 된다**(원본 data_flow.md §15). 이 트레이드오프를 수치로 직접 확인하는 것이 원본이 적은 가장 중요한 학습 목표이며, 현행 수치는 미확인이다.
- **고부하에서는 행 수 트리거가, 저부하에서는 시간 트리거가 지배한다 — 원본 가정이다.** 보정 7.1은 M 티어에서 행 수 트리거(현행 참고 50,000행)가 도달 불가능해 **시간 트리거가 지배**함을 보였다(10,000 pps × 1초 = 10,000행). 따라서 M 티어의 Stream 대기는 행 수가 아니라 시간 트리거 하나에 묶인다. **M+ 이상에서는 반대다** — 현행 R 50,000이 M+의 창(100,000행)보다 작아 행 트리거가 0.5초에 먼저 걸린다(W4 산술 보정 · [../06_pipeline/03_ingest_batch.md](../06_pipeline/03_ingest_batch.md)).

## ADR-09 반영 시 구간 변화

보정 7.1의 결정(ADR-09)은 컨슈머 N개가 읽기 · 디코딩만 하고 **단일 flusher**가 fan-in해 삽입한다. 파트 생성률이 컨슈머 수와 무관해지는 대신 구간 #6이 셋으로 쪼개진다.

| 원본 구간 | ADR-09 뒤 구간 | 시작 시각 | 끝 시각 | 지배 요인 | 원본 목표 |
|------|------|------|------|------|------|
| #6 Stream 대기 | 6a Stream 체류 | 엔트리 ID 시각 | XREADGROUP 수신 | 소비 루프 대기 · 컨슈머 수 | 없음 — 원본은 #6 하나로 셌다 |
| 상동 | 6b 디코딩 · 행 전개 | 수신 | 행 배열 완료 | piscina 워커(ADR-25) · 엔트리 크기 | 없음 |
| 상동 | 6c fan-in 버퍼 대기 | 행 배열 완료 | 플러시 시작 | **플러시 시간 트리거** | 없음 |
| #7 ClickHouse INSERT | 7 ClickHouse INSERT | INSERT 송신 | 응답 수신 | 배치 크기 — **flusher 1곳이라 배치가 컨슈머 수만큼 커진다** | 250 ms |

- 검산: 원본 구간 2(#6 · #7) → ADR-09 뒤 구간 4(6a · 6b · 6c · 7) · 합의 원본 목표 400 + 250 = **650** ms는 구간을 쪼개도 변하지 않는 비교 기준이다
- **지배 구간은 6c로 옮겨 간다.** 6a는 소비 루프가 BLOCK 대기로 거의 즉시 받고 6b는 워커 처리 시간이다 — 창 절반을 먹는 것은 6c다. 튜닝 손잡이는 여전히 플러시 시간 트리거 하나다.
- **컨슈머를 늘려도 6c와 #7은 줄지 않는다.** ADR-09 이전에는 컨슈머마다 독립 플러시라 컨슈머 3개가 파트 생성률 3배를 만들었고(보정 7.1), 이후에는 컨슈머 증설이 6a · 6b만 줄인다. 백프레셔 주의 단계의 "컨슈머 동시성 자동 증가"가 삽입 병목에 효과가 없는 이유가 이것이다 — [06_backpressure_failure.md](./06_backpressure_failure.md).
- **B안 · C안 비교는 S3의 실험이다.** 컨슈머 1개 + 시간 트리거 확대(B)와 async_insert(C)를 A와 파트 생성률 · E2E로 비교한다(원본 implementation_plan.md §7.1). ADR-09가 A를 잠정 채택한 상태이며 결과가 뒤집으면 ADR에 상태 항목을 단다.

## 조회 경로 예산

수집 경로와 따로 세는 요청 단위 예산이다. 목표치 정본은 REQ-NFR-07 · 08 · 09이고 전 행 미확인이다.

| 경로 | 원본 목표 p95 | 지배 요인 | 초과 시 조치 | 스위치로 가르는 비교 | 현행 |
|------|------|------|------|------|------|
| 최신값 조회(Redis) | 5 ms(원본 성능 목표 10 ms) | 네트워크 + HGETALL | 파이프라인화 · 요청 병합 | SW-02 on/off | 미확인 |
| 시계열 조회 — 캐시 히트 | 15 ms(성능 목표 20 ms) | gzip 해제 + 직렬화 — 워커 격리 대상 | 압축 레벨 조정 | SW-03 on/off | 미확인 |
| 시계열 조회 — 1일 · 캐시 미스 | 250 ms(성능 목표 300 ms) | ClickHouse 스캔 | 롤업 해상도 상향 | SW-03 off | 미확인 |
| Pub/Sub → WebSocket 도달 | 150 ms | 스로틀 창(현행 참고 100 ms) | 스로틀 창 조정 | SW-06 · SW-07 | 미확인 |
| 업무 데이터 CRUD | 80 ms(성능 목표 100 ms) | PostgreSQL 커밋 | 인덱스 점검 | 해당 없음 — 수집 부하 on/off로 가른다 | 미확인 |

- 검산: 조회 경로 = **5**
- **원본에는 목표가 두 벌이다** — 지연 예산표(원본 data_flow.md §15)의 구간 값과 성능 목표표(원본 architecture.md §16)의 합격 값. 구간 값이 합격 값보다 작은 것은 여유를 둔 것이며, 둘 다 원본 목표로만 인용한다.
- **Pub/Sub → WebSocket 150 ms는 스로틀 창이 대부분이다.** 창 100 ms로 병합하면 평균 대기가 창 절반이고 최악이 창 하나다 — 스로틀을 끄면(SW-07 off) 이 구간은 줄지만 프레임 수가 폭증한다.

## 알람 판정 구간 — 신설

원본 지연 예산표에는 **알람 판정 구간이 없다**(원본 implementation_plan.md §7.3). 판정이 Ingest 배치의 후처리로 수집 경로에서 도는데(ADR-11) 예산이 없으면, S7에서 E2E가 늘어도 어느 구간 탓인지 가를 자리가 없다. 이 절이 구간을 신설하고 값은 **미확인 — 확정 전 임의 값 고정 금지**로 등재한다.

| 하위 구간 | 시작 시각 | 끝 시각 | 지배 요인 | 원본 목표 | 현행 |
|------|------|------|------|------|------|
| A1 규칙 조회 | 판정 호출(ING-09) | 규칙 목록 확보 | cache 계열 히트 · 미스 시 PostgreSQL | 없음 | 미확인 |
| A2 상태 조회 | 규칙 확보 | 관련 rule_id 상태 확보 | **배치당 파이프라인 1회**(ADR-11) — 행당 왕복이면 행 수에 비례 | 없음 | 미확인 |
| A3 조건 평가 · 전이 | 상태 확보 | 전이 목록 완료 | 배치 행 수 · 규칙 수 | 없음 | 미확인 |
| A4 확정 쓰기 | 전이 목록 완료 | alarm_event 커밋 · 핫 상태 갱신 | 전이가 있을 때만 — PostgreSQL 커밋 | 없음 | 미확인 |
| A5 판정 전수 기록 | 전이 목록 완료 | alarm_eval 삽입 응답 | ClickHouse 삽입 — 원시 배치와 같은 재시도 정책 | 없음 | 미확인 |
| A6 발행 | 확정 쓰기 완료 | ch:alarm 발행 완료 | Redis 왕복 | 없음 | 미확인 |
| 판정 구간 | 판정 호출 | A4 · A5 · A6 중 마지막 완료 | 위 합계 | **없음 — 신설** | **미확인 — 확정 전 임의 값 고정 금지** |

- 검산: 하위 구간 **6** + 판정 구간 1 = **7**행
- **판정 구간은 E2E(ingested_at − ts) 밖이다.** 판정은 삽입 확정 뒤에 돌므로 ingested_at에 들어가지 않는다. 그래서 E2E만 재면 판정이 느려져도 드러나지 않는다 — 판정 구간을 따로 두는 이유다.
- **구조 관계 — 판정 구간은 플러시 주기 안에 머물러야 한다.** 판정이 flusher의 다음 플러시와 같은 흐름에서 돈다면 판정 시간이 6c에 더해져 다음 배치의 Stream 대기를 늘리고, 판정 구간이 플러시 주기를 넘으면 적체가 판정 쪽에 쌓인다. W4 판정 — flusher는 판정을 기다리지 않되 인계 깊이를 1로 제한한다(직렬 판정기). 판정이 플러시 주기보다 계속 느리면 flusher가 인계를 기다려 적체가 Stream lag로 드러난다 — [../06_pipeline/08_alarm.md](../06_pipeline/08_alarm.md)(W4). 이 관계는 1계층 구조값(두 주기의 대소)이라 값이 정해지지 않아도 판정 조건으로 쓴다.
- **알람 통지 지연 = E2E + 판정 구간 + Pub/Sub → WebSocket.** 운영자가 체감하는 알람 지연은 이 합이며 원본 목표가 없다. 디바운스(debounce_ms)는 예산이 아니라 의도된 지연이라 합에서 뺀다.

## 단일 이벤트 루프 공유

api는 한 프로세스라 수집 · 적재 · 판정 · 조회가 같은 이벤트 루프를 다툰다. 이 위험은 구간이 아니라 **모든 구간에 곱해지는 계수**다.

| 경합 원인 | 영향받는 구간 | 격리 수단 | 판정 지표 | 넘으면 |
|------|------|------|------|------|
| 디코딩 · MessagePack 해제 | 6b · 조회 전 경로 | piscina 워커(ADR-25) | nodejs_eventloop_lag p95 | 역할 분리 진입 조건 검토 |
| LTTB 다운샘플 · gzip | 시계열 조회 | 상동 | 상동 | 상동 |
| 판정 조건 평가 | A3 · 조회 전 경로 | 배치 단위 평가 · 필요 시 워커 | 상동 | 상동 |
| WebSocket 팬아웃 | Pub/Sub → WebSocket | 스로틀 병합(SW-07) | 상동 | 스로틀 창 확대 → 역할 분리 후 api 증설 |

- 검산: 경합 원인 = **4**
- 원본 진입 임계는 이벤트 루프 지연 p95 100 ms(원본 목표 · 4 vCPU 가정)이며 현행은 미확인이다. 임계의 정본은 [08_scaling_roadmap.md](./08_scaling_roadmap.md)다.

## 측정 지점

| 지표 | 계산식 | 수집 위치 | 걸리는 구간 |
|------|------|------|------|
| Modbus 왕복 | 요청 직전 · 응답 직후 시각 차 | Collector 히스토그램 | #2 |
| Stream 체류 | XREADGROUP 수신 시각 − 엔트리 ID 시각 | Ingest 히스토그램 | 6a |
| fan-in 버퍼 대기 | 플러시 시작 시각 − 행 배열 완료 시각(배치 내 최고 · 최저) | Ingest flusher 히스토그램 | 6c |
| 삽입 지연 | INSERT 전후 시각 차 | Ingest flusher 히스토그램 | #7 |
| **E2E 지연** | **ClickHouse에서 ingested_at − ts의 분위수** | 주기 쿼리 → 게이지(OBS-04) | E2E |
| 알람 판정 | 판정 호출 · 마지막 쓰기 완료 시각 차 | Alarm 히스토그램 | 판정 구간 · A1~A6 |
| API 지연 | 요청 · 응답 시각 차 | 미들웨어 히스토그램 | 조회 경로 5 |
| 이벤트 루프 지연 | nodejs_eventloop_lag | /metrics 기본 메트릭 | 전 구간 계수 |

- 검산: 측정 지점 = **8**
- **E2E를 두 컬럼의 차로 설계한 것이 이 예산의 핵심이다.** 별도 추적 시스템 없이 SQL 한 줄로 파이프라인 전체의 건강을 본다 — 이 컬럼 차가 없으면 E2E를 한 번에 잴 방법이 분산 추적뿐이고, 그것은 선택 프로파일이다.

E2E 게이지가 주기적으로 도는 쿼리의 모양은 아래와 같다. 창 길이는 2계층 조정값이다.

```sql
SELECT
    quantile(0.50)(dateDiff('millisecond', ts, ingested_at)) AS p50_ms,
    quantile(0.95)(dateDiff('millisecond', ts, ingested_at)) AS p95_ms,
    quantile(0.99)(dateDiff('millisecond', ts, ingested_at)) AS p99_ms,
    count() AS rows
FROM plc.tag_raw
WHERE ts > now() - INTERVAL 5 MINUTE
```

- **창을 ts로 자른다.** ingested_at으로 자르면 백프레셔로 늦게 들어온 행이 최근 창에 몰려 p99가 튄다 — 지연의 원인과 창의 기준이 같은 컬럼이 되어 측정이 자기 자신을 왜곡한다.
- 모드 D 백필 행은 ts가 과거라 창 밖에 떨어진다 — 모드 D를 E2E에서 빼는 규칙(REQ-NFR-03)이 창 조건으로 자동 성립한다.
