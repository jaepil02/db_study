**측정할 수 없게 된 것을 적어 두는 것도 설계의 일부다**(원본 tech_stack.md §10.6). 이 시스템의 최우선 목표가 측정 가능성이므로, 어떤 수치가 무엇을 재지 못하는지를 모르고 인용하면 그 수치는 틀린 결론의 근거가 된다. 이 문서는 한계 전수의 정본이며 [../03_requirements/13_nonfunctional.md](../03_requirements/13_nonfunctional.md)의 해석 규칙 5행과 [../04_architecture/05_latency_budget.md](../04_architecture/05_latency_budget.md)의 로컬 해석 4행이 여기를 가리킨다.

**이 머신은 원본 가정과 병목 방향이 반대다.** 원본은 4 vCPU급 · 메모리 여유를 가정했고 원본 실측 머신은 CPU 20스레드 · 가용 RAM 15 GB였다(원본 implementation_plan.md §2.1). 현행 측정 머신(macOS · Docker VM vCPU 14 · 할당 약 7.75 GB)도 방향이 같다. CPU가 남으니 원본이 "지킬 수 없다"고 한 원칙 하나(부하 생성기 격리)를 cpuset으로 되살릴 수 있고, 메모리가 모자라니 Redis maxmemory가 먼저 걸린다. 한계의 모양이 원본 표와 다른 이유다.

**한계마다 규칙이 붙는다.** 규칙 없는 한계 목록은 면책 조항이 된다 — 각 행은 "그래서 수치를 이렇게 읽는다"로 끝난다. 크기가 실측으로 정해지는 간섭(관측 스택 · 표본 추출)은 3계층 미확인이며 EXP-38 · 39가 잰다.

## cpuset으로 되살린 원칙과 남은 한계

원본은 "부하 생성기는 대상 호스트에서 실행하지 않는다 — 이 원칙은 로컬에서 지킬 수 없다"로 적었다(원본 tech_stack.md §8). 현행 측정 머신(Docker VM vCPU 14)에서도 CPU 집합을 갈라 이 원칙을 **부분적으로** 되살린다(원본 implementation_plan.md §2.4 · 배치 정본 [../04_architecture/03_execution_topology.md](../04_architecture/03_execution_topology.md)).

| 원칙 | 원본 상태 | cpuset 뒤 | 남은 한계 | 규칙 |
|------|------|------|------|------|
| 생성기와 대상의 CPU 분리 | 불가 — 완화책만 | k6 · 벤치마크 컨테이너 11-12 · 측정 대상 0-10 — **겹치는 집합 0** | 모드 A 생성기는 api 집합(0-4) 안 · datagen 프로세스는 k6 집합을 잠정 공유한다 | 생성기 위치를 기록 조건 칸에 적는다 |
| 관측 도구와 대상의 CPU 분리 | 불가 | 관측 스택 13 · 웹 개발 서버는 호스트 macOS 프로세스라 고정 불가 | Prometheus가 스크레이프로 api를 부르는 비용 · 저장소 통계 수집은 대상 CPU 안에서 돈다 | 정밀 세션은 프로파일 off |
| 코어 동질성 | 가정 | 없음 — 집합 번호가 P · E 어느 쪽인지 모른다 | 실행마다 배치가 바뀐다 | 3회 중앙값이 필수 |
| 캐시 · 메모리 대역 분리 | 해당 없음 | 없음 — L3 · 메모리 대역폭은 공유 | 생성기의 메모리 트래픽이 대상의 캐시 적중을 흔든다 | 생성기 부하가 큰 실험(Breakpoint)은 대상 지표의 해석에 적는다 |
| 대조 실험 자원 동일화 | 없음(대조군 없음) | ClickHouse · PostgreSQL CPU 집합 크기 · 메모리 상한을 같게 | 부하 실험 프로파일의 비대칭 배분과 다른 조건이다 | 대조 기록의 CPU 배치 칸 = 대조 동일화 |

- 검산: 원칙 = **5** · 배치 합 5 + 4 + 2 + 2 + 1 = **14** = VM vCPU 수(정본의 검산)
- **B형 — cpuset이 격리를 "해결"하지 않는 것은 설계 실패가 아니다.** 결론 — 원본 implementation_plan.md §2.4는 부하 생성기 격리 행을 "완화"에서 "해결"로 승격했지만, 코어 종류 미노출 · 캐시 공유가 남아 이 문서는 **부분 복원**으로 적는다. 반대 시나리오 — 해결로 적으면 3회 중앙값 규칙이 선택 사항처럼 읽혀 단일 실행 수치가 기록에 들어온다. 파생 지침 — cpuset은 오염원 하나(CPU 경합)를 없애고, 남은 분산은 반복 규칙이 처리한다.
- **이 배치는 vCPU 14 VM에 종속된다.** 머신이 바뀌면 배치를 다시 짜고, 다른 배치의 기록끼리 비교하지 않는다(조건 칸 CPU 배치).

## WSL2 mirrored 네트워킹의 영향

원본 implementation_plan.md §2.5의 영향 표를 측정 쪽에서 읽는다.

| 항목 | 영향 | 측정에 주는 것 | 규칙 |
|------|------|------|------|
| Windows 브라우저 → WSL2 서비스 | localhost로 포트 포워딩 없이 직결 | 브라우저 쪽 지연(WebSocket 수신 · 화면)이 NAT 모드보다 짧다 | 브라우저 쪽 수치를 다른 네트워크 모드 기록과 비교하지 않는다 |
| 127.0.0.1 바인드 | 유지 — 루프백을 호스트와 공유할 뿐 LAN에 노출하지 않는다 | 없음 | 해당 없음 — 노출 판정은 [../12_security/05_local_exposure.md](../12_security/05_local_exposure.md) |
| 루프백 경로 | NAT보다 한 단계 짧다 | E2E · 조회 지연이 **더 낙관적** | 네트워크 모드를 기록 조건 칸에 적는다 · 망 지연 가산 해석은 NAT보다 크게 |
| CORS 오리진 | 변화 없음 | 없음 | 해당 없음 |

- 검산: 항목 = **4** · 측정에 영향이 있는 행 **2**
- k6는 호스트(WSL2 안) 프로세스라 mirrored의 영향을 받지 않는다 — 영향은 Windows 쪽 브라우저에서 잰 값에만 걸린다. 서버 계측(히스토그램)은 네트워크 모드와 무관하다.

## 흐름별 병목과 측정이 가르지 못하는 경우

병목 후보 14행의 정본은 [../06_pipeline/01_flow_inventory.md](../06_pipeline/01_flow_inventory.md) §흐름별 병목 후보다. 이 표는 **측정이 두 후보를 가르지 못하는 경우**와 가르는 수단만 적는다.

| 헷갈리는 두 원인 | 증상 | 가르는 수단 | 가를 수 없는 경우 |
|------|------|------|------|
| Modbus 요청 수(#1) 대 생성기 CPU(#12) | 모드 A 폴링 주기 초과 | poll_duration · col_modbus_rtt_seconds 대 gen_worker_utilization | 둘 다 api 집합 0-4 안이라 CPU 포화면 둘이 동시에 오른다 — 모드 B로 적재 쪽을 따로 잰다 |
| 파트 생성률(#2) 대 디스크 IOPS(#3) | 삽입 지연 급증 | ch_new_parts_total 기울기 대 iostat 디스크 대기 | 머지 폭주가 디스크를 채우면 둘이 같은 순간 오른다 — 배치 크기만 바꾼 두 실행으로 가른다 |

| Redis 단일 스레드(#5) 대 api 이벤트 루프(#13) | 최신값 p95 악화 | redis_ops_per_sec · redis-benchmark 대조 대 nodejs_eventloop_lag_p95_seconds | Redis 명령 지연과 api 대기가 같은 요청 지연에 합쳐진다 — redis-benchmark 단독 상한과 비교한다 |

| api 이벤트 루프(#13) 대 호스트 CPU(#14) | 모든 지표 동시 악화 | api 컨테이너 CPU 대 머신 전체 CPU(docker stats · 호스트 도구) | 관측 스택 · 생성기가 켜진 상태면 호스트 CPU가 측정 대상 밖 소비를 포함한다 — 정밀 세션에서만 가른다 |
| 생성기 포화(#12) 대 시스템 상한 | 목표 부하 미달 | 생성기 달성 조건 · CPU 조건 | ①의 3배 여유가 확인되지 않은 부하 — 재지 않는다([05_load_scenarios.md](./05_load_scenarios.md) §생성기 포화 판정) |

- 검산: 쌍 = **7** · 병목 후보 14 중 쌍에 등장 = #1~#7 · #9 · #12 · #13 · #14 = **11** · 쌍에 없는 3(#8 PostgreSQL 커넥션 · #10 WebSocket 팬아웃 · #11 MV 체이닝)은 단독 지표로 가른다
- **병목 판정은 한 번에 한 주입 모드로만 한다**(REQ-GEN-05) — 모드 A와 B를 섞으면 #1과 #2를 가를 수 없다.

## 관측 스택 간섭

측정 도구가 측정 대상을 건드리는 자리 전수다. 크기는 전부 3계층 미확인이며 EXP-38이 같은 부하에서 조건 하나씩 바꿔 잰다.

| 간섭원 | 측정 대상에 더하는 것 | 켜지는 조건 | 규칙 |
|------|------|------|------|
| Prometheus 스크레이프 · 저장 | api의 /metrics 텍스트 생성 · 관측 집합 13 CPU · 디스크 쓰기 | 관측 프로파일 on | 정밀 세션은 off |
| Grafana 대시보드 조회 | Prometheus 쿼리 · 브라우저 렌더링 | 대시보드를 열어 둠 | 정밀 세션은 닫는다 |
| 저장소 통계 수집 | pg_stat_statements · system.parts · query_log · INFO 조회 | **항상**(OBS) | 수집 주기 고정 · 스크레이프와 독립(REQ-OBS-03) · 관측 쿼리 비율을 EXP-38이 잰다 |
| E2E 게이지 쿼리 | tag_raw 최근 창 스캔 | 항상 | 창을 ts로 잘라 스캔 범위를 묶는다(REQ-OBS-05) |
| 메모리 표본 추출 | Redis 명령 주기당 표본 × 2 | 항상 | 전수 순회 금지 · 표본 수 고정 |
| 컨슈머 랙 갱신 | 플러시마다 XINFO GROUPS 1회 | 항상 | 플러시당 1회 이상으로 늘리지 않는다 |
| 콘솔 · health 폴링 | 세 저장소 왕복 · /metrics 해석 | EXP-CONSOLE을 열어 둠 | 정밀 측정 모드로 폴링을 멈추거나 닫는다 |
| k6 원격 쓰기 | k6 CPU · Prometheus 쓰기 | 탐색 세션 설정 | 정밀 세션은 끈다 — 생성기 포화 판정이 흔들린다 |
| 구조화 로그 | 이벤트당 한 줄 쓰기 | 무효 · 의심 구간 발생 시 | 사건 드문 경로에만 — 행 단위 로그 금지 |

- 검산: 간섭원 = **9** · 항상 켜진 간섭원 **4**(저장소 통계 · E2E 게이지 · 메모리 표본 · 랙 갱신)
- **항상 켜진 넷은 정밀 세션에서도 끌 수 없다.** 그래서 그 비용은 "측정 대상의 일부"로 기록된다 — EXP-38의 목적은 그 비용을 없애는 것이 아니라 크기를 알아 해석에 적는 것이다.
- /metrics 응답 크기 · 스크레이프 지연도 이 표의 첫 행 비용이다([../07_api/10_metrics.md](../07_api/10_metrics.md) 미확인 행) — obs_metrics_response_bytes가 크기를 낸다.

## 측정 도구의 한계 등재

어느 계층도 강제하지 않는 측정 오차의 등재다(이식 패턴 한계 등재). "아무도 책임지지 않는다"를 누락이 아니라 기록된 상태로 둔다.

| # | 항목 | 강제 주체 | 막는 것과 못 막는 것 | 잔여가 담기는 자리 |
|:--:|------|------|------|------|
| 1 | 히스토그램 분위수 보간 | 버킷 경계 규칙(원본 목표 값 포함) | 판정 경계에서의 뒤집힘은 막는다 · 경계 사이 값의 오차는 못 막는다 | 분포 판정 기록은 k6 · SQL 정확 분위수를 병기 |
| 2 | E2E 게이지 근사 | 기록 SQL의 quantilesExact | 기록 수치는 정확하다 · 콘솔 · 대시보드의 게이지는 근사다 | 게이지 값을 기록에 옮기지 않는다([02_instrumentation.md](./02_instrumentation.md)) |
| 3 | 메모리 표본 추정 | 표본 수 · 표본 수 노출 | 전수 순회로 인한 멈춤은 막는다 · 드문 접두의 추정 흔들림은 못 막는다 | EXP-39 오차 · redis_prefix_sampled_keys |
| 4 | 트리밍 결함 개수 | PEL 쪽 정확 계수 | PEL 잘림은 정확히 센다 · 미배달 잘림은 사건 수만 센다 | 사건 1 이상이면 무손실 판정 불합격 |
| 5 | 판정 무효 구간의 표면 부재 | 계수 + 로그 이벤트 | 구간의 존재는 드러낸다 · 판정 이력 API 응답은 구간을 모른다 | 실험 기록이 로그에서 옮긴다 |
| 6 | 같은 머신 시계 | 호스트 커널 시계 공유 | 컨테이너 간 시각 차 계산은 성립한다 · 확장으로 머신이 나뉘면 성립하지 않는다 | 로컬 전용 범위 안에서만 6a · E2E를 인용 |
| 7 | 격자 6단계와 원시 보존 | 적재 시간 예산 관계 | 보존보다 긴 실험을 막는다 · 현행 보존에서 6단계를 수행할 수 없다 | 관측 범위를 5단계로 기록하거나 보존 연장을 조건으로 적는다([06_experiment_catalog.md](./06_experiment_catalog.md)) |
| 8 | 브라우저 쪽 지연 | 없음 — 서버가 볼 수 없다 | 서버 발행 → 송신까지는 잰다 · 수신 · 렌더링은 못 잰다 | k6 ws 기록 · 두 브라우저 수동 관찰(ACK 전파) |

- 검산: 등재 = **8**
- **#5 · #8은 설계가 고른 한계다.** 저장소를 늘리거나(무효 구간 테이블) 브라우저 계측을 서버로 보내는(수신 비콘) 대안은 측정 대상을 바꾸는 비용이 한계보다 크다고 판정했다 — 판정 근거는 [02_instrumentation.md](./02_instrumentation.md) §구간 기록 · §확인(ACK) 신호 부재의 계측.

## 수치 해석 규칙

기록의 해석 절이 지킬 규칙이다.

| 규칙 | 내용 | 어기면 |
|------|------|------|
| 원본 목표로 판정하지 않는다 | 원본 목표는 4 vCPU 가정 · 첫 실측이 기준선 | 다른 머신의 기준으로 이 머신을 판정한다 |
| 한계 행을 인용한다 | 해석 절에 걸리는 한계를 이 문서 표의 행으로 적는다 | 같은 수치가 읽는 사람마다 다른 한계로 해석된다 |
| 낙관 방향을 밝힌다 | 루프백 · mirrored가 지연을 낮춘다는 방향을 적는다 | 로컬 지연이 실환경 예측으로 인용된다 |
| 조건 밖으로 옮기지 않는다 | 다른 프로파일 · 배치 · 네트워크 모드로 수치를 일반화하지 않는다 | 한 머신 · 한 VM 할당의 값이 설계 상수가 된다 |
| 부재는 부재로 적는다 | 잴 수 없었던 것은 "측정 불가 — 한계 #N"으로 · 0으로 적지 않는다 | 측정 누락이 "효과 없음"으로 기록된다 |

- 검산: 규칙 = **5**
