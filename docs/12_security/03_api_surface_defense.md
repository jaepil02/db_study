**방어 지점은 NestJS 한 곳이다.** 프록시 · 로드 밸런서가 없으므로 CORS · Host 대조 · Origin 검증 · 입력 검증이 전부 api 코드 안에서 일어난다(원본 architecture.md §11.2 · §18). 앞단에 무언가를 끼워 넣었다가 걷어낼 일이 없다는 뜻이고, 동시에 이 계층이 빠지면 대신 막을 곳이 없다는 뜻이다.

**로컬 전용이라는 사실이 이 문서의 방어를 생략할 이유가 되지 않는다**(전역 불변식 로컬 전용 · REQ-GLB-19). 네트워크 경계는 127.0.0.1 바인드가 맡지만([05_local_exposure.md](./05_local_exposure.md)) 같은 머신의 브라우저 페이지 · 스크립트는 경계 안에 있다. 이 문서의 방어는 그 경계 안쪽을 향한다.

이 문서가 **정본으로 갖는 것은 하나다** — 내보내기 범위 상한. 헤더 모양 · 봉투 · 표면 번호의 정본은 [../07_api/01_conventions.md](../07_api/01_conventions.md)이고 여기서는 인용만 한다.

**D-16(사용자 결정 2026-10-11) 뒤 모든 표면은 무인증이다.** 토큰 · 역할 · 레이트 리밋 · 보안 헤더가 없고 표면 앞의 검사는 출처 방어(CORS · Host 대조 · WebSocket Origin)뿐이다([../07_api/01_conventions.md](../07_api/01_conventions.md) §출처 방어). 옛 정본 레이트 리밋 등급 · 한도 관계식과 auth 표면 CORS 제외 판정 · BFF 인증 경로의 출처 검사 · 로그인 시도 제한 판정은 대상과 함께 지웠다(원문 커밋 28c0cc9) — 계수할 신원도, 지킬 토큰도 없다.

- **조회는 거절하지 않고 보정하는데 내보내기는 거절한다(A형).** 통념은 두 표면이 같은 규칙을 쓴다는 것이다. 부정 — 조회는 해상도를 올려 같은 범위를 싸게 답할 수 있지만 내보내기는 정의상 원시라 올릴 해상도가 없다(REQ-TSQ-15). 진짜 축은 **보정 수단의 유무**다. 대체 경로 — 긴 범위 원시가 필요하면 범위를 나눠 여러 번 내보낸다.

### 내보내기 범위 상한

인계 "내보내기 범위 상한"([../07_api/05_timeseries.md](../07_api/05_timeseries.md) · [../02_features/07_timeseries.md](../02_features/07_timeseries.md))을 닫는다. **이 표가 내보내기 범위 상한의 정본이다.**

| 항목 | 계약 |
|------|------|
| 판정량 | 요청의 to − from(스냅 전 요청값) |
| 현행 참고 | **1일** — 2계층 조정값 · 소유 이 문서 |
| 하한 조건 | REQ-TSQ-15의 검증 사례(1일 원시 내보내기)가 상한 안에 든다 — 상한을 1일 아래로 내리면 요구사항 검증 자체가 400이 된다 |
| 상한 조건 | 원시 보존 기간 이하(현행 7일 · [../05_data_stores/08_retention_lifecycle.md](../05_data_stores/08_retention_lifecycle.md)) — 넘는 범위는 앞부분이 이미 지워져 빈 구간을 스캔한다 |
| 초과 시 | common.validation_failed/400 · details.fields reason range — 새 코드를 만들지 않는다 |
| 금지된 대체 동작 | 범위를 조용히 잘라 앞부분만 내보내는 것 · 해상도를 올려 내보내는 것 |
| 한도 | 없음 — 레이트 리밋 삭제(D-16) · 범위 상한이 요청 하나의 원시 스캔을 묶고 요청 수는 묶지 않는다 |

- 검산: 항목 = **7**
- **범위 상한은 브라우저도 지킨다.** 내보내기는 fetch로 받는다([../07_api/05_timeseries.md](../07_api/05_timeseries.md)) — 링크 다운로드가 아니라 스크립트가 응답을 받아 파일로 저장한다. 범위가 무한하면 태그 50 · 원시 해상도에서 한 응답이 브라우저 탭 메모리를 넘는다.
- 조용히 자르지 않는 이유 — 잘린 파일은 형식상 완전해 보여 분석 도구가 1일치를 7일치로 믿는다(REQ-TSQ-01이 태그 절단을 거절하는 이유와 같다).

## ClickHouse 파라미터 바인딩

원본은 "ClickHouse 쿼리는 반드시 파라미터 바인딩 · 태그 ID 배열은 정수 검증 후 사용"이라 적었다(원본 architecture.md §18). W7에 이 계약을 **REQ-GLB-24**로 채번했다([../03_requirements/01_global_rules.md](../03_requirements/01_global_rules.md)) — 이 절은 그 계약을 방어 관점에서 풀어 적는다.

| 규칙 | 적용 | 어기면 |
|------|------|------|
| 요청 값은 전부 바인딩 파라미터로 — 문자열 연결로 SQL을 만들지 않는다 | 조회 · 내보내기 · 최신값 복원 · PostgreSQL 업무 CRUD(REQ-GLB-24) | 요청 값이 SQL 문장이 된다 |
| 태그 ID 배열은 스키마 검증에서 정수 배열로 확정한 뒤 바인딩한다 | 05_timeseries #1 · #2 | 문자열이 섞인 배열이 바인딩 단계에서 형 변환 오류로 500이 된다 — 400이어야 할 것이 결함으로 기록된다 |
| 테이블 · 해상도는 **고정 대응표에서 고른다** — 요청 문자열을 테이블 이름으로 쓰지 않는다 | 해상도 → tag_raw · tag_1m · tag_1h · tag_1d | 식별자는 바인딩할 수 없다 — interval 값이 그대로 FROM 절에 들어가면 임의 테이블을 읽는다 |
| 집계 함수는 허용 5종 대응표에서 고른다 | aggregations | 요청 문자열이 함수 이름이 된다 |
| FORMAT 절은 csv · parquet 대응표에서 고른다 | 05_timeseries #2 | 요청 문자열이 출력 형식 지시가 된다 |

- 검산: 규칙 = **5**
- **바인딩으로 막을 수 없는 자리(식별자 · 함수 · 형식)는 대응표가 막는다.** 요청은 열거 값만 싣고, 서버가 그 값을 고정 문자열로 바꾼다 — 대응표 밖 값은 스키마 검증이 이미 400으로 끝냈다.
- **/metrics의 느린 쿼리 문형은 이 규칙의 부산물이다.** 값이 바인딩 자리로 빠져 있어 문형에 드러나지 않는다(REQ-OBS-10) — 바인딩을 어기는 코드가 하나라도 있으면 공개 표면에 요청 값이 실린다.

## WebSocket

Origin 검증과 종료 코드 7종을 방어 관점에서 다시 읽는다. 종료 코드의 정본은 [../07_api/11_websocket.md](../07_api/11_websocket.md)다.

### Origin 검증

| 관점 | 내용 |
|------|------|
| 규칙 | 핸드셰이크 Origin을 CORS 허용 목록과 **같은 목록**으로 검증 · 밖이면 업그레이드 뒤 4403 |
| 막는 것 | 다른 오리진 페이지의 브라우저 WebSocket — 브라우저는 Origin을 위조하지 못한다 |
| 막지 못하는 것 | **브라우저 밖 클라이언트** — Origin 헤더를 임의로 싣는다 · 신원 경계가 없다(무인증 · D-16) — 바깥 경계는 127.0.0.1 바인드다 |
| 적용 시점 | **S2부터** — 옛 첫 메시지 인증(S7)은 D-16 삭제([../07_api/11_websocket.md](../07_api/11_websocket.md) 연결 단계) |
| 리뷰 판정 | Origin 검증을 CORS와 같은 S2부터 적용한다 — W7 반영(REQ-GLB-26 ① · REQ-RLT-09 · 07_api/11) |

- 검산: 관점 = **5**
- **Origin 검증 없는 WebSocket은 CORS보다 넓게 열린다(A형).** 통념은 무인증 표면에서도 CORS가 다른 오리진을 막는다는 것이다. 부정 — CORS는 HTTP 응답에만 걸리고 WebSocket 핸드셰이크에는 걸리지 않는다. 같은 머신 브라우저의 아무 페이지나 ws://localhost:13000/ws/realtime에 붙어 subscribe를 보내면 실시간 프레임을 받는다. 진짜 축은 **Origin 검증의 적용 시점**이다. 대체 경로 — Origin 검증은 토큰이 필요 없어 S2부터 건다 — CORS를 S2부터 거는 근거(REQ-GLB-25)와 같다(W7 반영). 남는 것은 Origin을 위조하는 브라우저 밖 클라이언트이고, 첫 메시지 인증이 D-16으로 사라져 그 방어는 127.0.0.1 바인드뿐이다([05_local_exposure.md](./05_local_exposure.md)).

### 종료 코드 7종 리뷰

인계 "WS 종료 코드 8종 리뷰"를 닫았다. **판정 — 남은 7종을 유지한다. 새 코드를 제안하지 않는다.** 옛 4401(인증 대기 초과 · 토큰 불량)은 첫 메시지 인증과 함께 D-16 결번이다.

| 코드 | 방어 관점 | 판정 |
|:--:|------|------|
| 1000 | 정상 종료 — 방어와 무관 | 유지 |
| 1001 | 재기동 — 재연결 폭주의 시작점 · 백오프 상한이 흩는다 | 유지 |
| 4400 | 형식 위반 · URL 쿼리 구독 거절 — 정해진 메시지 모양 밖을 닫는 장치 | 유지 — 재연결하지 않아 형식 공격이 재시도 루프가 되지 않는다 |
| 4403 | Origin 밖 — 재시도로 풀리지 않는 거절 | 유지 — 재연결하지 않아 Origin 불일치가 재연결 루프가 되지 않는다 |
| 4408 | pong 미수신 — 죽은 연결 정리 | 유지 |
| 4413 | 느린 소비자 — 한 브라우저가 게이트웨이 메모리를 잡는 것을 끊는다 | 유지 — 송신 대기량 한도가 이 코드의 방어 값이다 |
| 4503 | Redis 불가 — 업스트림 실패를 원인과 함께 알린다 | 유지 |

- 검산: 코드 = **7** · 유지 7 · 신설 제안 0 · 결번 4401(D-16)
- **7종이 다루지 않는 위협은 연결 수다.** 전체 동시 연결 상한이 없어 한 스크립트가 소켓을 계속 연다 — 상한을 두면 초과를 알릴 종료 코드가 필요하지만, 상한 자체가 3계층 미확인(연결 수 상한 · [../07_api/11_websocket.md](../07_api/11_websocket.md))이라 코드를 먼저 만들지 않는다. 잔여로 등재한다([04_threat_model.md](./04_threat_model.md)).
- subscribe 폭주는 연결당 구독 설비 상한(subscribed.rejected reason limit)이 묶는다 — 메시지 수를 세는 장치는 없다(레이트 리밋 삭제 · D-16).

## 상태를 바꾸는 POST

인증이 없는 표면에서 **상태를 바꾸는 POST**(설비 가동 · 실행 시작 · 중단 · 센서 데이터 지우기)를 지키는 검사다(리드 판정 2026-10-11 · REQ-GLB-27). 계약의 정본은 [../07_api/01_conventions.md](../07_api/01_conventions.md) §출처 방어이고 여기서는 층마다 무엇을 막고 무엇이 남는지를 읽는다.

| 층 | 검사 | 실패 | 막는 것 | 못 막는 것(잔여) |
|------|------|------|------|------|
| BFF Origin | 요청 Origin이 허용 출처 2(http://localhost:13001 · http://127.0.0.1:13001)가 아니면 api를 부르지 않는다 · Origin이 없으면 같은 출처로 본다(브라우저는 교차 출처 POST에 Origin을 붙인다) | 403 본문 없음 | 다른 사이트 페이지의 fetch · 폼 POST가 BFF를 거쳐 api의 CORS · Host 대조를 대신 통과하는 것 | Origin을 붙이지 않는 같은 머신 프로세스(스크립트 · CLI) — 무인증 잔여 |
| BFF 본문 중계 | Content-Type · 본문을 바꾸지 않고 넘긴다 — 판정은 api | 해당 없음 | text/plain 단순 요청이 BFF에서 JSON으로 고쳐져 api 검사를 지나는 것 | 해당 없음 |
| api Content-Type | application/json이 아니면 거절(06_realtime #4 · 09_datagen #2 · #5 · #8) | 400 common.validation_failed(path header.content-type) | api 직결(13000)로 오는 폼 POST · text/plain 단순 요청 — 사전 요청 없이 실행되는 모양 전부 | application/json을 붙인 교차 출처 요청은 사전 요청에서 CORS가 막는다 — 같은 머신 프로세스는 막지 않는다 |
| api 본문 모양 | JSON 객체 · 엄격 스키마(모르는 키 거절) · 본문이 필요 없는 지우기 · 중단도 빈 객체 {} | 400 common.validation_failed(path body) | 본문 없는 POST · 배열 · 문자열 본문 | 해당 없음 |

- 검산: 검사 = **4**(BFF 2 + api 2)
- **B형 — 본문이 필요 없는 지우기 · 중단에 빈 객체 {}를 요구하는 것은 형식 집착이 아니라 교차 출처 실행을 막는 장치다.** 결론 — 상태를 바꾸는 POST는 Content-Type application/json의 JSON 객체 본문 없이는 400이다. 반대 시나리오 — 본문 없는 POST를 받으면 브라우저가 사전 요청 없이 보내는 단순 요청(폼 POST · no-cors fetch)으로 실행된다 — 발표 노트북 브라우저로 연 다른 사이트 하나가 설비 가동을 켜거나 센서 데이터를 전부 지운다(r5 검수 L9). 파생 지침 — 상태를 바꾸는 표면을 새로 열면 같은 본문 검사를 붙이고, BFF 경로는 중계 전에 Origin을 먼저 본다.
- **CORS와 겹치지 않는다.** CORS는 응답을 읽는 것만 막아 실행은 이미 끝난 뒤다 — 이 검사들은 실행 자체를 막는다. 브라우저 직결 표면(06_realtime #1 · #2 · 05_timeseries #1 · #2)은 상태를 바꾸지 않아 대상이 아니다.
- **보안 헤더가 없다는 것은 기록된 잔여다.** 지금 요구가 없고 코드에도 없다 — 브라우저가 JSON · CSV를 다른 형식으로 추측하는 위험은 [04_threat_model.md](./04_threat_model.md) 잔여가 받는다.

## 라이브 실행 표면

분산 처리 모니터링(EXP-FLOW) · 직접 비교 실험(EXP-LAB)의 시작 · 중단 버튼이 부르는 표면 넷(09_datagen #2~#5 · 브라우저 → BFF → api · no-store — 실행 종류 flow · compare)을 방어 관점에서 읽는다. 표면 계약의 정본은 [../07_api/09_datagen.md](../07_api/09_datagen.md), 실행 기전의 정본은 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md) §라이브 실행 — flow다. 이 표면은 **Stream에 수백만 포인트를 싣는 일을 버튼 하나로 시작한다** — 방어가 막아야 하는 것은 정보 유출보다 자원 소모와 측정 오염이다.

| 방어 | 계약 | 막는 것 | 못 막는 것(잔여) |
|------|------|------|------|
| 동시 1 | 진행 중 실행 하나(flow · compare가 서로 막는다 — 옛 perf는 D-16 폐지) — 겹친 시작은 datagen.run_in_progress/409(details 현재 runId · type) | 버튼 연타 · 두 탭 동시 시작 · 스크립트 반복 호출이 실행을 겹쳐 디스크 · 적체를 곱으로 쓰는 것 | 실행을 순차로 반복하는 것 — 한 실행이 끝나면 다음이 곧바로 시작된다 |
| 매개변수 화이트리스트 | flow pps · durationSec · bizPerSec · readsPerSec · compare part · spanHours 각 목록 — 밖이면 common.validation_failed/400 | 목록 밖 pps · 무한 지속 — 실행 하나의 자원 상한이 목록 최대값에 묶인다 | 목록 최대값 자체의 비용(flow 50,000 pps × 300초 · 조회 50/초 × 300초 = 15,000건 — 프로세스 안 호출이고 결과를 버려 노출은 없으며, 시계열은 태그 3 · 과거 10분 범위 · 동시 진행 상한(현행 참고 32)을 넘으면 건너뛰어 ClickHouse 부하가 묶인다) |
| 입력 검증 | runId는 UUID 형식만 — 아니면 400 · 없는 runId는 common.not_found/404 · stop은 멱등(종결 실행에 200) | 경로 값이 실행 조회 · 취소 대상 선택을 흔드는 것 | 해당 없음 |
| 시작 조건(D-16) | 직접 비교 넣기 · 무결성은 SW-09 off · 설비 가동 켜짐이면 400 · 조회 대결은 마지막 넣기가 완료가 아니면 409 datagen.compare_no_data · 센서 데이터를 지우는 동안은 모든 시작이 400(path purge) | 비교 사본에 가동 데이터가 섞이는 것 · 반쯤 지워진 구간으로 승패를 내는 것 · 지우는 동안 새 행이 생기는 것 | 실행 도중 설비를 켜는 것(한계 등재 [../05_data_stores/02_postgresql_constraints.md](../05_data_stores/02_postgresql_constraints.md) #28) · 지우기 잠금은 api 하나 기준(#30) |

- 검산: 방어 = **4** · 옛 실행 수명 객체 정리(perf) · 레이트 리밋 · 인가 3행은 D-16 삭제
- **인가가 없다(D-16).** 같은 머신의 어느 프로세스든 실행을 시작 · 중단하고, flow의 업무 명령이 시연 전용 행의 MST 쓰기 경로를 기동하며(actor null) compare 넣기가 비교 사본의 사흘 창을 비우고 다시 채운다 — 바깥 경계는 127.0.0.1 바인드뿐이다(잔여 [04_threat_model.md](./04_threat_model.md)).
- **동시 1은 실행끼리만 막는다.** 측정 실험과 라이브 실행이 겹치는 것은 표면이 모른다 — 실험 착수 전 gen_run_active 0 확인이 절차 쪽 방어다([../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md) §한 번에 한 계층). 잔여는 [04_threat_model.md](./04_threat_model.md)가 받는다.

### 게이트 판정

옛 부하 주입 bulk 표면(09_datagen #1)은 환경변수 게이트(기본 false)로 닫혀 있었다 — bulk 표면 · 게이트는 모드 C와 함께 D-16으로 지웠다. 라이브 실행 표면에 그런 게이트를 둘지 판정한다. **판정 — 게이트 환경변수를 두지 않는다.**

| 안 | 동작 | 실패 시나리오 | 판정 |
|------|------|------|------|
| ① 옛 bulk와 같은 게이트(기본 false) | 환경변수 + 재기동으로만 표면이 열린다 | 기본 기동에서 시작 버튼이 404가 된다 — 사용자가 요구한 "각 화면의 시작 버튼"이 설정을 바꾸기 전에는 동작하지 않고, 켜 둔 게이트는 health에서 보이지 않아 게이트 방치 잔여를 만든다 | 버림 |
| ② **게이트 없음** | 표면은 늘 열려 있고 방어는 위 표 6 | 로컬 사용자가 버튼으로 대량 적재 · 디스크 소모를 시작할 수 있다 | **채택** — 잔여 등재 |

- 검산: 안 = **2**
- **bulk와 다른 이유는 입력의 모양이다(B형).** 결론 — bulk는 요청 본문이 곧 적재 행이라 요청자가 임의 설비 · 임의 양을 tag_raw에 넣지만, 라이브 실행은 요청이 목록 값 몇 개뿐이고 행은 서버가 정해진 규칙으로 만든다(flow 발행은 시연 전용 설비의 flow 전용 태그 50 · quality 9로 · flow 업무 명령은 시연 전용 행(사이트 DEMO-FLOW · 라인 DEMO-FLOW-L · 설비 DEMO-FLOW-DEV)에만 · compare는 카드 라인 태그로 과거 구간에만 — 운영 행은 바뀌지 않는다). 반대 시나리오 — 게이트로 막으면 방어는 늘지 않고 기본 기동의 화면 기능만 사라진다. 파생 지침 — 라이브 실행에 요청 본문이 행을 싣는 매개변수가 생기면 이 판정을 다시 한다.
- 127.0.0.1 바인드가 바깥 경계를 긋는다([05_local_exposure.md](./05_local_exposure.md)) — 게이트 없음이 LAN 노출이 되지 않는 전제다.

## 센서 데이터 · 설비 가동 표면

버튼 하나로 쌓인 센서 데이터를 지우는 표면(09_datagen #8)과 공장 전체를 켜고 끄는 표면(06_realtime #4)이다(D-16 결정 3 · 5). 막아야 하는 것은 정보 유출이 아니라 **지우면 안 되는 것까지 지우는 것**과 **지운 결과가 거짓이 되는 것**이다. 표면 계약의 정본은 [../07_api/09_datagen.md](../07_api/09_datagen.md) §센서 데이터 · [../07_api/06_realtime.md](../07_api/06_realtime.md) #4다.

| 방어 | 계약 | 막는 것 | 못 막는 것(잔여) |
|------|------|------|------|
| 지우는 범위 고정 | 센서 데이터만 — ClickHouse 원본 · 롤업 3 · PostgreSQL 비교 사본 · Redis 대기줄 엔트리 · 지금 값 · 조회 사본 · 설비 · 태그 · 업무 · 실행 결과는 닿지 않는다 · PostgreSQL은 app_owner SECURITY DEFINER 함수 하나(app_rw에 TRUNCATE 권한이 없다) | 버튼 하나로 마스터 · 업무 원장 · 실행 결과까지 지우는 것 · app_rw 접속으로 아무 테이블이나 TRUNCATE하는 것 | 쌓인 센서 데이터 전부는 지운다 — 되돌릴 길이 없다(덤프 대상이 아니다 · [../05_data_stores/08_retention_lifecycle.md](../05_data_stores/08_retention_lifecycle.md) §센서 데이터 지우기) |
| 막는 조건 | data.purge_blocked/409 — reason run_in_progress · plant_running(끈 직후 수집기 포함 · 읽지 못하면 켜짐) · stream_backlog | 지우는 동안 새 행이 들어와 "지웠는데 남았다"가 되는 것 | 스풀 파일 재발행(대기줄 적체 검사가 보지 않는다) |
| 지우기 잠금 | 지우는 동안 실행 시작 · 설비 켜기 400(path purge) · 켜는 동안 지우기 409 · 겹친 지우기는 하나를 나눠 받는다 | 확인과 TRUNCATE 사이에 넣기 · 가동 켜기가 끼어드는 것 · 같은 지우기를 두 번 도는 것 | api를 여럿 띄우면 서로 모른다(한계 등재 [../05_data_stores/02_postgresql_constraints.md](../05_data_stores/02_postgresql_constraints.md) #30) |
| 설비 가동 쓰기 | 같은 상태면 쓰지 않는다 · 원자 스크립트 하나 · 봉인 계열 키(TTL 없음 · 축출 대상 아님) · 수집기 역할 재기동이면 기동 기본값(로컬 꺼짐) | 연타가 바뀐 시각을 흔드는 것 · 메모리 압박으로 켜 둔 상태가 사라지는 것 · 켜 둔 채 내린 스택이 재기동만으로 센서 행을 쌓는 것 | 누구든 켜고 끈다(무인증) — 켜 두면 디스크가 센서 데이터로 찬다(보존 7일이 상한) |

- 검산: 방어 = **4**
- **B형 — 지우기가 설비 가동을 대신 끄지 않는 것은 불편이 아니라 사람의 뜻을 지키는 장치다.** 결론 — 가동 중이면 409로 막고 가동을 건드리지 않는다. 반대 시나리오 — 지우기가 가동을 끄면 HMI를 보던 다른 화면 · 다른 사람의 공장이 버튼 하나로 멈추고, 끈 사실이 지우기 응답에만 남는다. 파생 지침 — 화면이 reason을 쉬운 말로 보이고 사람이 가동을 끈 뒤 다시 누른다.
