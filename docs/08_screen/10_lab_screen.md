이 문서는 발표의 "직접 해 보기" 첫 화면을 명세한다. **EXP-LAB은 ②③④가 보인 기록을 지금 시스템에서 다시 잰다** — 카드 라인 30대의 과거 구간 데이터를 Redis 대기줄(stream:plc:raw)로 보내 ClickHouse와 PostgreSQL 비교 사본(plc_tag_raw_control)에 **같은 묶음을 함께** 넣고(SW-09 gated — 게이트가 켜진 동안만 PostgreSQL에도 싣는다), 그 데이터로 소량 2 · 대량 2 질문의 조회 대결과 규칙 어긴 데이터 3종의 무결성 시험을 한다. 실행 기전의 정본은 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md) · 표면 계약은 [../07_api/09_datagen.md](../07_api/09_datagen.md)이고, 이 문서는 화면에 놓인 자리 · 문구 · 판독만 고정한다.

**⑤의 PostgreSQL은 TimescaleDB다 — ②③④가 보이는 기록의 일반 PostgreSQL과 다른 PostgreSQL이다**(D-05 부분 개정 · 사용자 결정 2026-10-12). 비교 사본은 TimescaleDB hypertable(칸 1일)이고 넣기가 끝날 때 그 구간 칸을 열 압축한 뒤 크기를 재며 조회 대결도 압축된 칸을 읽는다([../04_architecture/09_decision_records.md](../04_architecture/09_decision_records.md) ADR-32). 키 · 참조 · 값 규칙과 Redis 경유 · 같은 묶음은 그대로라 무결성 시험은 같은 뜻이다. ②③④의 PostgreSQL은 기록 035~053의 일반 행 저장 PostgreSQL이다 — 두 화면의 PostgreSQL 숫자를 같은 PostgreSQL의 다시 잰 값으로 읽지 않는다.

**패널마다 서버에 보관된 마지막 결과를 계속 보인다 — 단 실행 중인 패널은 진행 중 실행의 결과를 실시간으로 그린다**(사용자 결정 2026-10-11). 실행 결과는 run_result 테이블에 부분(part)별로 남고(완료한 실행만 결과를 남긴다), 화면은 들어올 때와 이 화면에서 지켜본 실행이 끝났을 때 부분별 최근 결과를 다시 읽는다. ▶를 누르면 그 패널은 지난 결과를 지우고(흐리게 겹쳐 두지 않는다) 1초마다 받는 진행 중 실행 객체의 result로 새 값을 찍는다 — 넣기는 선 그림이 1초마다 이어지고 행 수가 오르고 디스크 막대가 자라며, 조회 대결은 질문 하나 · 무결성은 시험 하나가 끝날 때마다 그 줄이 채워진다. 다른 두 패널은 지난 보관 결과 그대로다. 결과가 예상과 달라도(예: 넣기 묶음 시간은 PostgreSQL이 더 느리지 않을 수 있다) 고르지 않고 그대로 보인다(D-16). **결과는 측정 기록이 아니다** — 앱을 거친 라이브 실행이라 패널 툴팁마다 라이브 표지를 달고 docs/measurements를 만들지 않는다.

**업무 방해(센서를 쏟을 때 업무 1건이 얼마나 느려지나)는 이 화면에 없다.** 강도 3종 실측에서 같은 강도도 실행마다 느린 쪽 값이 크게 달라 "누가 느린지" 판정할 수 없었다 — D-16 뒤 사용자 결정으로 계약 · api · 화면에서 함께 지웠다(정본 [../01_overview/06_design_decisions.md](../01_overview/06_design_decisions.md) D-16 상태 줄).

**목적**: "같은 센서 데이터를 Redis로 두 DB에 넣어 보면?" — 넣는 속도와 크기, 소량 · 대량 조회, 규칙 어긴 데이터 처리를 두 DB에 같은 조건으로 시켜 보고 차이를 숫자로 본다.

**진입**: 좌측 내비 직접 해 보기 섹션 "직접 비교 실험". 진입 파라미터 없음.

- **넣기가 주인공이다.** 맞춤 보기에서 넣기는 왼쪽 두 줄 높이(열 비 1 : 1.12 · 행 비 1.1 : 1)이고 조회 대결은 오른쪽 위 · 무결성은 오른쪽 아래다. 작은 화면은 ① → ② → ③으로 쌓이고 패널마다 최소 높이 64(16rem)를 지킨다.
- **패널 번호 ①②③은 순서다.** 조회 대결은 넣기가 끝까지 간 구간의 데이터로 재므로 넣기 전에 누르면 api가 막는다(409 datagen.compare_no_data — "비교할 데이터가 없어요 — 먼저 ① 넣기를 해 주세요"). 무결성은 자기 시험 창에 따로 싣고 지우므로 넣기 없이도 돈다.
- **와이어프레임의 N · ○는 자리 예시다** — 실제 값은 §데이터 원천이 가리키는 결과 필드에서 읽는다.
- **와이어프레임은 끝난 결과의 모습이고, 실행 중인 패널은 같은 자리 · 같은 크기에 진행 중 값을 그린다**(사용자 결정 2026-10-11). 값이 늘어도 패널이 커지거나 페이지가 스크롤되지 않는다 — 반응형 규칙(맞춤 보기 페이지 스크롤 0 · 작은 화면 쌓기 · 최소 높이)은 실행 중에도 그대로다([01_standards.md](./01_standards.md) §반응형 규칙). 패널별 실행 중 모습은 §요소의 ① ② ③ 행이 갖는다.

| 정상 | 패널마다 마지막 결과 · 잰 시각(KST) · 설비 가동 중 표지 · 툴팁의 커밋 · SW-09 · 라이브 표지 — 신선도 기준은 잰 시각이다(결과는 다음 같은 부분 실행 전까지 그대로) · **실행 중인 패널은 진행 중 값** — 신선도 기준은 1초 폴링의 마지막 응답이고 잰 시각 줄 대신 "지금 재는 중" · 넣기는 결론 줄 대신 "넣는 중이에요"(같음 ✓ · ✕ 없음) · 끝나면 completed는 그 실행의 최종 결과 · stopped · failed는 지난 보관 결과 + "마지막 시도는 중단됐어요" · "마지막 시도는 실패했어요"(§비고) |

### 스위치 영향

| 스위치 | 이 화면에서 보이는 것 |
|------|------|
| SW-09 off | 넣기 · 무결성 ▶가 400으로 거절된다(PostgreSQL 비교 사본에 실을 길이 없다) — 진행 띠 "동시 적재 스위치(SW-09)가 꺼져 있어요 …" · 지난 결과는 그대로 · 조회 대결은 쌓인 데이터가 있으면 돈다 |
| SW-09 on | 넣기 · 무결성은 돈다 — 단 게이트와 무관하게 늘 COPY하므로 설비 가동 · 흐름 시연 데이터도 PostgreSQL 비교 사본에 실려 원본 전체 행 수(머리 툴팁)가 비교 구간보다 커진다(머리 행 수는 구간 안이라 그대로) |
| SW-09 gated(기본) | 넣기 · 무결성 동안만 게이트 키가 켜져 같은 묶음이 PostgreSQL에도 들어간다 — 그 밖의 가동 데이터는 ClickHouse에만 |

- 검산: 행 = **3**(SW-09의 값 3) · 다른 스위치는 실행 결과의 switches(툴팁)에만 보인다
- **머리 행 수는 비교 구간 안의 행 수다.** ClickHouse 원본에는 설비 가동 · 흐름 시연 데이터도 들어 있어 전체 행 수로 견주면 CH가 늘 커 보인다 — 그래서 머리는 마지막 넣기 구간 안의 두 저장소 행 수만 보이고, 원본 전체는 툴팁에 둔다.
- **비교 실험(넣기 · 무결성)은 설비 가동이 꺼져 있어야 시작된다.** 켜져 있으면 시작 전 거절(④)이다 — 가동 데이터가 같은 Redis 대기줄 · 같은 저장소 부하로 섞여 넣기 시간 비교가 흐려진다. 조회 대결은 가동 중에도 돌고, 그 결과에는 "설비 가동 중에 잰 값" 표지가 붙는다.

### 비고

- 실행 하나 = 부분 하나다(params.part) — 넣기 → 조회 → 무결성을 한 번에 돌리는 묶음 실행은 없다.
- 넣기는 구간 창을 통째로 비우고 다시 넣는다(사흘 창 — 기전 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md)) — 1시간치를 넣으면 앞서 넣은 하루치 데이터는 남지 않는다.
- 리드 통합 실측(2026-10-11 · 노트북 Docker · 설비 가동 끔 · SW-09 gated · **TimescaleDB 전환(2026-10-12) 전 — 일반 PostgreSQL 비교 사본**)에서 넣기 묶음 하나의 중간값은 PostgreSQL(PK · FK · CHECK)이 ClickHouse보다 길었고 디스크는 PostgreSQL이 수십 배 컸다 — 지금 비교 사본(TimescaleDB · 압축 뒤 크기)의 관찰이 아니다. 화면 수치는 실행마다 다시 재는 관찰값이고 정본 문장은 이 값을 인용하지 않는다.
- **끝날 때 깜빡이지 않는다.** 실행이 completed로 끝났는데 부분별 최근(runs/latest)이 아직 이 실행을 모르면(다시 읽기 전) 실행 객체의 최종 result를 그대로 보인다 — 지난 결과가 한 번 끼었다가 새 결과로 바뀌지 않게 한다. stopped · failed는 지난 보관 결과 + "마지막 시도는 중단됐어요" · "마지막 시도는 실패했어요" 줄이다(§요소 잰 시각 줄).
- **A형 — "넣는 중에 CH와 PG 행 수가 다르다 · 디스크 막대가 끝나는 순간 바뀌었다"는 버그가 아니다.** 통념은 같은 배치를 두 DB에 넣으니 넣는 중에도 행 수가 같고, 마지막으로 본 막대가 곧 최종 크기라는 것이다. 부정 — 넣는 중 행 수는 각 DB에 배치가 끝난 만큼(Ingest 계측)이라 그 순간 서로 다르고, 넣는 중 크기는 병합(OPTIMIZE) · 압축 전 · 마지막 읽기 뒤에 들어온 조각이 빠진 순간값이라 최종값과 다를 수 있다(어느 쪽으로든). 진짜 축은 **끝났는가**다. 대체 경로 — 같음 ✓ · ✕ · 디스크 배수 · 결론은 끝난 결과로만 내고(verify가 ClickHouse 병합 · PostgreSQL 압축 뒤 다시 잰다), 넣는 중에는 "넣는 중이에요"와 막대 툴팁 "넣는 중 크기 — 2초마다 다시 재요 · 끝나면 ClickHouse는 조각을 합치고 PostgreSQL은 압축한 뒤 다시 재요"가 그 사실을 말한다(필드 뜻 [../07_api/09_datagen.md](../07_api/09_datagen.md) §진행 중 결과(compare)).
- **A형 — "중단했더니 방금 그리던 그래프가 사라지고 지난 결과가 돌아왔다"는 버그가 아니다.** 통념은 멈춘 지점까지 그린 값이 남아야 한다는 것이다. 부정 — 진행 중 값은 보관되지 않는다 — run_result는 completed일 때만 결과를 남기고 stopped · failed는 result null로 남긴다. 진짜 축은 **끝까지 갔는가**다 — 중단된 넣기는 사흘 창을 비우고 앞부분만 채워, 그때까지의 행 수 · 크기 · 묶음 시간은 고른 구간의 답이 아니다. 대체 경로 — ▶로 다시 잰다.

## 공용 컨트롤

⑤ · ⑥ · ⑦ 머리 오른쪽에 같은 컴포넌트로 놓이는 조작 둘이다(components/controls). 같은 쿼리 키(plant · power · data · sensor · stats)를 나눠 써서 한 화면에서 켜거나 지우면 다른 조각이 같은 값을 본다. 화면마다 놓이는 것은 ⑤ 데이터 지우기 · ⑥ ⑦ 설비 가동 스위치 + 데이터 지우기다.

- **지우는 동안은 새 데이터를 만드는 시작을 막는다.** 지우기가 도는 몇 초 동안 실행 시작(직접 비교 · 직접 보내 보기)과 설비 가동 켜기는 400(path purge)으로 거절되고, 반대로 설비 켜기가 진행 중이면 지우기가 plant_running으로 거절된다(api 프로세스 안 잠금 — api를 여럿 띄우면 서로 모른다).
- **지우는 것은 쌓인 센서 데이터뿐이다(D-16 사용자 결정).** ClickHouse 원본 · 요약(1분 · 1시간 · 1일) · PostgreSQL 비교 사본 · Redis 대기줄(소비 그룹은 유지) · 지금 값 · 조회 사본 — 설비 · 태그 · 업무 기록 · 직접 비교 결과(run_result)는 남는다. 지울 범위의 정본은 api이고 화면은 확인 창에서 그 범위를 말할 뿐이다(기전 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md)).
- **api를 다시 띄우면 설비 가동은 기동 기본값으로 돌아간다.** 수집기 역할이 기동 때 ctl:plant:power를 지우고 기동 기본값(SENSOR_AUTOGEN — 로컬 Compose off)부터 시작한다 — 재기동만으로 데이터가 저절로 쌓이지 않게 한 사용자 결정(2026-10-03)을 잇는다. 키를 읽지 못하는 동안(Redis 불가)은 지금 상태를 그대로 둔다(plant-runtime.service.ts).
- **낙관적 갱신을 하지 않는다.** 스위치는 응답을 받은 뒤에 켜짐 · 꺼짐을 바꾸고, 지우기는 결과를 받은 뒤에 현황을 다시 읽는다 — 409 · 503이 올 수 있는 쓰기를 먼저 반영하면 되돌릴 때 두 상태를 본다.
- **상태를 바꾸는 POST는 다른 출처에서 부를 수 없다.** BFF가 실행 시작 · 중단 · 설비 가동 · 지우기 POST의 Origin을 확인해 허용 출처(http://localhost:13001 · http://127.0.0.1:13001) 밖이면 403으로 막고(Origin이 없으면 같은 출처 요청으로 보고 통과 — apps/web/lib/bff.ts), 화면은 JSON 본문으로 부른다(설비 가동 {on} · 지우기 {} — api가 JSON 본문을 요구한다). 계약 · 위협의 정본은 [../12_security/03_api_surface_defense.md](../12_security/03_api_surface_defense.md)다. **같은 머신의 다른 프로세스가 api(13000)를 직접 부르는 것은 막지 못한다** — 무인증 표면의 기록된 잔여다(D-16).
