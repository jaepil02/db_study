이 문서는 화면 문서가 인용하는 **공통 규격의 정본**이다. **D-14(사용자 결정 2026-10-03) 뒤 웹에 남은 화면은 둘이다** — EXP-PERF(성능 비교 · /performance) · EXP-FLOW(분산 처리 모니터링 · /monitoring) · 명세 [08_evidence_screens.md](./08_evidence_screens.md). **D-15(사용자 지시 2026-10-03) 뒤 두 화면은 한 장이다** — 스크롤 · 서랍 · 탭 없이 의도와 결론이 한 눈에 읽혀야 한다(§한 화면 원칙). 화면 문서 03~07은 폐지 화면의 원문을 보존한 채 상태 단락만 더했고, 이 문서의 규칙 가운데 폐지 화면에만 쓰이던 자리(업무 쓰기 응답 · 무효화 신호 수신 표 · 시계열 차트 규칙)는 api 표면이 남으므로(D-14 결정 1) 계약을 지우지 않고 "현행 화면 적용 없음"으로 표시한다. 화면 코드와 소속 파일의 정본은 [README.md](./README.md) 화면 인벤토리이고, 이 문서는 그 코드들이 지켜야 할 명세 모양 · 상태 표시 · 시각 · 에러 · 캐시 규칙을 고정한다. 개별 화면이 표준과 다르게 처리하면 그 화면 블록의 비고에 사유를 적는다.

**화면은 데이터를 소유하지 않는다.** 모든 수치는 07_api 표면을 거쳐 오고, 화면 명세는 어느 표면을 어떤 빈도로 부르는지와 그 응답을 어느 캐시 층이 얼마 동안 들고 있는지를 고정한다. 표면은 **메서드 + 경로**로 인용한다. 원본에 없는 표면은 07_api 해당 파일의 확정을 기다리며 "07_api/{파일} 확정 대기"로 적는다.

**이 문서가 닫는 인계 1건** — 무효화 체인 ⑥단의 신호 키 → 브라우저 쿼리 키 대응([../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) 미확인 등재)을 §무효화 신호 수신에서 고정한다. staleTime의 라이브러리 설정값은 [../09_tech_stack/01_frontend.md](../09_tech_stack/01_frontend.md)가 갖고, 이 문서는 값이 따라야 할 관계식을 갖는다.

## 화면 명세 템플릿

화면 하나 = H2 하나다. H2 제목은 "{화면 코드} — {화면명}"이고 아래 필드를 이 순서로 둔다.

| 필드 | 내용 | 비워 두면 |
|------|------|------|
| 메타 표 | 화면 코드 · 웹 경로 · 페르소나 · 역할(S7 이후) · 도입 단계 · 요청 경로(BFF 경유 · 직결) | 화면이 어느 단계에 생기고 누가 쓰는지 몰라 S2~S6 무인증 구간의 화면이 권한 검사를 기대한다 |
| 목적 | 페르소나가 이 화면에서 답을 얻는 질문 한 문장 | 요소가 목적 없이 늘어난다 |
| 진입 | 진입 경로와 진입 파라미터(설비 · 태그 · 범위) | 딥링크가 어떤 상태로 열리는지 정해지지 않는다 |
| 레이아웃 | plain 펜스 와이어프레임 1개 | 요소 표의 위치 열이 가리킬 자리가 없다 |
| 요소 표 | 요소 · 위치 · 동작 · 기능 ID · 표면 | 기능 → 화면 추적([02_traceability.md](./02_traceability.md))의 근거가 끊긴다 |
| 상태 4행 | 로딩 · 빈 값 · 오류 · 정상 — §상태 4행 | 실패가 빈 화면으로 보여 결함과 설계 동작을 가를 수 없다 |
| 호출 표면 | 메서드 + 경로 · 호출 시점 · 경로 · 응답에서 쓰는 필드 | 화면이 표면에 없는 필드를 기대한다 |
| 갱신 주기 | 폴링 · WebSocket 프레임 · 수동 · 신호 무효화 중 무엇으로 새 값을 얻는가 | 화면이 스스로 낡는다 |
| 캐시 층 | 브라우저 쿼리 캐시 · BFF 서버 fetch 캐시 · Redis · Dictionary 중 응답이 지나는 층과 staleTime | 옛 값이 보일 때 어느 층의 창인지 가를 수 없다 |
| 스위치 영향 | 이 화면의 표시가 달라지는 SW-NN과 그때 보이는 것 | 실험 중 화면 변화가 버그로 신고된다 |
| 비고 | 표준과 다른 처리 · 확정 대기 자리 | 해당 없음 |

- 검산: 필드 = **11**
- **요소 표의 기능 ID 열이 추적성의 정본 자리다.** [02_traceability.md](./02_traceability.md)는 이 열을 모아 세며, 요소 표에 없는 기능을 화면에 매핑하지 않는다.
- 레이아웃 펜스는 plain 와이어프레임이다. 한 장에 들어가는지의 기준(1440 × 900 픽셀 예산)은 §한 화면 원칙이 갖고, 색 값 · 간격 토큰은 [../09_tech_stack/01_frontend.md](../09_tech_stack/01_frontend.md)의 구성 선택을 따른다.

화면 블록의 골격이다.

```plain
## {화면 코드} — {화면명}
├── 메타 표          코드 · 경로 · 페르소나 · 역할 · 단계 · 요청 경로
├── 목적 · 진입      한 문장 · 진입 파라미터
├── 레이아웃         plain 와이어프레임
├── 요소 표          요소 · 위치 · 동작 · 기능 ID · 표면
├── 상태 4행         로딩 · 빈 값 · 오류 · 정상
├── 호출 표면        메서드 + 경로 · 시점 · 경로 · 쓰는 필드
├── 갱신 · 캐시      주기 · 층 · staleTime 관계
└── 스위치 영향      SW-NN별 표시 변화          ← 없으면 "해당 없음" 행 하나
```

- **요소 표와 호출 표면 표는 같은 표면을 두 방향에서 본다.** 요소 표는 사람이 누르는 것에서, 호출 표면 표는 네트워크에서 출발한다 — 한쪽에만 있는 표면은 화면이 부르지 않는 표면이거나 버튼 없는 호출이다.
- **화면 안의 하위 영역은 H3로 나누지 않고 요소 표의 위치 열로 가른다** — H3는 명세 필드 묶음(요소 · 상태 4행 · 호출 표면 등)에만 쓴다. 화면 코드로 시작하는 H2 하나에 화면 하나가 대응해야 [02_traceability.md](./02_traceability.md)의 화면 수 검산이 문서 구조로 확인된다.

## 상태 4행

모든 화면 블록은 아래 4행을 갖는다. 행을 빼거나 합치지 않는다 — 해당 없는 행은 "해당 없음"과 그 이유를 적는다.

| 상태 | 반드시 적을 것 | 금지 |
|------|------|------|
| 로딩 | 첫 페인트에 무엇이 먼저 보이는가 · 스켈레톤 영역 · 이전 값 유지 여부 | 표 전체를 스피너 하나로 가리기 — 부분 응답(최신값은 왔고 트렌드는 안 온 상태)을 볼 수 없게 된다 |
| 빈 값 | **빈 사실의 종류를 가른다** — 조건 결과 0 · 측정값 아직 없음(200 빈 목록) · 기능 미도입 단계 | "데이터 없음" 한 문구로 셋을 묶기 — 신규 설비의 빈 목록이 장애로 읽힌다 |
| 오류 | 받는 에러 코드 목록 · 코드별 표시는 §에러 코드별 사용자 표시를 인용 · 오류 중 기존 값의 처리 | 코드 없는 일반 오류 문구 · 오류 중 기존 값을 지워 빈 화면 만들기 |
| 정상 | 값이 무엇을 기준으로 신선한가(ts · 캐시 여부 · 해상도) · 사용자가 판단할 표지 | 신선도 표지 없이 값만 표시 — STALE · 다운샘플 · 캐시 히트가 정상 응답 안에 섞여 있다 |

- 검산: 상태 = **4**
- **200 응답 안의 경고를 오류 행이 아니라 정상 행에 적는다.** STALE 품질 · meta.downsampled · meta.cached · 비운 메타는 에러가 아니라 보정이다([../11_glossary/02_error_codes.md](../11_glossary/02_error_codes.md) §에러 코드가 아닌 것). 오류 행에 두면 화면이 보정을 실패로 그려 운영자가 정상 값을 의심한다.
- 권한 거부(403)는 오류 행 안에 적는다. 인증 부재(401)는 화면이 아니라 공통 셸이 처리한다 — §에러 코드별 사용자 표시.

## 한 화면 원칙

두 화면이 지키는 표현 원칙이다(D-15 — 사용자 지시 2026-10-03 · 학습자 눈높이 · 한 화면 · 설계 정본 .omc/plans/web-junior-redesign.md §1). 사용자는 1년차 학습자이고 "스크롤이나 접기 · 펼치기 없이 구현 의도와 내용이 한 눈에" 들어와야 한다. D-14 설계의 정보 4층(결론 띠 · 주 차트 · 원리 · 접힘 서랍)은 정보를 지우지 않고 서랍으로 내렸지만, 학습자에게는 서랍을 여는 일 · 코드표 · 지수 표기가 이해를 막았다 — 그래서 **세부는 화면에서 빼고, 정확성 계약만 각주와 툴팁으로 남긴다.** 요소별 배정은 각 화면 블록의 요소 표가 갖는다([08_evidence_screens.md](./08_evidence_screens.md)).

| # | 원칙 | 규칙 | 어기면 |
|:--:|------|------|------|
| 1 | 한 화면 = 한 장 | 1440 × 900 브라우저(본문 약 1192 × 844)에서 **세로 · 가로 스크롤 0 · 서랍 0 · 아코디언 0 · 탭 0** · 툴팁(ⓘ · 마우스 올림)은 보조 — 툴팁을 안 봐도 결론이 서야 한다 | 결론과 근거가 다른 스크롤 위치에 있어 둘을 대조할 수 없고, 접힌 자리는 학습자가 열지 않는다 |
| 2 | 의도 먼저 | 본문 맨 위에 질문형 제목 + 설명 한 줄 — "이 화면은 무엇을 보여 주나" | 그림부터 보이면 무엇을 비교하는 화면인지 알기 전에 숫자를 읽는다 |
| 3 | 결론 먼저 · 근거는 그림 하나 | 구역마다 굵은 결론 문장 → 그림 1개 → "왜?" 한두 줄 순서 | 답을 얻으려고 차트를 해석해야 해 첫 화면에서 결론을 놓친다 |
| 4 | 쉬운 말 · 용어는 괄호 | 우리말 먼저, 전문 용어는 뒤 괄호(작게) — 아래 용어표 | 코드표를 외운 사람만 화면을 읽는다 |
| 5 | 숫자는 적게 · 크게 · 읽히게 | "10억 행" · "40배 느림" · "0.1밀리초" — 지수 · 분위수 · 기록 번호 · 3회 값 · 소수 셋째 자리를 화면에 쓰지 않는다(툴팁은 허용) | 숫자의 단위를 한 번 더 셈해야 해 결론보다 표기가 먼저 읽힌다 |
| 6 | 색 3개 고정 | ClickHouse 주황 · PostgreSQL 파랑 · Redis 빨강 — 이긴 쪽 표시도 이 색 · 값 정본 §차트 표준 저장소 색 | 화면마다 색이 다르면 같은 저장소가 다른 것으로 읽힌다 |

- 검산: 원칙 = **6**
- **각주 · 툴팁으로 옮긴 계약은 계약 수에서 빠지지 않는다.** 지어낸 값 금지 · 승패는 3회 모두 같을 때만 · 시간은 참고값이라는 표기 · 4요소(커밋 해시 · 메모리 프로파일 · 용량 티어 · 스위치 상태) · 판독 계수는 [08_evidence_screens.md](./08_evidence_screens.md)의 표시 계약 표에 그대로 있고 표시 자리만 각주 한 줄과 각주 툴팁이다. 화면에서 뺀 요소(배수 지도 · 3회 값 · 원리 증거 · 분배 표 · 최근 목록 · 실행 단계 등)는 그 표시 계약도 함께 지웠다 — 기록 · 판독기 · api 표면은 남는다.
- **원칙 1의 예외는 작은 화면 하나다.** 1280 × 720 같은 작은 노트북은 콘텐츠 본문 스크롤을 허용한다(최소 대응) — 목표 해상도에서 스크롤이 생기면 결함이고, 작은 화면의 스크롤은 결함이 아니다.

화면 문구의 정본 용어표다. 왼쪽 열은 화면 1층(툴팁 밖)에 쓰지 않는다 — 문서 · 코드 · 툴팁은 왼쪽 열을 그대로 쓴다.

| 쓰지 않는다 | 쓴다 |
|------|------|
| 10^9 · 10^7.5 | 10억 행 · 약 3천만 행 |
| p50 · 중앙값 | 보통(중간값) — "중간값"은 각주에서만 |
| Q1~Q5 · I1 · I2 · EXP-NN · SW-NN · 기록 053 | 질문 이름("센서 1개 · 7일") · "PG(목차 있음)" — 코드는 툴팁에만 |
| 웜 · 콜드 | 쓰지 않는다(웜 기준 — 각주) |
| 구조 판정 · 참고값 · discarded · valid | "3번 모두 같은 결과" · "시간은 참고용" |
| 랙 · lag · 백프레셔 | 밀린 데이터 · 처리가 밀리는 중 |
| 배치 · flusher · XADD · XACK | 모아서 한 번에 저장(배치) |
| stream:plc:raw · stream:biz:cmd | 센서 대기줄(Stream) · 업무 대기줄 |
| 원자성 · 트랜잭션 | 전부 되거나 전부 안 되거나(트랜잭션) |
| 그래뉼 · B-tree · BRIN · MVCC · WAL · 파트 머지 | 화면 1층에 쓰지 않는다 — "왜?" 문장은 쉬운 비유로(목차 · 묶음 · 조각) |

- 검산: 용어 행 = **10**
- **용어표는 문구의 정본이지 사실의 정본이 아니다.** 쉬운 말로 옮겨도 사실은 정본 문서(05_data_stores/10 · 06_pipeline)의 것을 바꾸지 않는다 — 비유가 사실과 어긋나면 비유를 고친다.

1440 × 900의 픽셀 예산이다(셸 머리 56 · 좌측 내비 248 → 본문 약 1192 × 844 · 안쪽 여백 20).

| 화면 | 세로 배분(위에서 아래) | 진행 띠가 생기면 |
|------|------|------|
| EXP-PERF | 제목 · 설명 52 · 두 열(각 폭 약 566) 높이 약 680 · 한 줄 정리 + 각주 56 | 띠 32 — 그림 2 높이를 줄여 흡수 |
| EXP-FLOW | 제목 · 설명 52 · 숫자 4 84 · 흐름도 약 430 · 아래 줄(카드 3 · 모아서 대 하나씩) 약 170 · 각주 24 | 띠 32 — 남는 높이 안 |

- 검산: 화면 = **2** · 세로 합 EXP-PERF 52 + 680 + 56 = 788 · EXP-FLOW 52 + 84 + 430 + 170 + 24 = 760 + 띠 32 = 792 — 둘 다 본문 844 − 여백 40 = **804** 이하
- **예산은 설계값이다 — 측정값이 아니다.** 실제 높이는 구현이 정하고, 판정은 1440 × 900에서 본문 스크롤 요소의 scrollHeight ≤ clientHeight + 1(e2e)로 한다.

## 단계별 화면 가용성

화면은 학습 단계(정본 [../01_overview/05_priorities_roadmap.md](../01_overview/05_priorities_roadmap.md))에 따라 열린다. **S7 이전에는 인증이 없어 역할 열이 적용되지 않는다**(REQ-AUT-16).

| 단계 | 열리는 화면 | 인증 · 역할 | 화면이 전제하는 것 |
|------|------|------|------|
| S2~S4 | 현행 화면 없음 — 이 단계에 열리던 화면(DSH-REALTIME · EXP-CONSOLE · ANL-TREND · ADM-MASTER · EXP-COMPARE)은 D-14로 폐지 | 없음 | 해당 없음 — 표면은 api에 남는다(D-14 결정 1) |
| S5 · S6 | EXP-PERF · EXP-FLOW | 없음 | 격자 기록(048~053) · 역방향 기록(040~047)과 flow 프레임 발행이 두 화면의 전제 |
| S7 | 화면 추가 없음 — 이 단계에 열리던 화면(AUTH-LOGIN · ALM-CONSOLE · ALM-RULES · ADM-WORKORDER · ADM-AUDIT)은 D-14로 폐지 | 있음 — 역할 판정 적용 | 두 화면의 실행 조작부 시작 · 중단에 역할 판정(ENGINEER · ADMIN) · 로그인 자리는 §미확인 · 확정 대기 등재 |

- 검산: 현행 화면 = S5 2 = **2** — [README.md](./README.md) 화면 인벤토리와 같다
- **S2~S6의 화면에 권한 거부 행이 없는 것은 결함이 아니다.** 인증을 늦게 넣은 것은 학습 순서의 결과이며(D-07) 그 구간의 표면은 127.0.0.1 바인드 안에 있다. S7에서 역할 판정이 붙으면 같은 화면의 오류 행에 403이 더해진다.
- **S7 전후의 화면 체감 지연은 같은 스위치 상태라도 다른 조건이다.** 인증 · 인가 비용이 요청 경로에 더해진다 — 화면 관찰로 얻은 인상을 S7 전 측정 기록과 비교하지 않는다.

## 요청 경로와 공통 셸

같은 웹 화면이라도 요청 성격에 따라 경로가 둘로 갈린다. 기준의 정본은 [../07_api/01_conventions.md](../07_api/01_conventions.md)이고 이 표는 화면별 적용이다.

| 요청 | 경로 | 이 문서군의 화면 | BFF 서버 fetch 캐시 |
|------|------|------|------|
| 로그인 · 토큰 갱신 · 로그아웃 | 브라우저 → BFF → api | 공통 셸(S7 — 토큰 갱신만 · 로그인 · 로그아웃은 화면 없음(API 전용) — 로그인 화면은 D-14 폐지 · 셸에 사용자 메뉴 없음 · 리드 판정 2026-10-03) | 없음 |
| 사이트 · 라인 · 설비 · 태그 목록과 마스터 쓰기 | 브라우저 → BFF → api | 현행 화면 없음(폐지 전 ADM-MASTER · 설비 선택기) | 있음 — 쓰기 성공 시 체인 ⑤ |
| 작업지시 · 실적 · 알람 규칙 · 알람 이벤트 · 감사 · 명령 조회 · 라이브 실행(시작 · 현재 · 단건 · 중단) | 브라우저 → BFF → api | EXP-PERF · EXP-FLOW(실행 조작부 — 라이브 실행만 · 나머지는 현행 화면 없음) | **no-store** |
| 최신값 | 브라우저 → api 직결 | 현행 화면 없음(폐지 전 DSH-REALTIME) | 해당 없음 |
| 시계열 조회 · 내보내기 · 판정 이력 분석 | 브라우저 → api 직결 | 현행 화면 없음(폐지 전 ANL-TREND · DSH-REALTIME · ALM-RULES) | 해당 없음 |

| health · metrics(화면) | 브라우저 → BFF → api · 메트릭 텍스트 해석은 BFF가 한다 | EXP-PERF · EXP-FLOW(health — 각주 툴팁) · EXP-FLOW(metrics 5초) | 없음 |
| 측정 기록 읽기 | 브라우저 → BFF · BFF가 docs/measurements를 읽기 전용으로 읽는다 — api 표면 없음 | EXP-PERF(성능 보기 · 업무 보기) | 없음 — no-store(기록은 커밋으로만 바뀐다) |

- 검산: 요청 유형 = **8** · BFF 경유 5 + 직결 3 · 현행 화면 · 셸이 쓰는 유형 = 로그인 계열(셸) · no-store(라이브 실행) · WebSocket · health · metrics · 측정 기록 읽기 = **5** · 나머지 3은 표면이 api에 남고 웹 화면이 없다(D-14 결정 1)
- **알람 이벤트 · 확인 · 규칙은 BFF no-store다**(배정 정본 [../07_api/01_conventions.md](../07_api/01_conventions.md) §BFF 경유와 직결). 확인 직후 목록이 BFF 캐시의 옛 목록이면 확인한 알람이 미확인으로 남아 운영자가 두 번 누른다 — 작업지시 no-store와 같은 read-your-writes 요구다. D-14 뒤 이 경로를 부르는 웹 화면은 없고 배정은 BFF 라우트를 다시 둘 때의 계약으로 남는다.
- **health · metrics는 기계 호출에는 공개 직결이지만 화면은 BFF로 읽는다.** 브라우저가 Prometheus 텍스트 전체를 받아 파싱하지 않게 BFF가 해석한 결과만 내린다 — 같은 표면을 두 경로로 부르는 것은 호출 주체가 다르기 때문이다.
- **키셋 커서 목록은 "더 보기"로 이어 읽고 전체 건수를 표시하지 않는다.** 대상 표면(알람 이벤트 · 작업지시 · 실적 · 감사)은 전체 건수를 내지 않는다 — count가 범위 안 월 파티션 전부를 훑기 때문이다(07_api/01 §페이지네이션). 화면이 건수를 보이려고 전부 이어 읽으면 같은 비용을 브라우저가 대신 일으킨다.
- 판정 이력 분석은 alarm_eval 대량 스캔이라 시계열 조회와 같은 직결 경로에 둔다 — 응답이 크고 사용자별이라 BFF 중계 · 캐시 이득이 없다(원본 data_flow.md §7.2의 시계열 조회 근거).

공통 셸은 화면 코드가 아니다 — 모든 화면을 감싸는 레이아웃(좌측 내비 · 콘텐츠 머리)이며 기능 매핑에서 "공통"으로 센다([02_traceability.md](./02_traceability.md)). D-14 뒤 셸이 감싸는 화면은 둘이고 / 는 /performance로 보낸다.

```plain
┌──────────────────────────┬──────────────────────────────────────────────────────────┐
│ [DB] db_study        [⇤] │ 성능 비교                                     [머리 동작 자리] │ ← 콘텐츠 머리(고정 · 56px)
├──────────────────────────┼──────────────────────────────────────────────────────────┤
│ ⇲ 성능 비교              │ 진행 띠(실행이 있을 때만 · 머리 아래 한 줄)                 │
│ ⇄ 분산 처리 모니터링     │                                                          │
│ ──────────────────────── │   콘텐츠 본문 — 한 장(1440 × 900 스크롤 없음 · 작은 화면만 스크롤) │
│ 스택 표기                 │                                                          │
└──────────────────────────┴──────────────────────────────────────────────────────────┘
  좌측 내비 — 항목 2(섹션 없음 · 평평한 목록 · 전 행 같은 글자 · 34px · 아이콘) · 현재 화면은 경로의 가장 긴 접두 · [⇤] 접기 → 레일(56px · 아이콘 · 현재 항목 좌측 표지 · 접힘은 이 브라우저에 저장)
  콘텐츠 머리    — 화면명(h1) · 머리 동작 자리 · /monitoring에서만 흐름 구독 표지(EXP-FLOW 요소 — 셸 WS 표지 아님)
  머리 동작 자리 — 화면이 넘긴 조작을 머리 오른쪽에 그린다(두 화면 — 머리 버튼 · 상태 칩 · 08_evidence_screens §실행 패널 — 두 화면 공통 규칙 배치)
```

- **스크롤이 생긴다면 콘텐츠 본문 하나만 갖는다.** 페이지 전체(body)는 화면 높이에 고정하고 좌측 내비와 콘텐츠 머리는 움직이지 않는다(사용자 요구 2026-09-27 · 레이아웃 결정은 D-14 · D-15 뒤에도 유지). D-15 뒤 1440 × 900에서는 본문도 스크롤하지 않는다(§한 화면 원칙 원칙 1) — 이 규칙은 작은 화면에서 본문만 스크롤해 현재 위치 · 실행 상태 칩 · 연결 표지가 늘 보이게 하는 자리로 남는다.
- **셸 머리의 실험 조건 배지 · "기본 구성" 팝오버는 없다(D-14 결정 2).** 스위치 상태는 두 화면의 각주 툴팁이 보인다(D-15 — 측정 조건 서랍 폐지 · [08_evidence_screens.md](./08_evidence_screens.md)). 머리에서 지운 이유는 두 화면 모두 결론과 무관한 상시 표지가 머리를 먹던 배치였기 때문이다.
- **셸 머리에 WS 표지를 두지 않는다(리드 판정 2026-10-03).** 연결 상태는 EXP-FLOW 머리의 흐름 구독 표지 하나가 3상태(구독 중 · 재연결 중(다음 시도까지 초) · 끊김 — 4403 출처 거절 사유 포함)로 겸한다([08_evidence_screens.md](./08_evidence_screens.md) EXP-FLOW §요소). 셸 표지를 함께 두면 /monitoring 머리가 "구독 중"과 "연결"로 같은 사실을 두 번 말하고, /performance는 WebSocket을 쓰지 않으므로 셸 표지의 끊김이 성능 비교 화면의 고장으로 읽힌다.
- **화면 이름은 콘텐츠 머리의 h1 하나다.** 본문 첫 줄의 의도(질문형 제목 + 설명 한 줄 — §한 화면 원칙 원칙 2)는 화면 이름을 되풀이하지 않는 h2 · 문단이다 — 한 문서에 h1이 둘이면 보조 기술이 화면 이름을 두 번 읽고, 의도 줄이 화면 이름을 되풀이하면 같은 말이 두 줄을 먹는다.
- **한계 — 뒤로 가기의 스크롤 복원이 없다.** 브라우저의 스크롤 복원은 문서(window) 기준이라 콘텐츠 본문이 스크롤을 가지면 긴 목록에서 상세로 갔다가 돌아올 때 위치가 처음으로 간다. 필요해지면 경로별 본문 scrollTop을 세션에 저장해 되돌린다(미구현).

- **기본값과 다른 스위치는 각주 툴팁이 health 한 번으로 강조한다.** 이 시스템에서 "느리다"의 대부분은 스위치 하나로 설명된다([../01_overview/03_personas_roles.md](../01_overview/03_personas_roles.md)) — 그래서 셸 배지를 지우면서 그 일을 두 화면의 각주 툴팁으로 옮겼다(D-14 서랍 → D-15 각주). 구현 선택 스위치(SW-11 · SW-12)는 기본값(ingest · stream)과 다른 구현이 주입되면 강조한다 — SW-12 direct면 툴팁에 "업무 쓰기 옛 경로 — 202 · 명령 멱등 없음"을 붙인다. 툴팁은 health switches 전수를 싣으므로 스위치가 늘어도 모양은 그대로다.
- **WebSocket 연결은 셸이 하나만 연다.** 화면마다 연결을 열면 탭 하나가 연결 여럿을 가져 연결 수 메트릭이 사용자 수가 아니라 화면 전환 수를 센다. 구독 목록만 화면이 subscribe · unsubscribe 메시지로 바꾼다 — URL 쿼리 구독은 4400으로 닫힌다([../07_api/11_websocket.md](../07_api/11_websocket.md) §구독 방식 판정).

공통 셸의 요소 표다. 횡단 기능은 특정 화면이 아니라 셸이 받으므로 [02_traceability.md](./02_traceability.md)는 이 표를 "공통 셸" 행으로 센다.

- **공통 셸 요소는 화면 코드를 받지 않는다.** 셸에 코드를 주면 화면 수가 셸 하나 때문에 늘고, 셸이 없는 화면(없다)과 있는 화면을 가르는 뜻 없는 축이 생긴다 — 셸은 모든 화면을 감싸는 틀이므로 화면이 아니라 레이아웃이다.

| 실시간 링 버퍼 | WebSocket 프레임은 태그별 고정 길이 링 버퍼(Zustand 스토어)에 쌓고 uPlot에는 버퍼 참조를 넘긴다 · 버퍼 창 길이는 2계층(계약 이 문서 · 현행값 3,000슬롯 — [../09_tech_stack/01_frontend.md](../09_tech_stack/01_frontend.md) W6 판정 · S2 고정) | 프레임마다 배열을 새로 만들면 초당 10프레임에서 GC가 트렌드를 끊는다 |

- **B형 — 차트가 점을 덜 그리는 것은 결함이 아니라 서버 보호의 결과다.** 결론 — 긴 범위는 서버가 해상도를 올리고 LTTB로 줄여 보낸다. 반대 시나리오 — 브라우저가 원시를 받아 스스로 줄이면 1년 범위 요청이 ClickHouse 원시 스캔을 일으켜 적재까지 멈춘다(원본 data_flow.md §6.1). 파생 지침 — 원시가 꼭 필요하면 차트가 아니라 내보내기 표면(07_api/05)으로 간다.

## 시각 표시

정본은 [../11_glossary/05_units_and_time.md](../11_glossary/05_units_and_time.md) §표시 시간대다. 화면 쪽 적용만 적는다.

| 자리 | 규칙 | 금지 | 근거 |
|------|------|------|------|
| 표시 | 모든 시각을 **Asia/Seoul로 표시**한다 · 변환은 렌더 직전 한 번만 | 서버 KST 문자열에 브라우저 로컬 시간대를 다시 적용 — 9시간이 두 번 더해진다 | AC-04 |
| 표시 형식 | 날짜 · 시각 · 초까지 · 실험 화면(EXP)과 최신값 ts 툴팁은 밀리초까지(예외 — EXP-PERF · EXP-FLOW 실행 패널의 시작 · 종료 시각은 초까지 · 실행 단위가 초 이상이라 밀리초가 소음) · 시간대 표기 KST를 붙인다 | 시간대 표기 없는 시각 — 수동 조회(psql · clickhouse-client)의 기본 출력이 UTC(ADR-27)라 KST 표기가 없으면 9시간 차를 기준 없이 본다 | 원본 data_flow.md §17 "저장 시각과 UI 표시 시각 대조" |
| 입력 | 범위 입력은 KST로 받고 요청에는 **오프셋 포함 ISO 8601**(+09:00)로 보낸다 | 오프셋 없는 ISO 8601 — 서버가 400 common.validation_failed로 거절한다 | REQ-TSQ-02 |
| 응답 해석 | 측정 시각(ts · points 첫 열 · WS 값)은 **epoch ms 정수**, 업무 시각(At으로 끝나는 필드)은 **UTC ISO 8601(Z)**로 받는다 — 둘 다 Asia/Seoul로 한 번 변환해 그린다 | UTC 문자열을 KST로 착각해 변환 생략 · epoch를 초로 해석 | [../07_api/01_conventions.md](../07_api/01_conventions.md) §시각 직렬화 |
| 두 시각 | ts는 "측정 시각", ingested_at은 "적재 시각"으로 라벨을 가른다 · 최신값 화면의 신선도 기준은 ts다 | ingested_at을 "갱신 시각"으로 표시 — 백프레셔로 늦게 적재된 값이 방금 갱신된 것처럼 보인다 | REQ-RLT-03 |
| 달력 경계 | 1d 해상도 버킷의 하루는 KST 자정에 시작한다 · 축 눈금도 KST 자정 | UTC 자정 눈금 — 일별 막대가 오전 9시에 끊긴다 | [../05_data_stores/04_clickhouse_rollup.md](../05_data_stores/04_clickhouse_rollup.md) · [../11_glossary/05_units_and_time.md](../11_glossary/05_units_and_time.md) §달력 의미 경계 — 닫힌 목록 #3 · 1d 스냅은 DB가 UTC여도 KST 자정을 유지한다(ADR-27) |
| 경과 시간 | 시각이 아니라 길이라 시간대 변환이 없다 · 서버가 계산한 elapsedMs를 기준으로 두고 진행 중에만 그 뒤 흐른 길이를 더한다 · 종결이면 endedAt − startedAt · 형식 "3분 12.4초" | 브라우저 현재 시각에서 startedAt을 빼기 — 두 시계 차이가 경과에 섞인다 | [08_evidence_screens.md](./08_evidence_screens.md) §실행 패널 — 두 화면 공통 규칙 |

- 검산: 자리 = **7**
- **A형 — "화면 시각이 9시간 어긋났다"는 대개 저장 문제가 아니다.** 통념은 저장값이 틀렸다는 것이다. 부정 — 저장은 epoch이고 시간대 인자는 표시 · 파싱 · 달력 함수만 바꾼다. 진짜 축은 변환이 몇 번 일어났는가다. 대체 경로 — 같은 행을 epoch 밀리초로 보이는 툴팁과 수동 조회의 toUnixTimestamp64Milli 결과를 대조한다. 수동 조회는 UTC로 출력된다(ADR-27) — toTimeZone(ts, 'Asia/Seoul') 또는 epoch로 대조한다.
- **DB 처리 시간대 UTC(ADR-27) 뒤에도 화면 규칙은 불변이다** — API가 이미 UTC(epoch ms · Z)로 내리고 화면이 KST로 한 번 바꾼다.

## 업무 쓰기 응답 — 명령 경로

업무 쓰기는 api가 검증한 뒤 명령 스트림(stream:biz:cmd)에 싣고 워커가 PostgreSQL 트랜잭션으로 적용하며, api는 **커밋 결과를 받은 뒤에만** 응답한다(사용자 결정 2026-09-27 · 기전 정본 [../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) §업무 명령 경로). 결과가 대기 상한(현행 참고 5초) 안에 오면 화면이 받는 응답은 옛 경로와 같다. 달라지는 것은 아래 셋이고, 대상 화면은 업무 쓰기를 하는 화면 전부다. **D-14 뒤 현행 화면 적용 없음** — 업무 쓰기 화면(ADM-MASTER · ALM-RULES · ALM-CONSOLE(확인) · ADM-WORKORDER(S7 ②))이 모두 폐지됐고, EXP-FLOW의 flow 실행이 싣는 업무 명령은 api 안(BizWritePort)에서 들어가 화면이 이 응답을 받지 않는다. 표면은 api에 남으므로(D-14 결정 1) 계약은 그대로 둔다 — 웹이 업무 쓰기 화면을 다시 두면 이 절을 따른다.

| 응답 | 화면 표시 | 다음 동작 | 금지 |
|------|------|------|------|
| 대기 상한 안 결과(201 · 200 · 400 · 404 · 409 등) | 옛 경로와 같다 — 성공은 로컬 무효화 · 재조회 · 오류는 §에러 코드별 사용자 표시 | 해당 없음 | 해당 없음 |
| **202 + {cmdId, status: 'pending'}**(응답 헤더 Idempotency-Key가 같은 명령 ID) | 저장 버튼 자리에 "적용 대기 — 명령 접수됨" · 폼 입력 유지 · **폼 잠금**(같은 폼 재제출 막음) | 명령 조회 GET /api/v1/commands/{cmdId}([../07_api/01_conventions.md](../07_api/01_conventions.md) 명령 조회 표면 #1 · BFF 경유 no-store)를 1 · 2 · 4초 … 최대 30초 백오프로 부른다 — status applied → 결과의 httpStatus · result로 기존 성공 처리 · rejected → error.code로 기존 오류 처리 · failed → common.postgres_unavailable/503 처리(같은 키로 다시 보내기) · expired → "적용되지 않았다 — 유효 창 초과"(다시 보낼지는 사용자가 정하고 보내면 새 키) · pending이 명령 유효 창(현행 참고 300초)을 넘으면 "오래 대기 — 같은 명령으로 다시 보내기"(같은 키) · 조회 404는 "이 명령을 볼 수 없다"(행위자가 다름) · 결말이 나면 폼 잠금 해제 | 202를 성공으로 그려 성공 안내 · 로컬 무효화 · 새 키로 재제출(워커가 두 번 적용한다) |
| **업무 쓰기 요청의 common.postgres_unavailable/503**(Redis 불가로 명령을 싣지 못함 · PostgreSQL 불가 — 07_api/01은 두 원인에 한 코드를 쓴다) | 폼 영역 띠 "업무 쓰기 저장소 응답 불가 — 조회는 된다 · 같은 키로 다시 보내면 안전"(Redis 불가 · PostgreSQL 불가 두 원인에 맞는 문구) · 목록 · 상세 유지 · 폼 입력 유지 · 조회까지 실패하면 조회 영역은 자기 503 띠("업무 저장소 응답 불가")를 따로 보인다 | 백오프 뒤 재시도 버튼 — 같은 키로 보낸다(적용되지 않았으므로 이중 쓰기가 아니다) | 목록 · 상세 숨기기(Redis 불가만이면 읽기는 PostgreSQL 직행이라 살아 있다) · 코드 이름으로 원인을 짐작해 다른 대응을 두기 — 대응이 같다 |
| 같은 키 재시도 | 화면이 폼 제출마다 UUID를 만들어 요청 헤더 **Idempotency-Key**에 싣고, 결말(applied · rejected · expired)이 날 때까지 그 키를 쓴다 · 네트워크 실패로 응답을 못 받은 제출 · 503 뒤 재시도 · 오래 대기 재전송이 모두 같은 키다 · 입력을 고쳐 다시 저장하면 새 키 | 첫 판정(applied · rejected)의 응답을 그대로 받는다 | 재시도마다 키를 새로 만든다 · 키 없이 보내 api 발급 키에 기대기(응답을 못 받으면 키를 모른다) |
- 검산: 응답 = **4**
- **B형 — 202는 실패가 아니다.** 결론 — 명령은 스트림에 있고 워커가 적용하면 결과가 원장에 남는다. 반대 시나리오 — 202를 오류로 그리면 사용자가 다시 저장해 새 명령이 생기고, 워커가 멈췄다 돌아오면 두 명령이 차례로 적용돼 태그가 둘 생기거나 409가 뒤늦게 난다. 파생 지침 — 폼을 잠그고 명령 조회로만 결말을 본다.
- **명령 조회로 적용을 확인한 뒤의 재조회는 BFF 사본을 건너뛴다.** 202에는 BFF 체인 ⑤가 걸리지 않으므로(07_business_crud) 화면은 로컬 무효화에 더해 신선 창 표지(x-bff-fresh)를 달아 목록을 다시 읽는다 — 표지 없이 읽으면 revalidate 창(현행 참고 30초)만큼 옛 목록을 보고 "적용됐다면서 안 바뀌었다"로 신고된다.
- **SW-12 direct에서는 202 · 명령 조회 · Redis 불가로 인한 쓰기 503이 없다** — 옛 경로(api 직접 커밋)라 Redis 불가 중에도 쓰기가 된다. Idempotency-Key는 형식 검사만 하고 되싣지 않으며 같은 키 재요청을 막지 못한다. 화면은 같은 코드로 두 경로를 받는다 — 202가 오지 않을 뿐이다.
- 낙관적 갱신 금지(§에러 코드별 사용자 표시)는 그대로다 — 명령 경로에서는 응답 전 반영이 202 대기 동안 더 오래 거짓으로 남는다.

- **gcTime은 시계열 쿼리만 짧게 둔다.** 시계열 응답은 수백 KB이고 사용자별이라 화면을 떠난 뒤 오래 들고 있으면 탭 메모리가 범위 조회 횟수에 비례해 는다 — 현행값 60초 · 소유 [../09_tech_stack/01_frontend.md](../09_tech_stack/01_frontend.md).
- **작업지시 · 실적의 다른 사용자 화면은 cache:workorders TTL만큼 늦는 것을 허용한다.** 체인 ③ · ⑥을 걸지 않는 판정([../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md))의 화면 쪽 결과이며, 쓴 사람의 화면은 자기 쓰기 성공으로 즉시 무효화한다.
- 쿼리 키 표기의 가운뎃점은 키 배열의 원소 구분이다 — 구현에서는 배열 원소가 된다.

## 무효화 신호 수신 — 체인 ⑥단

마스터 쓰기 뒤 ch:cacheinv로 발행된 **무효화된 키 이름**을 RLT-09가 WebSocket으로 중계하고, 공통 셸이 받아 아래 쿼리 키를 무효화한다. **D-14 뒤 현행 화면 적용 없음** — 아래 표의 영향 화면이 모두 폐지돼 셸이 신호를 받지 않는다(§요청 경로와 공통 셸 — RLT-09는 화면 없음(API 전용)). 중계 표면은 api에 남으므로 계약은 그대로 둔다. 단 번호의 정본은 [../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) 무효화 체인 6단이다. 신호는 cacheinv 메시지(keys — 무효화된 키 이름 배열 · 접두 포함)로 오고 스로틀 병합 대상이 아니다([../07_api/11_websocket.md](../07_api/11_websocket.md)).

| 신호 키(ch:cacheinv) | 무효화할 쿼리 키 | 영향 화면 | 무효화하지 않는 것과 이유 |
|------|------|------|------|
| cache:tagmeta:{tag_id} | master · tags(목록 전부) · master · tag · {tag_id} · 그 태그를 가진 realtime · device · {device_id} · alarm · rules | ADM-MASTER · DSH-REALTIME · ALM-RULES | timeseries 쿼리 — cache:q 결과는 체인 대상이 아니라 재조회해도 서버가 옛 이름을 TTL만큼 낸다 · 재조회는 무거운 쿼리를 한꺼번에 다시 부를 뿐이다 |
| cache:devlist:{site_id} | master · devices · {site_id} · 같은 사이트 설비의 modbus 설정 조회 | ADM-MASTER · DSH · ANL · ALM-RULES 설비 선택기 | realtime 쿼리 — 설비 목록 변경은 최신값 Hash 내용을 바꾸지 않는다 |

- 검산: 신호 키 = **4**
- **사이트 · 라인 쓰기는 신호가 없다.** 두 목록은 Redis 사본을 두지 않아 ③에 실을 키 이름이 없다([../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) W5 판정) — 다른 사용자 화면은 staleTime(BFF revalidate 창 이하)만큼 옛 목록을 보이고, 쓴 탭은 자기 쓰기 성공으로 로컬 무효화한다.
- **ch:cacheinv에 오지 않는 키는 이 표에 없다** — cache:alarmevents · cache:workorders는 체인 ③을 걸지 않고(키 하나 DEL로 조합 전부가 지워진다), cache:q는 체인 대상이 아니다. 두 무효화 모두 쓴 사람 화면의 자기 쓰기 성공과 staleTime이 맡는다.
- **⑥은 쓴 사람의 탭을 위한 단이 아니다.** 쓴 탭은 쓰기 응답을 받는 순간 같은 쿼리 키를 로컬 무효화한다 — ⑥은 다른 사용자와 **같은 브라우저의 다른 탭**을 위한 단이다. 탭마다 WebSocket과 쿼리 캐시가 따로라 다른 탭은 신호로만 안다(AC-06 브라우저 층).
- **신호는 스로틀 대상이 아니고 병합하지 않는다.** 받은 키를 받은 대로 처리한다 — 병합하면 키가 빠질 수 있다([../06_pipeline/05_realtime_read.md](../06_pipeline/05_realtime_read.md) F-07 사이클 ④).
- **신호 뒤 2초는 신선 창이다(S4 판정 · 검수 M5).** ⑥ 신호는 ③ 시점에 발화해 BFF의 ⑤보다 먼저 닿을 수 있다 — 그대로 재조회하면 BFF 서버 사본의 옛 목록을 받아 staleTime 동안 새 값으로 믿는다. 셸은 master 계열 신호를 받으면 신선 창을 열고, 창 안의 master 조회는 표지(x-bff-fresh)를 달아 BFF가 서버 사본 없이 api를 읽게 한다(기전 [../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md)). 재연결 무효화는 신선 창 없이 BFF 사본을 거친다. AC-06 다른 탭 층은 이 창 아래에서 3/3 성립했다(기록 021).
- **신호를 놓치면 staleTime이 상한이다.** Pub/Sub은 전달을 보장하지 않는다 — 재연결 직후 공통 셸은 master 계열 쿼리를 한 번 무효화해 끊긴 동안 놓친 신호를 메운다. 최신값의 재연결 1회 동기화(REQ-RLT-13)와 같은 모양이다.
