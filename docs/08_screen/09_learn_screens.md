이 문서는 발표의 앞 절반 — "세 DB가 각자 무엇을 잘하나(개념)"와 "센서 데이터를 어디에 두어야 하나(비교)" — 를 맡는 네 화면을 명세한다. 네 화면은 **api 표면을 하나도 부르지 않는다.** ①은 정적 그림이고, ②③④는 BFF가 저장소 안의 측정 기록(docs/measurements)을 읽기 전용으로 판독한 값만 그린다 — 지금 돌고 있는 시스템을 다시 재지 않는다. 지금 시스템에서 다시 재는 길은 ⑤ 직접 비교 실험([10_lab_screen.md](./10_lab_screen.md))이다 — **단 ⑤의 PostgreSQL은 TimescaleDB(칸 나누기 · 열 압축)라 ②③④가 보이는 기록 035~053의 일반 PostgreSQL과 다른 PostgreSQL이다**(D-05 부분 개정 · [../04_architecture/09_decision_records.md](../04_architecture/09_decision_records.md) ADR-32).

**네 화면의 숫자는 전부 기록에서 온다 — 지어낸 값이 없다.** 판독기(lib/perf.ts · lib/evidence.ts)가 기록의 기계 판독 블록을 읽고, 화면 판독(lib/learn.ts)은 그 결과를 줄 · 막대 · 곡선 모양으로 바꾸기만 한다. 하나의 예외는 ④의 "센서 디스크 1년치"이고 화면이 **계산값** 표지를 단다(§LRN-ARCHITECTURE). 판독 규칙의 정본은 [../10_observability/04_experiment_protocol.md](../10_observability/04_experiment_protocol.md) §BFF 판독 규칙이고, 이 문서는 화면에 놓인 자리와 쉬운 말만 고정한다.

**측정 도구가 D-16으로 지워져 ②③④의 기록은 다시 잴 수 없다.** 기록 원문과 원시 데이터(docs/measurements/raw)는 남고 판독기는 그대로 돈다 — 그래서 화면은 기록이 바뀌지 않는 한 같은 값을 보인다. 화면 공통 틀(질문형 제목 · 설명 한 줄 · 회색 각주 · 반응형)은 [01_standards.md](./01_standards.md) §한 화면 원칙 · §반응형 규칙이 갖는다.

## 네 화면 공통

| 규칙 | 내용 | 어기면 |
|------|------|------|
| 기록만 | ②③④의 숫자는 BFF 기록 읽기 두 보기(view=perf — 격자 · 저장 크기 · view=evidence — 역방향 대조 · 동시 적재 계단)의 판독 결과만 쓴다 · 화면 판독은 새 숫자를 만들지 않는다 | 화면이 만든 숫자가 기록 값처럼 발표에서 인용된다 |
| 3번 모두 같을 때만 | 승패 · 방향은 기록의 3회 실행이 모두 같은 쪽을 가리킬 때만 그린다 — 아니면 막대 없이 "비슷" · "승패 미정"(속 빈 점) · 배수 글자가 1.0이면 "비슷" | 한 번의 우연한 차이가 결론으로 읽힌다 |
| 계산값 표지 | 기록 값을 곱해 만든 값(④ 1년치 디스크)은 줄 이름 옆에 "계산값" 표지와 툴팁의 계산식을 단다 | 계산값이 실측으로 읽힌다 |
| 진입 1회 읽기 | 화면에 들어올 때 한 번 읽고 폴링하지 않는다(staleTime 0 · 창 초점 · 재연결 재조회 없음) — 기록은 커밋으로만 바뀐다 | 기록이 안 바뀌는데 요청만 쌓인다 |
| 쉬운 말 | 질문 코드(Q1~Q5) · 실험 번호(EXP-NN) · 기록 번호 · 3회 값은 툴팁에만 · 화면은 "센서 1개 · 7일" · "한 건 찾기(점 조회)"처럼 쉬운 말 먼저 · 용어는 괄호 | 코드표를 아는 사람만 화면을 읽는다 |
| 저장소 색 | PostgreSQL 파랑 · ClickHouse 주황 · Redis 빨강(웹 상수 components/ui/store.ts) — 막대 · 선 · 점 · 머리 띠가 갖고 글자에는 진한 짝만 | 같은 저장소가 화면마다 다른 것으로 읽힌다 |

- 검산: 공통 규칙 = **6**
- **세 화면이 같은 쿼리를 나눠 쓴다.** 성능 보기(쿼리 키 measurements · perf — 응답이 수백 KB라 gcTime이 시계열과 같다)는 ② · ③ · ④가, 업무 보기(measurements · evidence)는 ② · ③이 읽는다 — 화면을 오가면 캐시가 재사용되고 진입마다 한 번 새로 읽는다.
- **B형 — 기록 화면이 지금 시스템 상태와 달라도 결함이 아니다.** 결론 — ②③④는 과거 측정(10억 행 격자 · 역방향 대조)을 보인다. 반대 시나리오 — 지금 쌓인 카드 라인 데이터로 다시 그리면 규모가 작아 ③의 역전 구간이 보이지 않고, 발표의 근거가 실행마다 바뀐다. 파생 지침 — 지금 시스템에서 확인하려면 ⑤ 직접 비교 실험으로 간다(같은 질문 성격의 소량 2 · 대량 2 · 무결성 3).

## LRN-CONCEPTS — 세 DB 한눈에

| 항목 | 내용 |
|------|------|
| 화면 코드 | LRN-CONCEPTS |
| 웹 경로 | /concepts(루트 / 가 이리로 넘어간다 — 발표 첫 화면) |
| 페르소나 | 시연 청중(선배 개발자) · 학습자 |
| 역할 | 보기 — 전원 무인증(D-16) |
| 도입 단계 | D-16 재구성(2026-10-11) |
| 요청 경로 | 없음 — 정적 화면(인라인 SVG) |

**목적**: "세 DB는 각자 무슨 일을 할까?" — 데이터가 들어와 화면에 보이기까지 Redis · PostgreSQL · ClickHouse가 일을 나눠 맡는 모습을 처리 방식 그림으로 본다.

**진입**: 좌측 내비 개념 섹션 "세 DB 한눈에" 또는 루트 /. 진입 파라미터 없음.

```plain
┌ 세 DB는 각자 무슨 일을 할까?  데이터가 들어와 화면에 보이기까지, 세 DB가 일을 나눠 맡아요. ──────────────┐
├ ● Redis ─────────────────┬ ● PostgreSQL ─────────────┬ ● ClickHouse ─────────────┤
│ 잠깐 맡아 두고 빨리 전해요   │ 틀리면 안 되는 기록을 지켜요  │ 엄청 많이 쌓고 한꺼번에 계산해요 │
│ [그림 3줄]                 │ [그림 3줄]                 │ [그림 3줄]                 │
│  메모리에서 바로 꺼내기       │  한 줄씩 통째로 저장          │  필요한 열만 골라 읽기         │
│  먼저 온 것부터 넘기기       │  목차로 바로 찾기             │  같은 값끼리 줄여 저장         │
│  자주 보는 답은 잠깐 보관     │  실패하면 전부 되돌리기       │  작은 조각을 뒤에서 합치기     │
│ ✓ 아주 빠름 ✓ 줄 세우기     │ ✓ 한 건 찾기 ✓ 되돌리기      │ ✓ 대량 집계 ✓ 작게 저장       │
│ ✕ 오래 · 많이 보관          │ ✕ 수억 행 집계               │ ✕ 한 건 수정 ✕ 규칙 검사       │
│ 여기서 대기줄 · 지금 값 · 조회 사본 │ 여기서 설비 · 태그 · 업무 기록 │ 여기서 센서 원본 · 요약        │
├ 데이터가 가는 길  [설비 30대 센서 값 · 화면 업무 명령] → [Redis 모두 여기를 거쳐요] → [ClickHouse 센서 원본 · 요약 · PostgreSQL 설비 · 태그 · 업무] → [화면] ┤
│ (회색 각주) 그림은 동작 원리를 줄여 그린 것이에요 — 실제로 잰 숫자는 다음 화면(장단점 · 시계열)에서 봐요            │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **세 칸 순서는 Redis · PostgreSQL · ClickHouse다.** Redis 빨강과 ClickHouse 주황은 색만으로 가르기 어려워 두 칸을 이웃에 두지 않고, 칸 머리에 늘 이름 글자를 함께 쓴다.
- **그림이 주인공이다.** 칸마다 그림 세 줄(왼쪽 그림 · 오른쪽 쉬운 말 본문 토큰 굵게 + 괄호 속 용어 각주 토큰 회색 — 세 줄의 글자가 같은 세로선에서 시작한다) — Redis 키 → 값 · 대기줄(Stream) · 사본(캐시) / PostgreSQL 행 저장 · 목차(B-tree) · 트랜잭션 / ClickHouse 열 저장 · 압축 · 병합.
- **숫자를 두지 않는다.** 이 화면은 원리만 말하고 잰 값은 ② · ③으로 넘긴다 — 각주가 그 길을 말한다.

## LRN-STRENGTHS — PG vs CH 장단점

| 항목 | 내용 |
|------|------|
| 화면 코드 | LRN-STRENGTHS |
| 웹 경로 | /strengths(옛 /performance도 이리로 넘어간다) |
| 페르소나 | 시연 청중 · 학습자 |
| 역할 | 보기 — 전원 무인증(D-16) |
| 도입 단계 | D-16 재구성(2026-10-11) |
| 요청 경로 | 브라우저 → BFF 기록 읽기(GET /bff/measurements?view=perf · view=evidence) — api 표면 없음 |

**목적**: "무엇이 강하고 무엇이 약할까?" — 같은 일을 두 DB에 시킨 기록으로, 일의 성격에 따라 이기는 쪽이 바뀌는 것을 줄다리기 막대 8줄로 본다.

│ 작업 도중 오류 시 되돌리기(트랜잭션)  (✓ 전부 되돌림)       │(✕ …)                                  │
│ 규칙 어긴 데이터 막기(제약 조건)     (✓ …)                 │(✕ …)                                  │
│ ClickHouse가 강한 것                                       │                                       │
│ 전체 데이터 훑기(전체 스캔)                                  │▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇ N배 빨라요            │
│ 긴 기간 조회(센서 1개 · 7일)                                 │▇▇▇▇▇▇▇▇ N배 빨라요                    │
│ 설비 하루치(설비 1대 · 하루)                                 │ … (기록이 정한 방향 · 비슷이면 가운데 회색) │
│ 저장 공간(압축)                                             │▇▇▇▇▇▇▇▇▇▇ N배 작아요                  │
├ 한 줄 정리 (많이 쌓아 두고 크게 훑는 데이터 → ClickHouse) (정확하게 한 건씩 다루는 데이터 → PostgreSQL) ──────┤
│ (회색 각주) 같은 일을 3번씩 시킨 중간값 · 누가 이기는지는 3번 모두 같을 때만 · 막대는 10배마다 한 칸 · 아래 4줄은 10억 행 ⓘ │
└──────────────────────────────────────────────────────────────────────────────────────────────┘

- **묶음은 배치만 정하고 막대 방향은 기록이 정한다.** 위 4줄은 "PostgreSQL이 강한 것", 아래 4줄은 "ClickHouse가 강한 것"으로 놓이지만, 어느 쪽으로 막대가 뻗는지는 그 줄의 기록이 정한다 — 예를 들어 "설비 하루치"는 기록에서 PostgreSQL이 이기면 왼쪽으로 뻗는다.
- **막대 길이는 로그다.** 길이 = log10(배수) ÷ log10(가장 큰 배수 · 최소 100배) — 10배마다 같은 간격 · 세로 눈금선(10배 · 100배 …) · 아주 짧아도 보이게 최소 3%.
- **정확성 줄은 길이가 없다.** 되돌리기 · 규칙 막기는 배수가 아니라 ✓ · ✕ 알약(지킨 쪽 저장소 연한 바탕 · 못 지킨 쪽 회색)이다.

## LRN-TIMESERIES — 시계열: PG에 vs CH에

| 항목 | 내용 |
|------|------|
| 화면 코드 | LRN-TIMESERIES |
| 웹 경로 | /timeseries |
| 페르소나 | 시연 청중 · 학습자 |
| 역할 | 보기 — 전원 무인증(D-16) |
| 도입 단계 | D-16 재구성(2026-10-11) |
| 요청 경로 | 브라우저 → BFF 기록 읽기(view=perf · view=evidence) — api 표면 없음 |

**목적**: "센서 데이터가 10억 행이 되면?" — 같은 센서 데이터를 두 DB에 10만 행부터 10억 행까지 넣고 같은 질문을 시킨 기록으로, 성능(왼쪽)과 관리 비용(오른쪽)을 나란히 본다.

**진입**: 좌측 내비 비교 섹션 "시계열: PG에 vs CH에". 진입 파라미터 없음.

```plain
┌ 센서 데이터가 10억 행이 되면?  같은 센서 데이터를 두 DB에 10만 행부터 10억 행까지 넣고, 같은 질문을 시켜 봤어요. ┐
├ 성능 ─────────────── — PostgreSQL(목차 B-tree) — ClickHouse ┬ 관리 비용 ──────────── 10억 행 넣었을 때 ┤
│ 소량 조회 — 센서 1개 · 최근 1시간      대량 집계 — 전체 설비 · 1분 평균 │ 디스크                                  │
│ (결론 한 문장)                        (결론 한 문장)              │ PG ████████████████ N GB                │
│ [곡선: 행 수 → 걸린 시간 · 두 축 로그]  [곡선 · 역전 구간 음영]      │ CH ▍ N GB                                │
│                                                                 │ ClickHouse가 N배 작게 저장해요           │
│ ✓ 넣기: 초당 N행까지 둘 다 문제없어요 (Redis 경유 · 실패 묶음 0)  │ 사람이 할 일  🔧 따로 설정 · 관리  ⟳ DB가 기본으로 │
│                                                                 │ 오래된 데이터 지우기 | partman      | TTL 7일 │
│                                                                 │ 지운 자리 청소       | autovacuum   | 병합    │
│                                                                 │ 찾기용 목차          | B-tree N GB  | 정렬 순서 N MB │
│ (회색 각주) 같은 일을 3번씩 시킨 중간값 · PG는 목차(B-tree)를 단 표 · 곡선의 두 축은 눈금마다 10배 ⓘ           │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **곡선 두 장이 주인공이다.** 소량 조회(Q1)와 대량 집계(Q4) — 가로 행 수(10만 → 10억 · 로그) · 세로 걸린 시간(로그) · PostgreSQL 파랑 · ClickHouse 주황 · 3회가 엇갈린 규모는 속 빈 점 · 역전 구간이 기록에 있으면 그 구간 음영.
- **넣기는 한 줄이다.** 동시 적재 계단 기록(045 — 같은 묶음을 Redis 경유로 두 DB에 동시에)의 판정한 계단 전부에서 실패 0이고 묶음 하나 넣는 시간 95% 값이 기준 안이면 ✓ "넣기: 초당 N행까지 둘 다 문제없어요" · 아니면 ✕ "… 안에서 실패나 지연이 있었어요".
- **관리 비용은 실측과 운영 작업 그림이다 — 클라우드 요금 환산이 없다(D-16).** 디스크 막대는 선형(큰 쪽 = 100%)이고, 사람이 할 일 3줄은 문장이 고정이며 목차 크기만 기록 값이다.

## LRN-ARCHITECTURE — PG 하나로 vs 나눠서

| 항목 | 내용 |
|------|------|
| 화면 코드 | LRN-ARCHITECTURE |
| 웹 경로 | /architecture |
| 페르소나 | 시연 청중 · 학습자 |
| 역할 | 보기 — 전원 무인증(D-16) |
| 도입 단계 | D-16 재구성(2026-10-11) |
| 요청 경로 | 브라우저 → BFF 기록 읽기(view=perf) — api 표면 없음 |

**목적**: "PostgreSQL 하나로 다 하면 안 될까?" — A "Redis + PostgreSQL"과 B "Redis + PG(업무) + CH(센서)"를 같은 기준으로 견준다. 둘 다 모든 데이터가 Redis를 거친다(D-16 사용자 전제).

**진입**: 좌측 내비 비교 섹션 "PG 하나로 vs 나눠서". 진입 파라미터 없음.

```plain
┌ PostgreSQL 하나로 다 하면 안 될까?  두 구성을 같은 기준으로 견줘 봐요. 둘 다 모든 데이터가 Redis를 거쳐요. ─────┐
│ 견주는 것            │ [A] Redis + PostgreSQL           │ [B] Redis + PG(업무) + CH(센서)          │
│                      │ [설비 → Redis → PG(업무 + 센서)]   │ [설비 → Redis → PG(업무) · CH(센서)]      │
├ 센서 대량 집계 ───────┼ N초                              │ N초 ✓ N배 빨라요                          │
│ 전체 설비 · 1분 평균 · 10억 행                                                                       │
├ 센서 디스크 1년치 [계산값] ┼ 약 N TB                     │ 약 N GB ✓ N배 작아요                       │
│ 카드 라인 30대                                                                                       │
├ 관리할 서버 ─────────┼ 2대 ✓ 1대 적어요                 │ 3대                                       │
├ 하나가 멈추면 ────────┼ 업무 · 센서 함께 멈춤             │ 한쪽만 멈춤 ✓ 덜 멈춰요                    │
├ (결론 한 줄) 센서 데이터가 많으면 나눠서(B)가 유리해요 — 대량 집계 N배 빠르고 1년치 디스크가 N배 작아요 · 대신 관리할 서버가 하나 늘어요 ┤
│ (회색 각주) 대량 집계는 10억 행 기록 · 1년치 디스크는 계산값 ⓘ                                          │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **점수판은 4줄이다.** 업무 1건 처리 시간 줄은 D-16 뒤 사용자 결정으로 지웠다(업무 방해 실측이 실행마다 흔들려 판정 불가 — 정본 [../01_overview/06_design_decisions.md](../01_overview/06_design_decisions.md) D-16) — 그래서 이 화면은 ⑤의 결과를 읽지 않는다.
- **더 나은 칸만 연한 회색 바탕 + ✓ + 짧은 말이다.** 값 글자는 hero 단계(가장 큰 숫자) · 숫자 비교는 작은 쪽이 낫고 배수 글자가 1.0이면 더 나은 쪽이 없다.
- **결론 한 줄은 점수판에 실제로 나온 숫자로만 짓는다.** 대량 집계 · 1년치 디스크에서 B가 이긴 숫자만 문장에 들어가고 없는 숫자는 문장에서 빠진다 — 둘 다 없으면 "두 구성의 차이를 잰 기록이 아직 부족해요".

### 요소

| 요소 | 위치 | 동작 | 기능 ID | 표면 |
|------|------|------|------|------|
| 화면 의도 | 본문 맨 위 | 질문형 제목 + 설명 한 줄 | 해당 없음 — 정적 | 해당 없음 |
| 구성 머리 2 | 점수판 위 | A · B 꼬리표 + 이름 + 작은 구조 그림(설비 → Redis → 저장소 — 저장소 색 · 접근성 이름에 구조 문장) | 해당 없음 — 정적 | 해당 없음 |
| 점수판 4줄 | 점수판 가운데 | 센서 대량 집계(기록) · 센서 디스크 1년치(계산값 표지) · 관리할 서버(고정) · 하나가 멈추면(고정) — 줄마다 이름 · 작은 설명 · A 칸 · B 칸 · 줄 툴팁에 근거 | 해당 없음 — 기록 판독 · 정적 | GET /bff/measurements(view=perf) |
| 결론 한 줄 | 점수판 아래 | 점수판 숫자로 지은 문장 · 끝에 "대신 관리할 서버가 하나 늘어요" | 해당 없음 — 기록 판독 | GET /bff/measurements(view=perf) |
| 각주 | 맨 아래 | "대량 집계는 10억 행 기록 · 1년치 디스크는 계산값" + ⓘ(판독 시각) | 해당 없음 — 기록 판독 | GET /bff/measurements |

- 검산: 요소 = **5** · 주 기능 = **0**(기록 판독 화면)

### 데이터 원천

| 줄 | 원천 | 쓰는 법 |
|------|------|------|
| 센서 대량 집계 | view=perf 격자 — 질문 Q4(전체 설비 · 1분 평균)의 가장 큰 규모 · A = PostgreSQL(B-tree) · B = ClickHouse | 승패 막대와 같은 규칙(3번 모두 같을 때만) |
| 센서 디스크 1년치 | **계산값** = 카드 라인 명목 초당 점(packages/shared card-line — 30대 태그 주기 합) × 31,536,000초 × 기록의 행당 바이트(PG 표 + 목차 · CH 압축된 열) | 툴팁에 식 · 초당 점 · 행 수 · 행당 바이트 · 기록 번호 · "보관 기간 · 요약 표 · 업무 데이터는 넣지 않은 센서 원본만의 값" |
| 관리할 서버 | 고정 — A Redis · PostgreSQL 2대 · B Redis · PostgreSQL · ClickHouse 3대 | A가 "1대 적어요" |
| 하나가 멈추면 | 고정 — A는 PostgreSQL이 멈추면 업무와 센서 저장이 함께 멈춘다 · B는 한쪽만 멈춘다 · 둘 다 Redis가 잠시 받아 둔다 | B가 "덜 멈춰요" |

- 검산: 줄 = 기록 1 + 계산값 1 + 고정 2 = **4**
- **A형 — 1년치 디스크는 잰 값이 아니다.** 통념은 화면의 크기 숫자가 실제로 1년을 쌓아 잰 것이라는 것이다. 부정 — 측정 도구는 D-16으로 지워졌고 1년치를 쌓은 기록은 없다. 진짜 축은 **기록이 확정한 행당 바이트 × 카드 라인이 1년 동안 보낼 행 수**라는 곱이다. 대체 경로 — 줄 이름 옆 "계산값" 표지와 툴팁의 식이 이 사실을 말한다. ⑤ 넣기(사흘치까지)가 지금 시스템에서 재는 크기 비는 ClickHouse 대 PostgreSQL(TimescaleDB 압축 뒤)이라 이 줄의 PostgreSQL(일반 행 저장 — 표 + 목차)과 다른 비교다.

### 상태 4행

| 상태 | 처리 |
|------|------|
| 로딩 | 구성 머리 2(정적)를 먼저 그리고 점수판 자리는 회색 틀 |
| 빈 값 | 기록이 없는 줄은 두 칸 "잰 값 없음" · 결론 문장에서 그 숫자가 빠진다 |
| 오류 | 성능 보기 읽기 실패면 점수판 자리에 "기록을 읽지 못했어요" · 구성 머리는 남는다 |
| 정상 | 4줄 · 더 나은 칸 표지 · 계산값 표지 · 결론 · 각주 툴팁의 판독 시각 |

### 호출 표면 · 갱신 · 스위치 영향

- 부르는 자리 = view=perf **1**(진입 1회 · no-store) · api 표면 = **0**.
- 스위치 영향 — 해당 없음(기록 판독 · 고정 문장).

### 비고

- 명목 초당 점은 카드 라인 정본(packages/shared/src/card-line.ts)의 태그 주기 합이라 설비 가동 여부와 무관하다 — 카드 라인 구성이 바뀌면 계산값이 같은 변경 단위에서 따라 바뀐다.
