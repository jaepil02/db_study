이 문서는 웹 7화면 중 ⑥ 분산 처리 모니터링과, ⑤ · ⑥이 함께 쓰는 실행 규칙(§실행 패널)을 명세한다(D-16). **EXP-FLOW는 "데이터가 Redis를 거쳐 어느 DB로 얼마나 가고, 모아서 처리하는 길과 하나씩 처리하는 길이 어떻게 다른가"**에 답한다. 화면은 관찰 표시에 더해 **실행 조작부** 하나를 갖는다 — 대용량 발행 · 업무 명령 · 조회를 함께 흘리는 flow 실행(GEN-12)을 시작 · 중단하고 완료와 소요 시간을 보인다. 저장소 정지 같은 장애 주입 버튼은 없다 — 장애는 호스트 셸의 스크립트가 일으킨다.

**옛 EXP-PERF(성능 비교 · /performance)는 D-16으로 폐지됐다.** 주 기능이던 성능 비교 라이브 실행(GEN-11 — 옛 perf 직접 재 보기)과 함께 화면 명세를 지웠고, 화면 코드는 결번으로 남는다(정본 [README.md](./README.md) §화면 인벤토리). 측정 기록의 형식과 BFF 판독 규칙의 정본은 [../10_observability/04_experiment_protocol.md](../10_observability/04_experiment_protocol.md)이며 그대로 남는다 — 폐지 전 화면 명세 원문은 커밋 28c0cc9에 있다.

**화면은 한 장이다(D-15 · D-16 반응형).** 1280 × 720 ~ 2560 × 1440에서 페이지 스크롤 · 가로 넘침 · 서랍 · 아코디언 · 탭이 없고, 맨 위의 의도 한 줄 → 결론 → 그림 하나 → "왜?" 한두 줄 → 회색 각주 순서로 읽힌다(원칙 정본 [01_standards.md](./01_standards.md) §한 화면 원칙). 글꼴 · 글자 단계 · 숫자 폭 · 묶음 · 테두리 · 포커스 · 움직임 같은 공통 시각 규격은 [01_standards.md](./01_standards.md) §글자와 화면 표면이 갖고, 이 문서는 화면에 그 규격이 놓인 자리와 크기를 적는다.

**화면의 수치는 측정 기록이 아니다.** EXP-FLOW는 지금 돌고 있는 시스템의 순간 관찰이고, 정본 문장은 화면 수치를 인용하지 않는다. **라이브 실행 결과도 기록이 아니다** — 앱(api)을 거쳐 흘리므로 결과에 항상 라이브 표지를 달고 측정 기록(docs/measurements)을 만들지 않는다.

## EXP-FLOW — 분산 처리 모니터링

| 항목 | 내용 |
|------|------|
| 화면 코드 | EXP-FLOW |
| 웹 경로 | /monitoring |
| 페르소나 | 실험 수행자(주) · 시연 청중 · 학습자 |
| 역할 | 보기 · 실행 조작부의 시작 · 중단 — 전원 무인증(D-16 — 로그인 · 권한 없음) · flow 프레임은 값이 아니라 개수 · 시간 · 명령 종류 · 결과 코드만 싣는다 |
| 도입 단계 | S5 — 적재 · WebSocket 게이트웨이가 선 뒤 |
| 요청 경로 | WebSocket은 셸의 연결 하나를 그대로 쓴다(api 직결 · subscribe_flow) · DB 노드의 양 · 크기와 밀린 데이터 · 측정 → 저장까지는 BFF 경유 메트릭 해석 · 각주 툴팁은 BFF 경유 GET /api/v1/health · 실행 조작부 — **브라우저 → BFF → api 표면 4**([../07_api/09_datagen.md](../07_api/09_datagen.md) #2~#5 · no-store) |

**목적**: 센서 데이터와 업무 데이터가 Redis 대기줄을 거쳐 각자에게 맞는 DB로 나뉘어 저장되는 모습을 움직임과 숫자로 본다 — 둘 다 Redis Stream을 지나되 **묶음(배치)으로 모아 가는 길과 명령 하나씩 순서대로 가는 길**이 왜 다른가. 조회는 줄을 서지 않고 Redis 사본을 먼저 본 뒤 없을 때만 DB로 간다는 것도 세 번째 줄로 함께 본다. 그 흐름을 이 화면에서 정한 초당 포인트 · 시간 · 업무 요청 빈도 · 조회 빈도로 직접 일으켜 볼 수도 있다(라이브 flow 실행).

**진입**: 좌측 내비 "분산 처리 모니터링". 진입 파라미터 없음 — 진입이 곧 subscribe_flow이고 이탈이 unsubscribe_flow다.

- **두 길을 한 그림에 위아래로 둔다(A형).** 통념은 "Redis를 거치면 비동기라 쓴 직후 조회가 옛 값을 본다"는 것이다. 부정 — 업무 명령은 api가 워커의 커밋 결과(biz:result · ch:bizreply)를 받은 뒤에만 기존 상태 코드로 응답하고, 워커는 무효화를 결과보다 먼저 한다([../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) §업무 명령 경로). 진짜 축은 **같은 Redis Stream이라도 단위와 순서 보장이 다르다**는 것이다 — 센서 길은 창마다 묶은 배치를 처리량 위주로 넣고, 업무 길은 명령 하나를 소비자 하나가 순서대로 트랜잭션에 넣는다. 대체 경로 — 센서 점은 행 수만큼 크게, 업무 점은 명령 하나로 작게 그리고, "모아서 대 하나씩" 막대가 같은 차이를 처리 시간으로 한 번 더 보인다.
- **A형 — 조회는 대기줄에 서지 않는다.** 통념은 "모든 요청은 Redis 대기줄을 거친다"는 것이다. 부정 — 대기줄을 타는 것은 위 두 줄(센서 · 업무 쓰기)뿐이다. 진짜 축은 **즉답이 필요한가**다 — 조회는 사람이 답을 기다리므로 줄을 세우면 앞 요청을 기다린 만큼 느려지기만 한다. 대체 경로 — 조회에서 Redis는 **먼저 확인하는 사본 자리**(칸 ⑤)다 — 있으면 바로 답하고 없을 때만 ClickHouse · PostgreSQL에 가서 사본을 담는다(기전 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md) §흐름 시연 실행 · [../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) §읽기 · 쓰기 경로). 그래서 조회 줄에는 점이 아니라 초당 수와 비율만 있다 — 조회는 flow 프레임 요약을 만들지 않는다.
- **점은 실제 묶음 하나다 — 연출이 아니다.** 점 하나가 flow 프레임의 요약 하나이고, 단계마다 머무는 시간의 비율이 그 묶음의 실제 단계 ms 비율이다. 요약이 오지 않으면 점도 없다 — 멈춘 그림이 곧 멈춘 적재다.
- **노드 이름을 쉬운 말로 바꿔도 단계는 남는다.** XACK · MV(tag_1m) · flusher · WS → 브라우저 · BFF는 노드로 그리지 않지만 배치 점의 단계 순서(XACK 포함)는 그대로 지나가고, 업무 갈래(트랜잭션 · 캐시 무효화)는 저장소 노드 · Redis 칸 안 숫자로 들어갔다(§표시 계약 노드와 숫자).
- **와이어프레임의 ○는 자리 예시다** — 실제 값은 §데이터 원천과 숫자 4 대응 표가 가리키는 flow 프레임 · 메트릭 필드에서 읽는다.

| 노드와 숫자 | 흐름도는 노드 12만 그린다 — XACK · MV · WS → 브라우저 · BFF 노드는 그리지 않되 배치 점의 XACK 단계는 남긴다 · 업무 갈래(트랜잭션 · 캐시 무효화)는 저장 DB 노드 · Redis 칸 안 숫자로 · Redis는 가운데 한 기둥으로만 그리고 저장 DB 칸에 따로 두지 않는다(업무 점이 PostgreSQL 다음 Redis로 가도 목적지가 아니라 사본 지움 · 결과 알림 자리로 읽히게) · DB 노드 · Redis 칸의 초당 값과 왜 나눌까 세 칸의 양은 같은 원천 · 같은 값 | 노드를 접으면서 단계까지 지우면 "대조군은 XACK 앞" 계약이 그림에서 사라지고, 노드와 카드가 다른 계산을 쓰면 한 화면에 같은 흐름의 숫자가 둘이 된다 |
| 원천 없는 값 | 원천 필드가 없는 값은 그리지 않는다 — 캐시 무효화 누적은 totals에 없어 숫자로 올리지 않는다 · 목적지가 아닌 저장소는 0이 아니라 갈래 없음 | 다른 값으로 대신 채우면 확인되지 않은 사실을 화면이 만든다 |
| 밀린 데이터 | 밀린 개수는 lag(stream.lag · consumer_lag · biz_stream_lag)이고 길이가 아니다 · 센서 대기줄과 업무 대기줄 값을 더하지 않는다(한 엔트리의 뜻이 다르다) · 주황 "처리가 밀리는 중"은 backpressure_stage가 0이 아닐 때만 | 길이를 쓰면 확인된 엔트리까지 밀린 것으로 읽히고, 화면이 임의 문턱으로 "밀림"을 정하면 같은 상태가 화면마다 다르게 판정된다 |
| 조회 줄 | 세 계열의 5초 두 응답 차 ÷ 경과 초 — **바로 응답** = hit 합(tsq_cache_requests_total · rlt_latest_requests_total · mst_cache_requests_total) · **ClickHouse까지** = tsq miss + rlt restored + rlt bypass · **PostgreSQL까지** = mst miss · **실패** = error 합(따로 — 0이 아닐 때만 줄 끝에) · 비율 분모는 세 계열 전 결과 합(실패 포함) · rlt_latest_points_served_total은 **점 수라 요청 수로 쓰지 않는다**(툴팁의 fresh 비율에만) · tsq_source_queries_total(ClickHouse 실제 호출 — 최근 구간 · 대기 소진 포함)도 툴팁에만 · 세 계열 차분이 모두 0이면 줄 대신 "조회 요청이 없어요 — 직접 보내 보기로 보내 보세요" · 카운터 감소(api 재기동)면 한 창 건너뛴다 | 점 수를 요청 수에 쓰면 지금 값 조회 한 번이 태그 수만큼 부풀고, 실패를 히트나 미스에 섞으면 Redis가 멈춘 동안 바로 응답 또는 DB 길이 늘어 보인다 · 0% 막대를 그리면 조회가 없는 것과 전부 미스인 것이 구분되지 않는다 |
| 라이브 표지 | 종결 띠 옆 · 지난번 글자 툴팁에 "내 측정(참고용)"과 툴팁 고정 문구 "라이브 실행 — 앱 경유 · 시연값 · 기록 정본 아님" · flow 실행 결과로 측정 기록을 만들지 않는다 | 시연 한 번의 보낸 수 · 드레인 시간이 EXP-45 같은 측정 기록의 값처럼 인용된다 |
| 실행 발행 원천 | flow 실행 중에는 진행 띠가 실행을 말하고, 카드 라인 설비 노드 툴팁이 "그중 직접 보내 보기 몫 초당 N개"(gen_points_generated_total의 mode 레이블 값 run — 모드 A(가상 PLC 레지스터 갱신)와 따로)를 덧붙인다 · **실행의 센서 점은 카드 라인 30대가 아니라 시연 전용 설비 DEMO-FLOW-DEV의 flow 전용 태그 50개에만 간다**(⑦ HMI의 지금 값 · 상태 · 최근 추이가 시연 값으로 바뀌지 않게 — apps/api/src/modules/runs/flow-runner.ts · demo-rows.ts) — 그래서 발생원 노드 "카드 라인 설비 30대 · 초당 N개 보냄"의 숫자에는 실행 중 이 시연 몫이 섞이고, 툴팁의 "그중 직접 보내 보기 몫"이 그 몫을 가른다(노드 이름과 숫자 범위가 어긋나는 잔여 — 웹 문구는 그대로다) · 실행의 업무 명령은 **시연 전용 설비 DEMO-FLOW-DEV(비활성 · 사이트 DEMO-FLOW · 라인 DEMO-FLOW-L)에만** 싣는 master.device.patch다(매번 새 이름 "시연 설비 {runId 앞 8자}-{명령 번호}" — 항상 실제 변경이라 트랜잭션 · 감사 · 무효화가 돈다 · **되돌림 없음** · actor null · 시연 전용 행이 없으면 prepare가 master.site.create → master.line.create → master.device.create → master.device.patch {isActive: false}(생성 표면이 isActive를 받지 않는다 — 07_api/04)를 같은 경로로 싣는다 · prepare 명령은 commandsSent에 세지 않는다) · 이 명령은 api 안에서 BizWritePort로 들어가므로 사람의 업무 요청 노드에서 시작한다 · 흐름 계약(flow 프레임 필드 · 단계 순서)은 바뀌지 않는다 — 실행은 발행 원천을 늘릴 뿐이다 | 실행이 늘린 발행이 모드 B 생성기 · 사람의 쓰기로 읽히고, 업무 명령의 이름 변경이 운영 설비를 바꾼 것으로 읽히며, 실행을 끝낸 뒤 줄어든 처리량이 적재 저하로 신고된다 |

- 검산: 계약 = 관찰 13 + 실행 조작부 2 = **15**
- **정밀 측정 중에는 이 화면을 닫는다(B형).** 결론 — 구독자가 있으면 워커가 배치 · 명령마다 요약을 만들고 Pub/Sub에 한 번 더 발행한다. 반대 시나리오 — 화면을 띄운 채 정밀 측정을 하면 PUBLISH 비용이 flusher 후속 구간에 섞인다. 파생 지침 — 구독자가 없으면(구독 중 표지 cache:flow:subscribed가 없거나 읽지 못하면) 발행 자체를 하지 않고([../07_api/11_websocket.md](../07_api/11_websocket.md) §흐름 이벤트 발행 조건), 실험 러너는 구독 표지가 없는 상태에서 측정 창을 연다 — 각주 툴팁이 이 문장을 싣는다.

| GET /api/v1/runs/current(#3) | 진입 1회 · 어떤 실행이든 running · stopping인 동안 1초 폴링 · 종결되면 멈춘다 · 시작 202 · 409 · 중단 응답 뒤 폴링 재개 | 상동 | run — 진행 중 실행 또는 마지막으로 끝난 실행 · 없으면 null |
| GET /api/v1/runs/{runId}(#4) | 시작 409 뒤 details.runId로 1회(다음 current 폴링을 기다리지 않고 조작부를 맞춘다) | 상동 | 실행 객체 전 필드 · 404면 current 재조회 |
| POST /api/v1/runs/{runId}/stop(#5) | 진행 띠 중단 클릭 | 상동 | 202 실행 객체(status stopping) · 200 이미 종결된 실행 그대로 · 404 |

- 검산: 부르는 자리 = WS 1 + 메트릭 1 + health 1 + 실행 표면 4(09_datagen #2~#5) = **7**
- **메트릭 5초 폴링(리드 판정 2).** DB 노드의 지금까지 · 크기가 15초마다 한 번 움직이면 점의 움직임과 어긋나 보인다. 대가는 BFF 해석 비용과 api 텍스트 생성이며, 저장소 계열은 OBS 수집 주기보다 빨리 바뀌지 않는다 — 같은 값이 반복되는 것을 각주 툴팁의 수집 나이로 보인다. 이 화면은 정밀 측정 중 닫는 화면이라 관측 부하가 측정 창에 섞이지 않는다.
- **캐시 층** — flow 프레임은 캐시 층이 없다(Pub/Sub · 링 버퍼 20). 메트릭 쿼리 키 obs · metrics · flow · staleTime 0(서버 층 없음). health obs · health · staleTime 0. 실행 쿼리 키는 runs · current · runs · {runId}다.

### 비고

- 흐름도는 SVG 직접 그리기다 — 시계열 차트가 아니라 uPlot · ECharts 대상이 아니다. 모아서 대 하나씩 막대도 ECharts가 아니라 HTML 막대다(막대 둘 · 같은 시작점 · 사람이 읽는 시간 글자) — **이 화면은 ECharts를 쓰지 않는다.**
- **맞춤 보기(1280 × 720 ~ 2560 × 1440) — 페이지 스크롤 0 · 흐름도 배율 1 이상(D-16 반응형).** 화면 틀이 셸 본문 높이에 꼭 맞고 흐름도가 남는 높이를 다 가진다(viewBox 1126 × 440 · meet). 숫자 4(64 → 88)와 아래 줄(124 → 160)은 글자 토큰과 같은 비율로 는다. **세로가 820px 미만이면 아래 줄(왜 나눌까 · 모아서 vs 하나씩)을 빼서** 흐름도가 배율 1(노드 글자 12px 이상)을 지킨다 — 반응형 규칙의 "넘치지 않게 줄 수를 줄인다"다([01_standards.md](./01_standards.md) §반응형 규칙). 옛 화면 최소 높이 750 · 1280 × 800 본문 스크롤 허용은 D-16으로 없어졌다. 1440 미만 창은 저장값이 없으면 사이드바 레일로 시작한다 — 사용자가 펼치면 그 선택이 이기고 흐름도 배율이 1 아래로 내려가는 것은 허용 예외다. 작은 화면(맞춤 보기 밖)은 흐름도가 원래 비율로 쌓이고 셸 본문만 세로로 스크롤한다.
- 링 버퍼 20은 화면 상수다 — 메모리는 배치 요약 20건 · 업무 요약 20건이고, 모아서 대 하나씩 막대가 이 링 버퍼를 표본으로 쓴다.
- 실행 조작부의 시작 · 종료 시각은 초까지다 — 예외([01_standards.md](./01_standards.md) §시각 표시 표시 형식 행).
- **flow 실행을 띄운 채 정밀 측정을 하지 않는다.** 실행은 적재 경로에 실제 부하를 싣는다 — 동시 실행 1 제한은 다른 실행과의 겹침만 막고 호스트 스크립트와의 겹침은 막지 않는다 — 측정 창을 열기 전에 진행 띠가 없는지 확인한다.

## 실행 패널

⑥ EXP-FLOW(type flow · GEN-12)와 ⑤ EXP-LAB(type compare — 넣기 · 조회 대결 · 무결성)이 함께 쓰는 실행 규칙의 정본이다(옛 EXP-PERF perf 실행 GEN-11은 D-16 폐지). **배치는 화면마다 다르다** — ⑥은 아래 §배치(셸 머리 버튼 · 선택 칸 · 진행 띠)이고 ⑤는 패널 ▶ 셋과 같은 진행 띠다([10_lab_screen.md](./10_lab_screen.md) §EXP-LAB). 버튼 상태 · 상태 칩 · 종결 표시 · 경과 시간 · 갱신과 응답 처리는 두 화면이 같다 — ⑤의 단계 문장 · 넣기 진행 막대 · 409 compare_no_data · 400 SW-09 off 문구는 ⑤ 문서가 갖는다. **실행은 종류를 합쳐 한 번에 하나다** — 실행이 서로의 관찰을 오염시키므로 api가 동시 실행을 409로 막는다([../07_api/09_datagen.md](../07_api/09_datagen.md) · 기전 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md)). 실행 상태는 api 인스턴스 메모리에만 있어 api를 재기동하면 사라진다 — 화면은 이것을 실패가 아니라 "지난 실행 기록이 없어요"로 보인다.

### 배치

실행 조작부는 **머리 버튼 · "지난번 …" 글자 + 진행 띠 한 줄**이다(D-15 · 설계 정본 .omc/plans/web-junior-redesign.md §2 · §3 직접 재 보기 행 · 다듬기 .omc/plans/web-ux-polish.md §2.1 · §7.1 R12). 옛 서랍(실행 단계 · 라이브 결과 · 실행 결과)은 없고, 아래 동작 규칙은 그대로다.

| 자리 | 놓이는 것 | 보이는 때 |
|------|------|------|
| 셸 머리 동작 자리(오른쪽) | 왼쪽부터 **"지난번 …" 글자**(12 회색 · 실패면 빨강 · 고정 폭 숫자 · 한 줄로 자르고 상세는 툴팁) · 머리 버튼("▶ 직접 보내 보기" — 재생 기호는 그린 아이콘) · 상태 칩 | 머리 버튼은 항상 · 상태 칩은 실행 중 · 멈추는 중에만(종결 뒤 숨김) · 지난번 글자는 이 화면 종류의 종결 실행이 있고 진행 띠가 그 실행을 그리지 않을 때만(같은 말 두 자리 금지) |
| 선택 칸(머리 버튼이 여는 겹침 칸 — 본문을 밀지 않는다) | 매개변수 선택 · 시작 · "다른 측정이 이미 돌고 있어요" 문구 · "아직 보내 보지 않았어요" | 버튼을 누를 때 · 시작 202를 받으면 닫힌다 |
| 진행 띠(본문 의도 줄 아래 얇은 한 줄) | 지금 단계(쉬운 말) · 진행 막대 · 경과 시간 · 중단(실행 중에만) · 방금 끝난 실행의 종결 띠(머리 "지난번 보내 보기") · 라이브 표지 · 409 · 404 · 요청 실패 · 폴링 실패 문구 · 띠 툴팁에 시작 · 종료 시각 | 실행이 running · stopping이거나 **이 화면에서 지켜보던 실행이 방금 끝났을 때(종결 뒤 30초)** · 다른 종류가 진행 중이면 "다른 측정이 이미 돌고 있어요" 한 줄과 그 화면 링크 · 요청 사건 · 폴링 실패 문구가 있을 때 |

- 검산: 자리 = **3**
- **진행 띠는 본문을 스크롤로 밀지 않는 높이 하나다.** 띠가 생기면(한 줄 24 + 여백 · 테두리 = 34) 흐름도가 높이를 줄여 흡수한다([01_standards.md](./01_standards.md) §한 화면 원칙). 실행 중이 아니고 방금 끝난 실행도 없고 띠 문구도 없으면 띠 자체가 없다.
- **"지난번 …" 글자는 키보드 · 낭독기로도 상세에 닿는다(다듬기 §7.1 R12).** 마우스는 툴팁(title)으로, 키보드는 탭으로 그 글자에 닿고(tabIndex 0 · 누르는 동작은 없다) 낭독기는 숨은 상세 문장(sr-only — 툴팁과 같은 내용 · 줄을 " · "로 이음)을 설명(aria-describedby)으로 읽는다 — 툴팁에만 두면 마우스 없는 사용자는 지난 결과의 결말 · 시각을 볼 길이 없다. 글자 모양 — 완료 EXP-FLOW "지난번 초당 1,000개 · 30초 · 완료"(보낸 시간은 이미 범위에 있다) · 중단 "… · 중단됨" · 실패 "… · 실패" · 범위를 모르면 머리 낱말("지난번 직접 재 보기" · "지난번 보내 보기")로 시작한다.
- **단계 목록 · 결과 표를 그리지 않는다.** 결과는 실행 동안의 흐름도가 보인다 — 단계 key · 단계별 소요 · publish detail은 띠 툴팁에만 둔다.

| stopped | 없음(숨김) | "중단됨 — 걸린 시간 1분 5.0초"(툴팁 첫 줄 — error가 있으면 "정리하다 실패했어요 — {error.message}" 전문 · 다음 줄 종료 시각) · error가 있으면(정리 실패) 뒤에 "정리하다 실패했어요({error.message})" | 멈춘 단계 이름 · 정리 단계는 중단이어도 돈다 |
| failed | 없음(숨김) | "실패했어요 — {error.message} · 걸린 시간 N분 N.N초"(툴팁 첫 줄 "실패 원인 — {error.message}" 전문 · 다음 줄 종료 시각) · 원인 메시지가 없으면 "원인을 알 수 없어요" · error.code가 있으면 툴팁에 코드(null 허용 — 실패 원인은 실행 객체 안의 관찰값이다) | 실패한 단계 이름 |

- **띠 글자는 잘린다(truncate).** 긴 오류 메시지는 띠 안에서 한 줄로 자르고 전문은 위 툴팁 첫 줄이 갖는다 — 띠가 두 줄이 되면 본문을 스크롤로 민다.
- **종결 뒤에는 칩과 중단 버튼을 숨긴다.** 종결 띠 머리가 "지난번 보내 보기"로 무엇을 보낸 결과인지 먼저 말하고 종결 문구 · 범위("초당 10,000개 · 60초")와 "내 측정(참고용)" 라이브 표지가 이어진다. 색은 띠가 갖는다 — 완료 초록 · 중단됨 회색 · 실패 빨강. 같은 결과를 칩 · 띠 · 지난번 글자 중 두 자리가 함께 말하지 않는다.
- 검산: status = **5**(전송 enum — 정본 [../11_glossary/03_enums_state_machines.md](../11_glossary/03_enums_state_machines.md)) · 종결 = completed · stopped · failed = **3**
- **종결 결과는 다음 시작 전까지 남는다 — 자리만 접힌다(B형 · 다듬기 §2.1).** 결론 — 이 화면에서 지켜보던 실행이 끝나면 종결 띠가 30초 동안 진행 띠 자리에 서고, 그 뒤(또는 이미 끝난 실행을 열면 처음부터) 띠는 애니메이션 없이 사라지고 셸 머리의 "지난번 …" 글자가 같은 결말을 다음 시작 전까지 말한다 — 접힘은 서랍이 아니다(여는 동작이 없고 상세는 툴팁 · 설명). 반대 시나리오 ① — 결과를 지우면 몇 분짜리 1억 행 실행이 자리를 비운 사이 끝났을 때 내 측정 점만 남아 끝났는지 멈췄는지 가를 수 없다 ② — 띠를 계속 두면 옛 결과가 본문 맨 위 한 줄(가장 좋은 자리)을 차지해 첫 시선이 지난 실행에 간다. 파생 지침 — api도 마지막으로 끝난 실행을 다음 시작 전까지 current로 내므로 다시 들어오면 지난번 글자가 보인다 · 30초는 화면 상수다(lib/runs RECENT_END_MS).
- 실패 띠는 오류 행이 아니다 — 실행 표면은 200으로 실행 객체를 냈고 failed는 그 안의 결과다. 표면 자체의 오류(409 · 404 · 400 · 5xx)만 §갱신과 응답 처리가 다룬다.

### 경과 시간

| 자리 | 값 | 갱신 | 형식 |
|------|------|------|------|
| 진행 중(running · stopping) | 마지막 응답의 elapsedMs + 그 응답을 받은 뒤 흐른 브라우저 단조 시계 | 1초 틱 · 응답이 올 때마다 기준을 서버 값으로 다시 맞춘다 | "1분 42초"(1초 단위) · 1분 미만 "42초" · 1시간 이상 "1시간 3분 12초" |
| 종결 | endedAt − startedAt(서버 elapsedMs와 같다) | 고정 | "3분 12.4초"(0.1초 단위 · 버림) · 1분 미만 "12.4초" · 1시간 이상 "1시간 3분 12.4초" |

- 검산: 자리 = **2** — 단계별 소요는 화면에 그리지 않는다(띠 툴팁의 단계 key 옆 소요는 종결 형식을 따른다)
- **경과 시간은 브라우저가 startedAt을 빼서 만들지 않는다(A형).** 통념은 "시작 시각을 알면 지금 시각에서 빼면 된다"는 것이다. 부정 — 브라우저 시계와 서버 시계의 차이(수 초일 수 있다)가 그대로 경과에 섞이고, 종결 뒤 총 소요와 진행 중 경과가 서로 다른 시계로 계산돼 완료 순간 숫자가 뒤로 튄다. 진짜 축은 **서버가 계산한 elapsedMs 하나를 기준으로 두고 브라우저는 그 뒤에 흐른 길이만 더한다**는 것이다. 대체 경로 — 종결 뒤에는 endedAt − startedAt 하나만 보인다.
- 시작 · 종료 시각은 UTC ISO 8601 Z로 와서 KST로 한 번 변환한다([01_standards.md](./01_standards.md) §시각 표시). 경과 시간은 시각이 아니라 길이라 시간대 변환이 없다.

### 갱신과 응답 처리

| 사건 | 처리 |
|------|------|
| 진입 | GET /api/v1/runs/current 1회 → run이 있으면 그 실행으로 조작부를 맞춘다(이 화면 종류가 아니면 시작 비활성과 "다른 실행" 링크만) · running · stopping이면 폴링 시작 |
| 폴링 | GET /api/v1/runs/current를 1초 간격(BFF no-store) — 동시 실행이 하나라 current가 곧 보고 있는 실행이다 · 앞 요청의 응답이 오기 전에 다음 요청을 보내지 않는다 · 종결 status를 받으면 멈춘다 · 화면을 떠나면 멈춘다(실행은 계속된다) · 폴링 중 current가 null을 내면(api 재기동으로 실행이 사라짐) 아래 404 행과 같이 "지난 실행 기록이 없어요" |
| 시작 202 | 응답의 실행 객체로 조작부를 바꾸고 폴링 시작 · 앞 실행의 종결 띠 · 지난번 글자를 지운다 |
| 시작 409 datagen.run_in_progress | details의 runId · type으로 조작부를 맞춘다(#4 단건 조회 1회 뒤 current 폴링) · **같은 종류**면 띠 "같은 측정이 이미 돌고 있어요 — 끝나면 다시 눌러 주세요"(자기 화면을 가리키지 않는다) · **다른 종류**면 띠 "다른 측정이 이미 돌고 있어요 — {화면} 화면에서 보기"(종류를 모르면 앞 절만) — 선택 칸에 다른 종류 링크 줄이 이미 있으면 409 띠를 생략한다 · 자동 재시도 없음 |
| 시작 400 common.validation_failed | **details.fields path로 가른다** — path purge(센서 데이터를 지우는 중 · 두 종류 모두)는 띠 "센서 데이터를 지우는 중이에요 — 끝난 뒤 다시 해 주세요" · path SW-09 · plant는 ⑤ 넣기 · 무결성만 받는 시작 전 거절이라 띠 문구가 [10_lab_screen.md](./10_lab_screen.md) §EXP-LAB 상태 오류 행에 있다 · 실행 객체가 생기지 않는다 · 그 밖 400은 매개변수 옆 "고른 값을 서버가 받지 않았어요 — 화면을 새로고침해 주세요" — 선택기가 화이트리스트 값만 내므로 여기 오면 화면과 서버의 목록이 어긋난 것이다(apps/web/lib/runs.ts refusedPath) |
| 중단 202 · 200 | 응답 객체로 조작부 갱신 · 202는 stopping으로 폴링 계속 · 200(이미 종결 — 멱등)은 곧바로 종결 표시 |
| 404 common.not_found(#4 · #5) | 실행이 api 메모리에서 사라졌다(api 재기동) — current 재조회 · 띠 "서버가 다시 켜져서 지난 실행 기록이 없어요"(api 재기동 · 실패로 기록하지 않는다) |
| 시작 · 중단 요청 실패(네트워크 · BFF 5xx) | 버튼을 요청 전 상태로 되돌린다("시작하는 중이에요…" · "멈추는 중이에요…" 해제) · 띠 "요청이 실패했어요 — 다시 눌러 주세요" · current 1회 재조회(요청이 실제로는 닿았을 수 있다) · 자동 재시도 없음 |
| 폴링 실패(네트워크 · BFF 5xx) | 마지막 실행 객체를 흐리게 유지 · 경과 틱을 멈춘다(끝났을지 모르는 실행을 계속 세지 않는다) · "상태를 못 읽었어요 — 다시 읽는 중이에요" · 1초 간격 재시도 계속 |

- 검산: 사건 = **9**
- **화면을 떠나도 실행은 멈추지 않는다(B형).** 결론 — 실행 주체는 api 프로세스이고 이탈 · 새로고침 · 탭 닫기는 중단 요청을 보내지 않는다. 반대 시나리오 — 이탈을 중단으로 삼으면 새로고침 한 번에 몇 분짜리 실행이 정리 단계로 끝나 시연이 날아가고, 다른 화면으로 옮겨 흐름을 보려던 조작이 실행을 죽인다. 파생 지침 — 멈추려면 중단 버튼을 누르고, 다시 들어오면 current가 진행 중 실행을 되찾는다. 다른 탭 · 다른 사용자가 시작한 실행도 current가 하나라 같은 조작부에 보인다.
- 호출 표면 4(POST /api/v1/runs · GET /api/v1/runs/current · GET /api/v1/runs/{runId} · POST /api/v1/runs/{runId}/stop)는 각 화면의 §호출 표면 · 갱신 표가 센다 — 이 절은 세지 않는다.
