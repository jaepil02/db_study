이 문서는 웹에 남은 화면 두 개를 명세한다(D-14). 두 화면은 학습 목표 ①(저장소 선택의 근거)의 앞면과 뒷면에 답한다 — **EXP-PERF는 "같은 데이터를 PostgreSQL과 ClickHouse에 넣으면 어떤 데이터에 무엇이 맞는가"**, **EXP-FLOW는 "데이터가 Redis를 거쳐 어느 DB로 얼마나 가고, 모아서 처리하는 길과 하나씩 처리하는 길이 어떻게 다른가"**다. 두 화면은 기록 · 관찰 표시에 더해 **실행 조작부** 하나씩을 갖는다 — EXP-PERF는 두 저장소에 같은 규모 · 같은 질문을 라이브로 돌리는 perf 실행(GEN-11), EXP-FLOW는 대용량 발행과 업무 명령을 함께 흘리는 flow 실행(GEN-12)을 시작 · 중단하고 완료와 소요 시간을 보인다. 조작부가 시작하는 것은 이 두 실행 종류뿐이고 저장소 정지 같은 장애 주입 버튼은 없다 — 장애는 호스트 셸의 스크립트가 일으킨다.

**두 화면은 한 장이다(D-15 — 사용자 지시 2026-10-03 · 학습자 눈높이 · 한 화면).** 1440 × 900에서 세로 · 가로 스크롤 · 서랍 · 아코디언 · 탭이 없고, 맨 위의 의도 한 줄 → 구역마다 결론 문장 → 그림 하나 → "왜?" 한두 줄 → 회색 각주 순서로 읽힌다(원칙 정본 [01_standards.md](./01_standards.md) §한 화면 원칙). **화면에서 뺀 것과 각주로 옮긴 것을 가른다** — 배수 지도 · 3회 값 · 원리 증거 · 저장 비용 · 적재 계단 · 분배 표 · 최근 목록 · 저장소 상세 · 실행 단계 · 결과 표는 화면에서 뺐고 그 표시 계약도 지웠다. 정확성 계약 넷 — **지어낸 값 금지 · 승패는 3회 모두 같을 때만 · 시간은 참고값이라는 표기 · 4요소(커밋 해시 · 메모리 프로파일 · 용량 티어 · 스위치 상태)** — 과 판독 계수는 지우지 않고 각주 한 줄과 각주 툴팁으로 자리만 옮겼다. 기록 · 판독기 · api 표면은 그대로다. **다듬기(사용자 지시 2026-10-03 · .omc/plans/web-ux-polish.md)는 구성 · 기능 · 문장 뜻을 바꾸지 않았다** — 글꼴 · 글자 단계 · 숫자 폭 · 묶음 · 테두리 · 포커스 · 움직임 같은 공통 시각 규격은 [01_standards.md](./01_standards.md) §글자와 화면 표면이 갖고, 이 문서는 화면마다 그 규격이 놓인 자리와 크기를 적는다.

**두 화면의 수치는 측정 기록이 아니다.** EXP-PERF 센서 데이터 구역은 기록을 읽어 그리지만 격자 기록 048~053이 전부 discarded라 걸린 시간은 **참고값**이고(리드 판정 1 · [../10_observability/04_experiment_protocol.md](../10_observability/04_experiment_protocol.md) §기록 상태와 정정의 화면 참고값 예외), 업무 데이터 구역은 valid 기록만 그리되 관찰 보조이며, EXP-FLOW는 지금 돌고 있는 시스템의 순간 관찰이다. 정본 문장이 인용하는 것은 기록의 구조 사실 · 결정적 값뿐이고 화면 수치를 인용하지 않는다. **라이브 실행 결과도 기록이 아니다** — 앱(api)을 거쳐 재므로 결과에 항상 라이브 표지를 달고, 측정 기록(docs/measurements)을 만들지 않으며, 곡선에서 기록 계열과 다른 마커로 그린다(대조 쿼리는 앱을 거치지 않는다는 판정 — [../02_features/12_permission_matrix.md](../02_features/12_permission_matrix.md) §실험 수행자와 실험 콘솔 — 과 충돌하지 않는 이유).

- **두 구역은 상자 두 겹이 아니라 머리 띠 + 본문 한 겹이다(다듬기 §2.2).** 구역 이름 · 결론은 연한 저장소 바탕의 머리 띠에, 그림 · 줄은 1px 중립 테두리 한 겹의 흰 본문에 둔다 — 본문 안 묶음(그림 1 · 그림 2 · 왜? · 업무 네 줄)은 가는 줄로 가르고 상자를 다시 두르지 않는다(카드 안 카드 금지 · 정본 [01_standards.md](./01_standards.md) §글자와 화면 표면). 옛 배치(2px 색 테두리 열 안에 상황 카드 4 · 왜? 카드 2 상자)는 무엇이 묶음인지 흐리고 시선이 테두리에 걸렸다.
- **화면에는 코드가 없다.** Q1~Q5 · I1 · I2 · EXP-NN · SW-NN · 기록 번호 · 10^N은 툴팁에만 있고 화면은 질문 이름("센서 1개 · 7일") · 행 수("10억 행") · "CH 7.8배" 같은 쉬운 말을 쓴다(용어표 정본 [01_standards.md](./01_standards.md) §한 화면 원칙). 와이어프레임의 ○는 기록에서 읽어 채울 자리이고 화면 명세는 수치를 소유하지 않는다.
- **승패는 3번 모두 같을 때만 그린다.** 그림 1의 방향(왼쪽 PG · 오른쪽 CH)은 그 점의 반복 3회 우열이 모두 같을 때(P4)만 서고, 엇갈리면 방향 없이 "승패 미정"이다 — 배수 글자는 중앙값 비라 참고값이고, 각주 한 줄이 그 사실을 늘 말한다.
- **"여기서 역전!"은 기록의 구조 판정이다 — 선의 교차가 아니다.** 표지 자리는 원천 기록 structuralRanges의 구간(반복 3회 우열 일치)이고, 곡선의 교차점과 표지가 어긋나면 표지가 맞다(중앙값 교차는 한 반복의 흔들림으로도 움직인다).
- **내 측정 점은 결론에 섞이지 않는다.** 라이브 실행 값은 그림 2 위에 다른 마커로만 겹치고 그림 1 · 역전 표지 · 왜? 두 줄에 들어가지 않는다 — 반복 3회 웜 · 앱 경유 · 단계 5 격자의 앞부분(정밀화 점 없음)이라 구조 판정의 조건을 갖추지 못한다.
- **업무 데이터 구역에는 직접 재 보기가 없다**(D-14 결정 3). 업무 워크로드 실행 표면이 없어 붙이려면 api 표면을 새로 만들어야 하고, 기록 판독만으로 결론이 선다 — 머리 버튼 하나가 센서 데이터 쪽 perf 실행만 시작한다.

- **버퍼 블록은 hit + read다**(05_data_stores/10 §원리 대응의 통일). read만 쓰면 웜에서 0에 가까워져 B-tree 페이지 방문 같은 구조가 사라진다. 몫이 100%를 넘는 질문(설비 1대 · 하루 — Q3 I2)은 방문 횟수라서다 — 카드 툴팁에 그 문장을 싣는다.
- **원리 문장 상수는 판독하지 않고 옮긴 상수다.** 기록에서 계산하는 것은 수치뿐이고 구조 문장은 05_data_stores/10의 표가 출처다 — 쉬운 말로 옮겨도 사실은 바꾸지 않고, 판독기 상수가 같은 변경 단위에서 따라간다.

### 판독 규칙

센서 데이터 구역은 BFF 판독 규칙([../10_observability/04_experiment_protocol.md](../10_observability/04_experiment_protocol.md) §BFF 판독 규칙) 1 · 2 · 4 · 6 · 7을 따르고 규칙 3(status valid)과 규칙 5(편차)를 **참고값 표기로 바꾼다**(리드 판정 1). 업무 데이터 구역은 같은 규칙 1~5 · 7을 따르고 규칙 6의 자리만 다르다(아래 업무 1).

| # | 규칙 | 어기면 |
|:--:|------|------|
| P1 | **원천 기록** — exp에 EXP-01~05가 있고 · structuralRanges가 배열이며 · 4요소가 완비된(규칙 4 · 도구 컨테이너 경로의 memoryLimitMb null은 run.memoryLimitSource가 공백 아닌 문자열이면 충족) 판독 가능 기록 가운데 **기록 번호가 가장 큰 하나** · 규칙 3의 status 조건(valid)은 적용하지 않되 **superseded(status superseded 또는 다른 valid 기록의 supersedes 대상)는 원천에서 뺀다** · 규칙 5(편차)는 적용하지 않는다 — 구조 판정은 편차 폐기를 적용하지 않는 판정이다 · structuralRanges가 배열이 아닌 대조 기록은 원천 후보가 아니고 판독 계수 "형식이 어긋난 structuralRanges 기록 N"으로 센다(각주 툴팁 — 0이어도 보인다) | 여러 기록의 구간을 섞으면 서로 다른 격자 · 정밀화 단계의 구간이 한 화면에 겹치고, 원천 번호가 없으면 어느 기록의 판정인지 되짚을 수 없다 |
| P2 | **단계 기록** — 원천 기록 conditions.stageRecords가 가리키는 기록만 곡선 · 왜? 두 줄에 더한다 · 목록이 없으면 원천 기록의 점만 그리고 각주 툴팁에 "단계 기록 목록 없음" · 목록의 기록이 superseded · 판독 불가 · 4요소 누락이면 빼고 센다 | 1차 격자(035~039 — 역방향 적재로 BRIN이 무너진 조건)의 점이 같은 선에 섞여 가짜 꺾임이 생긴다 |
| P3 | **참고값 표기** — status discarded 점도 그리되 선 모양으로 가르지 않는다 · 걸린 시간이 참고값이라는 사실은 각주 고정 문구 한 자리가 맡는다(§표시 계약 시간 참고값) · 편차 초과 점(repeat.threshold를 넘는 점 편차)은 점 툴팁에 "3번 값의 차이가 기준보다 큼" | 폐기 기록의 크기가 정본 곡선으로 읽히거나, 반대로 격자 실측 전체가 화면에서 사라진다 |
| P4 | **점 단위 우열** — dominance winner(unanimous true) 또는 pairVerdicts structuralWinner가 있으면 그 쪽 · null이면 미정 · 저장소 값은 한 모양으로 정규화한다(dominance의 reps · winner "CH" → clickhouse · "PG" → postgresql — pairVerdicts · structuralRanges · crossovers의 값) · 053 정밀화 점은 structuralRanges 행에서 계산(undetermined에 그 점 지수가 있으면 미정 · crossover가 있으면 a 이하는 from · b 이상은 to · null이면 winner · 방향을 찾지 못하면 미정 — 툴팁 "방향 미상") · 행 수 → 지수는 log10을 0.25 단위로 반올림 | 중앙값 비로 승패를 정하면 반복 사이에 뒤집힌 점이 한쪽 우세로 보인다 |

| 업무 1 | **규칙 6의 자리** — reverse는 exp에 EXP-40~44가 있는 기록만 · 행의 exp가 기록 머리 exp에 없으면 형식 위반 행 | 다른 실험의 폐기 · 누락이 이 구역 계수에 섞이거나 다른 실험 값이 카드에 들어간다 |
| 업무 2 | **같은 키 중복** — 같은 키(exp · op · store · variant · scale · concurrency · rate · read · metric)의 행이 여러 기록에 있으면 기록 번호가 뒤인 행만 남기고 센다 | 정정 없이 다시 잰 기록과 옛 기록이 한 칸에 겹친다 |

- 검산: 판독 = 센서 6(P1~P6) + 업무 2 = **8**
- **auxPoints(Q5x — 조건 없는 count)를 빼는 이유** — ClickHouse는 파트 메타데이터로 답해 데이터를 읽지 않는다(05_data_stores/10 §동일 쿼리 5종 A형). 한 축에 두면 "ClickHouse 전체 훑기 1 ms"로 읽힌다.
- **EXP-45(streamSteps) 판독 규칙 둘(판정 기준 · 판정 제외 계단)은 화면에서 적재 계단을 뺀 D-15로 이 표에서 빠졌다.** 판정 문장의 정본은 [../10_observability/04_experiment_protocol.md](../10_observability/04_experiment_protocol.md) §기계 판독 블록 streamSteps 행이고 러너 · 판독기가 그대로 공유한다.

- **기록 읽기는 폴링하지 않는다.** 기록은 커밋으로만 바뀐다 — 진입이면 충분하고, 폴링은 파일 읽기를 반복할 뿐이다. 1초 폴링은 실행 조작부의 #3(current) 하나이고 running · stopping 동안뿐이다. health도 폴링하지 않는다 — 스위치는 환경변수 + 재기동이라(D-06) 화면을 보는 동안 바뀌지 않는다.
- **캐시 층** — 브라우저 쿼리 키 measurements · perf · staleTime 0(서버 층 없음 · BFF no-store) · gcTime은 시계열 행과 같은 짧은 값(현행값 정본 [../09_tech_stack/01_frontend.md](../09_tech_stack/01_frontend.md) §gcTime) — 응답이 수백 KB라서다(정밀화 180점 + 단계 30점 × 5). 업무 보기 measurements · evidence · staleTime 0. health obs · health · staleTime 0. 실행 쿼리 키 runs · current · runs · {runId} · staleTime 0 · 서버 층 없음(실행 상태는 api 인스턴스 메모리 · BFF no-store) — [01_standards.md](./01_standards.md) §갱신 주기와 캐시 층 정렬의 라이브 실행 행.

### 스위치 영향

- 기록 판독은 현재 기동의 스위치가 아니라 기록에 박힌 switches를 각주 툴팁으로 보인다. 격자 기록은 SW-09 off · api 정지 조건(도구 컨테이너 경로)이다.
- 각주 툴팁의 지금 기동 칸은 health switches 전수를 그대로 보인다 — 스위치가 늘어도 칸 모양은 그대로이고, 기본값과 다른 스위치는 강조한다(옛 셸 실험 조건 배지의 역할 — D-14 결정 2).
- 라이브 실행도 스위치와 무관하다 — 실행 수명 객체(plc.run_perf_raw · run_perf_raw)를 저장소 안 서버 측 생성으로 채우고 적재 경로(ING) · 조회 캐시(cache:q)를 지나지 않는다(기전 정본 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md)). 격자 기록과 달리 api가 돌고 있는 조건이라 내 측정 점이 기록 선과 다른 것은 결함이 아니다 — 라이브 표지가 그 차이를 알린다.

- **두 길을 한 그림에 위아래로 둔다(A형).** 통념은 "Redis를 거치면 비동기라 쓴 직후 조회가 옛 값을 본다"는 것이다. 부정 — 업무 명령은 api가 워커의 커밋 결과(biz:result · ch:bizreply)를 받은 뒤에만 기존 상태 코드로 응답하고, 워커는 무효화를 결과보다 먼저 한다([../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) §업무 명령 경로). 진짜 축은 **같은 Redis Stream이라도 단위와 순서 보장이 다르다**는 것이다 — 센서 길은 창마다 묶은 배치를 처리량 위주로 넣고, 업무 길은 명령 하나를 소비자 하나가 순서대로 트랜잭션에 넣는다. 대체 경로 — 센서 점은 행 수만큼 크게, 업무 점은 명령 하나로 작게 그리고, "모아서 대 하나씩" 막대가 같은 차이를 처리 시간으로 한 번 더 보인다.
- **A형 — 조회는 대기줄에 서지 않는다.** 통념은 "모든 요청은 Redis 대기줄을 거친다"는 것이다. 부정 — 대기줄을 타는 것은 위 두 줄(센서 · 업무 쓰기)뿐이다. 진짜 축은 **즉답이 필요한가**다 — 조회는 사람이 답을 기다리므로 줄을 세우면 앞 요청을 기다린 만큼 느려지기만 한다. 대체 경로 — 조회에서 Redis는 **먼저 확인하는 사본 자리**(칸 ⑤)다 — 있으면 바로 답하고 없을 때만 ClickHouse · PostgreSQL에 가서 사본을 담는다(기전 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md) §흐름 시연 실행 · [../06_pipeline/07_business_crud.md](../06_pipeline/07_business_crud.md) §읽기 · 쓰기 경로). 그래서 조회 줄에는 점이 아니라 초당 수와 비율만 있다 — 조회는 flow 프레임 요약을 만들지 않는다.
- **점은 실제 묶음 하나다 — 연출이 아니다.** 점 하나가 flow 프레임의 요약 하나이고, 단계마다 머무는 시간의 비율이 그 묶음의 실제 단계 ms 비율이다. 요약이 오지 않으면 점도 없다 — 멈춘 그림이 곧 멈춘 적재다.
- **노드 이름을 쉬운 말로 바꿔도 단계는 남는다.** XACK · MV(tag_1m) · flusher · WS → 브라우저 · BFF는 노드로 그리지 않지만 배치 점의 단계 순서(XACK 포함)는 그대로 지나가고, 알람 세 갈래(판정 전수 · 전이 · 상태)는 저장소 노드 안 숫자로 들어갔다(§표시 계약 노드와 숫자).
- **와이어프레임의 ○는 자리 예시다** — 실제 값은 §데이터 원천과 숫자 4 대응 표가 가리키는 flow 프레임 · 메트릭 필드에서 읽는다.

- 검산: 요소 = 관찰 11(흐름 구독 표지 · 화면 의도 · 숫자 4 · 흐름도 · 조회 줄 · 배치 점 · 선 굵기 · 업무 점 · 왜 나눌까 세 칸 · 모아서 대 하나씩 · 각주) + 실행 조작부 6(매개변수 선택 · 시작 · 중단 · 상태 칩 · 진행 띠 · 종결 표시) = **17** · 이 화면이 주 화면인 기능 = GEN-12(실행 조작부 요소 6) · RLT-05 · 07(흐름 구독 표지) · OBS-01 · 02 · 03(흐름도 DB 노드 · OBS-01은 조회 줄도) · OBS-04(숫자 4 측정 → 저장까지) · OBS-05 · 06(각주) = **9** · 흐름 이벤트만 그리는 요소 5(배치 점 · 선 굵기 · 업무 점 · 왜 나눌까 세 칸 · 모아서 대 하나씩)는 기능 ID가 없고, 숫자 4 · 흐름도 2는 GET /metrics 값도 그려 OBS를 병기한다 · 조회 줄은 GET /metrics 값만 그려 OBS-01이고, 조회 결과를 내는 TSQ · RLT · MST 기능은 표면을 이 화면이 부르지 않으므로(실행이 프로세스 안에서 부른다) 주 · 보조로 세지 않는다 · 흐름 이벤트에 새 기능 ID를 만들지 않는다(리드 판정 1) · 주 · 보조 분류 정본 [02_traceability.md](./02_traceability.md)
- 검산: 흐름도 노드 = 어디서 오나 3(공장 센서 · 사람의 업무 요청 · 조회 요청) + Redis 칸 5(센서 대기줄 stream:plc:raw · 지금 값 · 업무 대기줄 stream:biz:cmd · 결과 알림 · 조회 사본 cache:q · cache:devlist) + 처리 2(모아서 한 번에 저장 · 하나씩 순서대로 처리) + 저장 DB 2(ClickHouse · PostgreSQL) = **12** · 조회 줄은 저장 DB 노드를 새로 두지 않고 위 둘을 다시 쓴다
- **화면에서 뺀 것** — 지표 띠 6의 보조 줄(판정 · 거절률 · 백프레셔 단계) · 분배 표(5 × 3) · 처리 방식 비교의 단계별 색 범례 · 서랍 5(최근 20배치 · 최근 20명령 · 저장소 상세 · 지연(E2E) 분위수 3 · 측정 조건) · 결과 표 · 실행 단계 목록은 D-15로 빠졌다. flow 프레임 · 메트릭 · 링 버퍼 20은 그대로이고, 다시 보이려면 이 표에 행을 먼저 둔다.
- **알람을 센서 길에 그리는 이유** — 알람 이벤트는 측정 사실에서 파생된 업무 데이터다. 판정 전수는 ClickHouse alarm_eval, 상태 전이만 PostgreSQL alarm_event로 간다([../06_pipeline/04_routing.md](../06_pipeline/04_routing.md) §분기 판정 트리) — 그래서 PostgreSQL로 가는 센서 갈래 이름이 "알람이 바뀔 때만"이고 표지가 드문 것이 설계의 결과다.
- **알람 확인(ACK)은 업무 길에 그린다.** ②계층 행을 사람이 ③의 방식으로 쓰는 유일한 자리라서다(04_routing) — 명령 kind alarm.event.ack로 같은 명령 스트림을 탄다.

- **정밀 측정 중에는 이 화면을 닫는다(B형).** 결론 — 구독자가 있으면 워커가 배치 · 명령마다 요약을 만들고 Pub/Sub에 한 번 더 발행한다. 반대 시나리오 — 화면을 띄운 채 EXP-45 계단을 재면 PUBLISH 비용이 flusher 후속 구간에 섞인다. 파생 지침 — 구독자가 없으면(구독 중 표지 cache:flow:subscribed가 없거나 읽지 못하면) 발행 자체를 하지 않고([../07_api/11_websocket.md](../07_api/11_websocket.md) §흐름 이벤트 발행 조건), 실험 러너는 구독 표지가 없는 상태에서 측정 창을 연다 — 각주 툴팁이 이 문장을 싣는다.

### 비고

- 흐름도는 SVG 직접 그리기다 — 시계열 차트가 아니라 uPlot · ECharts 대상이 아니다. 모아서 대 하나씩 막대도 ECharts가 아니라 HTML 막대다(막대 둘 · 같은 시작점 · 사람이 읽는 시간 글자) — **이 화면은 ECharts를 쓰지 않는다.**
- **1280 × 800 — 흐름도 배율 1을 지키고 본문 스크롤을 허용한다(다듬기 §7.1 R4).** 새로 연 창은 사이드바가 레일(56)로 시작해 가로가 흐름도 원래 폭(viewBox 1126)보다 넓고, 흐름도 최소 높이 454(viewBox 440 + 테두리 · 세로 여백 14)와 화면 최소 높이 750(52 + 64 + 454 + 124 + 24 + 칸 사이 8 × 4)이 세로 배율을 1로 받친다 — 바닥이 없으면 세로 704에 흐름도 408이라 0.895배로 줄어 노드 글자가 12px 아래로 내려간다. 대가는 본문 스크롤(약 46px · 진행 띠가 있으면 더)이고, 1440 × 900은 흐름도가 466 ~ 508이라 이 바닥에 닿지 않는다(스크롤 0). **사용자가 1280에서 사이드바를 직접 펼치면 그 선택이 이기고 흐름도 배율 0.858은 허용 예외다**(정본 [01_standards.md](./01_standards.md) §요청 경로와 공통 셸). 1920 × 1080은 공통 최대 폭 안에서 가로에 묶여 약 1.23배다.
- 링 버퍼 20은 화면 상수다 — 메모리는 배치 요약 20건 · 업무 요약 20건이고, 모아서 대 하나씩 막대가 이 링 버퍼를 표본으로 쓴다.
- 실행 조작부의 시작 · 종료 시각은 초까지다 — EXP-PERF 비고와 같은 예외([01_standards.md](./01_standards.md) §시각 표시 표시 형식 행).
- **flow 실행을 띄운 채 정밀 측정을 하지 않는다.** 실행은 적재 경로에 실제 부하를 싣는다 — 동시 실행 1 제한이 perf 실행과의 겹침만 막고, 호스트 스크립트 · k6 부하와의 겹침은 막지 않는다 — 측정 창을 열기 전에 진행 띠가 없는지 확인한다.

## 실행 패널 — 두 화면 공통 규칙

EXP-PERF(type perf · GEN-11)와 EXP-FLOW(type flow · GEN-12)의 실행 조작부는 매개변수 · 단계만 다르고 아래 규칙을 함께 따른다. **실행은 두 종류를 합쳐 한 번에 하나다** — 두 실행이 서로의 측정을 오염시키므로 api가 동시 실행을 409로 막는다([../07_api/09_datagen.md](../07_api/09_datagen.md) · 기전 [../06_pipeline/10_datagen_inject.md](../06_pipeline/10_datagen_inject.md)). 실행 상태는 api 인스턴스 메모리에만 있어 api를 재기동하면 사라진다 — 화면은 이것을 실패가 아니라 "지난 실행 기록이 없어요"로 보인다.

### 배치

| 자리 | 놓이는 것 | 보이는 때 |
|------|------|------|
| 셸 머리 동작 자리(오른쪽) | 왼쪽부터 **"지난번 …" 글자**(12 회색 · 실패면 빨강 · 고정 폭 숫자 · 한 줄로 자르고 상세는 툴팁) · 머리 버튼(EXP-PERF "▶ 내 컴퓨터에서 직접 재 보기" · EXP-FLOW "▶ 직접 보내 보기" — 재생 기호는 그린 아이콘) · 상태 칩 | 머리 버튼은 항상 · 상태 칩은 실행 중 · 멈추는 중에만(종결 뒤 숨김) · 지난번 글자는 이 화면 종류의 종결 실행이 있고 진행 띠가 그 실행을 그리지 않을 때만(같은 말 두 자리 금지) |
| 선택 칸(머리 버튼이 여는 겹침 칸 — 본문을 밀지 않는다) | 매개변수 선택 · 시작 · 예상 디스크 경고(EXP-PERF) · "다른 측정이 이미 돌고 있어요" 링크 · 역할 안내 · "아직 재 보지 않았어요"(EXP-FLOW는 "아직 보내 보지 않았어요") | 버튼을 누를 때 · 시작 202를 받으면 닫힌다 |
| 진행 띠(본문 의도 줄 아래 얇은 한 줄) | 지금 단계(쉬운 말) · 단계 n/m(EXP-PERF) · 진행 막대(EXP-FLOW) · 경과 시간 · 중단(실행 중에만) · 방금 끝난 실행의 종결 띠(머리 "지난번 직접 재 보기" · "지난번 보내 보기") · 라이브 표지 · 409 · 404 · 요청 실패 · 폴링 실패 문구 · 띠 툴팁에 시작 · 종료 시각 | 실행이 running · stopping이거나 **이 화면에서 지켜보던 실행이 방금 끝났을 때(종결 뒤 30초)** · 다른 종류가 진행 중이면 "다른 측정이 이미 돌고 있어요" 한 줄과 그 화면 링크 · 요청 사건 · 폴링 실패 문구가 있을 때 |

- 검산: 자리 = **3**
- **진행 띠는 본문을 스크롤로 밀지 않는 높이 하나다.** 띠가 생기면(한 줄 24 + 여백 · 테두리 = 34) EXP-PERF는 그림 2가, EXP-FLOW는 흐름도가 높이를 줄여 흡수한다([01_standards.md](./01_standards.md) §한 화면 원칙). 실행 중이 아니고 방금 끝난 실행도 없고 띠 문구도 없으면 띠 자체가 없다.
- **"지난번 …" 글자는 키보드 · 낭독기로도 상세에 닿는다(다듬기 §7.1 R12).** 마우스는 툴팁(title)으로, 키보드는 탭으로 그 글자에 닿고(tabIndex 0 · 누르는 동작은 없다) 낭독기는 숨은 상세 문장(sr-only — 툴팁과 같은 내용 · 줄을 " · "로 이음)을 설명(aria-describedby)으로 읽는다 — 툴팁에만 두면 마우스 없는 사용자는 지난 결과의 결말 · 시각을 볼 길이 없다. 글자 모양 — 완료 EXP-PERF "지난번 100만 행까지 · 3.0초"(걸린 시간이 답) · EXP-FLOW "지난번 초당 1,000개 · 30초 · 완료"(보낸 시간은 이미 범위에 있다) · 중단 "… · 중단됨" · 실패 "… · 실패" · 범위를 모르면 머리 낱말("지난번 직접 재 보기" · "지난번 보내 보기")로 시작한다.
- **단계 목록 · 결과 표를 그리지 않는다.** 결과는 EXP-PERF는 그림 2의 내 측정 점이, EXP-FLOW는 실행 동안의 흐름도가 보인다 — 단계 key · 단계별 소요 · publish detail은 띠 툴팁에만 둔다.

### 버튼 상태

| 요소 | 활성 조건 | 비활성일 때 표시 |
|------|------|------|
| 매개변수 선택 | current를 받았고 어떤 실행도 running · stopping이 아니다 | 진행 중이면 잠금 · 그 실행이 이 화면 종류면 그 params를 보인다 |
| 시작 | current를 받았고 · 어떤 실행도 running · stopping이 아니고 · 시작 요청이 응답을 기다리는 중이 아니고 · S7 뒤 역할이 ENGINEER · ADMIN | 다른 종류가 진행 중 — "다른 측정이 이미 돌고 있어요 — 분산 처리 모니터링 화면에서 보기" 링크(EXP-PERF에서는 /monitoring · EXP-FLOW에서는 "… 성능 비교 화면에서 보기" · /performance) · 같은 종류가 진행 중 — 비활성(중단만 켜진다) · 요청 중 — "시작하는 중이에요…"(두 번 눌러 409를 스스로 부르지 않게) · 역할 없음 — "엔지니어 · 관리자만 실행할 수 있어요" · 읽기 전(머리 버튼 툴팁) — "실행 상태를 읽는 중이에요" |
| 중단 | 이 화면 종류의 실행이 running · S7 뒤 역할이 ENGINEER · ADMIN | 누른 직후 응답 전부터 "멈추는 중이에요…" · status stopping이면 "멈추는 중이에요…" 비활성 · **종결이면 버튼을 숨긴다(비활성 아님 — 종결 띠 · 지난번 글자가 결말을 대신 말한다)** · 다른 종류 · 실행 없음이면 비활성 · 역할 없음 — "엔지니어 · 관리자만 실행할 수 있어요"(조작부 상태는 보인다) |

- 검산: 버튼 · 선택 요소 = **3**
- **시작은 current를 받기 전에 켜지지 않는다.** 진입 직후 켜 두면 다른 탭 · 다른 화면이 시작한 실행을 모르는 채 눌려 409가 사용자 조작의 첫 응답이 된다. 머리 버튼도 current를 받기 전에는 선택 칸을 열지 않는다.

### 상태 칩과 종결 표시

| status | 상태 칩 | 띠 문구 | 진행 띠 단계 칸 |
|------|------|------|------|
| running | "실행 중"(진행 표지) — 종결 전에만 그린다 | 없음 — 경과 시간이 1초마다 움직인다 | 지금 단계 이름 · n/m |
| stopping | "멈추는 중" | "멈추는 중이에요… — 하던 단계를 멈추고 정리하고 있어요"(단계 문장 — **진행 막대를 숨기고 띠 · 경과 · 버튼만** 둔다) | 취소가 걸린 단계 이름 |
| completed | 없음(숨김) | **"완료 — 걸린 시간 3분 12.4초"**(툴팁 — 종료 10:23:17 KST) | 없음 |
| stopped | 없음(숨김) | "중단됨 — 걸린 시간 1분 5.0초"(툴팁 첫 줄 — error가 있으면 "정리하다 실패했어요 — {error.message}" 전문 · 다음 줄 종료 시각) · error가 있으면(정리 실패) 뒤에 "정리하다 실패했어요({error.message})" | 멈춘 단계 이름 · 정리 단계는 중단이어도 돈다 |
| failed | 없음(숨김) | "실패했어요 — {error.message} · 걸린 시간 N분 N.N초"(툴팁 첫 줄 "실패 원인 — {error.message}" 전문 · 다음 줄 종료 시각) · 원인 메시지가 없으면 "원인을 알 수 없어요" · error.code가 있으면 툴팁에 코드(null 허용 — 실패 원인은 실행 객체 안의 관찰값이다) | 실패한 단계 이름 |

- **띠 글자는 잘린다(truncate).** 긴 오류 메시지는 띠 안에서 한 줄로 자르고 전문은 위 툴팁 첫 줄이 갖는다 — 띠가 두 줄이 되면 본문을 스크롤로 민다.
- **종결 뒤에는 칩과 중단 버튼을 숨긴다.** 종결 띠 머리가 "지난번 직접 재 보기"(EXP-FLOW는 "지난번 보내 보기")로 무엇을 잰 결과인지 먼저 말하고 종결 문구 · 범위("1천만 행까지" · "초당 10,000개 · 60초")와 "내 측정(참고용)" 라이브 표지가 이어진다. 색은 띠가 갖는다 — 완료 초록 · 중단됨 회색 · 실패 빨강. 같은 결과를 칩 · 띠 · 지난번 글자 중 두 자리가 함께 말하지 않는다.
- 검산: status = **5**(전송 enum — 정본 [../11_glossary/03_enums_state_machines.md](../11_glossary/03_enums_state_machines.md)) · 종결 = completed · stopped · failed = **3**
- **종결 결과는 다음 시작 전까지 남는다 — 자리만 접힌다(B형 · 다듬기 §2.1).** 결론 — 이 화면에서 지켜보던 실행이 끝나면 종결 띠가 30초 동안 진행 띠 자리에 서고, 그 뒤(또는 이미 끝난 실행을 열면 처음부터) 띠는 애니메이션 없이 사라지고 셸 머리의 "지난번 …" 글자가 같은 결말을 다음 시작 전까지 말한다 — 접힘은 서랍이 아니다(여는 동작이 없고 상세는 툴팁 · 설명). 반대 시나리오 ① — 결과를 지우면 몇 분짜리 1억 행 실행이 자리를 비운 사이 끝났을 때 내 측정 점만 남아 끝났는지 멈췄는지 가를 수 없다 ② — 띠를 계속 두면 옛 결과가 본문 맨 위 한 줄(가장 좋은 자리)을 차지해 첫 시선이 지난 실행에 간다. 파생 지침 — api도 마지막으로 끝난 실행을 다음 시작 전까지 current로 내므로 다시 들어오면 지난번 글자가 보인다 · 30초는 화면 상수다(lib/runs RECENT_END_MS).
- 실패 띠는 오류 행이 아니다 — 실행 표면은 200으로 실행 객체를 냈고 failed는 그 안의 결과다. 표면 자체의 오류(409 · 404 · 400 · 5xx)만 §갱신과 응답 처리가 다룬다.

### 경과 시간

| 자리 | 값 | 갱신 | 형식 |
|------|------|------|------|
| 진행 중(running · stopping) | 마지막 응답의 elapsedMs + 그 응답을 받은 뒤 흐른 브라우저 단조 시계 | 1초 틱 · 응답이 올 때마다 기준을 서버 값으로 다시 맞춘다 | "1분 42초"(1초 단위) · 1분 미만 "42초" · 1시간 이상 "1시간 3분 12초" |
| 종결 | endedAt − startedAt(서버 elapsedMs와 같다) | 고정 | "3분 12.4초"(0.1초 단위 · 버림) · 1분 미만 "12.4초" · 1시간 이상 "1시간 3분 12.4초" |

- 검산: 자리 = **2** — 단계별 소요는 화면에 그리지 않는다(띠 툴팁의 단계 key 옆 소요는 종결 형식을 따른다)
- **경과 시간은 브라우저가 startedAt을 빼서 만들지 않는다(A형).** 통념은 "시작 시각을 알면 지금 시각에서 빼면 된다"는 것이다. 부정 — 브라우저 시계와 서버 시계의 차이(수 초일 수 있다)가 그대로 경과에 섞이고, 종결 뒤 총 소요와 진행 중 경과가 서로 다른 시계로 계산돼 완료 순간 숫자가 뒤로 튄다. 진짜 축은 **서버가 계산한 elapsedMs 하나를 기준으로 두고 브라우저는 그 뒤에 흐른 길이만 더한다**는 것이다. 대체 경로 — 종결 뒤에는 endedAt − startedAt 하나만 보인다.
- 시작 · 종료 시각은 UTC ISO 8601 Z로 와서 KST로 한 번 변환한다([01_standards.md](./01_standards.md) §시각 표시). 경과 시간은 시각이 아니라 길이라 시간대 변환이 없다.

### 갱신과 응답 처리

| 사건 | 처리 |
|------|------|
| 진입 | GET /api/v1/runs/current 1회 → run이 있으면 그 실행으로 조작부를 맞춘다(이 화면 종류가 아니면 시작 비활성과 "다른 실행" 링크만) · running · stopping이면 폴링 시작 · S7 뒤 OPERATOR도 current · 단건 조회로 조작부 상태를 본다(시작 · 중단만 비활성) |
| 폴링 | GET /api/v1/runs/current를 1초 간격(BFF no-store) — 동시 실행이 하나라 current가 곧 보고 있는 실행이다 · 앞 요청의 응답이 오기 전에 다음 요청을 보내지 않는다 · 종결 status를 받으면 멈춘다 · 화면을 떠나면 멈춘다(실행은 계속된다) · 폴링 중 current가 null을 내면(api 재기동으로 실행이 사라짐) 아래 404 행과 같이 "지난 실행 기록이 없어요" |
| 시작 202 | 응답의 실행 객체로 조작부를 바꾸고 폴링 시작 · 앞 실행의 종결 띠 · 지난번 글자 · 내 측정 점을 지운다 |
| 시작 409 datagen.run_in_progress | details의 runId · type으로 조작부를 맞춘다(#4 단건 조회 1회 뒤 current 폴링) · **같은 종류**면 띠 "같은 측정이 이미 돌고 있어요 — 끝나면 다시 눌러 주세요"(자기 화면을 가리키지 않는다) · **다른 종류**면 띠 "다른 측정이 이미 돌고 있어요 — {화면} 화면에서 보기"(종류를 모르면 앞 절만) — 선택 칸에 다른 종류 링크 줄이 이미 있으면 409 띠를 생략한다 · 자동 재시도 없음 |
| 시작 400 common.validation_failed | 매개변수 옆 "고른 값을 서버가 받지 않았어요 — 화면을 새로고침해 주세요" — 선택기가 화이트리스트 값만 내므로 여기 오면 화면과 서버의 목록이 어긋난 것이다 |
| 중단 202 · 200 | 응답 객체로 조작부 갱신 · 202는 stopping으로 폴링 계속 · 200(이미 종결 — 멱등)은 곧바로 종결 표시 |
| 404 common.not_found(#4 · #5) | 실행이 api 메모리에서 사라졌다(api 재기동) — current 재조회 · 띠 "서버가 다시 켜져서 지난 실행 기록이 없어요"(api 재기동 · 실패로 기록하지 않는다) |
| 시작 · 중단 요청 실패(네트워크 · BFF 5xx · auth.forbidden/403) | 버튼을 요청 전 상태로 되돌린다("시작하는 중이에요…" · "멈추는 중이에요…" 해제) · 띠 "요청이 실패했어요 — 다시 눌러 주세요"(403이면 "엔지니어 · 관리자만 실행할 수 있어요") · current 1회 재조회(요청이 실제로는 닿았을 수 있다) · 자동 재시도 없음 |
| 폴링 실패(네트워크 · BFF 5xx) | 마지막 실행 객체를 흐리게 유지 · 경과 틱을 멈춘다(끝났을지 모르는 실행을 계속 세지 않는다) · "상태를 못 읽었어요 — 다시 읽는 중이에요" · 1초 간격 재시도 계속 |

- 검산: 사건 = **9**
- **화면을 떠나도 실행은 멈추지 않는다(B형).** 결론 — 실행 주체는 api 프로세스이고 이탈 · 새로고침 · 탭 닫기는 중단 요청을 보내지 않는다. 반대 시나리오 — 이탈을 중단으로 삼으면 새로고침 한 번에 몇 분짜리 실행이 정리 단계로 끝나 시연이 날아가고, 다른 화면으로 옮겨 흐름을 보려던 조작이 실행을 죽인다. 파생 지침 — 멈추려면 중단 버튼을 누르고, 다시 들어오면 current가 진행 중 실행을 되찾는다. 다른 탭 · 다른 사용자가 시작한 실행도 current가 하나라 같은 조작부에 보인다.
- 호출 표면 4(POST /api/v1/runs · GET /api/v1/runs/current · GET /api/v1/runs/{runId} · POST /api/v1/runs/{runId}/stop)는 각 화면의 §호출 표면 · 갱신 표가 센다 — 이 절은 세지 않는다.
