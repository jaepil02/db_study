F-03과 F-07은 **Redis의 휘발 사본을 읽는** 두 흐름이다. F-03은 요청 · 응답(rt:latest HGETALL)이고 F-07은 발행 · 구독(ch:rt · ch:alarm → WebSocket)이다. 한 파일에 두지만 흐름 ID를 합치지 않는다 — 지연 목표(원본 목표 10 ms 대 500 ms)와 병목 지표(Redis ops 대 이벤트 루프)가 다르다([01_flow_inventory.md](./01_flow_inventory.md)).

**최신값은 중복 저장의 유일한 예외이고 진실은 ClickHouse다**(REQ-GLB-11). 그래서 이 문서의 모든 판정은 두 질문으로 끝난다 — Redis 사본이 ClickHouse보다 **뒤처질 때**(정지 · 빈 키) 무엇을 보여 주는가, 사본이 ClickHouse보다 **옛 값으로 덮일 때**(순서 역전) 무엇이 막는가. 쓰기 주체의 선택(SW-11)과 ClickHouse 중단 중의 비교는 [11_backpressure_failure.md](./11_backpressure_failure.md)가, 응답 필드 모양은 [../07_api/06_realtime.md](../07_api/06_realtime.md)(W5)가 갖는다.

## 최신값 조회 판정 트리

원본 최신값 시퀀스(원본 data_flow.md §5)를 요청 하나의 판정으로 옮긴다. 우측은 응답이다.

```plain
GET 설비 전체 최신값(브라우저 → api 직결)
├─ 인증 · 레이트 리밋(S7부터 · AUT-04 · AUT-06) ─────────────────── 401 · 429
├─ SW-02 off(ClickHouseLatestValueReader · 실험 전용) ─────────── ClickHouse argMax 점조회 → 200
├─ Redis 접속 불가 · 타임아웃 ─────────────────────────── 503 realtime.latest_unavailable
└─ HGETALL rt:latest:{device_id} 1회
   ├─ 필드 있음 ───────────────────────────────────────── STALE 판정 · 메타 부착 → 200
   └─ 키 없음
      ├─ 설비가 마스터에 없음 ──────────────────────────────────── 404 common.not_found
      └─ 설비가 마스터에 있음 → lock:rebuild:rt:{device_id} SET NX PX
         ├─ 락 획득 → 최근 창 argMax 복원
         │  ├─ 행 있음 ────────── 조건부 쓰기로 워밍 · 락 해제 · STALE · 메타 → 200
         │  ├─ 행 없음(신규 설비) ────────── 워밍 없음 · 락 유지(만료까지) → 200 빈 목록
         │  └─ ClickHouse 불가 ────────────────────────────── 락 해제 → 200 빈 목록 + 계수
         └─ 락 실패 → 짧게 대기 후 HGETALL 재읽기
            ├─ 채워짐 ─────────────────────────────────────── STALE 판정 · 메타 → 200
            └─ 여전히 없음 ──────────────────── ClickHouse를 부르지 않는다 → 200 빈 목록
```

- **503은 Redis 접속 불가 하나뿐이다(B형).** 결론 — 키가 비는 것과 Redis에 닿지 못하는 것은 다른 사건이다. 반대 시나리오 — 접속 불가에서도 ClickHouse로 복원하면 대시보드의 초당 수백 회 점조회가 전부 ClickHouse로 쏟아져 대량 스캔 엔진이 점조회로 포화되고 적재 삽입까지 밀린다. 파생 지침 — 클라이언트도 503을 시계열 조회로 대체 호출하지 않는다(REQ-RLT-06).
- **복원은 설비당 한 번만 ClickHouse에 닿는다.** 락을 잃은 요청은 대기 뒤 재읽기만 하고 원천을 부르지 않는다 — 시계열 스탬피드의 "대기 소진 후 원천 직접 조회"와 반대다. 최신값은 요청 빈도가 조회보다 두 자릿수 높아 대기 소진이 곧 스탬피드가 된다([06_timeseries_read.md](./06_timeseries_read.md) §스탬피드와 대조).
- **404는 마스터 기준이다.** 키가 비었다는 이유로 404를 내지 않는다(REQ-RLT-07) — 설비 존재 확인은 cache:devlist 사본 또는 PostgreSQL이 한다.
- 단일 태그 최신값(RLT-02)은 태그 → 설비 해석이 먼저 필요하다 — 그 해석이 막히는 경우는 §메타 부착 판정.

## 응답 판정

| 사건 | 응답 | 원천 호출 | 락 | 계측 | 근거 |
|------|------|------|------|------|------|
| 정상 — 필드 있음 | 200 · 값 · 품질(STALE 판정 반영) · 메타 | 없음 | 없음 | 최신값 API 지연 | REQ-RLT-01 · 03 |
| 키 없음 · 복원 성공 | 200 · 복원 값 | ClickHouse 1회 | 획득 → 해제 | 복원 수 · 복원 지연 | REQ-RLT-05 |
| **키 없음 · 복원 창에 행 없음** | **200 · 빈 목록** | ClickHouse 1회 | **해제하지 않고 만료에 맡긴다** | 빈 복원 수 | 이 문서 판정 |
| 키 없음 · ClickHouse 불가 | 200 · 빈 목록 | 실패 1회 | 즉시 해제 | 복원 실패 수 | 이 문서 판정 |
| 키 없음 · 락 실패 · 재읽기에도 없음 | 200 · 빈 목록 | 없음 | 없음 | 대기 소진 수 | 이 문서 판정 |
| Redis 접속 불가 | 503 realtime.latest_unavailable | 없음 | 없음 | 503 수 | REQ-RLT-06 |
| 설비 · 태그가 마스터에 없음 | 404 common.not_found | PostgreSQL(사본 미스 시) | 없음 | 해당 없음 | REQ-RLT-07 |
| 단일 태그 · 태그 해석 불가(tagmeta 미스 + PostgreSQL 불가) | **503 common.postgres_unavailable** | PostgreSQL 실패 | 없음 | 해석 실패 수 | 이 문서 판정 |

- 검산: 사건 = **8** · 200 5 + 503 2 + 404 1 = **8**
- **빈 목록 200은 "설비는 있으나 측정값이 아직 없다"다.** 오류가 아니라 사실이다 — 첫 수집 전의 신규 설비, 보존 창을 넘게 멈췄던 설비가 여기에 든다. 응답의 빈 목록 표지 모양은 [../07_api/06_realtime.md](../07_api/06_realtime.md)(W5)가 정한다.

### 신규 설비 판정

인계 "복원 창에 행 없는 신규 설비 응답"을 닫는다. 판정은 **200 빈 목록 + 락 만료까지 재복원 금지**다.

| 안 | 동작 | 실패 시나리오 | 판정 |
|------|------|------|------|
| ① 404 | 행이 없으면 없는 설비로 본다 | 마스터에 방금 등록한 설비가 404가 되어 화면이 "존재하지 않는 설비"를 띄운다 — REQ-RLT-07 위반 | 버림 |
| ② 빈 결과를 캐시 | 빈 사실을 Redis에 기록 | rt 봉인 계열에 "값 없음" 표지를 쓰면 "ts,value,quality" 형식이 깨지고, 캐시 계열 새 키는 키 패턴 신설이다 | 버림 |
| ③ 매 요청 복원 | 빈 결과여도 락을 풀고 다음 요청이 다시 복원 | 대시보드가 초당 수 회 조회하는 신규 설비마다 ClickHouse argMax가 초당 수 회 — 복원 경로가 스탬피드가 된다 | 버림 |
| ④ **락 유지** | 빈 결과면 lock:rebuild:rt:{device_id}를 풀지 않아 만료 시간 동안 같은 설비의 재복원을 막는다 | 첫 값이 들어와도 락 만료 전까지는 이 경로가 아니라 적재의 최신값 쓰기로 채워진다 — 문제가 되지 않는다 | **채택** |

- 검산: 안 = **4**
- **④는 새 키 없이 부정 캐시를 얻는다.** 락 키는 이미 캐시 계열 TTL 필수 키이고(lock:rebuild:rt) 만료 계약은 "복원 쿼리 타임아웃 이상"이다([../05_data_stores/05_redis_keyspace.md](../05_data_stores/05_redis_keyspace.md)) — 빈 결과 동안의 재복원 억제 시간이 곧 그 만료 값이다.
- ClickHouse 불가는 빈 결과와 달리 락을 즉시 푼다 — 불가는 일시적이라 복구 직후의 첫 요청이 복원해야 한다.

### 메타 부착 판정

인계 "tagmeta 미스 + PostgreSQL 불가 시 최신값 응답"을 닫는다. 태그명 · 단위는 cache:tagmeta:{tag_id}에서 붙이고 미스면 PostgreSQL에서 채운다(REQ-RLT-04 · REQ-RLT-02).

| 경로 | tagmeta 미스 + PostgreSQL 불가 | 판정 | 근거 |
|------|------|------|------|
| 설비 전체(RLT-01) | 값은 Redis에 있다 · 이름 · 단위만 못 붙인다 | **200 — 값 · 품질은 내고 해당 태그의 이름 · 단위를 비운다** · 비운 수를 센다 | 메타는 해석이지 값이 아니다 — PostgreSQL 중단이 실시간 대시보드를 멈추면 "PostgreSQL이 멈춰도 시계열 조회는 계속"(REQ-MST-14)과 같은 원칙이 최신값에서만 깨진다 |
| 단일 태그(RLT-02) | 태그가 어느 설비 Hash에 있는지 모른다 | **503 common.postgres_unavailable** | 읽을 키를 정하지 못한다 — 모든 설비 Hash를 훑는 것은 KEYS 금지와 같은 비용이다 |

- 검산: 경로 = **2**
- **같은 원인에 응답이 둘인 것은 의도다.** 설비 전체는 값의 자리를 알고 이름만 모르지만, 단일 태그는 값의 자리 자체를 모른다 — 클라이언트 대응(설비 전체는 그대로 표시 · 단일 태그는 백오프)이 다르다.
- common.postgres_unavailable의 발생 표면에 최신값 단일 태그를 더하는 것은 [../11_glossary/02_error_codes.md](../11_glossary/02_error_codes.md) 정본의 표면 열 갱신이다 — 새 코드가 아니며 W4에서 선행 문서에 반영했다.

## STALE 판정 계약

판정식의 정본은 [../11_glossary/05_units_and_time.md](../11_glossary/05_units_and_time.md)이고 **배수의 소유처가 이 문서다**.

| 계약 요소 | 규칙 | 금지된 대체 |
|------|------|------|
| 판정식 | 현재(api 서버 시계) − ts > scan_rate_ms × 배수 이면 품질을 5로 바꿔 응답 | ingested_at으로 판정 — 늦게 적재된 값이 "방금 갱신"으로 보인다 |
| 배수 | 2계층 — **현행 참고 3 · 소유 이 문서** | 설비 단위 주기 — 태그별 scan_rate_ms를 쓴다 |
| 적용 시점 | 응답 직전 · 저장값은 바꾸지 않는다 | rt:latest에 5를 써 넣기 — 다음 적재가 덮어 판정이 사라진다 |
| 복원 값 | 복원한 값에도 같은 판정 — 오래된 복원 값은 곧바로 STALE | 복원 값을 신선하다고 표시 |
| 빈 목록 | 판정 대상 없음 | 해당 없음 |
| **메타 없는 태그** | cache:tagmeta 미스 + PostgreSQL 불가로 scan_rate_ms를 모르면 **판정 불가** — 저장 품질을 그대로 내고 staleAfterMs null로 표지한다(W5) | 5로 덮기 — PostgreSQL 장애 동안 신선한 값까지 전부 STALE이 되어 설비 이상과 메타 장애를 가를 수 없다 |

- 검산: 계약 요소 = **6**
- **ClickHouse 중단 중 STALE 전환이 SW-11 ingest의 드러냄 장치다(B형).** 결론 — 적재가 멈추면 최신값이 멈추고 배수 × 주기 뒤 STALE로 표시된다. 반대 시나리오 — STALE 표시를 끄면 운영자가 5분 전 값을 현재 값으로 읽는다. 파생 지침 — 잠정안 기간에도 STALE을 끄지 않는다(ADR-10 · REQ-RLT-16).
- **생성 모드 ts가 과거면 전부 STALE이다.** 판정식이 ts 의미를 따른 결과이며, 실시간 화면을 보는 실험은 현재 시각으로 생성한다.

## 덮어쓰기 순서 역전

한계 등재 #2(HSET은 무조건 덮어쓴다)와 인계 두 건(rt:latest 덮어쓰기 순서 역전 · 복구 중 순서 역전)을 닫는다. **판정 — rt:latest의 모든 쓰기는 필드 단위 조건부 쓰기다. 새 ts가 저장된 ts 이상일 때만 필드를 바꾼다.** 조건 비교와 쓰기는 서버 쪽 스크립트 1회로 원자적으로 한다.

역전이 생기는 자리를 먼저 센다. ADR-09 뒤에는 정상 적재가 단일 flusher의 창 순서라 역전 원인이 아니다.

| 역전 원인 | 옛 값이 늦게 오는 경로 | 무조건 덮어쓰면 | 조건부 쓰기에서 |
|------|------|------|------|
| 복구 중 스풀 재발행 | 위험 단계에 쌓인 옛 엔트리가 복구 단계에 새 수집분과 섞여 적재된다(ADR-23) | 재발행한 옛 값이 방금 쓴 새 값을 덮어 최신값이 과거로 돌아간다 | 옛 ts는 버려진다 |
| 회수된 PEL | XAUTOCLAIM이 인수한 옛 창이 새 창보다 뒤에 삽입된다 | 상동 | 상동 |
| 빈 키 복원 경합 | RLT가 ClickHouse를 읽는 동안 flusher가 새 값을 쓰고, RLT가 옛 복원 값을 쓴다 | 방금 들어온 값이 복원 값에 덮인다 | 복원 값이 버려진다 |
| SW-11 collector + 재발행 | Collector가 새 사이클 값을 쓴 뒤 스풀 재발행이 같은 파이프라인으로 옛 값을 쓴다 | 상동 | 상동 |
| 기동 복원 | Redis가 살아 있는데 ING 기동 복원이 argMax로 다시 쓴다 | AOF로 보존된 더 새 값이 창 경계의 옛 값에 덮일 수 있다 | 상동 |
| 컨슈머 간 순서(원본 우려) | 컨슈머마다 독립 플러시 — ADR-09 이전 구조 | 해당 없음 — 현행 구조에서 사라졌다 | 해당 없음 |

- 검산: 원인 = **6** · 현행 구조에서 실재 5 + 소멸 1
- **ts가 같으면 새 쓰기가 이긴다.** 같은 측정 시각의 두 값은 재전달 · 복원이 같은 행을 다시 쓰는 경우라 값이 같다 — 크거나 같음(≥)이면 멱등이다.
- **발행도 조건을 따른다.** 조건부 쓰기가 받아들인 필드만 ch:rt에 싣는다 — 버려진 옛 값이 WebSocket으로 나가 화면이 뒤로 가는 것을 막는다.
- **대가는 두 가지다.** ① 쓰기가 HSET에서 스크립트 1회로 바뀐다 — 파이프라인 왕복 수는 같다. ② 키 공간 정본의 봉인 래퍼(DurableKeyClient)가 노출하는 명령에 이 스크립트가 더해진다 — [../05_data_stores/05_redis_keyspace.md](../05_data_stores/05_redis_keyspace.md) 갱신은 W4에서 반영했다. 한계 등재 #2는 "막는 것 — 조건부 쓰기 · 못 막는 것 — 래퍼 밖 수동 조작"으로 바뀐다.
- 검증은 그대로다 — 수집 정지 · 랙 0 뒤 rt:latest 대 ClickHouse argMax(value, ts) 일치(AC-07).

## 기동 복원과 복원 창

| 복원 | 주체 | 창 | 조건 | 쓰기 |
|------|------|------|------|------|
| 기동 복원 | ING(SW-11 ingest) 기동 시 1회 | **최근 창 — 빈 키 복원과 같은 값**(현행 참고 10분 · 소유 이 문서) | 항상 — 조건부 쓰기라 보존된 새 값을 덮지 않는다 | 설비별 조건부 쓰기 |
| 빈 키 복원 | RLT 요청 시 · 설비당 락 1 | 상동 | 키가 없을 때만 | 상동 |

- 검산: 복원 = **2**
- **기동 복원은 보존 7일 전체를 훑지 않는다.** 원본은 "argMax 1회로 재구성"이라고만 적었다(원본 architecture.md §5). 창 없이 돌면 M 티어에서 원시 수십억 행을 한 번에 읽어 기동이 그만큼 늦고, 창 밖의 값은 어차피 배수 × 주기를 넘어 STALE이다 — 복원할 가치가 없다.
- SW-11 collector에서는 기동 복원의 소유자가 ING가 아니다 — Collector가 기동 로드 뒤 같은 창으로 복원한다. ADR-10이 "B의 기동 복원 소유 미결"을 B 확정 보류 사유로 적었고, 이 판정이 그 소유를 쓰기 주체와 같게 둔다.

## SW-11 두 구현의 조회 차이

F-03 관점의 차이만 적는다. ClickHouse 중단 재현 비교(갱신 공백 · argMax 불일치 · 수렴 시간)의 정본은 [11_backpressure_failure.md](./11_backpressure_failure.md)다.

| 항목 | ingest(기본) | collector |
|------|------|------|
| 최신값이 반영되는 시점 | 삽입 확정 · XACK 뒤 — Stream 대기 + 삽입 뒤 | XADD와 같은 파이프라인 — 수집 직후 |
| ClickHouse 중단 중 | 멈춘다 → STALE | 계속 갱신된다 |
| 최신값이 ClickHouse에 있는가 | 언제나 있다 | **없을 수 있다** — 적재 전 · DLQ 격리분 · 스풀 중 값 |
| 품질 2 · 4 값 | 적재된 그대로 | 발행한 그대로 |
| 조회 쪽 코드 | 같다 — 읽기 포트(SW-02)는 쓰기 주체를 모른다 | 상동 |

- 검산: 항목 = **5**
- **SW-11 비교는 SW-02 on으로만 한다**(조합 제약 #7). SW-02 off면 조회가 rt:latest를 읽지 않아 두 구현의 차이가 드러나지 않는다.

## F-07 실시간 푸시 한 사이클

원본 푸시 시퀀스(원본 data_flow.md §9)를 연결 한 번의 단계로 옮긴다.

```plain
① 연결          /ws/realtime — 핸드셰이크 Origin 검증(CORS 목록과 같은 규칙) · S7부터
② 인증          첫 메시지로 토큰 — URL 쿼리에 토큰을 받지 않는다(REQ-RLT-09)
③ 구독          설비 목록 → ch:rt:{device_id} SUBSCRIBE · 소켓 ↔ 설비 매핑을 인스턴스 레지스트리에
④ 수신          ch:rt(조건부 쓰기가 받아들인 필드) · ch:alarm(열림 · 닫힘) · ch:cacheinv(무효화 신호)
⑤ 병합          스로틀 창 안 같은 태그는 ts가 가장 큰 값 하나만 — 창 끝에 프레임 1회
⑥ 연결 관리     주기 ping · pong 연속 미수신이면 소켓 종료 · 구독 정리 · 구독자 0 채널 해지
⑦ 재연결        클라이언트 지수 백오프 → 재연결 직후 REST 최신값 1회로 공백을 메운다
```

- **⑤의 "최종값"은 도착 순이 아니라 ts 최대값이다.** 조건부 쓰기와 같은 기준이라 화면이 뒤로 가지 않는다 — 원본 "같은 태그의 중간값은 버리고 최종값만"을 ts로 정의했다.
- **ch:cacheinv는 스로틀 대상이 아니다.** 무효화 신호는 병합하면 키가 빠질 수 있다 — 받은 대로 중계한다(무효화 체인 ⑥단 · [07_business_crud.md](./07_business_crud.md)).
- 같은 프로세스인데 Pub/Sub을 지나는 대가는 루프백 1홉이며, 역할 분리 · 수평 확장 때 팬아웃 재작성을 면제받는 값이다(ADR-07).

### 푸시 조정값

| 조정값 | 현행 참고 | 소유 | 조회 계약 | 어기면 |
|------|------|------|------|------|
| 스로틀 창 | 100 ms(SW-07 — 0이면 PassthroughThrottle) | [../02_features/13_switch_matrix.md](../02_features/13_switch_matrix.md) · 이 문서 | 창 크기 0 초과만 병합 구현 · 0은 구현 교체 | 창 0의 병합 구현을 만들면 "병합 없음"과 "창 0 병합"이 계측에서 갈리지 않는다 |
| ping 주기 · pong 미수신 한도 | 30초 · 3회 | 이 문서 | 연결 수 × 주기 ÷ 30초가 이벤트 루프 부하다 | 짧게 잡으면 연결 500에서 ping만으로 초당 수십 프레임 |
| 재연결 백오프 | 1 · 2 · 4초 … 최대 30초 | 이 문서 · 클라이언트 | 상한 있는 지수 백오프(REQ-RLT-13) | 상한이 없으면 api 재기동 뒤 전 클라이언트가 같은 순간 재연결한다 |
| **소켓 송신 대기량 한도** | 미정 | [../07_api/11_websocket.md](../07_api/11_websocket.md) | **느린 브라우저 한 개**를 4413으로 절단 — 게이트웨이가 소켓마다 잰다 | 한도가 없으면 느린 탭 하나 몫의 프레임이 api 힙에 쌓인다 |
| Pub/Sub 출력 버퍼 한도 | 미정 | [../10_observability/01_metrics_catalog.md](../10_observability/01_metrics_catalog.md)(W6) · Redis 설정 | **api 구독 연결 보호의 최후선** — 넘으면 Redis가 api 인스턴스의 구독 연결을 끊어 그 인스턴스 전체 푸시가 멈춘다(4503 · W5) | 한도가 없으면 api가 채널을 못 따라갈 때 Redis 메모리를 먹어 봉인 계열 쓰기가 OOM에 가까워진다 |

- 검산: 조정값 = **5**
- **두 한도는 다른 대상을 끊는다(W5 판정).** 브라우저 단위 절단은 소켓 송신 대기량 한도이고, 출력 버퍼 한도는 api 프로세스와 Redis 사이의 구독 연결 하나를 끊는다 — 출력 버퍼로 느린 브라우저를 다루려 하면 탭 하나의 지연이 인스턴스 전원의 푸시 중단이 된다. 그래서 송신 대기량 한도가 먼저 걸리게 둔다.
- 원본 산정 "태그 500 · 10 Hz · 스로틀 없음 초당 5,000 프레임 → 100 ms 병합 초당 10 프레임"(원본 data_flow.md §9.1)은 원본 예상치다. 실측은 SW-07 on/off(AC-41)다.

## Pub/Sub 한계와 대응

| 한계 | 의미 | 대응 | 어느 쪽이 메우는가 |
|------|------|------|------|
| 전달 보장 없음 | 구독자가 없으면 메시지가 사라진다 | 저장은 반드시 별도 경로(tag_raw · alarm_event) | 적재 · 판정 흐름 |
| 재연결 공백 | 끊긴 동안의 값을 못 받는다 | 재연결 직후 REST 최신값 1회 · 알람 목록 재조회 | 클라이언트 |
| 느린 구독자 | 느린 브라우저면 게이트웨이 소켓 송신 대기량이 쌓이고 · api 구독 연결이 밀리면 Redis 출력 버퍼가 쌓인다 | 브라우저는 송신 대기량 한도로 4413 절단 → 재연결 · 출력 버퍼 한도는 구독 연결 보호의 최후선(4503) | 게이트웨이 · Redis 설정 · 클라이언트 |
| 구독자 전원 수신 | api 인스턴스가 늘어도 코드가 같다 | 해당 없음 — 장점 | 해당 없음 |
| 발행 실패 | FanoutPublisher가 계수하고 삼킨다 | 재연결 재조회가 메운다 | 클라이언트 |

- 검산: 한계 = **5**
- **알람 푸시 누락은 알람 확정에 영향을 주지 않는다**(REQ-RLT-14). ch:alarm은 통지이고 진실은 alarm_event다 — 재연결 뒤 목록 재조회가 놓친 이벤트를 보여 준다.
- SW-06 off(DirectGatewayFanout)는 발행자가 같은 프로세스의 게이트웨이를 직접 부르므로 api 인스턴스가 하나일 때만 쓴다(조합 제약 #6). 프레임 내용은 on/off가 같다(REQ-RLT-17).
