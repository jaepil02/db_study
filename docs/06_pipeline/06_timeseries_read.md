F-04는 **브라우저의 범위 조회가 롤업 · 원시에서 집계되어 돌아오기까지**다. 브라우저는 BFF를 거치지 않고 api에 직결한다 — 응답이 크고 사용자마다 달라 중계 · 캐시 이득이 없다(원본 data_flow.md §7.2). 이 흐름에서 Redis는 **목적지가 아니라 사본**이며(cache:q · lock:rebuild:q), 캐시 계열이라 실패하면 조용히 원천으로 우회한다(REQ-GLB-09).

**이 문서가 조정값의 소유처다** — TTL 구간 값 · 스탬피드 락 만료 · 대기 간격 · 캐시 호출 타임아웃(키 공간 TTL 조회 계약의 소유처 열 · REQ-TSQ-10 · 12). 해상도 경계(1시간 · 7일 · 90일)는 1계층 구조값이고 정본은 [../11_glossary/03_enums_state_machines.md](../11_glossary/03_enums_state_machines.md)다. 응답 필드 · 시각 형식은 [../07_api/05_timeseries.md](../07_api/05_timeseries.md)(W5)가 갖는다.

## 조회 판정 트리

원본 조회 시퀀스(원본 data_flow.md §6)와 스탬피드 시퀀스(원본 architecture.md §10.3)를 요청 하나의 판정으로 옮긴다.

```plain
POST 시계열 조회(브라우저 → api 직결)
├─ 인증 · 역할 · 레이트 리밋(S7부터) ──────────────────────────────────── 401 · 403 · 429
├─ 태그 수 상한 초과 ────────────────────────────────── 400 timeseries.too_many_tags
├─ 형식 위반(interval · aggregations · 오프셋 없는 ISO 8601 · from ≥ to) ──── 400 common.validation_failed
└─ 해상도 선택 → 예상 포인트 초과면 한 단계 상향 → 버킷 경계 스냅 → 정규화 키 cache:q:{sha1}
   ├─ 최근 구간(to가 현재 − 최근 창 이후) ─────────────────── 캐시 없이 ClickHouse → 200
   └─ GET cache:q:{sha1}(타임아웃이면 미스로 본다)
      ├─ 히트 ──────────────────────────────── 워커 gzip 해제 → 200 · meta.cached 참
      └─ 미스 → SET lock:rebuild:q:{sha1} NX PX
         ├─ 락 획득 → ClickHouse 집계 · dictGet · 필요 시 LTTB
         │  ├─ 성공 ─────────── SET cache:q(TTL 분류 + 지터) · 소유자 검증 해제 → 200
         │  └─ ClickHouse 불가 ────── 소유자 검증 해제 → 503 timeseries.clickhouse_unavailable
         └─ 락 실패 → 짧게 대기 후 GET 재조회(횟수 상한)
            ├─ 히트 ─────────────────────────────────────────────── 200 · meta.cached 참
            └─ 대기 소진 ── 락 없이 ClickHouse 직접 · 결과는 NX 쓰기 → 200(불가면 503)
```

- **거절 코드는 셋뿐이고 나머지 분기는 전부 200이다.** 해상도 상향 · 다운샘플 · 캐시 실패 · 락 실패 · 대기 소진은 에러가 아니라 보정이다 — "에러 코드가 아닌 것"([../11_glossary/02_error_codes.md](../11_glossary/02_error_codes.md)).
- **캐시 미스의 503은 ClickHouse 불가 하나다.** 대조군 PostgreSQL이나 rt:latest로 대신 답하지 않는다(REQ-TSQ-16) — 대조군을 원천으로 읽는 순간 두 저장소 중 무엇이 진실인지 흐려진다.
- 스위치 셋이 트리의 세 자리를 교체한다 — SW-03 off는 GET · SET을 없애고(항상 미스), SW-04 off는 스냅을 없애고, SW-05 off는 락 가지를 없앤다(REQ-TSQ-14).

## 해상도 자동 선택

| 범위 길이(to − from) | 테이블 | 버킷 | 원시 대비 스캔량 | 원본 예상 응답(M 티어) |
|------|------|------|:------:|------|
| 1시간 이하 | tag_raw | 없음 — 스냅 단위 1분 | 1 | 30~80 ms |
| 1시간 초과 ~ 7일 | tag_1m | 1분 | 1/60 | 40~150 ms |
| 7일 초과 ~ 90일 | tag_1h | 1시간 | 1/3600 | 30~100 ms |
| 90일 초과 | tag_1d | 1일(KST 자정) | 1/86400 | 20~60 ms |

- 검산: 해상도 = **4** · 예상 응답은 원본 예상치 — 3계층 미확인
- **상향 규칙** — 예상 포인트(태그 수 × 범위 ÷ 버킷 폭 · raw는 범위 ÷ 태그 scan_rate_ms)가 최대 포인트 수(현행 참고 2000 · 소유 [../07_api/05_timeseries.md](../07_api/05_timeseries.md))를 넘으면 한 단계 올린다. 사용자가 raw를 지정한 긴 범위도 같다 — 거절하지 않는다(REQ-TSQ-04). 실제 해상도는 meta.interval이 말한다.
- **B형 — 서버가 해상도를 강제하는 것은 편의가 아니라 보호 장치다.** 반대 시나리오 — 1년 범위를 원시로 받으면 M 티어에서 원본 산정 수천억 행 스캔이 ClickHouse를 메모리 한계로 죽이고 적재 삽입까지 멈춘다(원본 data_flow.md §6.1). 파생 지침 — 원시가 꼭 필요한 긴 범위는 조회 표면이 아니라 내보내기(§원시 내보내기)로 유도한다.
- 롤업 조회는 언제나 -Merge 조합자 + GROUP BY 버킷이다(REQ-TSQ-07) — 머지 전에는 같은 버킷의 부분 상태가 여러 행이다([09_rollup.md](./09_rollup.md)).

## 캐시 키 정규화 — SW-04

| 단계 | 처리 | SW-04 off(RawTimeKeyNormalizer) | 빠지면 |
|:-:|------|------|------|
| 1 | 해상도 확정 — 요청 값이 아니라 **선택 · 상향 뒤 값**을 키에 넣는다 | 같다 | 같은 요청이 상향 여부와 무관하게 한 키로 묶여 다른 해상도의 결과가 섞인다 |
| 2 | from · to를 해상도 버킷 경계로 **epoch 연산으로** 내림 — 1d는 KST 자정 | **생략** — 요청 시각 그대로 | 초 단위 now()가 키에 들어가 매 요청이 다른 키가 되고 히트율이 0에 수렴한다 |
| 3 | tagIds 정렬 · aggregations 정렬 | 같다 | 같은 조회가 순서만 달라 두 키가 된다 |
| 4 | 기본값 파라미터 제거 | 같다 | 기본값을 명시한 요청과 생략한 요청이 다른 키가 된다 |
| 5 | 정규화 문자열의 SHA-1 40자 → cache:q:{sha1} | 같다 | 해당 없음 |

- 검산: 단계 = **5** · SW-04가 바꾸는 단계 1(#2)
- **스냅한 범위가 곧 조회 범위다.** 캐시 여부와 무관하게 ClickHouse에도 스냅한 from · to로 묻는다 — 히트와 미스가 다른 범위의 결과를 내면 같은 화면이 새로고침마다 달라진다.
- **1d 스냅을 문자열 날짜로 하지 않는다.** 서버 시간대에 따라 다른 자정으로 내림되어 같은 조회가 두 키로 갈린다 — 버킷의 KST 자정과 같은 경계를 epoch로 계산한다([../05_data_stores/04_clickhouse_rollup.md](../05_data_stores/04_clickhouse_rollup.md) §일 경계 시간대 판정).

## TTL 구간 분류와 지터

**2계층 조정값 · 소유 이 문서.** "현재"는 api 서버 시계이고 현재 버킷은 선택된 해상도의 버킷이다([../11_glossary/05_units_and_time.md](../11_glossary/05_units_and_time.md)).

| 구간 | 판정(위에서부터 먼저 걸리는 것) | TTL 현행 참고 | 지터 | 근거 |
|------|------|------|:------:|------|
| 최근 구간 | to > 현재 − 최근 창(현행 참고 5분) | **캐시하지 않는다** | 해당 없음 | 계속 바뀌는 구간 — 최신값 API · WebSocket으로 유도 |
| 현재 버킷 포함 | to ≥ 현재 버킷 시작 | 30초 | ±20% | 진행 중 버킷이 갱신된다 |
| 완전 과거 | to < 현재 버킷 시작 | 300초 | ±20% | 데이터가 거의 불변이다 — §늦게 도착한 데이터 |

- 검산: 구간 = **3**
- **지터는 cache 접두 단건 키에만 래퍼가 자동으로 건다**(ADR-13). 대시보드가 30초마다 새로고침하면 여러 사용자의 캐시가 동시에 만료되어 ClickHouse에 동시 쿼리가 몰린다 — ±20% 무작위가 만료를 흩는다(원본 data_flow.md §6.2).
- **과거 구간을 명시적으로 무효화하지 않는다**(REQ-TSQ-10). 무효화 대상은 마스터 사본이고 시계열 결과는 TTL만으로 수명을 끊는다 — 태그명 변경은 결과가 아니라 dictGet이 조회 시점에 붙이므로 캐시된 결과의 이름은 TTL만큼 옛 이름이다(한계 등재 #14의 조회 쪽 모습).

### 진행 구간 분할

끝이 현재인 "최근 N분 · N시간" 조회는 통째로 캐시할 수 없다(REQ-TSQ-13 · TSQ-08).

| 조각 | 범위 | 원천 | 캐시 | 합치는 자리 |
|------|------|------|------|------|
| 확정 과거 | from ~ 현재 버킷 시작 | ClickHouse 롤업 · 원시 | 완전 과거 TTL | 클라이언트 |
| 진행 버킷 | 현재 버킷 시작 ~ 현재 | 최신값(rt:latest) 또는 짧은 TTL 조회 | 최근 구간이면 없음 | 클라이언트 |

- 검산: 조각 = **2**
- **서버는 합치지 않는다.** 두 조각은 원천 · 캐시 수명 · 지연이 달라 한 응답으로 합치면 한쪽 실패가 전체 실패가 된다 — 최신값 503이 과거 추이까지 지운다.

## 스탬피드 방지 — SW-05

캐시 미스에서 같은 키를 동시에 요청한 N명 중 한 명만 ClickHouse를 부르게 한다. 원본은 대기 "최대 3회"까지만 적었다.

| 계약 요소 | 규칙 | 현행 참고 · 소유 |
|------|------|------|
| 락 키 | lock:rebuild:q:{sha1} — 최신값 복원 락(lock:rebuild:rt)과 식별자 공간을 가른다 | [../05_data_stores/05_redis_keyspace.md](../05_data_stores/05_redis_keyspace.md) |
| 획득 | SET NX PX · 값 = 소유자 토큰 | 만료 5000 ms · 이 문서 |
| 해제 | 소유자 토큰 검증 스크립트 — 단순 DEL 금지 | 자기 락이 만료된 뒤 남의 락을 지운다 |
| 대기 | 락 실패 요청은 간격마다 GET 재조회 · 횟수 상한 | 50 ms × 3회 · 이 문서 |
| **대기 소진** | **락 없이 ClickHouse 직접 조회 · 결과는 선행 채움을 덮지 않는 쓰기(NX)** · 소진 수 계수 | 이 문서 판정 |
| 락 호출 실패(Redis) | 락 없이 원천 조회 — 스탬피드를 감수한다 | 캐시 계열 degrade |

- 검산: 계약 요소 = **6**

인계 "스탬피드 대기 소진 후 원천 직접 조회"를 닫는다. 요구 수준은 "요청자는 실패를 보지 않는다"(REQ-TSQ-12)다.

| 안 | 대기 소진 뒤 | 실패 시나리오 | 판정 |
|------|------|------|------|
| ① 503 | 거절 | 락 보유자가 느릴 뿐인데 기다린 요청 전원이 실패를 본다 — REQ-TSQ-12 위반 | 버림 |
| ② 락 재시도 | 락을 다시 잡으려 한다 | 락 보유자가 살아 있으면 계속 실패해 대기가 무한해진다 | 버림 |
| ③ **직접 조회 + NX 쓰기** | 락 없이 원천을 읽고 캐시가 비어 있을 때만 쓴다 | 소진이 잦으면 스탬피드가 부분적으로 돌아온다 — 소진 계수가 드러낸다 | **채택** |

- 검산: 안 = **3**
- **A형 — 현행 참고 값에서는 락이 스탬피드를 거의 막지 못한다.** 통념은 "락이 있으면 동시 N건이 ClickHouse 1회가 된다"이다. 부정 — 대기 총량이 50 ms × 3 = 150 ms인데 캐시 미스 재구성의 원본 목표는 250~300 ms라, 기다린 요청 대부분이 락 보유자가 끝나기 전에 소진되어 직접 조회로 간다. 진짜 축은 **대기 총량과 재구성 시간 p95의 대소**다 — 대기 총량 ≥ 재구성 시간 p95일 때만 락이 쿼리 수를 줄인다(1계층 관계). 대체 경로 — SW-05 실험(AC-25) 전에 재구성 시간을 재고 대기 간격 · 횟수를 이 관계에 맞춘다. 값 확정 전에는 소진 계수로 관계 위반을 드러낸다.
- **NX 쓰기인 이유** — 소진 요청과 락 보유자가 같은 키를 거의 동시에 채울 때, 두 결과는 같은 범위 · 같은 원천이라 내용이 같다. 덮어쓰면 TTL만 다시 시작되어 지터가 흩은 만료가 한 요청의 시각으로 다시 모인다.
- 락 보유자가 ClickHouse 불가로 실패하면 락을 즉시 해제한다 — 대기자가 만료 5초를 기다리지 않고 소진 경로에서 같은 503을 받는다.

## 캐시 호출 타임아웃과 degrade

| 호출 | 실패 · 타임아웃이면 | 응답 | 계측 |
|------|------|------|------|
| GET cache:q | 미스로 본다 → 락 가지 | 200(원천) | 캐시 실패 계수 · 지연 상승 |
| SET lock | 락 없이 원천 | 200 | 상동 |
| SET cache:q | 버린다 | 200 | 상동 |
| 락 해제 | 버린다 — 만료가 푼다 | 200 | 상동 |

- 검산: 호출 = **4**
- **타임아웃은 2계층 조정값 · 현행 참고 50 ms · 소유 이 문서**다(키 공간 미확인 등재의 확정 자리). 캐시 호출 타임아웃이 원천 조회 시간보다 길면 degrade가 오히려 느려진다 — 캐시 히트 목표(원본 목표 20 ms)보다 짧아야 의미가 있다.
- **캐시 실패를 에러 응답으로 올리지 않는다**(REQ-TSQ-11). 캐시 계열의 실패는 지연 상승으로만 드러난다 — 봉인 계열(최신값)의 503과 정반대 전략이다(ADR-05).

## 다운샘플 · 메타 부착

| 단계 | 기전 | 자리 | 이벤트 루프 |
|------|------|------|------|
| 1차 축소 | 롤업 테이블이 이미 버킷으로 접었다 | ClickHouse | 해당 없음 |
| 2차 축소 | 여전히 최대 포인트를 넘으면 태그마다 LTTB — meta.downsampled 참 | api | **워커**(ADR-25) |
| 극값 보존 | 알람 분석 요청은 버킷의 min · max 쌍을 그대로 낸다 | api | 해당 없음 |
| 메타 부착 | dictGet(plc.dict_tag)으로 태그명 · 단위 | ClickHouse 쿼리 안 | 해당 없음 |
| 압축 | gzip 후 cache:q 저장 · 히트 시 해제 | api | 워커 |

- 검산: 단계 = **5**
- **단순 n번째 추출을 쓰지 않는다.** 스파이크를 잃어 알람 원인 분석에서 이상치가 사라진다(원본 data_flow.md §6.3).
- **PostgreSQL이 멈춰도 메타가 붙는다.** Dictionary는 마지막 적재 값을 유지한다(REQ-TSQ-08) — 이 흐름은 PostgreSQL 중단에 영향받지 않는 흐름이다.
- COUNTER 태그의 구간 증가량을 max − min으로 읽는 조회는 랩어라운드 버킷에서 틀린다 — [04_routing.md](./04_routing.md) §생산 카운터 기전 판정.

## ClickHouse 불가

| 사건 | 응답 | 우회 | 근거 |
|------|------|------|------|
| 캐시 히트 | 200 | 해당 없음 | REQ-TSQ-16 |
| 캐시 미스(락 보유자 · 소진 요청 · 최근 구간) | 503 timeseries.clickhouse_unavailable | **없다** — 대조군 · rt:latest로 대신 답하지 않는다 | 상동 |
| 내보내기 응답 시작 전 | 503 timeseries.clickhouse_unavailable | 없다 | 상동 |
| 내보내기 스트림 도중 | 스트림 중단 — 종료 표지 모양은 W5 | 없다 | [../07_api/05_timeseries.md](../07_api/05_timeseries.md)(W5) |

- 검산: 사건 = **4**
- **히트가 200인 것은 캐시가 원천의 대리인이어서가 아니라 이미 확정된 결과여서다.** 완전 과거 구간은 TTL 안에서 원천과 같다 — 그 TTL이 ClickHouse 중단의 완충 시간이 된다.

## 늦게 도착한 데이터와 과거 캐시

**B형 — "완전 과거 구간은 불변"은 적체 소진 · 스풀 재발행 동안 거짓이다.** 결론 — 복구 단계에서 옛 ts의 행이 적재되면 이미 캐시된 과거 버킷의 결과가 원천과 달라진다. 반대 시나리오 — 이를 막으려 과거 구간을 명시적으로 무효화하면 적재 경로가 조회 캐시 키를 알아야 하고(키는 정규화 쿼리의 해시라 역산할 수 없다) 무효화가 KEYS 탐색이 된다. 파생 지침 — 불일치는 **완전 과거 TTL(현행 참고 300초)이 상한**이며, 복구 직후의 조회 결과를 판정에 쓰는 실험(AC-11 무손실 대조)은 캐시를 거치지 않는 ClickHouse 직접 count로 한다.

| 늦은 행의 원인 | 과거 버킷에 닿는 시점 | 캐시 불일치 상한 | 판정 자리 |
|------|------|------|------|
| 스풀 재발행(복구 단계) | 위험 단계 길이만큼 늦게 | 완전 과거 TTL | [11_backpressure_failure.md](./11_backpressure_failure.md) |
| ClickHouse 중단 뒤 적체 소진 | 중단 길이만큼 늦게 | 상동 | 상동 |
| DLQ 재처리 | 사람이 재처리한 시점 | 상동 | 상동 |
| 모드 D 백필 | 백필 시점 | 상동 — 백필 뒤 캐시 계열 키를 비운다(REQ-GLB-23) | [10_datagen_inject.md](./10_datagen_inject.md) |

- 검산: 원인 = **4**
