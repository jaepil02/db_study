계정은 **아이디·비밀번호 단일 체계**이며 직원·관리자·플랫폼 운영자가 같은 계정을 쓴다. 가입 단계에서 직원과 관리자를 가르지 않고 소속·역할은 사업장 등록(WRK-01)이나 초대 수락(WRK-05)이 결정한다. 그래서 미인증 인증 화면 4본은 **웹과 앱이 같은 기능군을 담고 하나의 화면 코드**를 공유한다(PUB-SIGNUP · PUB-LOGIN · PUB-PASSWORD-RESET · PUB-CONSENT).

**웹에서 이 4본은 프리렌더 공개 페이지가 아니라 SPA 축에 속한다**(D-20). 프리렌더 대상은 랜딩·요금제 2본뿐이고, 인증 4본은 admin·system과 같은 산출물·같은 오리진 안의 **미인증 진입점**이다 — 로그인 성공 직후 세션 쿠키를 받은 브라우저가 다른 산출물로 건너가지 않으므로 복귀 대상 전달과 오픈 리다이렉트 차단(§1-2)이 한 곳에 모인다. PUB 접두는 표면이 아니라 미인증이라는 인증 상태를 뜻하며, 화면 코드와 표면 병기(웹 + 앱)는 전환 후에도 불변이다.

인증 이후는 표면이 갈린다. **사업장을 만들고 고르는 흐름은 관리자 웹**(ADM-WORKPLACE-SELECT · ADM-WORKPLACE-CREATE)이고 **초대를 받는 흐름은 직원 앱**(APP-INVITE)이다. 계정 설정도 갈라서 관리자 웹은 ADM-ACCOUNT, 직원 앱은 APP-SETTINGS가 담당한다 — 담는 액션이 다르기 때문이 아니라 표면마다 진입 맥락과 되돌아갈 자리가 다르기 때문이다.

**동의는 가입의 한 단계이자 개정 재동의의 게이트**다. 두 진입이 같은 화면 코드(PUB-CONSENT)를 쓰고 제출 후 목적지만 갈린다. **위치정보 동의는 약관·개인정보와 분리된 별도 동의**여야 위치정보법 §18을 충족하므로 하나의 체크박스로 묶지 않는다.

## PUB-SIGNUP — 회원가입

| 항목 | 내용 |
|------|------|
| 화면코드 | PUB-SIGNUP |
| 라우트 | web_front SPA /signup · app_front 인증 스택 SignUp |
| 접근권한 | 비인증. 인증 사용자가 접근하면 진입 분기(AUT-10)의 목적지로 되돌린다 |
| 우선순위 | P0 |

**목적**: 아이디·비밀번호로 계정을 만들고 필수 동의를 마쳐 진입 분기까지 도달한다.

**진입경로**: PUB-LANDING·PUB-PRICING의 가입 버튼 · PUB-LOGIN의 가입 링크 · 초대 공유 코드를 받은 미가입자의 앱 진입.

**화면 기능**

| 기능 | UI/처리 | 기능ID |
|------|---------|--------|
| 가입 입력·검증 | 여섯 필드다 — **아이디**(4~20자 · 영소문자와 숫자 · 첫 글자는 영문 · 예약어 금지) · **비밀번호**(8자 이상 · 영문·숫자·특수문자 중 2종 이상) · **이름**(2~50자) · **연락처**(국내 휴대폰 또는 E.164) · **복구 이메일**(선택) · **약관·개인정보 동의**(필수) · **위치정보 동의**(선택 — 미동의 시 GPS 체크인만 차단, D-19). 클라이언트와 서버가 같은 규칙으로 검증하되 **서버 판정이 최종**이다 | AUT-01 |
| 아이디 중복 확인 | 형식 검증을 통과한 값만 조회하고 **가용 여부만** 표시한다. 입력 디바운스 **약 400밀리초** 후 표시하며 호출 빈도를 제한한다. 계정 상태·프로필을 함께 보여주지 않는다 | AUT-04 |
| 비밀번호 강도 표시 | 약함·보통·강함 3단계를 실시간으로 보인다. 강도 표시는 안내이며 통과 판정은 정책 검증이 한다 | AUT-04 |
| 동의 수집 | 약관·개인정보·위치정보 **세 종류를 각각 체크**하고 각 항목에서 전문 보기(PUB-LEGAL)로 이동할 수 있다. **하나의 체크박스로 묶지 않는다** — 묶으면 위치정보법 §18의 별도 동의 요건이 충족되지 않는다. 동의 이력은 문서 버전과 시각까지 기록된다 | AUT-01 · PRV-02 |
| 경합 재검증 | 사전 중복 확인을 통과했어도 가입 트랜잭션에서 아이디 유일성을 다시 확인한다. 경합으로 인한 중복은 **제출 후 아이디 필드로 오류를 되돌린다** | AUT-04 |
| 가입 후 진입 | 성공 시 인증 컨텍스트를 수립하고 소속·소유 사업장이 0개면 진입 분기(ADM-WORKPLACE-SELECT)로 보낸다 | AUT-01 · AUT-10 |

**주요 UI 요소**: 브랜드 헤더, 가입 폼(아이디 + 중복 확인 상태 · 비밀번호 + 강도 표시 + 표시 토글 · 비밀번호 확인 · 이름 · 연락처 · 복구 이메일), 동의 체크 3항목(각각 전문 보기 링크), 서버 오류 배너, 제출 버튼, 로그인 링크.

**레이아웃·스크롤·모바일**: 단일 폼 카드를 가운데 정렬한다 — 인증 화면 4본에만 허용된 폭 상한 예외다(§5-2). 폼 카드가 스크롤 소유자이며 페이지 자체에 이중 스크롤을 만들지 않는다. 768 미만에서는 카드 좌우 여백만 좁히고 필드는 1열을 유지한다. 앱에서는 키보드가 올라올 때 제출 버튼이 가리지 않도록 본문을 밀어 올리고 안전 영역 위에 버튼을 띄운다.

**상태 처리**

| 상태 | 처리 |
|------|------|
| 로딩 | 활성 약관 문서 3종을 읽는 동안 동의 영역만 스켈레톤으로 자리를 잡고 나머지 필드는 즉시 입력 가능하다 |
| 빈 상태 | 해당 없음 — 폼 화면이며 0건이 될 목록이 없다 |
| 에러 | auth.username_taken/409는 아이디 필드에 "이미 사용 중인 아이디입니다"로 되돌린다 · auth.phone_taken/409는 연락처 필드로 · auth.weak_password/422는 비밀번호 필드로 · auth.consent_required/422는 동의 영역으로 붙인다. common.validation_failed/400·common.invalid_format/400은 서버가 준 필드 경로에 그대로 붙이고, system.terms_not_found/404는 "약관을 준비 중입니다"와 문의 경로를 폼 상단 배너에 낸다 |
| 권한거부 | **로그인 유도의 반대 방향**이다 — 이미 인증된 사용자는 차단이 아니라 진입 분기의 목적지로 되돌린다(§1-2 권한 안내) |

**데이터 연동**

- 아이디 중복 확인 → GET /v1/auth/username-available → **users**(가용 여부만 반환). 활성 약관 조회 → GET /v1/terms/{kind}/active(종류 3종) → **terms_documents**. 가입 제출 → POST /v1/auth/signup → **users** · **profiles** · **user_consents** 단일 트랜잭션. **낙관적 갱신 없음** — 서버 확정 후 이동한다. 상세 정본은 [../06_api/03_auth.md](../06_api/03_auth.md) · [../06_api/15_privacy.md](../06_api/15_privacy.md)다.

**담은 기능ID**: AUT-01 · AUT-04 · AUT-10(진입 분기) · PRV-02

**비고**: 비밀번호는 **원문·해시를 응답·로그·감사 전후값 어디에도 남기지 않는다.** 화면 계약으로는 제출 실패 시에도 입력값을 유지하되 비밀번호 필드만은 유지하지 않는 편이 안전하나, v1은 재입력 부담을 줄이기 위해 유지하고 화면 이탈 시 즉시 비운다. **동의 화면을 별도 코드(PUB-CONSENT)로 둔 것과 이 화면 안에서 동의를 함께 받는 것은 모순이 아니다** — 가입 흐름은 한 화면에서 끝내고, PUB-CONSENT는 이미 가입한 사용자의 개정 재동의 게이트를 담당한다. 두 자리가 같은 문안 모듈을 공유한다.

## PUB-LOGIN — 로그인

| 항목 | 내용 |
|------|------|
| 화면코드 | PUB-LOGIN |
| 라우트 | web_front SPA /login · app_front 인증 스택 SignIn |
| 접근권한 | 비인증. 인증 사용자가 접근하면 진입 분기(AUT-10)의 목적지로 되돌린다 |
| 우선순위 | P0 |

**목적**: 아이디·비밀번호로 인증 컨텍스트를 받고 표면에 맞는 목적지로 들어간다.

**진입경로**: 미인증 상태의 보호 경로 접근 · PUB-LANDING 헤더 · 로그아웃 후 이동 · 앱 최초 실행 · 세션 폐기 후 자동 이동.

**화면 기능**

| 기능 | UI/처리 | 기능ID |
|------|---------|--------|
| 로그인 | 아이디·비밀번호를 제출해 표면별 인증 컨텍스트를 받는다 — **관리자 웹·시스템 웹은 서버 세션**(쿠키 + CSRF 토큰) · **직원 앱은 access와 refresh 토큰 쌍**이다 | AUT-02 |
| 실패 응답 통일 | 아이디 미존재와 비밀번호 불일치를 **하나의 문안으로 통일**해 사용자 열거를 막는다 — auth.invalid_credentials/401. 클라이언트도 응답 본문에 따라 문안을 가르지 않는다 | AUT-02 |
| 계정 상태 차단 표시 | 인증 성공 직후 계정 상태를 다시 판정한다. 정지는 **사유와 해제 예정일**을 담아 보이고(auth.account_suspended/403) 삭제는 접근 불가 안내로 수렴시킨다(auth.account_deleted/403) — 자격증명 오류(401)와 계정 상태 차단(403)은 사용자가 할 일이 다르므로 문안을 가른다 | AUT-02 · AUT-08 |
| 시도 제한 표시 | 아이디와 접속 지점 조합의 실패 횟수를 서버가 제한하며 초과 시 **재시도 가능 시각**을 함께 보인다 — common.rate_limited/429 | AUT-02 |
| 진입 분기 | 성공 후 목적지를 판정한다 — 직원 앱은 STAFF 이상 멤버십 · 관리자 웹은 OWNER·MANAGER 멤버십 · 시스템 웹은 플랫폼 권한 보유다. 멤버십 0개는 진입 분기 화면, 1개는 자동 선택, 2개 이상은 사업장 선택으로 보내고 대기 초대만 있으면 초대 수락으로 보낸다 | AUT-10 |
| 복귀 경로 보존 | 미인증으로 되돌려진 경우 원래 요청 경로를 보존해 로그인 후 그 자리로 돌려보낸다. **내부 경로만 허용**해 오픈 리다이렉트를 막는다 | AUT-03 |
| 재동의 게이트 | **필수 2종(약관·개인정보)**의 개정 문서에 재동의가 남아 있으면 목적지로 보내기 전에 동의 화면(PUB-CONSENT)을 먼저 띄운다. **위치정보 개정은 진입을 막지 않는다**(D-19) | PRV-02(연계) |

**주요 UI 요소**: 브랜드 헤더, 로그인 폼(아이디 · 비밀번호 + 표시 토글), 서버 오류 배너, 제출 버튼, 비밀번호 재설정 링크, 가입 링크.

**레이아웃·스크롤·모바일**: 단일 폼 카드 가운데 정렬이며 PUB-SIGNUP과 같은 규격을 공유한다. 폼이 짧아 스크롤이 발생하지 않는 것이 기본이고, 오류 배너가 붙어 높이가 늘어도 카드 안에서 흡수한다. 앱에서는 자동 로그인 시도 중 이 화면 대신 시작 화면을 보이고, 토큰 검증 실패로 이 화면에 도달하면 사유를 안내한다.

**상태 처리**

| 상태 | 처리 |
|------|------|
| 로딩 | 앱은 저장된 토큰 검증 동안 진행 표시를 두고, 웹은 세션 확인 동안 폼을 잠근다. 검증이 끝나기 전에 입력을 받지 않는다 |
| 빈 상태 | 해당 없음 — 폼 화면이다 |
| 에러 | auth.invalid_credentials/401은 "아이디 또는 비밀번호가 올바르지 않습니다" 단일 문안으로 배너에 낸다 · auth.account_suspended/403은 정지 사유와 해제 예정일을 함께 · auth.account_deleted/403은 접근 불가 안내와 문의 경로 · common.rate_limited/429는 재시도 가능 시각을 보인다. 네트워크 실패는 자격증명 오류와 문안을 가른다 |
| 권한거부 | **로그인 유도의 도착지**다. 이 화면 자체는 거부되지 않으며, 인증 사용자의 접근만 진입 분기 목적지로 되돌린다(§1-2 권한 안내) |

**데이터 연동**

- 제출 → POST /v1/auth/login → **users** · **profiles**(마지막 로그인 시각 갱신). 진입 판정 → GET /v1/me/entry-context → **workplace_members** · **workplaces** · **system_admins**. 재동의 대기 조회 → GET /v1/me/consents/pending → **user_consents** · **terms_documents**. **낙관적 갱신 없음.** 상세 정본은 [../06_api/03_auth.md](../06_api/03_auth.md)다.

**담은 기능ID**: AUT-02 · AUT-03(복귀 경로 보존) · AUT-08(차단 발현) · AUT-10 · PRV-02(연계)

**비고**: **자격증명 오류를 401, 계정 상태 차단을 403으로 가르는 것이 이 화면의 핵심 규약**이다. 두 응답을 하나로 합치면 정지 사유와 해제 예정일을 안내할 수 없고, 반대로 아이디 존재 여부를 문안으로 가르면 계정 열거 경로가 된다. **세션 관리(AUT-03)의 표면은 이 화면의 복귀 경로 보존과 폐기 후 이동뿐**이며 검증·갱신·폐기 자체는 화면 없는 전역 처리다.

## PUB-PASSWORD-RESET — 비밀번호 재설정

| 항목 | 내용 |
|------|------|
| 화면코드 | PUB-PASSWORD-RESET |
| 라우트 | web_front SPA /password-reset · /password-reset/[token] · app_front 인증 스택 PasswordReset |
| 접근권한 | 비인증. 인증 상태에서도 강제 이탈 없이 통과한다 — 복구 링크로 온 사용자가 비밀번호를 바꿀 방법을 잃지 않게 한다 |
| 우선순위 | P1 |

**목적**: 복구 이메일로 재설정 링크를 받고 새 비밀번호를 설정한다.

**진입경로**: PUB-LOGIN의 재설정 링크 · 재설정 메일의 링크.

**화면 기능**

| 기능 | UI/처리 | 기능ID |
|------|---------|--------|
| 재설정 요청 | 아이디 또는 복구 이메일을 입력해 재설정 링크 발송을 요청한다. **응답은 계정 존재 여부와 무관하게 동일**하며 발송 빈도를 제한한다 — 응답이 갈리면 존재 확인 경로가 된다 | AUT-07 |
| 미등록 계정 안내 | 복구 이메일이 등록되지 않은 계정을 위해 **플랫폼 지원 담당의 보조 재설정 경로**를 같은 화면에 안내한다. 특정 계정이 미등록인지는 알려주지 않고 안내 문구를 항상 노출한다 | AUT-07 |
| 새 비밀번호 설정 | 링크의 토큰으로 진입해 새 비밀번호를 설정한다. 가입과 동일한 정책으로 검증하며 성공 시 **기존 세션과 refresh token을 전부 폐기**하고 로그인 화면으로 보낸다 | AUT-07 |
| 무효 링크 안내 | 만료(1시간)·사용 완료·불일치 토큰은 재설정 요청 단계로 되돌리고 **자가 재요청 경로**를 제공한다 — auth.reset_token_invalid/400 | AUT-07 |
| 반복 실패 처리 | 반복 실패는 호출 빈도 제한과 보안 이벤트 기록 대상이다. 화면은 재시도 가능 시각만 안내한다 | AUT-07 |

**주요 UI 요소**: 요청 단계(아이디 또는 이메일 필드 · 발송 버튼 · 보조 재설정 안내 · 로그인 링크), 발송 완료 안내(메일 확인 안내 · 만료 안내 · 다시 보내기), 설정 단계(새 비밀번호 · 확인 · 제출 버튼), 무효 링크 안내(재요청 버튼 · 로그인 링크).

**레이아웃·스크롤·모바일**: 인증 화면 4본의 단일 폼 카드 규격을 공유한다. 요청 · 발송 완료 · 설정 · 무효 네 단계를 **같은 카드 안의 상태 전환**으로 처리하고 새 레이어를 만들지 않는다(§3-1). 768 미만에서 카드 여백만 좁힌다.

**상태 처리**

| 상태 | 처리 |
|------|------|
| 로딩 | 링크 진입 시 토큰 검증 동안 진행 표시를 두고, 검증이 끝나기 전에 비밀번호 입력을 받지 않는다 |
| 빈 상태 | 해당 없음 — 폼 화면이다 |
| 에러 | auth.reset_token_invalid/400은 무효 링크 단계로 전환하고 재요청 버튼을 둔다 · auth.weak_password/422는 비밀번호 필드에 붙인다 · common.rate_limited/429는 재시도 가능 시각을 보인다. **발송 실패는 사용자에게 실패로 보이지 않는다** — 계정 존재 여부를 노출하지 않기 위해 요청 응답을 항상 완료 안내로 수렴시키고 실패는 서버 로그와 운영 알림으로 처리한다 |
| 권한거부 | 해당 없음 — 인증 여부와 무관하게 항상 열린다. 이 화면만은 인증 사용자도 진입 분기로 되돌리지 않는다 |

**데이터 연동**

- 요청 → POST /v1/auth/password-reset/request → **password_reset_tokens**(해시 저장 · 만료 1시간). 설정 → POST /v1/auth/password-reset/confirm → **users**(비밀번호 재해시) · **security_events** · 세션과 refresh token 전체 폐기. **낙관적 갱신 없음.** 상세 정본은 [../06_api/03_auth.md](../06_api/03_auth.md)다.

**담은 기능ID**: AUT-07

**비고**: **v1은 메일 발송 실패를 재시도하지 않는다** — 실패 로그만 남기고 사용자 응답은 성공과 동일하게 유지하며 반복 실패는 운영 알림으로 통보한다. 화면에는 이 사실이 드러나지 않으므로, 사용자가 메일을 받지 못하는 경우의 유일한 구제 경로는 **플랫폼 지원 담당의 보조 재설정**(SYS-USERS)이고 그래서 요청 단계에 그 안내를 상시 노출한다.

## PUB-CONSENT — 약관·개인정보·위치정보 동의

| 항목 | 내용 |
|------|------|
| 화면코드 | PUB-CONSENT |
| 라우트 | web_front SPA /consent · app_front 인증 스택 Consent |
| 접근권한 | 비인증(**개정 재동의 게이트 — 로그인 ④가 차단한 컨텍스트 발급 전 진입**) · 본인(APP-PRIVACY 미동의 항목·체크인 유도 진입) 두 진입을 모두 받는다 |
| 우선순위 | P0 |

**목적**: 약관·개인정보·위치정보 문서의 활성 버전에 동의를 받고, **필수 2종(약관·개인정보)**의 개정 시 재동의를 완료해 진입을 다시 연다 — 위치정보 개정은 진입을 막지 않는다(D-19).

**진입경로**: 개정 재동의 대상자의 로그인 직후 게이트 · APP-PRIVACY의 미동의 항목 동의 · 위치정보 미동의 상태에서 체크인을 시도한 경우의 유도.

**화면 기능**

| 기능 | UI/처리 | 기능ID |
|------|---------|--------|
| 동의 수집 | 문서 종류 **3종을 각각 표시하고 각각 체크**한다 — 약관(TERMS) · 개인정보(PRIVACY) · **위치정보(LOCATION)**. 각 항목에서 전문(PUB-LEGAL)으로 이동할 수 있고 버전과 유효 시작일을 함께 보인다 | PRV-02 |
| 별도 동의 분리 | **위치정보 동의를 다른 둘과 묶지 않는다**(위치정보법 §18). 위치정보 항목에는 **수집 항목 · 이용 목적 · 보유기간**을 함께 고지한다 | PRV-02 |
| 필수·선택 구분 | 약관·개인정보는 필수이며 미동의 시 진입할 수 없다. **위치정보는 미동의로도 진입할 수 있고 GPS 체크인만 막힌다** — 미동의 선택 시 그 사실과 결과를 안내하고 나중에 APP-PRIVACY에서 동의할 수 있음을 밝힌다 | PRV-02 |
| 재동의 게이트 | **필수 2종(약관·개인정보)의 개정 문서가 있으면** 목적지로 보내기 전에 이 화면을 띄우고, **재동의는 새 버전에 대한 신규 동의 이력으로 기록**한다. 기존 이력을 덮어쓰지 않는다. **위치정보 개정은 진입을 막지 않고** 체크인 시도 시점에 이 화면으로 유도한다(D-19) | PRV-02 · SYS-11(연계) |
| 멱등 처리 | 같은 사용자·종류·버전의 중복 동의 제출은 멱등 성공으로 처리한다 — privacy.consent_version_conflict/409는 사용자에게 오류로 보이지 않고 정상 완료로 수렴시킨다 | PRV-02 |
| 제출 후 분기 | 재동의 게이트에서 온 경우 **동의 완료 후 로그인을 다시 수행해** 원래 목적지로(REQ-SYS-16), APP-PRIVACY에서 온 경우 동의 현황으로, 체크인 유도에서 온 경우 체크인 화면으로 되돌린다 | AUT-10(연계) |

**주요 UI 요소**: 헤더(재동의 사유 안내), 문서 항목 3블록(제목 · 버전 · 유효 시작일 · 요약 · 전문 보기 링크 · 동의 체크), 위치정보 고지 블록(수집 항목 · 목적 · 보유기간), 전체 동의 체크, 제출 버튼, 위치정보 미동의로 계속하기 링크.

**레이아웃·스크롤·모바일**: 인증 화면 4본의 폼 카드 규격을 공유하되 문서 요약이 길어질 수 있어 **카드 본문이 스크롤 소유자**이고 제출 버튼은 카드 하단에 고정한다. 768 미만에서 문서 항목을 1열로 쌓고 앱에서는 하단 제출 버튼을 안전 영역 위에 띄운다. **전체 동의 체크가 개별 체크를 대신하지 않는다** — 전체 동의를 눌러도 개별 항목의 체크 상태가 그대로 보여야 사용자가 무엇에 동의했는지 확인할 수 있다.

**상태 처리**

| 상태 | 처리 |
|------|------|
| 로딩 | 활성 문서 3종을 읽는 동안 항목 자리를 잡는 스켈레톤을 보이고 제출 버튼을 잠근다 |
| 빈 상태 | 해당 없음 — 활성 버전은 종류별로 정확히 1개이므로 0건 목록이 발생하지 않는다 |
| 에러 | system.terms_not_found/404는 "약관을 준비 중입니다"와 문의 경로를 내고 제출을 막는다 · auth.consent_required/422는 미체크 항목을 강조한다 · privacy.consent_version_conflict/409는 오류로 표시하지 않고 완료로 수렴시킨다 |
| 권한거부 | 재동의 게이트 진입은 로그인 ④가 차단한 **컨텍스트 발급 전 상태라 미인증을 허용**한다 — 재동의 화면은 미인증 상태에서 열리고 동의 완료 후 로그인을 다시 수행한다(REQ-SYS-16). 본인 진입(APP-PRIVACY·체크인 유도)의 미인증 접근은 **로그인 유도**로 되돌린다(§1-2) |

**데이터 연동**

**담은 기능ID**: PRV-02 · SYS-11(연계) · AUT-10(연계)

**레이아웃·스크롤·모바일**: 단계 표시와 하단 액션 바(이전 · 다음/사업장 등록)를 스크롤 밖에 고정하고 **단계 본문(이름 있는 스크롤 영역)만 스크롤한다**(§5-3) — 1024 이상에서 콘텐츠 영역은 스크롤하지 않고, 인증 이후 화면이라 폭 상한을 두지 않는다(§5-2). 등록 직후 결과 화면도 같은 규칙이다. 1920·1440에서는 근무지 단계를 좌측 폼 + 우측 지도 2단으로 배치하고, 768 경계에서 지도를 폼 위로 올려 1열로 접는다. 지도 높이는 화면 높이에 비례해 잡되 390에서도 반경 원이 보이는 최소 높이를 확보한다. **지도 조작에 키보드 대체 경로를 둔다** — 좌표를 직접 입력할 수 있어야 한다(§5-1).

**레이아웃·스크롤·모바일**: **섹션 배치(SN)**다(§5-3) — 1024 이상에서 왼쪽 섹션 목록 + 오른쪽 **한 섹션만** 열고 콘텐츠 영역은 스크롤하지 않으며 섹션 본문만 스크롤한다. 연 섹션은 탭 쿼리 section이 가져 고지 줄의 액션이 프로필 섹션을 바로 연다. **탈퇴는 마지막 섹션**이라 다른 구획과 분리되고 목록에서 골라야 열리며, 색만으로 구분하지 않고 제목과 안내 문안으로 성격을 밝힌다(§5-1). 1024 미만은 전 섹션을 세로로 쌓고 본문이 스크롤한다. 비밀번호 입력이 있는 폼(비밀번호 변경 · 재인증 다이얼로그)은 아이디 자동완성 앵커를 품는다(§4-4). 확인 단계는 같은 블록 안의 상태 전환으로 처리하고 새 레이어를 만들지 않는다.

| 로딩 | 계정 정보·소속 사업장 요약 자리를 잡는 스켈레톤을 보이고 액션 버튼을 잠근다 |
| 빈 상태 | 소속 사업장이 0개면 요약 카드에 "소속된 사업장이 없습니다"와 등록 경로를 안내한다. 그 밖에는 해당 없음 — 계정 정보는 항상 존재한다 |
| 에러 | auth.invalid_credentials/401은 현재 비밀번호 필드(재인증에서는 다이얼로그 안)에 되돌린다 · auth.weak_password/422와 auth.password_unchanged/422는 새 비밀번호 필드로 · auth.reauth_required/401은 재인증 단계로 되돌린다(프로필 저장이 토큰 만료로 막히면 폼 아래 한 줄로 "저장을 다시 눌러 비밀번호를 한 번 더" 안내한다) · **auth.phone_taken/409는 새 연락처 필드에 붙이고 다이얼로그를 닫는다** — 다이얼로그 안의 일반 실패 문구로 뭉치면 어느 칸인지 알 수 없다 · common.validation_failed/400의 필드 상세는 그 필드에 붙인다 · 실패해도 입력을 지우지 않는다(§3-3) · **auth.owner_must_transfer/409는 탈퇴 블록에 "소유한 사업장을 먼저 폐쇄해 주세요"와 해당 사업장 목록·폐쇄 화면 링크를 함께 낸다** — 차단 사유만 알리고 해소 경로를 주지 않으면 사용자가 막힌 채로 남는다 |
| 권한거부 | **권한 안내**다 — 정지 계정은 비밀번호 변경과 탈퇴를 막고 사유를 보인다. 미인증 접근은 **로그인 유도**로 되돌린다(§1-2) |

**데이터 연동**

- 동의 내역 조회 → GET /v1/me/consents → **user_consents** · **terms_documents**. 계정 조회 → GET /v1/auth/session → **users** · **profiles**. 소속 요약 → GET /v1/me/workplaces → **workplace_members** · **workplaces**. 재인증 → POST /v1/auth/reauth(purpose PROFILE_UPDATE · ACCOUNT_DELETE). 프로필 수정 → PATCH /v1/me/profile(바뀐 필드만 · 연락처 · 복구 이메일이 실리면 X-Reauth-Token) → **profiles** · **security_events** — 응답은 세션 조회와 같은 모양이다(#17). 비밀번호 변경 → PATCH /v1/me/password → **users** · **security_events**. 탈퇴 차단 판정 → GET /v1/me/deletion-preflight → **workplaces** · **workplace_members**. 탈퇴 → DELETE /v1/me → **users** · **profiles** · **workplace_members** · **account_status_events** 단일 트랜잭션. **낙관적 갱신 없음.** 상세 정본은 [../06_api/03_auth.md](../06_api/03_auth.md)다.

**담은 기능ID**: **AUT-05** · AUT-06 · AUT-08 · AUT-09 · WRK-06(진입점) · CMP-07(고지) · **PRV-02(동의 내역)**

**비고**: **관리자 웹과 직원 앱의 계정 화면을 코드로 나눈 이유는 담는 기능이 갈리기 때문**이다. 이 화면은 소속 사업장 요약과 탈퇴 차단 판정을 다루고, 직원 앱의 APP-SETTINGS는 본인 인적사항 변경 요청과 사업장 전환을 함께 담는다. 두 화면이 공유하는 것은 비밀번호 변경(AUT-06)과 탈퇴(AUT-09) 두 축이며, 같은 계약을 같은 문안으로 구현한다. **프로필 수정(AUT-05)은 계정의 이름 · 연락처 · 복구 이메일을 바꾸며 사업장 인사 레코드의 성명·연락처와는 별개 축이다** — 직원 인적사항은 ADM-EMPLOYEE-DETAIL과 직원 앱의 변경 요청 경로가 갖는다. **재인증 문턱을 연락 축에만 둔다** — 복구 이메일은 비밀번호 재설정 링크의 수신처라 세션을 탈취한 사람이 바꾸면 계정 탈취가 완성되지만, 이름에 재인증을 요구하면 오탈자 하나에 비밀번호를 다시 받게 된다(계약 정본 [../06_api/03_auth.md](../06_api/03_auth.md) #17).
