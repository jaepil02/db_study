## 이 문서군의 성격

본 문서군은 **to-be 설계 정본**이다. 아직 구현이 없으므로 모든 서술은 "구현이 이렇게 되어야 한다"는 계약이며, 근거는 실측이 아니라 **원천 문서(docs_ref2/ 4본)와 확정 결정(D-NN · ADR-NN)**이다. 구현이 진행되면 각 문서를 as-built로 승격하고 실측 근거(코드 경로·DB 카탈로그·실브라우저 검증)로 갱신한다.

**미확인과 미설계를 구분한다.** "미확인 — 확인 전 시드 금지"로 등재된 값은 확인된 값처럼 쓰지 않고 미확인 상태 그대로 등재한다 — **원천 등재분 16건은 2026-08-03 전건 확인 완료됐고**(정본 [01_overview/05_priorities_roadmap.md](./01_overview/05_priorities_roadmap.md)) 이 원칙은 이후 새로 생기는 미확인 항목에 적용된다. 설계하지 않은 것(v1.1 이월)은 부정형으로만 언급한다.

## 편집 전 필수 절차

1. [README.md](./README.md)의 **고정 기준**을 확인한다. 수치를 바꾸는 편집이면 정본과 파생 집계를 같은 변경 단위에서 함께 고친다.
2. 서술의 근거를 명기한다 — 원천 문서(docs_ref2/ 경로 평문) 또는 결정 ID(D-NN · ADR-NN). 근거 없는 신규 사실을 만들지 않는다.
3. **같은 폴더 기존 문서의 골격(메타 블록 · H2 순서 · 표 컬럼)을 우선 따른다** — "동일한 형식, 다른 내용"이 원칙이다.
4. **"문서에 없다"고 결론짓기 전에 세 자리를 다 본다** — 이 문서군은 같은 표면을 **표면 요약 표 · 계약 표 · 서술 문단** 세 자리에서 다루므로, **검색어가 한 축만 훑으면 다른 축은 없는 것으로 보인다.** 실측 사례 — 급여 선점검의 점검 항목이 계약 표에 있는데 표면 번호로만 검색해 "정본이 없다"고 결론지은 자리가 있었다(2026-09-08). **없다는 결론은 있다는 결론보다 근거가 더 필요하다.**

## 열거의 정합

- 개수를 쓰면 그 자리에서 항목을 세어 맞추고 검산식을 남긴다.
- 다른 문서의 집계를 빌려 쓰지 않는다 — 정본을 다시 세거나 정본을 링크한다.
- 세는 기준이 둘이면 기준을 밝힌다(예: 화면 수는 H2 블록만, 화면 내 요소 H3 제외).
- 전수 · 유일 · ~만 · ~뿐으로 단언하기 전에 정본 집합을 확인한다.
- 항목을 추가·삭제하면 그 항목을 세는 모든 자리를 훑는다.
- 같은 사실의 정본을 둘로 만들지 않는다.
- **한 문서가 같은 수치를 여러 자리에서 세지 않는다.** 세는 자리를 하나로 두고 나머지는 그것을 가리킨다 — 표·검산식·각주가 각각 세면 **갱신이 한 자리만 닿고 나머지가 조용히 어긋난다.** 실측 사례가 넷이다: 접근 모델의 도입 문장이 표와 갈렸고(15종 vs 6행 합 16), 정책 전수 절의 헤딩 넷이 정책 수 요약 표와 갈렸으며, 함수 구성 표의 계·검산식·실측 각주가 세 자리로 흩어져 있었고, ADR-25가 "급여 계산만 payroll 모듈 안에"처럼 **배타 열거**로 새 계층이 생기는 순간 틀렸다.
- **"불변"을 말하는 문장에 수치를 박지 않는다.** 무엇이 왜 안 바뀌는지를 적고 **값은 정본이 갖는다** — "정책 169는 불변"이 아니라 "ALTER POLICY라 정책 수는 불변"이다. 값을 박아 두면 다음 신설마다 **이력이 아닌 자리가 또 어긋나고**, 개정일 줄과 달리 그 문장은 현재 상태를 서술하므로 고쳐야 하는데 검산에 걸리지 않아 남는다. **실측 근거** — V0715~V0718의 개정일 줄이 전부 "정책 172 · 봉인 72 · 헬퍼 39는 전건 불변"으로 값을 박아 뒀는데 **V0720 하나가 그 다섯 줄을 한꺼번에 과거 사실로 만들었다.** 개정일 줄은 이력이라 고치지 않으므로 그대로 남지만, **같은 문장이 본문에 있었다면 다섯 자리를 찾아 고쳐야 했다** — "ALTER POLICY라 정책 수는 불변"이었다면 한 자리도 움직일 필요가 없었다.
- **표는 열 수를 지킨다.** 두 열에 공통인 내용은 칸을 비우지 않고 **상동**으로 적거나 **표 밖으로 뺀다** — **빈 칸은 "왼쪽에만 해당한다"로 읽혀 쓰려던 뜻의 반대가 된다.** 대조표에 대조 아닌 행이 섞이면 표의 축도 함께 흐려지므로, 그런 행은 애초에 표 밖 항목이다.
- **어긋난 사례 하나가 분류를 강제한다.** 같은 형태의 사례를 여러 번 겪어도 분류는 저절로 나오지 않는다 — **앞의 것들과 증상 등급이 다른 사례가 나올 때** 비로소 기존 분류가 무엇을 빠뜨렸는지 드러난다. 그러므로 사례를 더할 때 **"이번엔 다른 형태"로 적고 넘어가지 말고 그것이 기존 분류의 어느 칸에도 들어가지 않는지를 먼저 본다** — 들어가지 않으면 칸을 늘리는 것이 아니라 **분류 축 자체를 다시 짜야 하는 신호**다. 실측 사례 — 서버 배치 읽기 축의 네 번째가 앞의 셋과 증상 등급이 달라, 읽기를 **두 종류로만 세고 있었다**는 것이 그때 드러났다(계산 입력 · 대상 열거의 입력에 **판정 입력**이 빠져 있었다).
- **닫는 축을 목록으로 쓰지 않는다.** "현재 X와 Y가 둔다"처럼 전수를 세는 형태는 새 항목이 생기는 순간 틀리는데 **틀렸다는 사실이 드러날 자리가 없다.** 판정 기준은 하나다 — **그 문장이 항목 하나가 늘었을 때 틀리는가.** 예시로 드는 것은 괜찮다.

## 범위 규약

범위는 **v1 98기능**(원천 docs_ref2/features_p0.md의 필수 94 + D-23 채택 4)이다. v1.1 이월 41기능과 영구 제외 6기능은 [01_overview/02_goals_scope.md](./01_overview/02_goals_scope.md)의 Out 범위 표가 유일한 등재처이며, 다른 문서는 부정형으로만 언급한다(예: "ADVISOR 역할은 v1에 두지 않는다(WRK-13 이월)"). 이월 기능이 데이터 모델에 남긴 확장 지점은 주석·비고로만 표기하고 미사용 구조를 미리 만들지 않는다.

## 하지 말 것

- v1 제외 기능을 현행 범위처럼 서술하지 않는다.
- 미확인 기준값을 확정 값처럼 쓰지 않는다 — "미확인 — 확인 전 시드 금지"를 유지한다.
- 정본 밖에서 ID를 채번하지 않는다. 미러(06_api/02_errors.md)에서 코드를 신설·개명·폐기하지 않는다.
- 인라인 백틱을 쓰지 않는다.
- 확정된 결정(D-NN · ADR-NN)을 재론하는 서술을 다른 문서에 흩뿌리지 않는다 — 결정 문서를 링크한다.
- 근거 없는 구체 수치(요율·세액·한도)를 본문에 박지 않는다 — 기준값 테이블 조회 계약으로 서술한다.
- legacy(구 Supabase 설계) 개념을 부활시키지 않는다 — Supabase Auth · Edge Function · 클라이언트 직결 데이터 접근 전제 서술 금지. 재구축 스택은 Java · Spring Boot · Spring Data JPA + MyBatis · React + Vite + React Router · React Native다(D-21). **Flyway와 Spring Security는 금지 대상이 아니다** — 2026-09-06 전환으로 현행 스택에 편입됐다(ADR-27 · ADR-25).
- **NestJS를 현행 스택으로 서술하지 않는다**(D-21). Prisma · Prisma 클라이언트 확장 · Node.js 런타임 · npm 스크립트 · 모듈/프로바이더/가드/인터셉터 어휘를 백엔드 계약처럼 쓰지 않는다. 언급이 필요하면 "NestJS 전제 서술을 두지 않는다"는 부정형으로만 적는다. Node.js · npm · Vitest는 web_front · app_front 축에서만 쓴다.
- **Next.js를 현행 스택으로 서술하지 않는다**(D-20). 라우트 그룹 · 서버 미들웨어 · 서버 컴포넌트 셸 · 정적 생성 · 증분 재생성 · Server Actions · Route Handler · NEXT_PUBLIC 접두를 계약처럼 쓰지 않는다. 언급이 필요하면 "Next.js 전제 서술을 두지 않는다"는 부정형으로만 적는다.
