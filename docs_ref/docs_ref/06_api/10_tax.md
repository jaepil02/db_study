v1의 신고 범위는 **기한 알림 + 퇴사 관련**이다(D-09). 원천징수이행상황신고 · 지급명세서 · 연말정산 · 중도퇴사자 정산 · 보수총액신고 · 일용근로내용 확인신고서는 v1에 두지 않으며, 그래서 그 표면을 만들지 않는다.

**자동 제출을 하지 않는다.** 이 도메인의 산출 표면은 전부 EDI 업로드용 **데이터 생성까지**이고 실제 제출은 사용자가 홈택스·4대보험 EDI에서 수행한다. 다만 **기능을 만들지 않는 것과 잘못된 값을 조용히 내는 것은 다르므로**, 미지원 범위를 명시적으로 고지하는 표면(#11)을 따로 둔다.

**퇴사 한 건이 세 종류의 시계를 예고하되 시작 사건은 같지 않다** — 4대보험 상실신고(적용 보험 중 가장 이른 기한 — 건강보험 14일 · 그 밖 다음달 15일)와 금품청산·퇴직금 지급(퇴직일 + 14일)은 퇴직 사실에서 기산하므로 **퇴사 연동 트리거**([05_hr.md](./05_hr.md))가 과제를 만들고, 이직확인서(요청일 + 10일)는 근로자의 발급 요청일부터 기산하므로 **#5 요청 접수 표면**이 만든다. 과제의 기산일과 기한은 생성 후 불변이라 아직 오지 않은 요청을 기준으로 미리 만들 수 없다. 감지는 #12가 담당하며 **실행 시각이 아니라 기준일 파라미터로 동작해 재실행 시 같은 결과를 낸다**.

## 공통 규약

| 항목 | 규칙 |
|------|------|
| 스코프 | 전 관리 표면이 /v1/workplaces/{workplaceId}/tax/… 이고 스트리밍 종점만 /v1/tax/documents/download/{token}이다 |
| 권한 축 | MANAGER 전용이다. STAFF가 접근하는 표면이 없고 OWNER 전용 액션도 없다 |
| 멱등 | 신고자료 생성(#1)과 이직확인서 생성(#5) **2표면**이 Idempotency-Key 필수다. 외부에 나가는 문서를 만드는 표면이라 중복 생성이 곧 중복 제출 위험이다 |
| 잠금 | 별도 잠금이 없다. 산출은 확정된 급여·인사·보험 데이터를 읽어 문서를 만드는 읽기 중심 경로다 |
| 페이지네이션 | 오프셋 2표면(#2 · #6) · 범위 조회 1표면(#10). 기한 캘린더는 월·연 단위 조회라 스스로 상한을 갖는다 |
| 산출물 저장처 | **documents 단일**이다. 신고자료·이직확인서의 실체·파일 해시·보존기한을 documents가 일원 보유하며 **별도 내보내기 작업 원장(export_jobs)을 쓰지 않고 export 네임스페이스 에러 코드도 쓰지 않는다** |
| 다운로드 | 토큰 발급(#4 · #8) → 스트리밍(#9) 2단이다. 만료·재사용은 payslip.download_token_expired/410으로 명세서와 코드를 공유한다 |
| 전용 코드 없음 | **TAX 도메인은 전용 에러 코드를 두지 않는다.** 실패 원인이 전부 상위 도메인(급여 · 인사 · 기준값)의 코드로 표현된다 |
| 자동 제출 금지 | 어떤 표면도 외부 기관에 제출 요청을 보내지 않는다. 산출물은 사용자가 내려받아 직접 업로드한다 |
| 계산 재사용 | 이직확인서의 평균임금은 급여 도메인의 산식(REQ-PAY-09)을 **재사용**한다. 별도 산정 축을 만들지 않는다 |

⑥ 기한 등록         **취득·상실신고 기한은 적용 보험 중 가장 이른 값**이다(건강보험 14일 · 그 밖 다음달 15일).

| 항목 | 2. 목록 | 3. 상세 | 4. 내보내기 토큰 |
|------|--------|--------|-----------------|
| 입력 | reportType · status · 기간 · employeeId · 오프셋 | — | format(EDI · XLSX) |

- **상실일과 퇴사일은 다르다.** 상실일은 최종 근무일 기준이며 이 구분을 흐리면 신고 기한과 보험료 부과 기간이 함께 틀어진다(REQ-TAX-01).
- **보험관리번호의 조회처는 사업장이다.** 고용보험과 산재보험이 사업장(장소) 단위로 성립하므로 번호도 직원이 아니라 사업장에 붙으며, 직원별 보험 적용정보는 가입 여부·취득일·상실일·보수월액만 반환한다. **번호 축은 보험 계열마다 다르므로** 고용·산재 공용 번호와 연금·건강 각각의 번호를 구분해 담고, 대상 보험의 번호가 비면 그 보험의 자료 생성을 **workplace.mgmt_no_required/422**로 막고 **비어 있는 계열을 details로 반환**한다(REQ-TAX-01). details는 배열이고 원소는 **insuranceType**(자료 생성이 막힌 보험)과 **mgmtNoField**(채워야 할 칸 — insuranceMgmtNo · pensionMgmtNo · healthMgmtNo) 둘이다 — 앞은 **무엇이 막혔는지**를, 뒤는 **어디를 채우면 되는지**를 알린다. 계열 매핑은 REQ-HRM-17 이 정본이며 화면은 mgmtNoField 로 사업장 설정의 해당 칸으로 잇는다. **404가 아니다** — 자원이 없는 것이 아니라 전제가 비어 있는 것이며, 404는 존재 은닉 축이라 「채우면 된다」를 「없다」로 알린다.
- **#2의 허용 정렬에 대상자명이 있는 것은 화면의 기본 정렬이 기한 잔여일 오름차순 → 직원명 오름차순이기 때문이다**(ADM-TAX-FILING). **접수일(requestedAt)은 여기 없다** — 이직확인서 전용 열이라 이 표면에서는 전건 널이고, 같은 원장을 쓴다는 이유로 열면 **아무것도 정렬하지 않는 축**이 생긴다.
- **대상자명 정렬은 인사 원장이 아니라 산출 자료 스냅샷의 값을 본다.** 응답에 실리는 이름이 그 스냅샷의 값이고(아래 「원천을 다시 읽지 않는다」와 같은 축) **표시와 정렬이 다른 원천을 보면 정렬된 목록이 정렬되지 않은 것처럼 보인다** — 개명한 대상자가 있으면 즉시 드러난다. 인사 원장을 조인하지 않는 것이 이 축의 계약이다.
- **자동 제출은 범위 밖**이다. 응답에 submissionChannel을 담아 사용자가 어디에 업로드해야 하는지 안내하되 서버가 호출하지 않는다.
- **과제 행은 이 표면이 처음 만드는 것이 아닐 수 있다.** 상실 과제는 퇴사 확정([05_hr.md](./05_hr.md) #35)이, 취득 과제는 입사 확정(#11)이 먼저 열어 두며 **멱등키 축이 같아 같은 행을 가리킨다**(취득 = **(직원, 입사일)** · 상실 = (직원, 최종 근무일)). 그래서 이 표면은 행을 여는 것이 아니라 **이번에 만든 산출 자료 스냅샷을 그 행에 붙인다** — **먼저 열린 행의 detail은 기한 시계를 열 때의 값이라 보험별 항목값이 없고**, 그것을 그대로 실으면 목록·문서가 옛 스냅샷을 읽는다.
- **취득 신고의 기준일은 입사일 하나로 닫혀 있다.** 법정 취득일이 고용된 날이고 **기한이 기산일에서 파생**되므로, 이 표면과 입사 확정(#11)이 값을 달리 유도하면 같은 의무가 다른 마감을 갖고 멱등키까지 갈려 **같은 기한이 캘린더에 두 번 뜬다.** 그래서 취득 축에는 **유도 기준일이 없고** 요청의 baseDate 도 받지 않는다. 실리면 **common.validation_failed/400** 이며 field 는 baseDate · 문안은 「취득 신고의 기준일은 입사일로 고정됩니다.」다 — 전제가 비어 있는 것(422)이 아니라 **그 자리에 올 수 없는 값**이라 형식 축이다. **조용히 무시하지 않는 이유**는 무시하면 사용자가 자기가 넣은 날로 자료가 만들어졌다고 믿고, 응답의 기준일이 다른 것을 값이 저장되지 않은 것으로 읽기 때문이다. **보험별 실제 취득일은 축이 아니라 내용**이라 산출 자료 스냅샷에 남는다.
- **취득 응답의 기준일 축이 상실과 다르다.** 취득은 baseDate 가 언제나 입사일이고 derivedBaseDate 가 그와 같은 값이라 **baseDateCorrected 는 항상 false** 다 — 고를 여지가 없으면 「정정」이 성립하지 않는다. 그 축은 **상실에만** 남으며 상실은 유도값(최종 근무일)과 요청값이 다를 때 true 이고 **정정한 기산일에서 기한이 다시 파생**된다. 입사가 확정되지 않은 직원의 취득 자료 생성은 **common.validation_failed/400** · field baseDate 이며 문안은 「입사가 확정되지 않아 취득 신고 기준일을 정할 수 없습니다.」다.
- **기한 기준값 부재는 payroll.missing_reference_value/422이고 details가 누락 키를 낸다** — **배열이며 없는 키를 전부 담는다**(원소는 category = FILING_DEADLINE과 key = insurance_acquisition:{보험} 또는 insurance_loss:{보험}). **하나만 알리면 사용자가 같은 실패를 네 번 만난다** — 보험별로 갈린 기한이 여럿 비면 각각을 채워야 하기 때문이다. **code만으로는 무엇을 채워야 하는지 알 수 없다** — 이 코드가 기준값 여러 종을 한 코드로 대표하므로 details를 두는 판정 기준에 걸린다([01_conventions.md](./01_conventions.md)). **적용 보험의 키 중 하나라도 비면 과제를 만들지 않는다** — 부분 파생을 하면 없는 기한이 조용히 빠져 실제보다 늦은 마감이 굳는다.

- **#6의 허용 정렬에만 접수일이 있다.** 화면의 목록 열이 퇴직자 · 접수일 · 기한 잔여일 · 상태이고 **접수일 열을 갖는 표면이 이곳뿐**이기 때문이다 — 다른 유형의 과제는 접수일이 없어 전건 널이다. 대상자명 정렬이 산출 자료 스냅샷의 값을 보는 것은 #2와 같다.
- **요청 접수일을 반드시 기록한다**(REQ-TAX-02). 10일 시계의 기산일이 접수일이라 이 값이 없으면 기한 자체가 성립하지 않는다.
- **이 표면이 기한 과제(SEPARATION_CERTIFICATE)의 유일한 생성 지점이다.** 퇴사 연동 트리거는 이 과제를 만들지 않는다 — 과제의 기산일·기한은 생성 후 불변이라 요청이 오기 전에 만들면 사실과 다른 기한이 굳고 접수 시점에 고칠 수 없다. 같은 직원·같은 요청의 중복 접수는 멱등키가 흡수한다.
- 위반 시 과태료는 10만·20만·30만원이며 **퇴사자가 실업급여를 받지 못하면 즉시 민원**이 되므로 #12가 임박을 경보한다.

| 알림 연동 | 사전 알림은 compliance_deadline 타입으로 발송한다. 발송 주체는 #12다 |
| 기준값 부재 | 기한 정책값이 없으면 그 항목을 만들지 않고 부재를 응답에 드러낸다. **임의 기본 기한을 만들지 않는다** |

**어긋남 등재를 정정한다 — 정본 쪽이 틀렸던 자리다**(2026-09-10). 2026-09-09에 "web_front mock의 취득 신고 기한 취득일 + 14일이 정본(다음달 15일)과 다르다"고 등재했으나, **조문 본문을 확인한 결과 건강보험은 실제로 취득·상실일부터 14일**이다(국민건강보험법 §8② · §10② — 출처 정본 [../03_requirements/18_official_references.md](../03_requirements/18_official_references.md)). **어긋난 쪽은 mock이 아니라 「넷을 한 값으로 단정한」 정본이었다.** 지금의 계약은 **적용 보험 중 가장 이른 기한**이고 mock의 14일은 건강보험 적용 시 맞는 값이다 — 다만 **적용 보험과 무관하게 늘 14일로 적는 것은 여전히 어긋남**이라 프런트 정합은 남는다(다른 세션 범위라 여기서 고치지 않는다). **같은 숫자가 세 축(건강보험 신고 · 금품청산·퇴직급여 · 검증 대기 자동 정지)에 걸쳐 있다는 관찰은 유지되며**, 그것이 **"14일이 보이면 어느 축인지 먼저 묻는다"**를 요구하는 근거다.
| 원천징수 항목 | 항목은 캘린더에 표기하되 **산출 표면을 두지 않는다** — v1 미지원이며 #11이 그 사실을 고지한다 |
| 원천세 과제 생성 | **WITHHOLDING_FILING 과제를 만드는 주체는 급여 확정 트랜잭션의 부수효과**다([08_payroll.md](./08_payroll.md) #17). 이 표면은 만들어진 과제를 읽기만 한다 |
| 원천세 기한 파생 | 파생 입력은 두 축이다 — **사업장의 원천세 납부 주기 설정**(월별 · 반기납부 특례)과 **신고 기한 정책값 category**다. 값으로 파생하면 **월별 납부는 귀속 지급일의 익월 10일 · 반기납부 특례는 7월 10일과 1월 10일**이며, 두 축 중 하나라도 없으면 과제를 만들지 않고 payroll.missing_reference_value/422로 부재를 드러낸다(REQ-TAX-03) |

### 11. GET /v1/workplaces/{workplaceId}/tax/unsupported-scope — v1 미지원 범위 고지 (TAX-11)

| 미지원 항목 | v1 처리 |
|------------|--------|
| 원천징수이행상황신고서 · 지급명세서 · 연말정산 · 중도퇴사자 정산 · 보수총액신고 · 일용근로내용 확인신고서 | 미지원을 명시하고 홈택스·EDI 직접 처리를 안내한다. 지급명세서는 **2027-01 지급분부터 매월 전환이 확정**되어 있어 향후 산출 단위를 처음부터 월로 설계한다 |
| **두루누리 사회보험료 지원** | 지원 대상이면 근로자 부담분까지 지원되어 **공제액과 명세서 금액이 실제와 달라진다**. "두루누리 대상일 수 있으니 확인하라"는 안내를 계산 결과에 표기하고 결과에 적용 여부 필드를 미리 둔다 |
| **일용근로자(DAILY) 급여·원천징수** | 고용형태 DAILY는 급여 계산 대상에서 **명시적으로 차단**한다. 일용 분리과세·소액부징수를 구현하지 않은 채 상용 로직으로 계산하면 세액이 틀린다 |
| 포괄임금·고정OT | 포괄임금 계약 사업장은 v1 대상이 아님을 고지한다. 실근로 가산과의 차액 산정을 구현하지 않는다 |
| 휴업수당 | v1 범위 밖이다 |

- 이 표면이 존재하는 이유는 **조용히 틀린 값을 내지 않기 위해서**다(REQ-TAX-05). 미지원 기능을 안 만드는 것으로 끝내면 사용자는 제품이 처리했다고 믿는다.
- 응답은 항목별 사유와 대체 경로(홈택스 · EDI · 노무 상담)를 함께 담는다. 등재 정본은 [../01_overview/02_goals_scope.md](../01_overview/02_goals_scope.md)의 Out 범위 표다.
- **계산 결과는 참고자료이며 신고·납부의 최종 책임이 사업주에게 있음**을 함께 고지한다(REQ-GLB-20).

### 12. 정기작업 checkComplianceDeadlines (배치)

| 항목 | 내용 |

| 동작 | 금품청산 14일 · 이직확인서 10일 · 4대보험 상실신고 기한의 **임박과 경과를 감지해 경보**한다 |
