insadesk의 데이터 접근 표면은 **Spring REST 단일 축**이다. 웹(web_front)과 앱(app_front)이 같은 엔드포인트를 공유하고 인증 축만 갈린다 — 웹은 세션 쿠키 + CSRF 헤더, 앱은 Bearer JWT다(REQ-AUT-08). 브라우저는 API 서브도메인을 **직접 호출**하며 중간 프록시·BFF를 두지 않는다(D-03).

이 문서는 전 도메인 파일이 인용하는 규약의 정본이다. 도메인 파일은 여기를 참조하고 다시 정의하지 않으며, 여기서 정하지 않은 것만 그 도메인의 공통 규약 절에 적는다.

**판정은 언제나 서버다.** 클라이언트 검증은 사용성 보조이고, 최종 강제는 서비스 레이어 1차 검증 + PostgreSQL RLS 2차 심층방어다([../04_architecture/03_multitenancy_rls.md](../04_architecture/03_multitenancy_rls.md)). 계산·시각·권한 판정 결과를 클라이언트에서 받아 그대로 저장하는 표면을 만들지 않는다.

## 표면 계층

| 계층 | 방식 | 무결성 강제 | 쓰는 곳 |
|------|------|------------|---------|
| REST | HTTP 요청·응답 JSON. 컨트롤러 진입에서 요청 DTO를 선언적 검증으로 파싱한다 | 필터 체인·서비스 계층(멤버십·역할·활성 사업장) → 서비스 규칙 → DB 제약·RLS | 조회·변이 전량 |
| SSE | 서버 → 클라이언트 단방향 이벤트 스트림. Redis 채널 팬아웃 | 연결 수립 시 인증·수신자 스코프 고정. 이후 이벤트는 그 스코프만 흐른다 | 인앱 알림 배달(NTF-01) **1표면** |
| 다운로드 | 1회용 토큰 발급 + 서버 스트리밍 응답 | 토큰 단기 만료·1회 소비 · 세션·IP·user agent 보조 바인딩 | 명세서 · 근로계약 완료본 · 민감 문서 · 임포트 실패 리포트 · 임금대장 · 신고자료 · 감사 내보내기 |
| 서버 내부 | HTTP 표면이 없는 종점 — 정기작업 · 도메인 이벤트 부수효과 · 자동 기록 | 서버 전용 실행 경로. 사용자 세션으로 도달할 수 없다 | 정기작업 8건 · 위치정보 확인자료 기록 · 알림 발화 · 퇴사 연동 트리거 |

계층을 고르는 기준은 하나다 — **클라이언트가 요청할 수 있는 일인가.** 요청할 수 있으면 REST이고, 서버가 밀어 주기만 하면 SSE이며, 응답 본문이 파일이면 다운로드이고, 사용자가 요청할 수 없어야 하면 서버 내부다. **WebSocket·GraphQL을 쓰지 않으며, 웹 호스팅 계층에 업무 데이터 경로를 두지 않는다**(D-20 · [../08_tech_stack/03_backend.md](../08_tech_stack/03_backend.md)).

## 기본 경로·버저닝

| 항목 | 규약 |
|------|------|
| 호스트 | API는 api 서브도메인(EC2)에 두고 웹은 app 서브도메인(Vercel)에 둔다 — 전환 후에도 **웹 오리진은 하나**다(D-20). 브라우저가 api를 직접 호출한다(D-03) |
| 경로 접두 | 모든 엔드포인트는 /v1로 시작한다. 문서의 경로 표기는 접두를 포함한 전체 경로다 |
| 버저닝 방식 | **경로 버저닝**이다. Accept 헤더 협상·쿼리 파라미터 버전을 쓰지 않는다 |
| 버전 증분 조건 | 기존 필드 삭제·의미 변경·필수 파라미터 추가처럼 **기존 클라이언트를 깨뜨리는 변경**에만 /v2를 연다. 필드 추가·선택 파라미터 추가는 v1 안에서 한다 |
| 동시 운영 | 앱은 스토어 심사·사용자 업데이트 지연 때문에 구버전이 남는다. 새 버전을 열면 직전 버전을 최소 1개 릴리스 주기 동안 함께 운영한다 |

**경로 버저닝을 택한 근거**는 표면이 셋(직원 앱 · 관리자 웹 · 시스템 웹)이고 그중 하나가 강제 업데이트를 걸 수 없는 모바일 앱이라는 점이다. 헤더 협상은 프록시·캐시·로그에서 버전이 보이지 않아 어느 클라이언트가 무엇을 부르는지 운영 중에 분간할 수 없고, 브라우저 주소창·curl 재현에도 헤더를 매번 실어야 한다. 경로에 박으면 nginx 접근 로그와 OpenAPI 문서에서 버전이 그대로 드러난다.

## 자원 명명

| 규칙 | 내용 |
|------|------|
| 형태 | **케밥 표기 복수형 명사**다 — /v1/workplaces · /v1/payroll-runs · /v1/attendance/change-requests |

| 필드 | 요청·응답 JSON 필드는 **카멜 표기**다. DB 컬럼의 snake_case를 그대로 노출하지 않는다 |
| 동사 | 자원 CRUD로 표현되지 않는 **상태 전이·실행**만 하위 경로 동사로 둔다. 전부 POST이며 **그 자원에 일어나는 일을 이름으로 갖는다** — /confirm · /void · /approve · /complete · /waive처럼 쓴다. **동사 목록을 여기서 닫지 않는다** — 전이가 늘면 동사가 늘고, 열거를 정본으로 두면 **늘 때마다 이 칸이 틀리는데 드러날 자리가 없다**(실측 — 기한 과제의 완료·면제가 열거 밖이었다) |
| 동사를 쓰는 근거 | 급여 확정은 payroll_runs 한 행의 status만 바꾸는 것이 아니라 검증·잠금·동결·명세서 큐 등록을 한 트랜잭션으로 수행한다. PATCH { status } 로 표현하면 클라이언트가 상태 문자열을 고르는 모양이 되어 허용 전이 판정이 요청 본문 검증으로 밀려난다 |
| 동사를 나누는 기준 | **전이마다 요구 입력이 다르면 전이마다 동사를 둔다.** 한 표면에 몰면 **필수 여부가 본문 값에 따라 갈리는 조건부 검증**이 되어, "무엇이 필수인가"를 스키마가 아니라 분기 코드가 갖는다. 실측 — 기한 과제의 OPEN → COMPLETED와 OPEN → WAIVED는 **면제만 사유가 필수**라 하나의 PATCH로는 표현되지 않았다([11_compliance.md](./11_compliance.md) #14 · #15) |
| 중첩 깊이 | 경로 중첩은 **사업장 → 자원 → 하위 자원** 3단까지다. 그보다 깊어지면 하위 자원을 최상위로 올리고 쿼리 필터로 좁힌다 |

## 사업장 스코프

**활성 사업장은 경로에 명시한다** — /v1/workplaces/{workplaceId}/... 다. 헤더·쿠키·서버 세션에 담아 암묵 전달하지 않는다.

| 항목 | 규약 |
|------|------|
| 전달 방식 | 경로 변수 {workplaceId}. 사업장 스코프 자원의 모든 엔드포인트가 이 접두를 갖는다 |
| 서버 재검증 | 매 요청 (요청자, workplaceId) 멤버십·역할·사업장 상태를 다시 판정한다. 불일치는 **auth.workplace_forbidden/403**이다(REQ-WRK-20) |
| 스코프 밖 자원 | 계정 단위 자원은 /v1/me/... · /v1/auth/... · /v1/notifications이고, 플랫폼 운영은 /v1/system/...이다. 셋 다 사업장 접두를 갖지 않는다 |
| RLS 연동 | 1차 인가 통과 후 **DataSource 프록시가 트랜잭션 진입 시 세션 변수를 설정**한다 — 주입 변수는 **5종**(현재 사용자 · 시스템 컨텍스트 · 트랜잭션 컨텍스트 3 — 초대 수락 · 사업장 폐쇄 · 사업자 재검증)이며 **활성 사업장·역할은 세션 변수로 두지 않고** 행의 사업장 열과 헬퍼로 평가한다(D-21 · ADR-28). 경로 변수 {workplaceId}는 서비스 1차 검증의 입력이다 |
| 캐시 격리 | 클라이언트 쿼리 키에 workplaceId가 반드시 들어간다. 전환(WRK-06) 시 타 사업장 응답이 캐시에 남지 않는다 |

**경로에 두는 근거는 전환의 정합성이다.** 활성 사업장을 서버 세션에 두면 같은 URL이 사용자의 마지막 전환 시점에 따라 다른 데이터를 돌려준다 — 브라우저 탭 둘을 서로 다른 사업장으로 열 수 없고, 응답을 캐시 키로 구분할 수도 없으며, 로그의 요청 한 줄만 보고 어느 테넌트의 조회였는지 알 수 없다. 앱 역시 토큰 채널이라 서버 세션 축이 아예 없다.

## 인증

| 표면 | 자격 증명 | 상태 변경 요청 |
|------|----------|---------------|
| 관리자 웹 · 시스템 웹 · 공개 페이지(web_front) | **세션 쿠키** — HttpOnly · Secure · SameSite=Lax · Domain은 상위 도메인 스코프(D-03) | **CSRF 토큰 헤더 필수.** 부재·불일치는 auth.csrf_token_invalid/403 |
| 직원 앱(app_front) | **Bearer JWT** — Authorization 헤더. access + refresh 2종, refresh 회전 재발급 | CSRF 대상이 아니다 — 쿠키 자동 전송이 없어 교차 출처 위조가 성립하지 않는다 |

- **두 채널이 같은 엔드포인트를 공유한다.** 가드가 Authorization 헤더를 먼저 보고 없으면 세션 쿠키로 판정한다. 한 요청이 두 자격 증명을 동시에 실어 오면 거부한다 — 어느 쪽으로 인가됐는지가 감사 로그에서 갈린다.
- 미인증 공개 경로는 **회원가입 · 로그인 · 아이디 중복 확인 · 비밀번호 재설정 요청과 확정 · 약관·개인정보·위치정보 활성 문서 조회**(이상 REQ-AUT-12) · **CSRF 토큰 발급**(REQ-AUT-08 웹 세션 계약의 파생 — 로그인 요청 자체가 상태 변경이라 토큰이 선행해야 하는 순환 방지다, [03_auth.md](./03_auth.md) #4) · **요금제 목록**(REQ-SUB-01 · D-02)뿐이다. 그 밖은 전부 인증을 요구한다.
- 만료·revoke·서명 불일치는 **auth.token_invalid/401**이다. 계정 상태가 SUSPENDED·DELETED로 바뀌면 다음 요청에서 auth.account_suspended/403 · auth.account_deleted/403으로 끊긴다.
- CORS 허용 오리진은 웹 오리진 하나이며 자격 증명 전송을 허용한다. **CORS 위반에는 전용 에러 코드를 두지 않는다** — 프리플라이트 단계에서 브라우저가 차단해 응답 본문이 애플리케이션에 도달하지 않는다.

### 재인증

민감 작업은 비밀번호 재인증 토큰을 선행 요구한다(REQ-AUT-25).

| 항목 | 규약 |
|------|------|
| 발급 | POST /v1/auth/reauth에 현재 비밀번호를 보내 단기 재인증 토큰을 받는다. 토큰은 Redis에만 두고 데이터베이스에 저장하지 않는다 |
| 전달 | 대상 요청의 X-Reauth-Token 헤더에 싣는다 |
| 수명·소비 | 단기 유효(5분)이며 **작업 단위로 1회 소비**한다. 재사용·만료는 auth.reauth_required/401이다 |
| 대상 표면 | 민감정보 원문 복호화 · 민감 문서 다운로드 토큰 발급 · 사업장 폐쇄 · 계정 탈퇴 |

## 멱등

**멱등키는 같은 요청의 중복만 막고 서로 다른 요청의 경합은 막지 못한다**(REQ-GLB-15). 두 장치를 함께 쓴다 — 멱등키는 재시도의 부수효과를, 트랜잭션 잠금은 동시 요청의 경합을 막는다.

| 항목 | 규약 |
|------|------|
| 헤더 | Idempotency-Key. 클라이언트가 생성한 UUID이며 요청마다 새로 만든다(재시도는 같은 값을 재사용한다) |
| 저장 | **멱등 축 둘의 정본은 REQ-GLB-14**([../03_requirements/01_global_rules.md](../03_requirements/01_global_rules.md))이며 여기서 다시 정의하지 않는다. 이 표면들이 거는 것은 **요청 축**이고 물리 저장처는 **idempotency_records**(테이블 61 — 컬럼·제약 명세는 [../05_database/17_infra.md](../05_database/17_infra.md)) |
| 재요청 | 같은 키 + 같은 본문이면 **최초 응답을 그대로 재생**한다(부수효과를 다시 일으키지 않는다) |
| 키 충돌 | 같은 키 + 다른 본문은 거부한다. 도메인 전용 코드가 있으면 그것을(payroll.confirmation_conflict/409 · payslip.bulk_conflict/409) 없으면 common.conflict/409를 쓴다 |
| 보존 | 키 기록은 24시간 보존한다. 그보다 오래된 재시도는 새 요청으로 처리한다. **판정은 읽는 쪽의 조회가 거르는 것이고 지우는 배치에 매이지 않는다** — 배치가 멈추면 24시간이 지난 키의 재시도가 영영 충돌한다 |
| 누락 | 대상 표면에 헤더가 없으면 common.validation_failed/400으로 거부한다. 서버가 임의로 키를 만들지 않는다 |

- 기록의 상태는 **STARTED · COMPLETED · DISCARDED** 셋이고 **DELETE 표면을 두지 않는다** — 근거는 REQ-GLB-14가 갖는다. 표면 쪽에서 보이는 결과는 하나다: **실패한 요청의 키는 같은 값으로 다시 쓸 수 있다.**
- **재생은 상태 · Content-Type · 본문 셋이 모두 첫 응답과 같아야 성립한다** — 재요청 행의 "그대로"가 요구하는 바이트 동일성이 이 셋에 걸린다. 보관 형식의 근거는 [../05_database/17_infra.md](../05_database/17_infra.md)다.
- 멱등키가 필요 없는 변이는 **자연 고유 제약**이 중복을 막는다 — 초대 중복(동일 사업장·대상 PENDING 1건) · 명세서 원본(payroll_run_id, employee_id 부분 유니크) · 스냅샷((workplace_id, base_date, scope) 유일) · 알림 읽음(중복 읽음은 멱등 성공)이다.
- **목록 공통 내보내기 발급([04_workplace.md](./04_workplace.md) #35 · [14_system.md](./14_system.md) #36)은 멱등키를 요구하지 않는다.** 산출 비용은 크지만 발급의 부수효과가 1회용 토큰 하나이고, 멱등 재생은 이미 소비됐을 수 있는 토큰을 돌려주어 재시도가 쓸 수 없는 토큰을 받는다. 중복 발급은 쓰이지 않은 토큰이 만료로 사라질 뿐이다 — 임금대장 내보내기 토큰([08_payroll.md](./08_payroll.md) #21)과 같은 판단이다.

## 연동 테이블의 코드 표기

각 도메인 문서의 연동 테이블 절에서 **코드 집합의 정본이 따로 있는 행은 표면 번호와 코드를 함께 적는다.** 현재 대상은 **audit_logs**(action 코드)와 **notifications**(타입 코드) 둘이다.

| 행 | 채번 정본 | 함께 적는 것 |
|----|----------|-------------|
| audit_logs | [../05_database/15_system.md](../05_database/15_system.md) action 코드 집합 절 | 표면 번호마다 **action 코드** · 그 표면이 **사유 필수인지** |
| notifications | [../05_database/13_notification.md](../05_database/13_notification.md) 타입 카탈로그 | **타입 코드**와 **그것을 발화하는 표면 번호**의 대응 |

- **어느 쪽이든 06_api에서 코드를 신설하지 않는다.** 채번은 위 두 정본에서만 한다.
- **코드를 적지 않으면 표면과 코드를 잇는 자리가 어디에도 없어 어느 방향으로든 빠진다.** 2026-09-07 근태 도메인에서 양방향이 함께 드러났다 — 연동 표가 기록을 요구하는데 코드가 채번되지 않은 표면이 셋(#5 · #6 · #11), 코드는 개방 목록에 있는데 연동 표가 그 표면을 적지 않은 자리가 둘(#14 · #15)이었다.
- **코드가 존재한다는 것 자체가 그 표면이 기록을 남긴다는 계약이다** — 쓰는 자리가 없으면 코드는 채번될 이유가 없다. 그래서 코드 집합과 표면 집합은 서로를 코드로 가리켜야 대조가 성립한다.
- **알림 축을 함께 넣는 근거는 같은 결손이 그 축에서도 났다는 것이다.** 05_hr 연동 표가 #22 · #25에 알림을 계약했는데 카탈로그에 코드가 없어 **type FK가 그 발송 자체를 막고 있었다**(contract_sent · contract_signed 채번으로 해소). **코드 집합의 정본과 표면의 정본이 따로 있는 축은 전부 같은 결손을 낸다** — 그래서 이 규약은 감사 축 전용이 아니다.
- **사유 필수 여부를 함께 적는 이유도 실측에서 나왔다.** 근태 연동 표가 여섯 표면을 묶어 "사유 필수 감사"로 적고 있었으나 실제로 사유가 필수인 것은 마감 축 셋뿐이었다.

| 방식 | 적용 | 근거 |
|------|------|------|
| **오프셋** | 멤버 · 직원 · 근로조건 이력 · 계약 · 문서함 · 근태 수정 요청 · 휴가 신청 · 급여 실행 · 명세서 · 기한 과제 · 시스템 콘솔 검색 | 모집단이 **사업장 활성 멤버 30명 상한**(REQ-SUB-06) 또는 한 급여월 단위라 총 건수가 세 자리를 넘지 않는다. 마감 작업 화면이 "전체 12건 중 처리 3건"을 요구하는데 **커서는 총 건수를 주지 않는다** |
| **커서** | 알림 · 감사 로그 · 위치정보 이용·제공 사실 확인자료 · 명세서 교부 이력 | 넷 다 시간 역순으로 **무한 증가**하고 조회 중에도 새 행이 앞에 쌓인다. 오프셋은 그 순간 같은 행을 두 번 주거나 건너뛴다. **감사 로그(#19)만 예외로 총 건수를 첫 묶음에 싣는다** — 시스템 콘솔이 "전체 N건"을 요구해서다. 나머지 셋은 총 건수가 화면 요건이 아니다 |
| **범위 조회** | 근태 일 집계 · 출퇴근 기록 · 근무 스케줄 · 휴가 달력 · 잔여 연차 · 기한 캘린더 · 급여 이력 | 조회 단위가 기간이라 스스로 상한을 갖는다. 쪽을 나누면 달력·차트가 잘린다 |

오프셋 목록의 요청 파라미터는 page(1부터) · size(기본 20 · 상한 200)이고 응답은 다음과 같다.

```json
{
  "items": [],
  "page": { "number": 1, "size": 20, "totalCount": 37, "totalPages": 2 }
}
```

커서 목록의 요청 파라미터는 cursor(첫 요청은 생략) · size(기본 20 · 상한 200)이고 응답은 다음과 같다.

```json
{
  "items": [],
  "page": { "size": 20, "nextCursor": "eyJ0IjoiMjAyNi0wOC0wM1QwMTowMDowMFoiLCJpIjoiLi4uIn0", "hasMore": true }
}
```

`totalCount`는 **선택**이다 — 커서 목록 대부분은 담지 않고, 감사 로그(#19)만 **첫 요청(커서 생략)에서만** 값을 싣고 이어 읽는 묶음은 `totalCount`를 아예 내지 않는다(null이 아니라 필드 생략 — 응답 직렬화가 non_null이다). 조회 중에도 앞에 행이 쌓이는 목록이라 이어 읽는 묶음에서 다시 세면 값이 첫 묶음과 어긋날 수 있어서다.

```json
{
  "items": [],
  "page": { "size": 20, "nextCursor": "eyJ0IjoiMjAyNi0wOC0wM1QwMTowMDowMFoiLCJpIjoiLi4uIn0", "hasMore": true, "totalCount": 128 }
}
```

범위 조회의 요청 파라미터는 from · to(둘 다 YYYY-MM-DD · 포함 구간)이고 응답은 다음과 같다.

```json
{
  "items": [],
  "range": { "from": "2026-07-01", "to": "2026-07-31" }
}
```

- **커서는 불투명 문자열**이다. (정렬 기준 시각, id) 복합 키를 base64url로 감싼 값이며 클라이언트가 해석·조립하지 않는다. 형식이 깨진 커서는 common.validation_failed/400이다.
- **hasMore와 nextCursor는 함께 검증한다.** hasMore=true이면 nextCursor는 비어 있지 않은 문자열이어야 하고, hasMore=false이면 nextCursor=null이어야 한다. 두 값이 어긋난 응답은 계약 검증 실패다.
- **size는 1~200 정수만 허용한다.** 생략하면 20이고 0 이하 · 정수가 아닌 값 · 201 이상은 클램프하지 않고 **common.validation_failed/400**으로 거부한다. 클라이언트와 MSW도 같은 경계로 검증한다.
- **범위 조회는 서버가 기간 길이 상한을 강제한다** — 일 단위 목록은 366일, 월 단위 목록은 36개월이다. 초과는 common.validation_failed/400이며 클라이언트가 기간을 나눠 다시 부른다.
- **오프셋이 총 건수를 넘으면 빈 배열과 실제 totalCount를 돌려준다.** 오류로 만들지 않는다 — 목록이 줄어드는 동안 마지막 쪽을 보고 있던 화면이 오류로 깨지지 않게 한다.
- 단건 응답은 자원 객체를 그대로 반환한다. **성공 봉투는 목록에만 둔다.**

### 웹 DataTable 누적 조회

관리자·시스템 웹의 서버 목록 DataTable은 API 방식은 바꾸지 않고 사용자 화면의 페이지 번호와 크기 선택기만 없앤다. 첫 조회와 이어 읽기는 **정확히 200건씩** 요청한다. API 기본값 20은 다른 클라이언트와 명시적 size가 없는 호출을 위한 계약이고, 웹 DataTable은 항상 size=200을 보낸다.

| 항목 | 규약 |
|------|------|
| 오프셋 이어읽기 | 내부 pageParam을 1부터 1씩 늘려 page={pageParam}&size=200으로 호출한다. page는 사용자 URL 상태가 아니다 |
| 커서 이어읽기 | 첫 요청은 cursor를 생략하고 size=200을 보내며, 이후 응답의 nextCursor를 해석하지 않고 cursor={nextCursor}&size=200으로 전달한다 |
| 범위 조회 | from · to가 조회 상한이므로 누적 조회로 바꾸지 않는다 |
| 쿼리 키 | workplaceId · 역할 · 검색 · 필터 · 정렬을 포함한다. page · size · cursor는 이어읽기 위치이므로 키에서 제외한다 |
| 누적 규칙 | items만 응답 순서를 유지해 붙이고 안정 식별자로 중복을 제거한다. summary · range · employees · registrationNumbers · totalUnfiltered 등 부가 메타데이터는 첫 묶음을 기준으로 고정한다 |
| 초기화 | 검색·필터·정렬·사업장·역할이 바뀌거나 관련 변이가 성공하면 기존 누적을 버리고 첫 200건부터 다시 읽는다. 사용자가 누르는 “처음부터 새로고침”도 같은 동작이다 |
| 자동 재조회 | 창 포커스·네트워크 재연결만으로 이미 쌓인 모든 묶음을 순차 재조회하지 않는다. 최신화는 위 초기화 경계와 명시적 새로고침으로 수행한다 |

- **오프셋의 한계는 사라지지 않는다.** 조회 중 다른 사용자가 앞쪽 행을 삽입·삭제하면 경계 중복은 안정 식별자 제거로 줄일 수 있지만, 건너뛴 행은 복원할 수 없다. 완전한 스냅샷 일관성이 필요한 표면은 별도 버전에서 커서 전환 또는 스냅샷 토큰을 결정해야 한다.
- 작은 모달 선택 목록 · 로컬 계산 표 · 범위 조회는 공용 DataTable 누적 조회 대상이 아니다. 이 예외를 이유로 서버 목록 화면에 페이지 번호 UI를 다시 만들지 않는다.

## 정렬·필터

| 항목 | 규약 |
|------|------|
| 정렬 파라미터 | sort=필드명 · order=asc 또는 desc. 다중 정렬을 받지 않는다 — 화면이 필요로 하는 정렬 축은 목록마다 하나다 |
| 허용 필드 | 목록마다 **허용 정렬 필드를 화이트리스트로 선언**한다. 목록 밖 필드는 common.validation_failed/400이다. 임의 컬럼 정렬을 열면 인덱스 없는 정렬이 그대로 실행된다 |
| 안정 정렬 | 모든 목록은 마지막 정렬 키로 id를 붙인다. 값이 같은 행의 순서가 요청마다 흔들리면 오프셋 쪽 나눔이 행을 흘린다 |
| 기본 정렬 | 시간 축이 있는 목록은 created_at 내림차순 · id 내림차순, 카탈로그성 목록은 sort_order 오름차순 · code 오름차순이다 |
| 필터 | 쿼리 파라미터로 받고 파라미터명은 카멜 표기다. 다중 값은 쉼표로 잇는다(status=PENDING,APPROVED) |
| 검색 | q 파라미터 하나로 받고 서버가 대상 필드를 정한다(REQ-WRK-25). 입력은 trim하고 **50자**를 넘으면 클램프하지 않고 common.validation_failed/400(field q)으로 거부한다. 부분 일치는 `LIKE`/`ILIKE`의 메타문자(`\` · `%` · `_`)를 이스케이프한 뒤 `ESCAPE '\'`로 비교한다 — 그러지 않으면 검색어의 `%`·`_`가 임의 문자(열)로 해석돼 의도와 다른 조건으로 조회된다 |
| 미선언 파라미터 | 스키마에 없는 쿼리 키는 무시하지 않고 거부한다. 오타 난 필터가 조용히 전체 조회로 되는 것을 막는다 |

## 시간·금액 직렬화

| 항목 | 표현 | 근거 |
|------|------|------|
| 시각 | **UTC ISO 8601 문자열**(2026-08-03T00:20:00Z). 표시 시간대 환산은 클라이언트가 한다 | 저장이 timestamptz(UTC)이고 표시가 KST다(REQ-GLB-07) |
| 날짜 | **YYYY-MM-DD 문자열**. 근무일 · 급여월 귀속일 · 효력일 · 기준일이 여기 해당한다 | date 컬럼을 Date 객체로 파싱하면 UTC 자정으로 해석돼 **KST 일자가 하루 밀린다**([../08_tech_stack/03_backend.md](../08_tech_stack/03_backend.md)) |
| 급여월 | YYYY-MM 문자열 | 귀속 단위가 월이며 일자가 없다 |
| 금액 | **JSON 문자열**("1830000"). 단위는 원(KRW)이며 소수점을 두지 않는다 | 저장이 bigint라 JSON number로 실으면 IEEE754 배정밀도 한계에서 정밀도가 조용히 깨진다(REQ-GLB-02) |
| 비율·시급 환산액 | **JSON 문자열**("0.045" · "10322.5806") | NUMERIC 고정소수점이다. number로 바꾸는 순간 반올림 규칙이 깨진다 |
| 좌표·정확도 | **JSON 문자열**("37.566512" · "18.00") | 위경도와 정확도(m)도 NUMERIC 컬럼이다. 지오펜스 거리 판정의 입력이라 number 역직렬화로 정밀도가 흔들리면 경계에서 판정이 갈린다 |
| 시간 | **정수 분**(JSON number). 480은 8시간이다 | 근로시간의 저장·연산 단위가 정수 분이다 |
| 일수 | **JSON 문자열**("15.5"). 연차 일수가 여기 해당한다 | 0.1일 단위 올림이라 십진 표현이 필요하다 |
| 불리언·enum | 불리언은 JSON boolean, enum은 대문자 문자열이다 | enum 값 집합의 정본은 [../09_glossary/03_enums_state_machines.md](../09_glossary/03_enums_state_machines.md)다 |

- **요청도 같은 규약이다.** 금액·비율·일수는 문자열로 받아 문자열로 검증하고, 숫자 타입으로 파싱하지 않는다.
- **응답의 파생 금액을 클라이언트가 다시 계산하지 않는다.** 합계·차감액·실수령액은 전부 서버 산출값을 그대로 표시한다. 화면 계산값과 확정값이 어긋나면 사용자는 어느 쪽이 맞는지 알 수 없다.

## 에러 응답 규격

실패는 전 표면이 같은 모양이다.

```json
{
  "code": "payroll.missing_reference_value",
  "message": "귀속기간에 필요한 기준값이 없어 계산할 수 없습니다.",
  "details": [
    { "category": "TAX_TABLE", "baseDate": "2026-07-25" },
    { "category": "HEALTH_RATE", "baseDate": "2026-07-01" }
  ]
}
```

| 필드 | 타입 | 내용 |
|------|------|------|
| code | string | {domain}.{snake_case}. **클라이언트 분기의 유일한 근거**다 |
| message | string | 한국어 기본 문안. 표시 전용이며 분기 근거가 아니다 |
| details | array 또는 object · 선택 | 사용자가 조치할 수 있는 도메인 값만 담는다 — 행 번호 · 필드명 · 사유 코드 · 대상 자원 ID · 현재 사용량과 한도 |

- **details에 내부 정보를 싣지 않는다** — 스택 트레이스 · SQL · DB 제약명 · 원문 예외 메시지 · 서버 파일 경로 · 환경변수는 어느 상황에서도 응답에 나가지 않는다(REQ-GLB-19).
- **details가 필요한 표면은 정해져 있다.** 판정 기준은 하나다 — **한 코드가 여러 항목을 대표하고 사용자가 그 항목 각각을 조치해야 하는가.** **항목마다 코드가 다르면 code 가 이미 무엇을 조치할지 말하므로 details 를 두지 않는다** — 멤버 제외가 그 형태다(선행조건 4종이 각각 별개 코드이고, 목록이 필요한 자리는 에러가 아니라 **선행조건 조회 표면의 blockers 배열**이다). 현재 이 기준을 만족하는 것은 신고자료의 빈 관리번호 계열(workplace.mgmt_no_required — insuranceType · mgmtNoField) · 마감 차단 사유 배열(attendance.closing_blocked) · 임포트 행 오류(import.validation_failed) · 명세서 필수항목 누락 목록(payslip.missing_required_field) · 한도 초과의 사용량과 필요 등급(subscription 계열) · 폐쇄·퇴사 선행조건 미충족 목록(workplace.close_blocked · hr.resignation_blocked) · **누락 기준값 키 목록(payroll.missing_reference_value)** · **최저임금 미달의 적용 기준값(hr.below_minimum_wage — minimumHourlyWage · effectiveFrom)**이다. 그 밖의 코드는 code와 message만 낸다. **최저임금 미달에 환산시급을 싣지 않는다** — 그 값은 §1.1 min_wage_conversion 이 반올림을 금지한 몫이라 계산 계층이 아예 만들지 않는다(판정에 필요한 것이 몫이 아니라 대소 관계뿐이라 양변에 분모를 곱해 곱셈으로 비교한다). 응답에 실으려고 나누면 금지된 반올림을 하게 되고, 절사는 미달을 과다 경고하고 절상은 실제 미달을 놓친다.
- 에러 코드의 채번 정본은 [../09_glossary/02_error_codes.md](../09_glossary/02_error_codes.md)이고 본 폴더의 미러는 [02_errors.md](./02_errors.md)다.
- **같은 사유에 두 코드를 두지 않는다.** 도메인 전용 코드가 있으면 common 계열로 폴백하지 않는다.

## 상태코드 규약

| 상태 | 의미 | 대표 사례 |
|:----:|------|----------|
| 200 | 조회·수정·상태 전이 성공 | 목록 조회 · 승인 · 마감 · 확정 |
| 201 | 자원 생성 성공. Location 헤더에 생성 자원 경로를 싣는다 | 사업장 등록 · 초대 생성 · 휴가 신청 · 급여 실행 생성 |
| 202 | 접수 성공 · 처리 진행 중 | 명세서 일괄 발행 · 감사 내보내기 생성 · 임포트 검증 |
| 204 | 성공 · 본문 없음 | 로그아웃 · 알림 읽음 · 스케줄 삭제 |
| 400 | 요청 형식·파라미터 검증 실패 | 요청 DTO 검증 실패 · 커서 형식 오류 · 정렬 필드 화이트리스트 밖 |
| 401 | 미인증 · 재인증 필요 | 세션·토큰 부재·만료 · auth.reauth_required |
| 402 | 구독 한도·만료로 차단 | 사업장 등록 한도 · 활성 멤버 한도 · 구독 만료 |
| 403 | 권한 없음 **또는 적용 대상 아님** | 역할 부족 · CSRF 실패 · 5인 미만 연차 미적용 |
| 404 | 자원 부재 **또는 존재 은닉** | 타인 명세서 · 타인 알림 · 대상 멤버십 없음 |
| 409 | 충돌 — 중복 · 상태 불일치 · 동시성 · 선행조건 미완 | 중복 확정 · 마감된 기간 수정 · 폐쇄 선행조건 미충족 |
| 410 | 만료·1회용 소진 | 초대 토큰 만료 · 다운로드 토큰 만료·재사용 |
| 413 | 요청 크기 초과 | 임포트 파일 · 문서함 업로드 |
| 422 | **전제 미충족 — 조치하면 진행 가능** | 기준값 누락 · 스냅샷 부재 · 지오펜스 밖 · 최저임금 미달 |
| 429 | rate limit 초과 | 로그인 실패 누적 · 재설정 메일 발송 빈도 |
| 500 | 분류되지 않은 서버 실패 | 내보내기 파일 생성 실패 |
| 503 | 외부 서비스 장애 | 국세청 진위확인 API 장애·timeout |

### 403과 422를 가르는 기준

**403은 "당신에게 이 기능이 적용되지 않는다"이고 422는 "지금은 조건이 안 맞지만 채우면 된다"**다(REQ-GLB-19). 상태코드가 곧 화면 문안과 다음 행동을 가른다.

```plain
요청 거부
├─ 사용자가 지금 할 수 있는 조치가 있는가?
│  ├─ 없다 — 역할·적용 대상이 아니라서다        → 403
│  │    · 5인 미만 사업장의 법정 연차 조회       leave.not_applicable/403
│  │    · MANAGER의 급여 무효화 시도             payroll.void_forbidden/403
│  │    · 본인 요청의 본인 승인                  attendance.self_approval_forbidden/403
│  └─ 있다 — 빠진 전제를 채우면 된다             → 422
│       · 기준값 등록                            payroll.missing_reference_value/422
│       · 상시근로자 산정 실행                   leave.employee_count_snapshot_required/422
│       · 근무지 반경 안에서 재시도              attendance.out_of_geofence/422
└─ 조치 대상이 "다른 작업의 완료"인가            → 409
     · 근태 마감 후 급여 계산                    payroll.attendance_not_closed/409
     · 미발행 명세서 처리 후 폐쇄                workplace.close_blocked/409
```

- **404를 존재 은닉에도 쓴다.** 타인 명세서·타인 알림·타인 초대는 403이 아니라 404다 — 403은 "그 자원이 존재한다"는 사실을 알려 준다.
- **413과 422를 구분한다.** 업로드 크기 초과는 요청 표면에서 끊기므로 413이고, 파일 안 행의 검증 실패는 422다.

## rate limit

| 항목 | 규약 |
|------|------|
| 코드 | common.rate_limited/429. 응답에 Retry-After 헤더와 재시도 가능 시각을 함께 싣는다 |
| 대상 표면 | 로그인(IP, username 조합) · 아이디 중복 확인 · 비밀번호 재설정 요청 · 사업자 진위확인 · 다운로드 토큰 발급 · 재인증 토큰 발급 · 인증 후 일반 API |
| 한도 정본 | 전 축의 키와 한도는 [../04_architecture/02_authn_session.md](../04_architecture/02_authn_session.md) rate limit 표가 갖는다. 이 문서에 값을 다시 정의하지 않는다 |
| 업무 표면 2축 | **사업자 진위확인 — (사업장, 일) 20회** · **다운로드 토큰 발급 — (사용자, 시간) 60회**. 둘은 외부 API 호출량과 파일 반출량을 묶는 축이라 인증 후 일반 API 한도와 별도로 센다 |
| 축 | 미인증 표면은 IP + 입력값 조합, 인증 표면은 사용자 ID다. **사업장 축으로 묶지 않는다** — 한 사업장의 한 사용자가 다른 멤버의 사용을 막게 된다. **예외는 사업자 진위확인 하나**이며, 국세청 API 호출량 자체가 사업장 단위 자원이라 (사업장, 일) 축으로 센다 |
| 누적 실패 | 로그인 실패는 성공 시 카운터를 초기화한다. 잠금은 시간 만료로만 풀린다 |
| 초과 응답 | 실패 사유를 구분하지 않는다 — 계정 존재 여부가 rate limit 응답 차이로 새면 열거 방지가 무너진다 |

## 파일 업로드·다운로드

| 항목 | 규약 |
|------|------|
| 업로드 방식 | multipart/form-data 단일 요청이다. 클라이언트가 오브젝트 스토리지에 직접 올리는 경로를 두지 않는다 — MIME·매직넘버 검증과 메타 기록이 서버 한 곳에서 끝나야 한다 |
| 업로드 검증 순서 | ① 크기 상한 → **common.payload_too_large/413** ② MIME 허용 목록 → 도메인 코드 ③ **매직넘버와 확장자 일치** → common.validation_failed/400. ①을 먼저 봐야 큰 파일을 읽지 않고 끊는다 |
| 다운로드 방식 | **1회용 토큰 발급 + 서버 스트리밍** 2단이다. 오브젝트 스토리지 서명 URL을 클라이언트에 직접 주지 않는다 |
| 토큰 계약 | 단기 만료 · 1회 소비 · 세션과 IP와 user agent 보조 바인딩. 만료·재사용은 **payslip.download_token_expired/410**이며 명세서·민감 문서·계약 완료본이 이 규약을 공유한다(REQ-HRM-24 · REQ-SLP-08). 목록 공통 내보내기 토큰([04_workplace.md](./04_workplace.md) #36)은 **export.expired/410**이다. 없음 · 만료 · 재사용 · 바인딩 불일치에 **소유자 불일치**까지 한 코드로 수렴하는 원칙은 같다 |
| 스트리밍 응답 | Content-Type은 실제 MIME, Content-Disposition은 attachment + 파일명이다. 인라인 실행을 허용하지 않는다 |
| 열람 기록 | 다운로드 성공은 교부·열람 이력에 남는다(payslip_deliveries · audit_logs). **기록 실패 시 파일을 내보내지 않는다** |
| 산출 시점 | 파일 토큰(명세서 · 민감 문서 · 계약 완료본 · 임포트 리포트 · 임금대장)은 **이미 만들어진 파일**을 가리킨다. 목록 공통 내보내기 토큰은 **조건(목록 · 검색어 · 필터 · 정렬 · 열 · 사유)을 봉인**하고 파일은 **다운로드 순간** 서버가 만들며 저장하지 않는다. 다운로드에서 목록 인가를 다시 판정한다 |
| 목록 내보내기 | 요청은 화면 조건 그대로이고 열은 목록 선언의 부분집합이며 민감 목록은 사유가 필수다. **XLSX 칸은 전부 문자열**이다(금액 · 정수 · 날짜 포함 — 숫자 칸·날짜 칸은 배정도다). 감사는 다운로드에서 1행을 남긴다(list.export · list.export_sensitive · **전송보다 먼저**). 계약 정본은 [04_workplace.md](./04_workplace.md) #35 · #36이다 |
| 브라우저 생성 파일 | **업무 데이터를 담지 않는 파일은 토큰 다운로드 대상이 아니다.** 임포트 양식(EMPLOYEES 머리글 1줄 CSV · UTF-8 BOM)은 브라우저가 만든다 — 서버 밖으로 나가는 업무 데이터가 없어 토큰 · 감사 계약이 걸릴 자리가 없다. OPENING_BALANCE는 머리글 정의가 없어 양식을 내지 않는다 |

**서명 URL을 클라이언트에 노출하지 않는 근거**는 철회 불가능성이다. 발급된 서명 URL은 만료 전까지 누구에게 전달되든 열리고 서버가 회수할 수 없는데, 대상이 주민번호·계좌·임금 정보를 담은 법정 문서다. 1회용 토큰은 서버가 소비 여부를 알고 있어 재사용을 끊을 수 있고 열람 이력도 남는다.

## SSE

| 항목 | 규약 |
|------|------|
| 표면 | GET /v1/notifications/stream **1개뿐**이다(NTF-01). 다른 도메인에 스트림을 추가하지 않는다 |
| 인증 | 웹은 세션 쿠키, 앱은 Authorization 헤더다. 쿼리 파라미터로 토큰을 받지 않는다 — 접근 로그와 리퍼러에 남는다 |
| 스코프 | 연결 수립 시 수신자(recipient_user_id)를 고정한다. 사업장 필터는 클라이언트가 하지 않고 이벤트 payload의 workplaceId로 화면이 가른다 |
| 구독 단위 | **수신자 고정 단일 스트림 하나뿐이다.** 사업장 단위 구독·구독 해제·재구독 표면을 두지 않으며 사업장 전환(WRK-06)이 연결을 다시 맺게 하지 않는다 |
| 팬아웃 | 생산자는 Redis 채널에 발행하고 각 인스턴스가 자기 연결에만 전달한다. **사용자·사업장 분리는 서버 내부 Redis 채널의 축**이며 클라이언트 계약에 드러나지 않는다([../04_architecture/10_realtime_files.md](../04_architecture/10_realtime_files.md)) |
| 유실 보충 | **재접속 시 목록 조회로 보충한다**(REQ-NTF-02). 스트림을 정본으로 삼지 않는다 — 알림 원장의 정본은 서버 목록이다 |
| 페이로드 | 알림 id · type · title · deeplink · createdAt까지다. **금액·개인정보 상세를 싣지 않는다**(REQ-NTF-01) |
| 프록시 | nginx가 이 경로의 버퍼링을 끄고 타임아웃을 길게 잡는다 |

## 하지 말 것

- **GraphQL을 두지 않는다.** 표면은 REST 단일이다. 클라이언트가 필드를 고르는 축이 생기면 권한 판정 단위가 엔드포인트에서 필드로 흩어져 마스킹·복호화 통제(REQ-HRM-04)를 표면 단위로 강제할 수 없다.
- **부분 응답(필드 선택 파라미터)을 두지 않는다.** 같은 이유이며, 목록 응답에서 민감 필드를 제외하는 것은 서버가 표면마다 고정한다.
- **클라이언트가 계산한 값을 신뢰해 저장하지 않는다.** 근로시간 · 수당 · 공제액 · 실수령액 · 지오펜스 통과 여부 · 상시근로자 수는 전부 서버 산출값이며 요청 본문으로 받지 않는다.
- **클라이언트 시각을 기록 시각으로 쓰지 않는다.** 출퇴근 시각은 서버 시각이고 기기 시각은 위험 플래그 판정용 별도 필드다(REQ-ATT-01).
- **활성 사업장을 서버 세션·헤더로 암묵 전달하지 않는다.** 경로 변수가 유일한 전달 축이다.
- **금액·비율을 JSON number로 싣지 않는다.** 응답 직렬화기에서 BigInt·Decimal을 number로 넘기는 경로를 만들지 않는다.
- **PATCH { status } 로 상태를 전이하지 않는다.** 허용 전이 판정이 요청 본문 검증으로 밀려난다. **규약이 있다는 사실이 그 규약을 지키게 하지 않는다** — 이 문장이 등재된 채로 기한 과제 전이 하나가 PATCH로 남아 있었고([11_compliance.md](./11_compliance.md) — 2026-09-09 정정), **금지 문장은 도메인 문서를 훑는 검사와 함께 있어야 실효를 갖는다.**
- **오브젝트 스토리지 서명 URL을 응답에 담지 않는다.** 다운로드는 1회용 토큰 + 서버 스트리밍뿐이다.
- **에러 응답에 내부 식별자·원문 예외를 담지 않는다.**
- **한 엔드포인트가 여러 사업장의 데이터를 한 번에 반환하지 않는다.** 예외는 계정 단위 자원(소속 사업장 목록 · 알림 · 구독)뿐이며 그 목록도 사업장 업무 데이터를 담지 않는다.
- **삭제 표면을 기본으로 두지 않는다.** 근태 이벤트 · 감사 로그 · 동의 이력 · 확정 급여 · 명세서는 물리 삭제 표면이 없다. 취소·무효화·정정본이 그 자리를 대신한다.
