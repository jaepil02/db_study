인사 데이터는 **급여 계산의 입력 원천**이다. 부양가족 수와 8~20세 자녀 수가 없으면 소득세 계산이 시작되지 않고, 근로조건이 없으면 기본급을 낼 수 없으며, 보험별 가입 대상 판정이 없으면 공제액이 틀린다. 그래서 이 도메인의 쓰기 표면은 대부분 **누락 시 하류 계산을 차단하는 값을 채우는 경로**다.

**민감정보 표면은 셋으로 갈린다** — 목록·상세는 마스킹 값만(#1 · #3), 저장은 암호화 전용 표면(#5), 원문 열람은 4요건을 모두 통과해야 하는 1회성 표면(#6)이다. 하나의 자원 표현에 마스킹과 원문을 섞지 않는 이유는 응답 필드 단위로 권한을 판정하는 순간 통제가 표면 단위로 강제되지 않기 때문이다([01_conventions.md](./01_conventions.md)).

**근로계약은 서버 보관만으로 교부 의무가 이행되지 않는다**(REQ-HRM-22). 그래서 발송(#22)이 상태 전이와 교부 이력을 함께 만드는 별도 표면이고, 본인 상세(#36) · 서명(#25) · 다운로드(#26 · #30)가 그 뒤를 잇는다. **직원이 교부 사실을 확인하는 자리는 #36**이며 그 응답이 채널과 시각을 담는다.

### 1·2·3·4. 직원 목록·생성·상세·수정 (HRM-01 · HRM-03)

```json
{
  "employeeId": "…",
  "name": "김직원",
  "birthDate": "1993-05-14",
  "jobTitle": "매니저",
  "status": "ACTIVE",
  "workerType": "EMPLOYEE",
  "source": "MANUAL",
  "isMinor": false,
  "taxProfile": { "dependentCount": 2, "childCount8To20": 1 },
  "personalInfoMasked": { "residentNo": "930514-1******", "bankAccount": "우리 1002-***-**1234" },
  "completeness": { "taxProfile": true, "employmentTerms": true, "insurance": false, "personalInfo": true }
}
```

| 항목 | 1. 목록 | 2. 생성 | 3. 상세 | 4. 수정 |
|------|--------|--------|--------|--------|
| 필터·입력 | q · status · employmentType · workerType · isMinor · 오프셋 | name · birthDate · gender · address · phone · emergencyContact · jobTitle · userId(선택) · taxProfile | — | 인적사항 필드 부분 갱신 |
| 권한 | MANAGER | MANAGER | **STAFF는 본인 레코드만** · MANAGER는 전원 | MANAGER |
| 응답 | 요약 + completeness + 관리 축(아래 목록 항목 예시) | 생성 자원 + 201 Location | 위 예시 전체 | 갱신 자원 |
| 마스킹 | 마스킹 값만 | 민감정보는 여기서 받지 않는다 — #5 전용 | 마스킹 값만 | 민감정보 필드를 받지 않는다 |
| 실패 | — | hr.duplicate_active_employee/409 · common.invalid_format/400 | common.not_found/404 | common.validation_failed/400 |

목록 항목(#1)은 위 예시에 더해 다음 관리 축을 싣는다 — 명부에서 다음 행동을 고르는 값이다.

```json
{
  "phone": "01012345678",
  "addressRegion": "서울특별시 성동구",
  "resignationDate": null,
  "appLinked": true,
  "currentTerms": { "employmentType": "CONTRACT", "payType": "HOURLY", "weeklyContractualMinutes": 1200, "shortTime": false, "fixedTermEndDate": "2026-12-31", "probationEndDate": "2026-08-31" },
  "latestContract": { "status": "SIGNED", "delivered": false },
  "insuranceEnrollment": { "nationalPension": true, "health": true, "employment": true, "industrialAccident": true },
  "leaveBalanceDays": "12.5"
}
```

- **목록은 급여 금액 · 상세 주소 · 계좌 · 주민번호 원문을 싣지 않는다**([../07_screen/01_standards.md](../07_screen/01_standards.md) §3-4 민감 열). 주소는 서버가 **시·도 · 시·군·구까지만** 남기며 모양을 모르는 주소는 잘라 내지 않고 비운다 — 원문은 #3만 낸다.
- currentTerms는 **기준일에 유효한 세대 하나**다 — employmentType 필터가 보는 세대와 같다. 없으면(근로조건 미등록 · 효력 전) 비운다. probationEndDate는 입사일 + 수습 개월 − 1일이며 수습이 없거나 입사 미확정이면 비운다. shortTime은 저장 시 서버가 산출한 주 15시간 미만 플래그다.
- latestContract는 **취소본을 건너뛴 최신 세대**다. delivered는 발송이 **실제로 도달해 교부가 성립했는가**다(#22는 도달했을 때만 교부 시각을 적는다) — SENT인데 false면 직원이 받지 못해 서명할 수 없는 상태(계정 미연결 등)이고, SIGNED인데 false면 교부 의무가 남은 상태다(REQ-HRM-22). 작성한 적이 없으면 비운다.
- insuranceEnrollment는 상실하지 않은 기록만 본다. 보험별 값이 비면 **기록 없음**, false면 **가입 제외로 기록함**이다. 기록이 하나도 없으면 객체를 비운다. 장기요양은 건강보험을 따르므로 싣지 않는다.
- leaveBalanceDays는 휴가 도메인이 재산출한 leave_balances.balance_days를 **읽기만** 한다(목록의 부수 정보 — 구조 규약 §2). 산출 전이면 비운다.
- **부양가족 수와 8~20세 자녀 수는 필수 관리 항목**이다(REQ-HRM-02). 두 값이 비면 급여 소득세 계산이 시작조차 되지 않으므로 completeness.taxProfile로 부재를 드러내고 급여 표면이 payroll.missing_reference_value가 아니라 자신의 차단 코드로 막는다.
- user_id는 nullable이다 — 초대 수락 전 임포트로 먼저 만들어진 직원이 존재할 수 있다(REQ-HRM-01).
- **모든 조회는 workplace_id 스코프로 격리한다.** 1차 검증은 가드가, 2차 방어는 RLS가 진다.
- STAFF는 인적사항을 직접 수정하지 않는다 — 변경은 #7의 요청 경로를 거친다.

- **복호화 결과를 클라이언트가 캐시하지 않는다.** 응답 헤더에 no-store를 싣고 화면은 표시 후 메모리에서 지운다.

- STAFF는 이 두 표면에 접근하지 않는다. 본인 마스킹 정보는 #3이 준다.

### 8·9·10. 근로조건 이력 조회·등록·수정 (HRM-02)

```json
{
  "employmentType": "PART_TIME",
  "payType": "HOURLY",
  "baseWage": "11000",
  "contractualMinutes": 1200,
  "workDays": ["MON", "WED", "FRI"],
  "dailyMinutes": { "MON": 240, "WED": 240, "FRI": 240 },
  "breakPolicy": "AUTO_DEDUCT_30",
  "probationMonths": 0,
  "effectiveFrom": "2026-09-01",
  "effectiveTo": null

```

```plain
① 단위 검증               payType별 baseWage 단위 — HOURLY 원/시 · MONTHLY 원/월 · DAILY 원/일
                         금액은 문자열로 받아 문자열로 검증한다(REQ-GLB-02)
                         workDays — MON·TUE·WED·THU·FRI·SAT·SUN 7값 집합 · 중복 없이 최소 1요일
                         빈 배열·범위 밖 값·중복 → common.validation_failed/400(REQ-HRM-06)
② 최저임금 대조           시급 환산액이 기준값 최저임금 미만 → hr.below_minimum_wage/422
③ 단시간 필수 항목         employmentType=PART_TIME이면 dailyMinutes 필수(기간제법 §17)
                         누락 → hr.contract_missing_field/422
④ 유효기간 겹침 판정       직원당 effective 구간 겹침 → hr.term_overlap/409 (DB EXCLUDE 제약이 최종 강제)
⑤ 초단시간 표시           contractualMinutes < 900(주 15시간)이면 주휴·퇴직금·일부 보험 적용 예외
                         후보 플래그를 세워 #17 판정의 입력으로 넘긴다
⑥ INSERT · 감사 기록
```

- **월 중 변경은 기간을 분할해 각각 계산한 뒤 합산한다**(REQ-PAY-13). 그래서 이 표면은 기존 행을 덮어쓰지 않고 새 유효기간 행을 쌓는다 — #10은 **아직 시작하지 않은 미래 구간**만 수정할 수 있고 이미 지난 구간은 새 행으로만 바꾼다.
- contractualMinutes는 **분 단위 정수**다. 주 소정근로시간을 시간 단위 실수로 받으면 통상시급 divisor 산출에 부동소수점이 유입된다.
- **v1은 단순 시급·월급제로 한정한다.** 포괄임금·고정OT 필드를 두지 않는다.

### 11·12·13. 입사 확정·퇴사 선행조건·퇴사 처리 (HRM-03 · HRM-04)

| 항목 | 11. 입사 확정 | 12. 퇴사 선행조건 | 13. 퇴사 처리 |
|------|--------------|------------------|--------------|
| 입력 | hireDate · probationMonths · probationWageRate · jobTitle · payrollStartDate | — | resignationDate · reason(자진 · 권고 · 계약만료 · 해고) · lastWorkDate · insuranceLossDate · settlementRequired |
| 검증 | 수습 감액 3요건 · 기존 ACTIVE 직원의 hire_date 충돌 | 읽기 전용 | **퇴사일이 입사일보다 빠를 수 없다** |
| 차단 | hr.hire_date_conflict/409 · hr.duplicate_active_employee/409 · hr.rehire_requires_new_employee/409 | blockers 배열 반환 | **hr.resignation_blocked/409** + 미충족 항목 상세 |
| 트랜잭션 | employees.status=ACTIVE(입사일 확정) · **멤버십이 이미 ACTIVE인지 확인**(전이가 아니다 — 계정 미연계 직원은 멤버십 축 자체가 없어 그냥 지나간다) · **4대보험 취득 과제 생성 시도**(INSURANCE_ACQUISITION). 기본 연차 잔액·근태 스케줄 초안·급여 기준 초안은 **이 트랜잭션이 만들지 않는다** — 아래 pendingLinkages 표가 그 갈래다 | — | employees.status=RESIGNED · **멤버십은 사유 매핑에 따라 LEFT 또는 REMOVED** · 계약 SIGNED→ARCHIVED · #35 트리거 |
| 응답의 미처리 | **pendingLinkages** — 이 트랜잭션이 만들지 못한 부수효과의 이름이다 | — | 상동. **linkages**(처리한 갈래)와 짝을 이룬다 |

수습 감액은 **3요건을 모두 충족할 때만** 허용한다(REQ-HRM-09).

```plain
probationWageRate < 100% 요청
├─ ① 1년 이상의 기간을 정한 근로계약인가            아니면 감액 불가
├─ ② 수습 시작일부터 3개월 이내인가                 아니면 감액 불가
└─ ③ 한국표준직업분류 대분류 9(단순노무)가 아닌가    맞으면 감액 불가
    하나라도 미충족 → 100% 지급으로 강제하고 사유를 응답에 담는다
```

퇴사 차단 사유(#12 · #13)는 셋이다 — **진행 중 급여 확정 · 미처리 휴가/근태 승인 · 대상자가 OWNER 역할 보유**다.

- **초대 수락으로 만들어진 직원 행은 hire_date가 비어 있는 입사 미확정 상태**다(REQ-HRM-01). #11이 hire_date를 기록하는 시점에 재직이 확정되며, 목록 표시와 중복 차단 분기는 **hire_date 유무**를 축으로 가른다.
- **hire_date는 연차 산정과 근속(퇴직금) 기산일**이다. 입사일이 사업장 생성일보다 이를 수 있다 — 기존 사업장을 이관해 온 경우다.
- **퇴사 사유가 멤버십 종료 상태를 가른다**(REQ-HRM-12) — **자진 퇴사 · 계약만료 = LEFT**(자발 이탈) · **권고사직 · 해고 = REMOVED**(강제 이탈)다. LEFT만 재초대 수락으로 재활성화되므로(REQ-WRK-17) 사유를 무시하고 일괄 LEFT로 두면 강제 이탈자가 재초대 링크로 복귀한다.
- **퇴사자 재입사는 기존 RESIGNED 레코드를 재활성화하지 않고 새 고용기간 이력을 만든다**(REQ-HRM-11). 재활성화 시도는 hr.rehire_requires_new_employee/409다.
- 상실일과 퇴사일은 다르다 — 상실일은 최종 근무일 기준이며 신고자료([10_tax.md](./10_tax.md))의 입력이자 **상실 신고 기한의 기산일**이다.
- **#11이 4대보험 취득 과제를 연다**(2026-09-10 — 종전 미결 해소). 기산일은 **입사일**이고 멱등키 축도 입사일이다 — **근로관계 하나에 취득신고 의무가 하나**이며 신고자료 생성 표면([10_tax.md](./10_tax.md) #1)도 같은 축으로 같은 행을 찾는다. 뒤에 적용정보(#15)가 다른 취득일로 저장돼도 **이미 열린 과제의 기한은 소급 변경되지 않는다**(trigger_date·due_date 불변 가드). 파생 규칙의 정본은 [../05_database/12_compliance.md](../05_database/12_compliance.md)다.
- **입사 쪽에 서버 내부 표면을 채번하지 않았다.** 퇴사가 #35를 갖는 이유는 **한 트랜잭션이 세 도메인의 후속 과제를 동시에 만들기 때문**이고 취득은 갈래가 하나뿐이라 #11의 부수효과로 닫힌다 — 표면을 늘리면 API 표면 수가 움직이는데 **만드는 일은 같다.**

**pendingLinkages — #11 · #13의 응답이 만들지 못한 갈래를 이름으로 담는다.** 침묵보다 낫다 — 응답에 없으면 무엇이 자동으로 만들어지지 않았는지가 화면과 감사 어디에도 남지 않는다.

| 표면 | 값 | 나오는 조건 |
|------|-----|-----------|
| #11 입사 확정 | LEAVE_BALANCE · ATTENDANCE_SCHEDULE_DRAFT · PAYROLL_TERMS_DRAFT | **소유 모듈이 아직 없다** — 자리 자체가 비어 있다 |
| #11 입사 확정 | **INSURANCE_ACQUISITION_TASK** | **기한 기준값이 없어 그 과제만 막혔다.** 시드에 취득 기한 키가 등재되면 이 이름은 사라진다 |
| #13 퇴사 처리 | **INSURANCE_LOSS_TASK · WAGE_SETTLEMENT_CLOCK · SEVERANCE_PAYMENT_CLOCK** | 상동 — 해당 갈래의 기한 기준값 부재 |

- **값의 의미가 2026-09-10에 바뀌었다** — 종전에는 「소유 모듈이 없어 만들지 못한 갈래」였고 지금은 **「기한 기준값이 없어 못 만든 갈래」**다(#11의 앞 세 값만 옛 뜻을 유지한다). REQ-HRM-13의 나머지 갈래는 **기존 경로**라 미처리 대상이 아니다 — 마지막 급여 정산 표시는 employees.settlement_required, 미사용 연차수당은 급여 정산 라인, 이직확인서는 발급 요청 접수 표면([10_tax.md](./10_tax.md) #5)이다.
- **한 갈래의 차단이 나머지를 되돌리지 않는다.** 기준값 한 행이 없다고 입사·퇴사 확정 전체가 막히면 그 사업장은 인사를 진행할 수 없고, 임의 기한을 세우면 **사업주는 제품이 관리하고 있다고 믿은 채 법정 기한을 넘긴다.**
- **#13의 응답은 linkages(처리한 갈래)를 함께 낸다** — 처리된 것에는 CONTRACT_ARCHIVED · INSURANCE_LOST · SEVERANCE_ASSESSMENT와 위 세 시계 중 실제로 열린 것이 들어간다.

### 18~23. 근로계약 템플릿·작성·발송·취소 (HRM-06)

| 항목 | 18. 템플릿 | 19. 초안 생성 | 20·21. 목록·상세 | 22. 발송 | 23. 취소 |

법정 명시사항 5종(근로기준법 §17)을 검증한다 — **① 임금의 구성항목·계산방법·지급방법 ② 소정근로시간 ③ 휴일 ④ 연차유급휴가 ⑤ 취업의 장소와 종사할 업무**다. 단시간근로자는 근로일별 근로시간이 추가 필수다.

- **이메일 축의 수신 주소는 profiles.recovery_email이고 서버 함수로 읽는다.** 그 표의 SELECT 정책은 본인 축과 플랫폼 축뿐이라 관리자 세션은 직접 읽지 못하며, 정책에 서버 축을 결합하는 대신 정의자 헬퍼 **workplace_member_email(wid, user_id)**(정본 [../05_database/08_rls_policies.md](../05_database/08_rls_policies.md) 헬퍼 #45)가 서버 컨텍스트에서 주소 한 값만 낸다 — 명세서의 대체 교부 경로([09_payslip.md](./09_payslip.md) #17)와 **같은 헬퍼**다. **계정 미연계 직원은 두 채널 모두 도달하지 않는다** — 그 직원의 주소를 담는 열이 v1 스키마에 없다. 교부가 성립하지 않은 채 SENT로 남고 deliveredAt이 빈 것을 #36이 보인다.
- **#20 latestOnly=true는 직원별 최신 세대 한 건만 낸다** — 취소본을 건너뛴 가장 높은 version이다. 서명 전 수정이 취소본과 새 세대를 쌓으므로 전체 이력(기본값 false)은 한 사람이 여러 줄을 차지한다. 다른 필터(status · employeeId · q)는 최신 세대를 고른 뒤에 건다.
- 상태 전이는 **DRAFT → SENT → SIGNED → ARCHIVED**와 **SENT → CANCELLED**다. 서명 전 수정은 새 버전을 발송하고 기존 발송본을 취소하는 방식이며, 같은 계약본을 고치는 경로를 두지 않는다.
- **취소 사유의 목적지는 audit_logs다**(action **contract.cancel** · 채번 정본 [../05_database/15_system.md](../05_database/15_system.md)). contracts에 취소 사유 열이 없고 상태만 CANCELLED로 바뀌므로 **그 밖에 남길 자리가 없다** — 취소는 발송본을 죽이고 직원이 받은 서명 요청을 무효화하는 되돌릴 수 없는 전이라 사유가 보존되어야 한다(REQ-GLB-17). 전후값은 **상태 문자열뿐**이고 계약 문안은 PII라 담지 않는다(REQ-SYS-10).
- **사유는 표면이 강제하고 DB 가드 배열은 건드리지 않는다.** reason은 요청 본문 필수(2~500자)이며 누락·공백은 common.validation_failed/400이다. **사유 필수 판정 배열은 건드리지 않는다**(정본 [../05_database/15_system.md](../05_database/15_system.md)) — 같은 사유를 두 층에서 강제하면 정본이 둘이 된다(compliance_task.waive와 같은 축이다).
- **금액·시간·날짜가 근로조건과 불일치하면 차단이 아니라 경고**다. 계약 문안이 근로조건 이력보다 앞설 수 있고(신규 조건의 계약을 먼저 발송) 차단하면 정상 절차가 막힌다.
- SIGNED → ARCHIVED는 근로관계 종료·계약 만료 시 #35가 자동 처리한다. **ARCHIVED 서명본도 보존기간 내 본인 읽기 전용 열람 대상**이다.

- **STAFF에게 열되 요청 스키마를 좁히는 것이 이 축의 안전 장치다.** employeeId·category·sensitivity를 서버가 고정하므로 STAFF는 타인 문서를 만들 수도, 민감 분류로 올릴 수도, 임의 카테고리로 문서함을 오염시킬 수도 없다. **역할로 요청 스키마가 갈리는 표면**이며 이는 응답 범위가 역할로 갈리는 #3 · #28과 같은 계열이다.
- **모순 해소 기록**: 화면 정본이 근태 수정 요청·휴가 신청에 증빙을 요구하는데(REQ-ATT-16 · [../07_screen/05_app_employee.md](../07_screen/05_app_employee.md)) 유일한 업로드 표면이 MANAGER 최소 역할이라 직원이 자기 증빙을 올릴 경로가 없었다. 전역 불변식인 **본인 소유권 인가**를 업로드에도 적용해 해소한다.
- **#30이 계약 완료본 · 문서함 · 근로자명부 산출물을 함께 처리한다.** 토큰이 대상 document_id와 목적을 담고 있어 종점을 나눌 이유가 없고, 열람 이력 기록 로직도 한 곳에 모인다.
- **오브젝트 스토리지 서명 URL을 응답에 담지 않는다**([01_conventions.md](./01_conventions.md)). 대상이 주민번호·임금 정보를 담은 법정 문서라 철회 불가능한 URL을 만들지 않는다.
- 연소자 법정 비치 서류(가족관계증명서 · 친권자 동의서)도 이 문서함에 올린다 — #33이 그 비치 여부를 점검한다.
- **#28은 본인 축 호출에서도 오프셋 봉투를 그대로 낸다.** 응답은 items와 page(number · size · totalCount · totalPages)이며 **본인 문서가 적다는 이유로 전량 반환 형태로 바꾸지 않는다** — 같은 표면이 역할에 따라 다른 봉투를 내면 클라이언트가 응답 모양으로 자기 역할을 역추론하게 되고, MANAGER 축은 사업장 전원의 문서라 쪽 나눔이 필요하다.
- **기록 실패 시 파일을 내보내지 않는다.** 열람 이력이 남지 않는 다운로드를 허용하지 않는다.

### 31·32. 근로자명부 완전성 검증·내보내기 토큰 (HRM-11)

- **데이터는 employees와 employment_terms에 이미 있다.** 구현 범위는 완전성 검증과 양식 출력이며 별도 입력 표면을 만들지 않는다(REQ-HRM-25).
- 누락 항목은 차단하지 않고 목록으로 제시해 보완을 유도한다 — 명부는 작성 의무이지 완전해야 출력되는 문서가 아니다.
- 보존기간은 **퇴직일 + 3년**이며 생성된 문서의 retention_until에 반영한다.

### 35. 퇴사 확정 연동 트리거 (서버)

| 표면 없음 근거 | 퇴사 한 건이 세 도메인의 후속 과제를 동시에 만든다. 이를 개별 표면으로 나누면 관리자가 여섯 번을 눌러야 하고 하나를 빠뜨리면 법정 기한을 놓친다 |
| 실패 처리 | **기한 기준값이 없으면 그 갈래만 만들어지지 않고 나머지는 만들어진다** — 퇴사 확정을 롤백하지 않으며 만들지 못한 갈래는 #13 응답의 pendingLinkages에 이름으로 남는다. **compliance_tasks에 실패 상태로 남기지 않는다**(2026-09-10 정정) — status는 OPEN · COMPLETED · WAIVED 3값뿐이라 실패를 담을 자리가 없고, 담으려면 상태를 늘려야 하는데 **만들어지지 않은 의무는 원장의 행이 아니다** |
| 퇴직급여 판정의 부재 처분 | **확정 급여가 없어도 차단하지 않는다** — 판정 실행 표면([08_payroll.md](./08_payroll.md) #26)은 payroll.severance_source_missing/409로 막지만 이 트랜잭션은 **판정 행을 남기고 calc_basis에 사유를 적으며 금액 열을 비운다**. **0원을 채우지 않는 것이 계약**이다 — 채우면 그것이 사업주에게 지급액으로 읽힌다 |

- **입사 쪽에 대응하는 트리거가 없었다 — 2026-09-10 닫혔다.** 종전에는 [../05_database/12_compliance.md](../05_database/12_compliance.md)의 파생 표가 **취득 과제(INSURANCE_ACQUISITION)를 입사 확정(HIRE)이 만든다**고 단정하는데 **#11이 compliance_tasks를 만들지 않아** 표가 6종을 세고 집행 계약이 5종만 있는 상태였다. **#11의 부수효과가 그 자리를 닫았고 서버 내부 표면은 채번하지 않았다** — 취득은 갈래가 하나뿐이라 #35 같은 트리거 표면이 필요 없다(위 #11 절).
- **대칭이 맞지 않아 보였던 것은 갈래 수의 차이였다.** 퇴사는 세 도메인의 후속 과제를 동시에 만들어 서버 표면 하나로 묶을 값이 있었고, 입사는 그렇지 않다.

- **목록(#24)만으로는 두 기능행이 성립하지 않는다.** 근로기준법 §17 명시사항 5종을 직원이 확인하려면 항목별 원문을 실을 자리가 필요하고, 교부 성립(REQ-HRM-22)을 직원 화면이 보이려면 채널·시각이 필요한데 목록 응답은 사업장명·고용형태·상태·발송일까지다. 요약에 원문을 얹으면 목록이 계약 전문을 N건 실어 나른다.
- **statedTerms는 계약 PDF의 원문 사본이 아니라 항목별 발췌**다. 전문은 #26 → #30의 완료본이 담당하며 이 표면은 화면이 5종 충족을 항목 단위로 보이기 위한 축이다. 필수 명시사항의 검증 지점은 초안 생성(#19)과 발송(#22)이고 코드는 hr.contract_missing_field/422다.
- **CMP-07 집행 표면 열거의 갱신은 후속이다.** 본 표면은 퇴사자 본인 법정문서 열람의 집행 지점이 맞으나, 그 열거의 정본은 [11_compliance.md](./11_compliance.md) #13과 [README.md](./README.md) 기능 커버리지 표에 있고 지금 "05_hr #24~#26"으로 적혀 있다. **두 자리를 같은 변경 단위에서 함께 고쳐야 하므로 이번 개정에서는 열거를 건드리지 않았다**([../03_requirements/17_traceability.md](../03_requirements/17_traceability.md) §5 등재).
- **관리자 상세(#21)와 다른 표면인 근거는 인가 축**이다. #21은 사업장 스코프·멤버십 인가이고 #36은 계정 스코프·소유권 인가다. 한 표면으로 합치면 퇴사한 직원의 본인 계약 열람이 멤버십 가드에서 먼저 끊긴다.
