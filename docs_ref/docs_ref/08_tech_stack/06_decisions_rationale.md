각 기술 결정의 근거를 카테고리 **6종**으로 나눠 기록한다. 검산: 프레임워크 1 + 데이터 접근 1 + 인증·세션 1 + 인프라·배포 1 + 모바일 1 + 품질·도구 1 = **6**.

**본 문서는 ID를 채번하지 않는다.** 제품 결정(D-NN)의 원문은 [../01_overview/06_design_decisions.md](../01_overview/06_design_decisions.md)에, 기술결정(ADR-NN)의 채번과 논증은 [../04_architecture/09_decision_records.md](../04_architecture/09_decision_records.md)에 있다. 여기서는 이미 정해진 결정의 근거만 서술하고 번호는 정본 문서를 가리킨다.

근거는 채택안의 장점이 아니라 **버린 대안이 어떻게 실패하는가**를 먼저 쓴다.

## 프레임워크

| 결정 | 근거 |
|------|------|
| 단일 웹 앱 · 단일 산출물(D-20) | 공개 페이지·관리자 웹·시스템 웹을 별개 앱으로 나누면 인증 쿠키·디자인 토큰·API 클라이언트·타입 생성 파이프라인이 셋으로 복제되고, 셋 중 하나만 갱신되는 드리프트가 일상이 된다. 표면 분리는 라우트 계층과 클라이언트 가드로 충분하며, 산출물을 하나로 두면 웹 오리진도 하나로 유지돼 쿠키 스코프(D-03) 전제가 그대로 남는다 |
| 빌드·라우터 = Vite + React Router(ADR-24) | 공개 페이지 프리렌더를 별도 도구로 붙이면 도구 축이 하나 늘고, 후보였던 전용 프리렌더 플러그인은 전부 0.x이거나 수년째 방치라 안정 API 계약이 없다. 라우터에 프리렌더가 내장된 조합을 고르면 "공개는 정적 · 나머지는 SPA"가 한 앱·한 빌드로 끝난다. 타입 안전성이 더 앞선 대안(TanStack Router)은 프리렌더가 없고 2026-05 공급망 침해 이력이 있어 버리며, 공개 사이트를 별도 정적 사이트 생성기로 떼는 안은 토큰·폰트 이중화와 약관 이원화 위험을 되불러온다 |
| 공개 페이지를 빌드 프리렌더로 둔다(D-02 수단 개정 · D-20) | 랜딩·요금제를 외부 사이트 빌더에 두면 서비스 배포와 분리돼 관리 축이 갈라진다. 검색 노출이 필요한 2본만 빌드 시점에 정적 HTML로 굽고 나머지는 같은 앱이 담는다 |
| 법정 문서는 프리렌더하지 않는다(D-20) | 약관을 정적 산출물로 구우면 활성 버전 전환마다 재빌드가 필요하고, 재빌드 전까지 화면에 뜬 약관 버전과 동의 이력의 버전이 갈라진다. 클라이언트 조회로 활성 버전을 그때그때 받으면 재빌드 트리거 자체가 사라져 그 위험이 원천 제거된다 |
| 인증 후 화면 = 클라이언트 렌더 SPA(D-04 대체 · D-20) | 웹 서버에서 업무 데이터를 미리 가져오면 세션 쿠키를 웹 서버로 다시 태워야 하고, 인가 판정 지점이 웹 서버와 API 서버 둘로 갈라진다. 웹 호스팅 계층에 서버 실행 경로를 아예 두지 않으면 그 갈림 자체가 성립하지 않는다 |
| 웹 호스팅에 서버 실행 경로를 두지 않는다 | 데이터 경로가 웹 서버를 경유하면 D-03의 서브도메인 직접 호출 전제가 무너지고, 앱(app_front)은 그 경로를 쓸 수 없어 같은 업무 로직을 두 벌 유지해야 한다. 웹과 앱이 같은 REST 표면을 공유하는 것이 계약을 하나로 유지하는 유일한 방법이다 |
| 라우트 보호를 서버 미들웨어에 두지 않는다(D-20) | 정적 배달 계층에는 판정할 서버가 없다. 클라이언트 라우터 가드는 사용자가 조작할 수 있는 번들 안에 있으므로 **신뢰 계층이 아니라 UX 보조**이며, 최종 강제는 서버 검증과 RLS가 맡는다. 가드를 계층으로 세면 실제보다 방어가 두꺼워 보이는 착시가 생긴다 |
| UI 컴포넌트 라이브러리 미채택 | 라이브러리를 쓰면 디자인 시스템 토큰을 라이브러리 테마 규약으로 한 번 더 번역해야 하고, 컴포넌트 하나가 규약을 벗어날 때마다 오버라이드가 쌓인다. Tailwind 유틸리티 + 자체 컴포넌트 + lucide-react로 구성한다 |
| 차트 라이브러리 미채택 | v1 범위에 대시보드·통계 화면이 없다. 쓰지 않을 의존성을 미리 넣으면 번들과 업그레이드 부담만 남는다 |
| 폰트 셀프호스팅(IBM Plex Sans KR) | 빌드 시 외부 폰트 서비스를 호출하면 그 서비스의 일시 장애가 배포 실패로 직결된다. 서브셋 woff2를 저장소에서 서빙해 빌드를 네트워크 의존에서 분리한다 |
| Spring Boot 채택(D-21 · ADR-25) | 프레임워크 없이 얇은 HTTP 계층만 조립하면 인가 필터·트랜잭션 경계·모듈 경계를 프로젝트마다 새로 설계하게 되고, 13개 도메인이 각자 다른 관례를 갖는다 — 그 차이는 인가 판정과 확정 불변식처럼 **틀리면 되돌릴 수 없는 자리**에서 드러난다. 패키지를 계층 우선으로 나누는 안도 버렸다 — 도메인 경계가 구조에 드러나지 않아 모듈 간 직접 호출을 구조로 막을 수 없다. 자동 구성 · 필터 체인 · 트랜잭션 경계 · 스케줄링이 한 축으로 모이는 프레임워크를 고르고, 경계는 common · core · modules 패키지 3축과 4계층이 진다. 언어 축 자체를 옮긴 근거는 D-21이 소유한다 — 급여 계산 결정론과 행 단위 보안 주입이라는 **실패 비용이 가장 큰 두 자리**를 팀이 가장 덜 익숙한 스택에 두지 않는다 |
| 리액티브 스택 미채택 | 세션 컨텍스트 주입이 트랜잭션에 바인딩된 커넥션을 전제하고(ADR-28) 쓰기 축이 블로킹이다. 비동기 축을 섞으면 주입 지점이 하나라는 보장이 깨지고, 주입 누락이 조회 실패가 아니라 **격리 없는 조회**로 나타날 경로가 생긴다. 타깃 규모에서 얻는 처리량 이득이 그 위험을 넘지 않는다 |
| 도메인 모듈 13 = 문서 도메인 13 | 모듈 경계를 코드 편의로 나누면 요구사항 문서와 모듈이 대응하지 않아 "이 REQ는 어느 모듈인가"가 매번 판단 사안이 된다. 문서 도메인과 1:1로 맞춘다 |
| 마이크로서비스 미채택 | 서비스를 쪼개면 급여 확정처럼 근태·인사·기준값을 한 트랜잭션으로 묶어야 하는 연산이 분산 트랜잭션이 된다. 결정론과 확정 불변식을 지키는 비용이 규모 대비 과하다 |

## 데이터 접근

| 결정 | 근거 |
|------|------|
| 데이터 접근 = JPA 쓰기 + MyBatis 읽기 2축(D-21 · ADR-26) | 경계 없이 도메인마다 편한 도구를 고르는 안을 버렸다 — 영속성 컨텍스트가 아직 반영하지 않은 변경을 직접 SQL이 보지 못하고, 반대로 직접 갱신을 컨텍스트가 모른 채 낡은 엔티티를 든다. 호출 순서 규율로 막으면 **위반이 리뷰에 걸리지 않는 종류의 결함**이 되고 가장 비싸게 드러나는 자리가 급여 확정이다. 쓰기를 한 축으로 좁히면 그 문제의 성립 조건이 사라진다. 매핑 단일 축(JPA만)도 버렸다 — 동적 정렬·필터와 1:N 중첩을 코드로 조립하면 **발행 SQL이 보이지 않아** **61개** 테이블·173정책 위에서 어느 정책이 어느 조회를 막는지 추적할 수 없다. SQL 매퍼 단일 축도 버렸다 — 61테이블의 매핑을 손으로 유지하고 상태 전이가 규칙인 쓰기 경로에서 변경 추적과 낙관적 잠금을 매번 다시 만들게 된다 |
| 스키마 소유 = 데이터베이스(엔티티 생성 금지 · 검증만) | 엔티티에서 스키마를 생성하면 EXCLUDE 제약·RLS 정책·부분 인덱스·가드 트리거·보안 정의자 함수처럼 매핑이 표현하지 못하는 객체가 정의에서 사라지고, **다음 적용이 그것들을 조용히 지운다.** 엔티티를 정본으로 두는 안은 도구가 바뀌어도 같은 판정을 받는다(D-05의 버린 대안 ②가 그대로 성립한다). 데이터베이스가 정본이고 엔티티는 수기로 쓴 사본이며, 기동 시 스키마는 **검증만** 한다 |
| 마이그레이션 = 루트 db_migration raw SQL + Flyway(ADR-27) | 매핑 도구의 마이그레이션 기능은 RLS 정책·EXCLUDE 제약·트리거 함수를 생성하지 못해 결국 수동 SQL을 덧붙이게 되고, 그 순간 이력이 두 갈래가 된다. 자체 러너 유지도 버렸다 — 러너가 하는 일(이력 조회 · 체크섬 · 번호순 적용 · 실패 시 중단)이 표준 도구의 기본 동작과 같고, **다른 언어 런타임을 이미지에 하나 더 넣어야 한다는 원래 근거가 런타임 통일로 사라졌다.** 직접 만든 러너는 체크섬·정렬·부분 실패의 경계 사례를 스스로 검증해야 한다. 적용 이력 테이블은 **업무 스키마 밖**에 둔다 — 안에 두면 도구가 만든 테이블 하나 때문에 테이블 61종 검수 기준이 어긋나고, 그 예외를 문서에 적기 시작하면 검수가 무뎌진다. db_migration/을 backend/ 안에 넣는 안도 버렸다 — 위치 지정은 간단해지지만 **스키마 정본이 애플리케이션 저장소의 하위 폴더가 되어 "데이터베이스가 정본"이라는 축이 배치에서 흐려진다** |
| RLS 주입 = DataSource 프록시(ADR-28) | 컨텍스트 주입을 호출부 책임으로 두면 새 메서드 하나가 주입을 빠뜨렸을 때 그 쿼리만 격리 없이 실행되고 **사고가 나기 전까지 드러나지 않는다.** 커넥션 풀의 연결 초기화 구문이나 전역 설정으로 주입하는 안은 더 나쁘다 — 풀에 반납된 연결이 이전 요청의 컨텍스트를 물려받아 **다음 사용자가 남의 데이터를 본다.** 영속성 계층의 쿼리 가로채기 지점에 거는 안도 버렸다 — 쿼리 단위라 트랜잭션 경계와 어긋나고 **다른 데이터 접근 축의 쿼리를 가로채지 못해 읽기 경로 전체가 컨텍스트 없이 나간다.** 데이터소스 프록시가 트랜잭션 진입 시 한 번 주입하면 두 축이 같은 지점을 지나고, 주입 누락은 유출이 아니라 조회 실패로 나타난다 |
| RLS를 처음부터 ENABLE + FORCE | 나중에 켜면 이미 작성된 모든 쿼리가 정책 소급 작성 대상이 되고, 그때는 어느 쿼리가 어떤 권한을 전제했는지 아무도 모른다. FORCE를 빼면 테이블 소유자 접속이 정책을 통째로 건너뛴다 |
| bigint·numeric을 long·BigDecimal로 강제 | PostgreSQL 타입이 맞아도 필드를 부동소수점 타입으로 선언하면 부동소수점 금지 원칙(REQ-GLB-02)이 데이터 접근 계층에서 조용히 깨진다. 십진 타입을 부동소수점에서 만드는 호출도 같은 경로다 — 생성 시점에 이미 값이 어긋난다. 오차는 급여 확정 후 명세서 금액 불일치로 처음 드러나며, 그때는 이미 교부된 뒤다 |
| date = 시간대 없는 날짜 타입(LocalDate) | 시간대를 끌고 들어오는 구형 날짜·시각 타입으로 받으면 자정 기준 해석으로 KST 일자가 하루 밀리고, 근무일·급여월·효력일이 하루 밀리면 귀속월 전체가 틀어진다. **문자열로 우회하는 안도 이제 버린다** — 문자열은 그 실패를 피하려던 수단이었을 뿐 형식 검증과 비교 연산을 코드로 다시 만들게 하는데, 시간대를 갖지 않는 날짜 타입에서는 실패의 성립 조건 자체가 없다. 대신 **구형 타입의 사용을 금지**하는 계약을 두고 기동 스모크 테스트가 검사한다(ADR-17 개정) |
| 드라이버 전역 옵션으로 타입 해석을 바꾸지 않는다 | 두 데이터 접근 축이 같은 드라이버를 공유하므로 전역 변경은 의도하지 않은 경로까지 함께 바꾸고, **어느 축이 그 설정을 전제하는지가 코드 어디에도 드러나지 않는다.** 설정 한 줄이 사라지면 매핑이 조용히 달라진다. 계약의 축을 드라이버 설정이 아니라 **선언된 자바 타입**으로 옮기고, 검증 대상도 설정값이 아니라 실제 반환 타입으로 둔다 |
| 급여 계산을 순수 함수 계층으로 격리 | 계산 코드가 데이터베이스·현재 시각에 접근할 수 있으면 결정론(REQ-GLB-01)은 규칙일 뿐 강제가 아니다. 입출력이 값 객체뿐인 계층으로 격리해 접근 자체를 불가능하게 만든다 |
| 검증 = Bean Validation 단일 축 | 검증을 서비스 계층 수기 코드로 두는 안을 버렸다 — 같은 규칙이 도메인마다 다시 쓰이고 어느 필드가 검증됐는지가 호출 경로마다 달라진다. 프레임워크 밖 스키마 검증 라이브러리를 따로 얹는 안도 버렸다 — **선언이 DTO와 스키마 두 곳으로 갈라지고**, 문서 생성기가 보는 것과 실제로 검증되는 것이 어긋나 OpenAPI 계약이 느슨해진다. 선언을 DTO 한 곳에 모으면 검증·문서·타입이 같은 출처를 갖는다. 원래 이 축에서 지적됐던 위험(미선언 필드가 조용히 통과하는 것)은 **역직렬화에서 미선언 속성을 실패로 다루는 계약**으로 막고, 금액을 문자열로 유지하는 규칙은 common의 자체 제약 애노테이션으로 한 번만 만든다 |
| OpenAPI 문서에서 프론트 타입 생성 | 요청·응답 타입을 손으로 쓰면 서버 계약이 바뀌어도 클라이언트가 컴파일을 통과한다. 계약 위반이 런타임에야 드러나고, 그 지점이 급여 금액 필드면 화면에 undefined가 뜬다 |

## 인증·세션

| 결정 | 근거 |
|------|------|
| 웹 = 세션 쿠키 · 앱 = JWT | 웹에 JWT를 쓰면 토큰을 어딘가에 저장해야 하고 어느 저장소를 골라도 스크립트 접근 위험이 남는다. 앱에 세션 쿠키를 쓰면 쿠키 저장소·CSRF·도메인 규약을 네이티브에서 재현해야 한다. 각 표면이 자기 플랫폼의 기본 수단을 쓴다 |
| 쿠키 Domain=.{domain} + SameSite=Lax(D-03) | app.{domain}과 api.{domain}이 다른 오리진이므로 쿠키 도메인을 상위로 올리지 않으면 API 요청에 세션이 실리지 않는다. SameSite=None까지 풀면 서드파티 컨텍스트에서도 실려 CSRF 표면이 넓어진다 |
| 서브도메인 직접 호출(D-03) | 웹 서버가 API를 프록시하면 요청마다 홉이 하나 늘고 SSE 연결이 프록시 타임아웃에 걸린다. 무엇보다 앱은 프록시를 쓸 수 없어 인증·에러 규약이 표면마다 갈라진다 |
| 세션 스토어 = Redis | 세션을 데이터베이스에 두면 요청마다 업무 데이터베이스에 부하가 걸리고 만료 정리 정기작업이 필요해진다. 프로세스 메모리에 두면 배포할 때마다 전원이 로그아웃된다. TTL 만료가 내장된 저장소를 쓴다 |
| Redis 클라이언트 단일화 | 클라이언트를 둘 섞으면 연결 풀·타임아웃·재연결 정책이 두 벌이 되고, 장애가 났을 때 어느 축이 끊긴 것인지 로그에서 갈라 보기 어렵다. 세션 스토어는 프레임워크 표준 클라이언트를 전제하므로 다른 클라이언트를 고집하면 그 자리에 어댑터를 하나 더 유지하게 된다. 세션·블랙리스트·채널·스케줄 락을 한 클라이언트로 통일해 연결 관리와 장애 표면을 하나로 둔다 |
| JWT 폐기 = Redis 블랙리스트 | JWT는 발급 후 서버가 무효화할 수단이 없다. 로그아웃·계정 정지가 토큰 만료까지 반영되지 않으면 정지된 계정이 남은 수명만큼 계속 접근한다 |
| 자격 증명 전략 계층 미채택 | 자격 증명이 로컬 하나뿐인데 전략 계층을 얹으면, 실제 분기인 "세션 쿠키냐 토큰이냐"가 전략 콜백 안으로 숨어 필터 체인만 보고는 어느 경로가 무엇을 신뢰하는지 읽을 수 없다. 소셜 로그인이 없어 프로바이더 생태계 이점도 없다. 반대로 **보안 프레임워크를 아예 쓰지 않는 안도 버렸다** — 필터 순서 · 인가 결정 지점 · CSRF 토큰 · 세션 고정 방지를 직접 만들면 그것이 곧 자체 보안 프레임워크이고, 검증되지 않은 쪽이 남는다. 필터 체인과 인가 결정 지점까지만 쓰고 그 위에 추상 계층을 두지 않는다(ADR-05 개정) |
| 2단 방어 — 서비스 검증 + RLS | 애플리케이션 검증만 두면 새 엔드포인트 하나가 사업장 스코프 검사를 빠뜨렸을 때 다른 사업장 데이터가 그대로 나간다. RLS만 두면 "권한 없음"과 "데이터 없음"이 구분되지 않아 사용자에게 잘못된 안내가 나간다. 둘 다 둔다 |
| 재인증 토큰을 Redis에 둔다 | 5분 수명 토큰을 데이터베이스에 쓰면 회전 빈도만큼 쓰기가 쌓이고 법정 보존 대상도 아니다 |

## 인프라·배포

| 결정 | 근거 |
|------|------|
| 웹 = Vercel · API = EC2 분리 | API를 서버리스에 올리면 SSE 장기 연결과 정기작업·PDF 렌더링처럼 수명이 긴 작업이 실행 시간 제한에 걸린다. 웹을 EC2에 올리면 정적 배달·CDN·프리뷰 배포를 직접 운영해야 한다. 각 워크로드를 맞는 곳에 둔다 |
| 프리뷰 빌드는 고정 픽스처로 렌더한다 | 프리뷰가 운영 API를 호출하면 미검증 코드가 실데이터 경로에 붙고, 공개 페이지 확인이라는 목적에 비해 노출 표면이 과하다. 요금제·약관 샘플을 고정 픽스처로 두면 확인 목적은 그대로 달성된다 |
| 단일 EC2 + Docker Compose | 컨테이너 오케스트레이터를 쓰면 클러스터 운영·네트워크 정책·시크릿 관리가 통째로 따라오는데, 타깃 규모(상시 근로자 1~30인 사업장)에서 얻는 가용성 이득이 그 비용을 넘지 않는다. 확장 시점의 판단은 로드맵에 둔다 |
| postgres·redis를 호스트 포트로 노출하지 않는다 | 노출하면 보안 그룹 규칙 하나가 데이터베이스를 인터넷에 여는 사고 경로가 된다. 외부 진입점을 nginx 하나로 고정한다 |
| 관리형 데이터베이스(RDS) 미채택 | 관리형으로 옮기면 백업·패치·고가용성을 얻지만 v1 단계에서 고정 비용이 매출보다 먼저 발생한다. 확장 지점으로 남기고 v1은 컨테이너로 운영한다 |
| S3 서울 리전 고정 | 주민번호·계좌·근로계약·명세서가 담긴다. 국외 리전에 두면 국외 이전 고지·동의 절차가 추가로 필요해지고, 그 절차 없이 저장하면 그 자체가 위반이다 |
| 파일은 비공개 + 1회용 토큰 + 서버 스트리밍 | 공개 URL을 만들면 링크 하나가 유출되는 순간 인증 없이 명세서가 열리고, 클라이언트에 저장소 서명 URL을 내려주면 그 수명 안에서 소지자 누구에게나 열린다. 다운로드는 **1회용 토큰을 발급해 서버가 소유권을 검증한 뒤 스트리밍**으로만 내려주며, 저장소 서명은 서버 안에 머문다(ADR-16) |
| 백업 = pg_dump 일일 + S3 | WAL 아카이빙 기반 시점 복구를 켜면 베이스 백업·아카이브 보존·복구 리허설을 함께 운영해야 한다. 타깃 규모에서 하루치 재입력이 감당 가능하다고 보고 RPO 24시간을 인정한다. 이 값을 감추지 않고 문서에 남긴다 |
| Redis 분산락은 정기작업 전용 | 업무 데이터 경합까지 Redis 락으로 막으면 락 서버가 잠깐 끊긴 사이에 급여 확정 불변식이 함께 무너진다. 업무 경합은 데이터베이스 트랜잭션 잠금으로, 정기작업 중복 실행만 분산락으로 막는다 |
| 작업 큐 미채택 | 정기작업은 8건이고 전부 저빈도다. 큐를 도입하면 워커 프로세스 분리·재시도 정책·대시보드 운영이 따라오는데, 얻는 것은 8건에 대한 재시도뿐이다. 시각 트리거 + 스케줄 락 + 멱등키로 같은 보장을 만든다. 채번·논증 정본은 [../04_architecture/09_decision_records.md](../04_architecture/09_decision_records.md) |
| 실시간 = SSE(WebSocket 미채택) | v1의 실시간 요구는 인앱 알림 배달 하나이며 서버 → 클라이언트 단방향이다. WebSocket을 쓰면 양방향 프로토콜·핸드셰이크·하트비트·프록시 설정을 관리하면서 절반만 쓴다 |
| PDF = headless Chromium 렌더링 | 좌표·셀 폭을 코드로 조립하는 라이브러리는 명세서 항목이 늘 때마다 레이아웃을 다시 맞춰야 하고, 한글 폰트 임베딩과 줄바꿈을 라이브러리 규약대로 따로 해결해야 한다. HTML 템플릿은 관리자 웹 미리보기와 그대로 공유된다. 대신 브라우저 인스턴스는 풀로 관리하고 동시 실행 수에 상한을 둔다 |
| 문자 발송을 v1에 두지 않는다 | 문자 대체 발송은 v1 알림 범위 밖이다. 사업자를 정하지 않은 채 특정 SDK를 코드에 박으면 교체 시 발송 호출부 전체가 바뀌므로, 도입 시점에도 어댑터 인터페이스 뒤에 두고 사업자 확정 전에는 구현을 채우지 않는다 |
| 스케줄 락에 표준 구현을 쓴다(직접 구현 미채택) | 직접 구현을 버렸다 — 조건부 설정과 소유자 확인 해제만 있으면 될 것 같지만 실제로 필요한 것은 **스케줄 등록 지점에 물려 락 획득 실패 시 실행 자체를 건너뛰는 배선**과 최소·최대 락 유지 시간, 그리고 인스턴스 간 시계 오차 처리다. 그것을 직접 만들면 경계 사례를 스스로 검증해야 하고, 검증이 빠진 채로도 **정상 동작처럼 보인다** — 중복 실행은 배포 창이 겹치는 드문 순간에만 드러난다. 이 축에는 스케줄러에 그대로 붙는 유지되는 표준 구현이 있으므로 "방치된 의존성을 피한다"는 이유가 성립하지 않는다. 락 저장소는 이미 쓰는 Redis를 그대로 쓴다 |

## 모바일

| 결정 | 근거 |
|------|------|
| React Native CLI bare(Expo 관리 워크플로 미채택) | 위치 측위·보안 저장소·서명 캔버스 캡처는 전부 네이티브 설정을 직접 만져야 한다. 관리 워크플로를 얹으면 이 설정들이 config 플러그인 계층을 거치고, 라이브러리가 플러그인을 제공하지 않는 순간 결국 bare 프로젝트를 열게 된다. 그때는 두 방식의 단점만 남는다. 반면 **Expo Modules 패키지를 bare에 개별 설치하는 것은 관리 워크플로 도입이 아니므로** 이 근거의 적용 대상이 아니다 |
| 앱은 직원 표면만 담는다 | 관리자 업무까지 앱에 넣으면 급여 확정·기준값 설정 같은 되돌리기 어려운 조작이 작은 화면과 불안정한 네트워크 위에 놓인다. 사업장 운영은 관리자 웹의 몫이다 |
| 토큰을 Keychain/Keystore에 저장 | AsyncStorage·MMKV는 평문 저장소다. 기기 백업·루팅 환경에서 그대로 읽힌다. MMKV의 암호화 옵션도 대체재가 아니다 — 암호화 키 자체의 보관처를 해결해 주지 않는다 |
| 보안 저장소 라이브러리 교체 | 오래 표준으로 쓰이던 패키지의 npm 배포본에 New Architecture 구현이 없어 **제거가 예고된 레거시 호환 계층 위에서만 동작**하고, 구현이 병합된 뒤로도 배포가 나오지 않았다. JWT 보관은 앱 보안의 최종 방어선이라 그 축을 예고된 제거 대상에 두지 않는다. **대체 후보였던 Expo Modules 패키지도 설치 도구가 현재 React Native 메이저를 지원하지 않아 v1에 들일 수 없다** — 그래서 귀결은 다음 행의 자체 모듈이다 |
| 측위 라이브러리에 실기기 검증을 채택 조건으로 건다 | 채택 후보가 New Architecture 대응은 끝냈으나 릴리스가 2년째 멈춰 있고 수정이 미병합으로 쌓여 있다. "최신 안정판 고정"이라는 일반 규약이 여기서는 도피구가 되지 않는다 — 최신판이 곧 2년 된 판이다. 근태 체크인은 법정 기록의 입구이므로 검증 통과를 조건으로 두고 미통과 시 대안으로 교체한다 |
| 백그라운드 위치 권한 미요청 | 상시 추적은 개인위치정보 처리 범위를 넓혀 별도 동의와 이용 사실 확인자료 부담을 키우고, 스토어 심사에서 필요성 소명을 요구받는다. 체크인 판정에 필요한 것은 그 순간의 좌표 하나뿐이다 |
| 지오펜스 판정을 서버가 한다 | 클라이언트 판정은 우회 가능하다. 앱이 "반경 안"이라고 보고하면 서버는 그것을 검증할 방법이 없다. 좌표를 받아 서버가 판정한다 |
| 오프라인 기록 미채택 | 오프라인 큐를 두면 체크인 시각과 기록 시각이 갈라지고, 지오펜스·지각 판정·마감 잠금이 어느 시각을 기준으로 하는지가 요청마다 달라진다. 온라인 전제로 두고 실패를 그 자리에서 표시한다 |
| 로컬 데이터베이스 미채택 | 오프라인 기록이 없으면 로컬에 영속할 업무 데이터가 없다. 서버 상태 캐시는 메모리 캐시로 충분하고, 디스크에 남기면 분실 기기에서 급여 이력이 읽힌다 |
| 전자서명 캔버스 자체 구현 | 웹뷰 기반 서명 라이브러리는 서명 데이터를 base64 문자열로 브리지 왕복시키고 앱에 웹뷰 런타임을 통째로 들인다. 필요한 것은 궤적을 받아 이미지로 캡처하는 것뿐이다 |
| 푸시 알림을 v1에 두지 않는다 | 푸시(NTF-02)는 v1.1 이월이며 v1 알림 배달은 인앱 단일 채널이다. 스택에 전달·표시 라이브러리를 미리 올려 두면 쓰지 않는 의존성의 공급망·업그레이드 부담만 남고, 실제로 이 축의 표시 라이브러리는 2026-04에 아카이브됐다. 도입 시점에 그때의 유지보수 상태로 다시 고른다 |
| 알림 본문에 금액·개인정보를 넣지 않는다 | 앱 밖 도달 수단의 본문은 잠금화면에 그대로 뜬다. 명세서 발행 알림에 금액이 들어가면 기기를 든 누구에게나 급여가 보인다. 채널이 무엇이든 같은 규칙을 적용한다 |
| 웹과 앱의 스타일 토큰 정의를 두 벌 유지한다 | 앱 스타일링 라이브러리의 안정판이 웹보다 한 메이저 아래의 Tailwind 설정 축에 묶여 있어 설정 형식 자체가 다르다. 억지로 한 벌로 맞추려면 preview 버전을 프로덕션에 들여야 한다. 정의는 두 벌로 두되 값의 출처를 디자인 토큰 표 하나로 고정해 값이 갈리는 것을 막고, 라이브러리 다음 메이저가 안정화되면 통합을 재평가한다 |
| 상시 내비게이션을 드로어로 둔다(하단 탭 미채택) | 상시 이동 항목이 8개다. 5탭에 담으려면 셋을 탭 밖으로 밀어야 하고, 밀린 항목은 어느 탭 안에 숨었는지 사용자가 기억해야 하는 위치가 된다. 탭을 8개로 늘리는 안은 좁은 폭에서 라벨이 잘리고 44포인트 터치 타깃도 무너진다. 드로어는 항목 수가 늘어도 라벨과 배지를 온전히 보이고, 대신 잃는 것은 한 번의 탭 이동이라 진입 빈도가 낮은 항목이 많은 이 표면에서는 손해가 작다. 상시 신호는 앱바 햄버거의 점 표시가 대신한다(정본 [../07_screen/01_standards.md](../07_screen/01_standards.md) §4-2) |
| 보안 저장소를 자체 네이티브 모듈로 구현한다 | 남은 선택지가 셋이었다 — 배포본에 New Architecture 구현이 없는 기존 표준 패키지 · 설치 도구가 현재 React Native 메이저를 지원하지 않는 Expo Modules 패키지 · 평문 저장소다. 앞의 둘은 우리가 고칠 수 없는 남의 릴리스 일정에 JWT 보관을 매고, 셋째는 애초에 대안이 아니다. 필요한 표면은 읽기·쓰기·삭제 세 개뿐이라 자체 구현 범위가 작고, 플랫폼 API(Keychain · AndroidKeyStore)는 라이브러리보다 오래 산다. 대가는 iOS·Android 코드 두 벌의 유지다 |
| 실시간 수신 전송을 추상화 뒤에 둔다 | 채택한 폴리필은 대안이 없다시피 하지만 릴리스가 정체돼 있다. 화면과 훅이 이 패키지를 직접 알면 교체가 곧 화면 수정이 된다. 스트림 인터페이스를 하나 두고 실 전송과 mock 전송을 같은 자리에 끼우면, 교체 비용이 파일 하나로 묶이고 서버 없는 단계에서도 알림 흐름을 그대로 시연할 수 있다. 채널 유실 대비는 추상화가 아니라 **폴링 폴백**이 진다 — 실시간 채널을 유실 방지의 유일한 수단으로 삼지 않는다 |
| 앱 폰트를 번들한다(웹과 다른 서체) | 시스템 폰트에 맡기면 같은 화면이 iOS·Android·기기 설정마다 다른 자소 폭으로 그려져 금액 자릿수 정렬과 표 레이아웃이 흔들린다. 웹과 같은 서체로 맞추는 안은 앱 번들에 담을 가중치가 늘고 한글 서브셋 크기가 커져 설치 용량으로 되돌아온다. 앱은 3단 가중치면 충분하므로 **가중치 수와 서브셋 범위를 줄인 서체를 따로 고르고**, 값의 일관성은 서체 이름이 아니라 디자인 토큰 표가 진다 |
| 환경 주입을 생성 스크립트로 한다 | 런타임 환경변수 라이브러리는 iOS·Android 빌드 설정을 양쪽 다 물고 들어와, 값 하나를 바꾸는 일이 네이티브 프로젝트 변경이 된다. 빌드 전에 환경 파일을 병합해 타입이 붙은 상수 모듈을 생성하면 의존이 늘지 않고 오타가 타입 검사에서 잡힌다. 대가는 생성물을 만드는 단계를 설치·실행·검증 앞에 붙여야 한다는 것이며, **시크릿은 어느 방식이든 앱 번들에 넣지 않는다** — 클라이언트 번들은 해체 가능하다 |
| 생체 인증을 재인증 수단으로 인정하지 않는다 | 생체 등록은 기기 소유자 단위라 계정 소유자와 일치한다는 보장이 없다. 민감정보 열람 재인증은 비밀번호 재확인 단일 경로로 둔다 |

## 품질·도구

| 결정 | 근거 |
|------|------|
| 패키지 관리 = 표면별 분기(backend Gradle · 프런트 npm) | 세 표면을 한 패키지 매니저로 묶는 안을 버렸다 — JVM 빌드를 npm 스크립트로 감싸도 실제 빌드 도구는 그대로여서 **위장 계층만 하나 늘고** CI가 두 도구를 다 설치하게 된다. 프런트 축에서 pnpm·yarn을 버린 이유는 그대로다 — 별도 설치와 corepack 버전 고정이 CI·온보딩에 한 축을 더하고, 심볼릭 링크 node_modules를 React Native Metro가 기본 해석하지 못해 app_front에 hoisting 설정을 계속 유지해야 한다. npm은 Node.js 24 LTS 동봉이라 도구 축이 하나 줄고 npm ci가 락 파일 재현을 보장하며, Gradle 축은 래퍼와 의존성 잠금 파일이 같은 재현성을 준다 |
| npm workspaces 미채택 — 3개 독립 패키지(D-06) | workspaces로 묶으면 공유 코드를 담을 네 번째 패키지 폴더가 생겨 확정된 3폴더 구조가 깨지고, 루트 호이스팅이 표면의 의존성 경계를 흐린다. **백엔드가 JVM 축으로 옮겨가면서 묶을 여지 자체가 더 줄었다** — 호이스팅 문제는 이제 웹과 앱 둘 사이에서만 성립한다. 계약 공유는 OpenAPI 타입 생성으로 충분하다. 채번·논증 정본은 [../04_architecture/09_decision_records.md](../04_architecture/09_decision_records.md) |
| 생성 타입을 클라이언트 저장소에 커밋 | 커밋하지 않으면 클라이언트 빌드가 backend/ 소스를 필요로 하게 되고, 프론트 배포가 백엔드 저장소 상태에 묶인다. 백엔드가 다른 런타임이라 **클라이언트 CI에 JVM 빌드를 얹어야 하는 문제까지 따라온다** |
| CI에서 타입 재생성 후 diff 검사 | 검사가 없으면 서버 계약이 바뀌어도 클라이언트 타입이 그대로 남아 컴파일이 통과한다. 계약 드리프트를 잡을 수 있는 유일한 자동 지점이다 |
| 테스트 러너를 표면별로 둔다(ADR-29) | 러너를 다시 하나로 맞추려는 안을 버렸다 — 백엔드가 다른 언어가 되면서 **통일 대상 자체가 사라졌고**, 각 표면이 자기 생태계 표준을 따르는 편이 유지 비용이 낮다. 관례 통일은 CI 단계 이름과 게이트 구성이 대신 진다. 통합 테스트를 인메모리 데이터베이스로 도는 안도 버렸다 — 행 수준 보안·배제 제약·부분 유일 인덱스가 없거나 다르게 동작해 **2단 방어의 2단째가 실제로 도는지를 검증할 수 없고**, 통과하는 테스트가 방어가 있다는 착각만 남긴다. 공용 개발 데이터베이스에 붙이는 안은 격리 테스트를 격리되지 않은 환경에서 돌리는 것이다 |
| 앱만 Jest + RNTL 유지 | React Native preset과 Metro 트랜스폼이 Jest에 묶여 있다. 러너 통일보다 플랫폼 표준을 따르는 편이 유지 비용이 낮다 |
| 골든 케이스에 근사 비교를 쓰지 않는다 | 허용 오차를 두는 순간 부동소수점 회귀가 테스트를 통과한다. 그 오차가 명세서 금액 불일치로 드러날 때는 이미 교부된 뒤다 |
| 기준값 누락을 부정 케이스로 검증 | 계산이 차단되는 것이 정상 동작이다. 기본값·직전 연도 값 대체가 일어나지 않음을 확인하지 않으면, 조용히 틀린 세금이 계산돼도 테스트는 전부 초록이다 |
| 프로젝트 고유 정적 분석 규칙 4종 | 부동소수점 금지·시각 의존 금지·RLS 우회 금지·시크릿 노출 금지는 리뷰로 지키기에는 위반 지점이 너무 많고 위반 비용이 너무 크다. 규칙으로 차단한다. **구성은 4종 그대로이고 판정 축만 표면을 따라 갈린다** — 앞의 셋은 백엔드의 구조 검사·컴파일 시점 분석이, 넷째는 웹의 정적 분석 규칙이 집행한다 |
| TypeScript 메이저를 한 단계 낮게 고정한다(web_front · app_front) | 최신 메이저는 타입 인지 정적 분석 도구의 지원 범위 밖이라, 최신을 고집하면 금액 문자열 규약과 비동기 규칙을 클라이언트 축에서 검증할 수단을 v1 내내 잃는다. 다음 마이너에서 재평가한다. **backend는 TypeScript 축이 아니므로 이 판단의 적용 대상이 아니다** |
| 정적 분석 버전을 표면별로 갈라 둔다 | 모바일 공식 설정 패키지의 허용 범위가 웹이 쓰는 메이저를 포함하지 않는다. 억지로 맞추면 공식 설정을 버리고 앱 규칙을 직접 유지해야 한다. 축이 갈리는 것을 인정하고 각 표면이 자기 생태계의 표준을 따른다 |
| 앱 스토어 배포 자동화 미채택 | v1 릴리스 빈도가 낮고 서명·프로비저닝 자동화는 그 자체로 시크릿 관리 표면을 늘린다. 수동 배포로 두고 필요해지면 도입한다 |
| 운영 데이터를 로컬에 두지 않는다 | 개발 환경은 접근 통제·감사·암호화가 운영 수준이 아니다. 주민번호·계좌가 담긴 데이터를 옮기는 순간 그 환경이 유출 경로가 된다 |
