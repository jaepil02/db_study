정기작업은 사용자 요청 없이 서버가 스스로 도는 처리다. v1 필수는 **8건**이며 전부 시각 트리거로 등록한다. 별도 작업 큐 인프라를 두지 않는다 — 8건은 저빈도이고, 큐를 도입하면 워커 분리·재시도 정책·대시보드 운영이 따라오는데 얻는 것은 그 8건에 대한 재시도뿐이다(ADR-12).

큐가 없어도 보장은 세 장치로 만든다. **분산락**이 중복 실행을 막고, **멱등키**가 재실행의 중복 부수효과를 막고, **재시도 상한과 종결 처리**가 실패를 조용히 성공으로 바꾸지 않게 한다. 세 장치는 서로를 대체하지 못한다 — 락은 동시 실행을, 멱등은 반복 실행을, 종결 처리는 영구 실패를 각각 담당한다.

**작업 목록·주기·관련 기능의 정본은 [../02_features/15_scheduled_jobs.md](../02_features/15_scheduled_jobs.md)다.** 본 문서는 그 목록을 실행 구조 관점(락 키 · 멱등 단위 · 재시도 성격)에서 다시 본다.

## 실행 구조

| # | 작업 | 주기(KST) | 실행 단위 | 멱등 단위 | 실패 성격 |
|---|------|----------|----------|----------|----------|
| 1 | expireInvitations | 30분 | 전 사업장 순회 | 초대 행의 상태 전이(PENDING → EXPIRED). 이미 종결된 행은 건너뛴다 | 다음 주기가 이어받는다 |
| 2 | autoUnsuspendAccounts | 매일 00:05 | 계정 순회 | 정지 만료 계정의 상태 전이(SUSPENDED → ACTIVE) | 다음 주기가 이어받되 로그인 경로가 개별 복귀를 보조한다 |
| 3 | checkSubscriptionExpiry | 매일 00:10 | 계정 순회 | (구독, 판정 기준일) 1회 | 다음 주기가 이어받는다 |
| 4 | rollupAttendanceDaily | 매일 00:20 | 사업장 · 근무일 | (직원, 근무일) 집계 갱신. 재실행이 같은 값으로 수렴한다 | 사업장 단위로 격리한다. 한 사업장 실패가 다른 사업장을 막지 않는다 |
| 5 | accrueAndExpireLeave | 매일 00:40 | 사업장 · 직원 | (직원, 발생·소멸 사유, 기준일) 원장 1행 | 원장이 중복 적립되지 않도록 부분 유일 제약이 최종 방어다 |
| 6 | recomputeEmployeeCountSnapshot | 매일 02:20 | 사업장 · 기준일 | (사업장, 기준일, 산정 범위) 스냅샷 1행 | 스냅샷 누락은 급여·연차를 차단하므로 실패를 즉시 알린다 |
| 7 | checkComplianceDeadlines | 매일 08:30 | 사업장 · 과제 | (사업장, 과제, 판정 기준일) 알림 1회 | 다음 주기가 이어받는다. 중복 알림을 만들지 않는다 |
| 8 | retryPayslipAndPush | 15분 | **미렌더(PENDING) · 실패 상태 명세서** | (명세서, 재시도 회차) 1회 | 5회 초과 시 실패를 유지하고 dead letter로 넘긴다 |

검산: 초대 만료 1 + 정지 해제 1 + 구독 만료 1 + 근태 롤업 1 + 연차 적립·소멸 1 + 상시근로자 스냅샷 1 + 법정 기한 감지 1 + 명세서 재시도 1 = **8**.

- **작업은 사업장을 순회하되 한 트랜잭션이 여러 사업장을 가로질러 쓰지 않는다.** 사업장 하나의 실패가 전체 실행을 되돌리면 이미 성공한 사업장까지 다시 돌아야 한다.
- 실행 컨텍스트는 시스템 컨텍스트를 켠 상태이며 사용자 요청 경로에서는 절대 켜지 않는다(정본 [03_multitenancy_rls.md](./03_multitenancy_rls.md)).
- **rollupAttendanceDaily는 마감된 기간을 건너뛴다.** 마감 뒤 집계가 다시 바뀌면 확정 급여의 입력이 사후에 달라져 재현성이 깨진다(REQ-ATT-20).

## 분산락

| 항목 | 계약 |
|------|------|
| 수단 | **Redis 락**을 쓴다. 작업 이름별 키에 소유자 식별자와 만료를 함께 걸고, 획득한 인스턴스만 실행한다 |
| 획득 실패 | 실행하지 않고 조용히 종료한다. 실패가 아니라 정상 동작이다. **명시 재실행도 이 문은 지난다** — 동시 실행 방어는 우회할 축이 아니라서이며, 그 경로에서는 SKIPPED 1행이 남고 요청은 common.conflict/409 다 |
| 만료 | 작업 예상 소요의 여유 배수로 잡되 **작업 주기보다는 짧게** 잡고, 장기 작업은 실행 중 갱신한다. 만료 없이 잡지 않는다 — 프로세스가 죽으면 락이 영구히 남는다. 값은 아래 락 유지 시간 절이 정본이다 |
| 해제 | 소유자 확인 후 해제한다. 다른 인스턴스가 이미 잡은 락을 해제하지 않는다 |
| 인스턴스 1개에서도 생략하지 않는다 | 배포 중 구·신 컨테이너가 잠시 겹치고 수동 재실행도 있다. **락은 인스턴스 수가 아니라 실행 경로 수에 대한 방어**다 |
| 업무 경합과의 경계 | **업무 데이터 경합은 Redis 락으로 막지 않는다.** 급여 확정 중 근태 수정 · 초대 수락 시 인원 한도 재검증 · 연차 원장 동시 차감은 데이터베이스 트랜잭션 잠금으로 막는다. 락 서버가 잠깐 끊겼을 때 업무 불변식이 함께 무너지면 안 된다(ADR-13) |

### 락 유지 시간

| lockAtMostFor | 작업 | 주기 |
|------|------|------|
| **25분** | expireInvitations | 30분 |
| **12분** | retryPayslipAndPush | 15분 |
| **30분** | autoUnsuspendAccounts · checkSubscriptionExpiry · checkComplianceDeadlines | 매일 1회 |
| **60분** | rollupAttendanceDaily · accrueAndExpireLeave · recomputeEmployeeCountSnapshot | 매일 1회 |

검산: 30분 주기 1 + 15분 주기 1 + 일 1회 6 = **8**.

- **주기보다 짧게 잡는다.** 길게 잡으면 프로세스가 죽어 남은 락이 다음 주기까지 살아 있어 그 주기가 통째로 건너뛰어진다. 고빈도 작업 둘이 주기의 8할 남짓(30분 → 25분 · 15분 → 12분)인 이유가 이것이다.
- **일 1회 작업의 30분과 60분을 가르는 축은 순회 규모다.** 사업장·직원 전수를 도는 집계 산출 3건(rollupAttendanceDaily · accrueAndExpireLeave · recomputeEmployeeCountSnapshot)이 60분이고 나머지 3건이 30분이다.
- **lockAtLeastFor는 시각 트리거 축의 값이며 전건 30초**다. 작업이 즉시 끝나도 그만큼 락을 유지해, 인스턴스 간 시계 차이로 같은 주기가 두 번 실행되는 것을 막는다.
- **명시 재실행은 lockAtLeastFor가 0이다.** 위 방어가 겨냥하는 것은 **같은 발화 시각을 시계가 어긋난 두 인스턴스가 함께 집는 상황**인데, 재실행은 발화가 아니라 사람이 부른 요청이라 그 조건이 성립하지 않는다. 0으로 두지 않으면 **아무것도 돌고 있지 않은 30초 동안 락 미획득이 나고**, 그 응답이 말하는 「같은 작업이 이미 돌고 있다」가 사실이 아니게 된다(2026-09-10 실측 — 연속 재실행이 그 자리에서 막혔다). **실행 중 상호 배제는 lockAtMostFor가 그대로 지킨다** — 재실행이 우회하는 것은 완료 뒤의 유지이지 락 자체가 아니다.
- **부하 실측 후 조정 대상이다.** 재시도 상한·백오프와 마찬가지로 법정 기준이 아니라 운영 판단이라 기준값 테이블에 넣지 않고 애플리케이션 설정으로 관리한다.

## 멱등 계약

**정기작업의 정확성은 "한 번만 돈다"가 아니라 "여러 번 돌아도 같다"로 보장한다.** 시각 트리거는 실행 창 안에서 수행되고 배포·장애·수동 재실행이 겹치므로, 정확히 한 번을 전제한 설계는 반드시 깨진다.

| 유형 | 기법 |
|------|------|
| 상태 전이형(1 · 2 · 3) | 전이 조건을 만족하는 행만 대상으로 삼는다. 이미 전이된 행은 조건에서 빠지므로 반복 실행이 무해하다 |
| 집계 갱신형(4 · 6) | 키가 같으면 같은 값으로 수렴하는 갱신을 쓴다. 누적 가산을 쓰지 않는다 — 재실행이 값을 두 배로 만든다 |
| 원장 생성형(5) | (대상, 사유, 기준일) 부분 유일 제약을 최종 방어로 둔다. 애플리케이션 선검사만으로는 동시 실행을 막지 못한다 |
| 알림 발송형(7) | (사업장, 과제, 판정 기준일) 단위 멱등키로 중복 발송을 막는다. 같은 기한을 매일 다시 알리지 않는다 |
| 외부 부수효과형(8) | 명세서 생성·발송에 멱등키를 붙인다. 재시도가 두 번째 파일·두 번째 교부 기록을 만들지 않는다 |

- 멱등키 형식은 (사업장, 멱등키) 부분 유일이며 형식 정본은 [../09_glossary/04_id_conventions.md](../09_glossary/04_id_conventions.md)다.
- **멱등성은 경합을 막지 못한다.** 같은 요청의 중복만 흡수하며 서로 다른 요청의 경합은 트랜잭션 잠금이 담당한다(REQ-GLB-15).

## 실패 처리

```plain
작업 실행
├─ 락 획득 실패 → 종료(정상)
└─ 락 획득
   ├─ 대상 순회
   │  ├─ 항목 성공 → 다음 항목
   │  └─ 항목 실패 → 오류 기록 + 계속 진행(항목 단위 격리)
   ├─ 실패 항목 있음
   │  ├─ 회차 1~5 실패 → 백오프(1 · 2 · 4 · 8 · 16분) 후 다음 주기가 재시도한다
   │  └─ 회차 6 실패 → 실패 상태 유지 + dead_letter_at 기록 + 관측 채널 운영 경보
   └─ 실행 결과 기록(시작·종료 시각 · 대상 수 · 성공·실패 수 · 실패 사유)
```

| 항목 | 계약 |
|------|------|
| 항목 단위 격리 | 한 대상의 실패가 나머지 대상을 막지 않는다. 순회 전체를 되돌리지 않는다 |
| 재시도 상한 | **5회**다. 회차를 대상 행에 누적 기록해 다음 실행이 이어받는다 |
| 백오프 | 지수 백오프 **1분 → 2분 → 4분 → 8분 → 16분**이다. 다음 시도 예정 시각을 대상 행에 기록하고 그 시각 이전에는 재시도하지 않는다 |
| 회차 해석 | 회차는 **1이 최초 실행**이다. 회차 n이 실패하면 그 다음 실행이 재시도 n이므로 대기 시간은 백오프 n번째 값이고, 회차 1~5의 실패에 1 · 2 · 4 · 8 · 16분이 차례로 붙는다. **재시도 여지가 없는 것은 6회차 실패**이며 그 자리에서 dead letter로 넘어간다. 검산: 총 실행 6 = 최초 1 + 재시도 5 |
| 주기와의 관계 | 백오프 간격이 작업 주기보다 짧으면 **다음 주기가 곧 다음 시도**다. 같은 실행 안에서 즉시 반복하지 않는다 — 원인이 외부 장애면 즉시 반복이 부하만 키운다 |
| 상한 도달 | 재시도 5회를 다 쓰고 **6회차가 실패하면** **실패 상태를 유지**하고 대상 행에 **dead_letter_at을 기록**한 뒤 **시각 트리거의** 재시도 대상에서 제외한다. 재개는 담당자의 명시 재시도 조작으로만 하며 **그 조작의 표면은 [../06_api/14_system.md](../06_api/14_system.md) #34**다 — 기준일을 지정한 재실행이고 **이 열을 보지 않는다**(보면 재개 경로가 자기 자신에게 막힌다) |
| 상한 도달 경보 | dead letter 기록과 함께 **관측 채널로 운영 경보**를 보낸다(구조화 로그 오류 수준 + 에러 추적 — ADR-23). **인앱 알림 경로를 쓰지 않는다** — 인앱 알림 자체가 정기작업 실패의 영향을 받는 경로이고, 운영 경보는 사업장 사용자가 아니라 서비스 운영자가 받아야 한다 |
| 외부 API 타임아웃 | 연결 **3초** · 전체 **10초**다. **v1 적용 대상은 국세청 사업자 진위확인 API · SMTP 둘**이며 타임아웃 초과는 실패로 처리해 재시도 대상에 넣는다. 푸시 채널(FCM)은 **v1 외부 의존 2종에 포함되지 않으며 호출 지점도 없다**(알림 배달은 인앱 단일 채널 · NTF-02 이월) — 도입 시 외부 의존에 추가하고 같은 값을 적용한다. 타임아웃 없이 호출하면 한 대상의 응답 지연이 순회 전체를 멈춘다 |
| 조용한 성공 금지 | 실패를 성공으로 기록하거나 로그만 남기고 넘어가지 않는다. **명세서 생성 실패가 성공으로 기록되면 교부 의무 미이행이 드러나지 않는다** |
| 실행 이력 | 작업별 실행 결과를 기록해 마지막 성공 시각을 조회할 수 있게 한다. **작업이 아예 돌지 않은 것과 돌았지만 대상이 0건인 것을 구분**한다 |
| 원 이벤트 보호 | 알림 생성 실패가 원 이벤트를 롤백하지 않는다. 급여 확정이 알림 실패로 되돌아가서는 안 된다(REQ-NTF-02) |

**위 수치는 설계 재량값이며 기준값 테이블 대상이 아니다.** 재시도 상한 5회 · 백오프 1~16분 · 타임아웃 3초/10초는 법정 기준이 아니라 운영 판단으로 정한 값이라, 기준값 테이블(요율·세액표·한도 등 법정값 전용)에 넣지 않고 애플리케이션 설정으로 관리한다. 바꿀 때는 본 절을 고치고 [../03_requirements/15_nonfunctional.md](../03_requirements/15_nonfunctional.md)의 REQ-TEC-09 · REQ-NFR-07을 같은 변경 단위에서 함께 고친다.

**retryPayslipAndPush의 대상은 실패분만이 아니다.** 급여 확정이 만든 PENDING 명세서를 렌더해 GENERATED로 올리는 것이 이 작업의 첫 대상이며(정본 [../06_api/09_payslip.md](../06_api/09_payslip.md) #1 처리 · #18), **그 자리를 두지 않으면 확정 트리거가 만든 큐에 소비자가 없어 명세서가 PENDING에서 멈춘다**(2026-09-11 실측 — 259건 정체 · 이 작업의 target_count가 전건 0). 렌더를 확정 트랜잭션에 두지 않는 것이 그 분리의 이유다 — 브라우저 풀을 기다리는 동안 급여월 잠금을 쥐고 렌더 실패가 확정을 되돌린다. **교부(DELIVERED)까지 밀지는 않는다** — 그 전이의 주체는 관리자의 게시 행위 하나뿐이다.

**retryPayslipAndPush는 이 계약의 특례가 아니라 적용 사례다.** 15분 주기는 작업의 실행 간격이고 5회 상한·백오프는 개별 명세서의 재시도 축이라 축이 다르다 — 실패한 명세서 하나는 다음 시도 예정 시각을 지난 15분 주기 실행에서만 재시도되며, 5회를 넘기면 dead letter로 넘어가 15분마다 무한 재시도되지 않는다. 파이프라인 상세는 [10_realtime_files.md](./10_realtime_files.md)다.

## 실행 이력

실행 결과는 scheduled_job_runs(테이블 60)에 남는다. 컬럼·저장 계약의 정본은 [../02_features/15_scheduled_jobs.md](../02_features/15_scheduled_jobs.md) 공통 규약 표이며, 본 절은 **부분 유일 제약이 고빈도 작업에 만드는 결과**를 등재한다.

부분 유일 제약은 (작업명, 기준일)에 대해 상태가 RUNNING 또는 SUCCEEDED인 행을 1건으로 강제한다. 그런데 expireInvitations(30분)와 retryPayslipAndPush(15분)는 **같은 기준일로 하루 48회 · 96회 발화**하므로 두 번째 실행이 새 RUNNING 행을 넣으려 하면 제약 위반으로 막힌다. 그래서 실행을 여는 쪽이 새 행을 만드는 대신 **기존 행을 이번 실행으로 되돌린다** — 제약을 우회하지 않고 그 아래에서 동작한다.

**결과적으로 고빈도 작업 둘은 하루치 이력이 최신 1행으로 접힌다.**

| 관측 목적 | 접힌 뒤에도 성립하는가 |
|------|------|
| 그날 한 번도 돌지 않음 | 성립한다 — 그 기준일의 행이 없다 |
| 돌았으나 대상 0건 | 성립한다 — SUCCEEDED + target_count 0으로 남는다(REQ-NFR-16) |
| 마지막 성공 시각 | 성립한다 — 되돌린 행의 시작 시각이 최신 실행을 가리킨다 |
| **하루 안의 회차별 이력** | **성립하지 않는다** — 같은 기준일의 지난 실행이 덮인다 |

- **접히는 것은 성공 경로뿐이다.** 제약이 거는 상태는 RUNNING · SUCCEEDED 둘이므로 FAILED 행은 재시도 회차만큼, SKIPPED(락 미획득) 행은 발생한 만큼 그대로 쌓인다. 실패와 락 경합의 이력은 잃지 않는다.
- **한계를 감수하는 이유는 이 테이블의 목적이 멈춘 배치를 드러내는 것이기 때문이다.** 그 목적은 접힌 뒤에도 유지되고, 회차별 이력을 남기려면 성공 경로에 하루 48행 · 96행을 쌓아야 한다.
- 회차별 이력이 필요해지면 부분 유일 제약의 축을 바꾸는 스키마 변경이 선행한다. **애플리케이션이 제약을 피해 행을 늘리는 방식으로 바꾸지 않는다.**

## KST 경계

| 항목 | 계약 |
|------|------|
| 프로세스 시간대 | **Asia/Seoul 고정**이다. 컨테이너 환경변수와 애플리케이션 설정 양쪽에 명시한다 |
| 트리거 표현 | 시각 표현식은 KST 기준으로 읽는다. 프로세스 시간대가 다르면 전 작업이 통째로 밀린다 |
| 일 경계 판정 | 근무일·귀속월·기준일은 KST로 산출한다. 저장은 UTC지만 판정은 KST다(REQ-GLB-07) |
| 전일 대상 | 00시대 작업(2 · 3 · 4 · 5)의 대상 일자는 **KST 기준 전일**이다. 실행 시각에서 역산하지 않고 기준일을 인자로 계산해 재실행이 같은 대상을 잡게 한다 |
| 실행 창 | 지정 시각 정각이 아니라 실행 창 안에서 수행된다. **분 단위 정확도를 전제한 판정을 두지 않는다** |
| 순서 의존 | 00:20 근태 롤업이 00:40 연차 적립보다 앞서 도는 순서에 의존하지 않는다. 각 작업이 자기 입력의 준비 여부를 스스로 확인하고, 준비되지 않았으면 다음 주기로 미룬다 |

### 작업별 기준일

**작업은 실행 시각이 아니라 기준일로 동작하므로 기준일이 곧 대상 집합이다.** 위 전일 대상 행이 열거하는 00시대 작업 넷 밖은 전부 당일이며, 열거 밖이라는 사실만으로 판정하기에는 헷갈리는 자리가 있어 8건을 전수로 적는다.

| 기준일 | 작업 | 근거 |
|------|------|------|
| **전일** | autoUnsuspendAccounts · checkSubscriptionExpiry · rollupAttendanceDaily · accrueAndExpireLeave | 00시대 작업 넷(2 · 3 · 4 · 5)이며 위 전일 대상 행이 열거한다 |
| **당일** | expireInvitations · recomputeEmployeeCountSnapshot · checkComplianceDeadlines · retryPayslipAndPush | 그 열거 밖이다 |

검산: 전일 4 + 당일 4 = **8**.

**recomputeEmployeeCountSnapshot(02:20)이 이 표에서 가장 틀리기 쉬운 자리다.** 00시대가 아닌 새벽 작업이라 시각만 보면 전일처럼 읽히지만 기준일은 **당일**이다.

당일이어야 하는 근거는 연차 적립이 **전일 기준 스냅샷**으로 판정한다는 계약이다([../02_features/15_scheduled_jobs.md](../02_features/15_scheduled_jobs.md) accrueAndExpireLeave 절). D일 02:20이 D일 스냅샷을 만들어야 다음 날 00:40의 연차 적립이 요구하는 전일 스냅샷이 실제로 존재한다. 전일로 두면 D일 02:20이 D-1 스냅샷을 만들어 다음 날이 요구하는 D일 스냅샷이 영영 생기지 않고, 최신 스냅샷이 늘 하루 뒤처진다.

**이것이 실행 순서 의존을 만들지는 않는다.** 두 작업은 서로의 완료를 기다리지 않으며, 각자 자기 입력의 준비 여부를 확인하고 준비되지 않았으면 다음 주기로 미룬다(위 순서 의존 행). 스냅샷이 없으면 연차 발생이 차단되는 것이 정상 동작이다.

## v1에 두지 않는 정기작업

원천이 정의한 정기작업 13건 중 **5건을 v1.1로 미룬다** — 급여 월별 통계 재계산 · 기준값 누락 점검 · 미마감 귀속월 안내 · 보존만료 데이터 파기 · 연차 사용촉진 판정이다. 검산: v1 8 + 이월 5 = **13**.

- **기준값 누락 점검의 공백은 수동 절차로 대체한다.** 요율·세액표가 비어 있으면 급여가 통째로 틀리므로, 귀속월 계산 착수 전에 담당자가 기준값 커버리지를 확인하는 운영 절차를 둔다. 계산 시점의 차단(REQ-GLB-09)은 그대로 작동하므로 누락이 조용히 통과하지는 않는다.
- **보존만료 파기가 자동으로 돌지 않는다.** 보존 기한 필드는 확정 시점에 채워 두고, 파기는 v1.1에서 배치로 수행한다. 기한이 지났다고 v1이 임의로 지우지 않는다.
- 이월 항목의 재등재 시점 정본은 [../01_overview/05_priorities_roadmap.md](../01_overview/05_priorities_roadmap.md)다.
