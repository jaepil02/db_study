인증 축은 표면에 따라 둘이다 — **웹(관리자 웹 · 시스템 웹)은 서버 세션 쿠키**, **직원 앱은 JWT**다. 두 축은 자격 증명 전달 방식만 다르고 그 뒤의 인가·격리 경로는 완전히 같다. 어느 축으로 들어오든 요청은 같은 가드를 지나고 같은 RLS 컨텍스트를 주입받는다.

**요청을 가로채 판정하는 서버 계층이 웹에 없다**(D-20). 웹 산출물은 정적 HTML과 SPA 번들뿐이라 진입 분기는 **클라이언트 라우트 가드**가 수행하며, 그것은 신뢰 계층이 아니라 UX 보조다. 최종 판단은 항상 API 서버가 내린다(REQ-AUT-12). 세션이 만료됐거나 계정이 정지된 경우 화면은 열리고 첫 API 호출이 거부되어 로그인으로 되돌아간다 — 이 동작이 정상이다.

토큰·세션의 물리 저장 위치는 전부 Redis이며 업무 데이터베이스에 두지 않는다. 근거는 [09_decision_records.md](./09_decision_records.md) ADR-05 · ADR-11이다.

## 인증 축 대조

| 항목 | 웹(관리자 웹 · 시스템 웹) | 직원 앱 |
|------|--------------------------|---------|
| 자격 증명 전달 | 세션 쿠키 자동 전송 | Authorization 헤더 Bearer |
| 저장 위치 | 서버 Redis 세션 스토어. 브라우저에는 세션 식별자만 | 기기 보안 저장소(Keychain · Keystore) |
| 쿠키 속성 | HttpOnly · Secure · SameSite=Lax · Domain=.{domain} · Path=/ | 해당 없음 |
| 스크립트 접근 | 불가(HttpOnly) — access token을 자바스크립트에 노출하지 않는다 | 앱 코드만 접근. 평문 저장소(AsyncStorage 계열)를 쓰지 않는다 |
| 상태 변경 요청 보호 | **CSRF 토큰 필수**. 부재·불일치는 auth.csrf_token_invalid/403 | CSRF 토큰 불요 — 헤더 인증은 브라우저가 자동 전송하지 않는다 |
| 만료 처리 | 유휴 만료 · 활동 시 연장 · **절대 상한 별도**(컨텍스트 수명 절) | access 만료 임박 시 refresh로 회전 재발급 |
| 폐기 수단 | 세션 키 삭제(즉시 반영) | Redis 블랙리스트 등재(잔여 수명만큼 TTL) |
| 자동 로그인 | 세션 유효 기간 내 재방문 시 유지 | 앱 재실행 시 refresh 회전으로 복구 |
| 실시간 수신 인증 | Domain=.{domain} 쿠키가 SSE 연결에 자동 실린다 | Authorization 헤더 |

- **쿠키 도메인을 상위로 올리는 것은 D-03의 실무적 귀결이다.** 웹은 app 서브도메인, API는 api 서브도메인이라 도메인을 좁히면 API 요청에 세션이 실리지 않는다. SameSite를 None까지 풀지 않는 이유는 서드파티 컨텍스트 전송을 열면 CSRF 표면이 넓어지기 때문이다.
- **웹에 JWT를 쓰지 않고 앱에 세션 쿠키를 쓰지 않는다.** 각 표면이 자기 플랫폼의 기본 수단을 쓴다 — 웹의 토큰은 어느 저장소를 골라도 스크립트 접근 위험이 남고, 앱의 쿠키는 저장소·CSRF·도메인 규약을 네이티브에서 재현하게 만든다.

## 컨텍스트 수명

수명 4종의 값은 본 절이 정본이다. **다른 문서에서 다시 정하지 않고 인용한다.**

| 항목 | 값 | 근거 |
|------|:--:|------|
| 웹 세션 유휴 | **2시간** | 민감 작업은 재인증(5분 · 1회 소비)이 따로 막으므로 세션 자체를 극단적으로 짧게 할 이유가 없다. 근태 마감·급여 확정은 한 번에 끝나지 않는 작업이라 30분 유휴는 실무에서 끊긴다. 활동 시 연장이라 작업 중에는 끊기지 않는다 |
| 웹 세션 절대 상한 | **12시간** | **신설 계약이다.** 활동 시 연장만 두면 탭을 열어 둔 브라우저의 주기적 요청이 세션을 무기한 연장한다. 하루를 넘기지 않게 한다 |
| 앱 access | **15분** | 짧아 탈취 창이 좁다. refresh 회전이 있어 사용자에게 재로그인이 보이지 않는다. app_front가 이미 이 값으로 구현돼 있어 계약 드리프트를 만들지 않는다 |
| 앱 refresh | **14일** | 모바일 재로그인은 입력이 번거롭다. 회전하므로 탈취분은 다음 정상 회전에서 재사용 시도로 드러난다 |

- **유휴 만료와 절대 상한은 대체재가 아니다.** 유휴는 자리를 비운 사용자를 끊고, 절대 상한은 계속 쓰는 사용자도 하루 안에 다시 인증하게 한다. 하나만 두면 각각 반대쪽 경로가 열린다.
- **절대 상한의 기산점은 인증 시각이다** — 세션 생성 시각이 아니다. CSRF 토큰 발급이 로그인보다 앞서 세션을 만들므로 두 시각이 갈린다.
- **앱 access가 refresh보다 짧은 것이 회전의 전제다.** 두 값이 같으면 회전할 시점이 없다.
- 수명이 다해 거부되는 응답은 웹·앱 모두 auth.token_invalid/401이다. 앱은 이 코드에서만 회전을 시도하므로 다른 코드를 내면 회전이 돌지 않는다.

## 로그인 판정 순서

자격 증명 검증을 통과했다고 인증이 성립하지 않는다. **계정 상태 선검증이 컨텍스트 발급보다 앞선다**(REQ-AUT-09) — 정지·탈퇴 계정에 세션을 먼저 발급하면 그 세션이 살아 있는 동안 접근이 열린다.

```plain
로그인 요청 (username · password)
├─ rate limit 초과? ──── 예 → common.rate_limited/429 (+ 재시도 가능 시각)
│                              (IP, username) 조합 실패 누적으로 판정
└─ 아니오
   ├─ 자격 증명 불일치? ── 예 → auth.invalid_credentials/401
   │                            아이디 미존재와 비밀번호 불일치를 한 코드로 통일한다(열거 방지)
   └─ 일치
      ├─ users.status = DELETED? ── 예 → auth.account_deleted/403 · 컨텍스트 즉시 폐기
      ├─ users.status = SUSPENDED? ─ 예 → auth.account_suspended/403 (+ 사유 · 해제 예정일)
      │                                    suspended_until < 현재 시각이면 ACTIVE로 복귀시킨 뒤 통과
      └─ ACTIVE
         ├─ 필수 2종(약관·개인정보) 문서 재동의 필요? ── 예 → auth.consent_required/422
         │  (위치정보 개정은 진입을 막지 않는다 — GPS 체크인만 다시 잠긴다 · D-19)
         └─ 아니오 → 인증 컨텍스트 발급 (웹 = 세션 + CSRF 토큰 · 앱 = access + refresh)
                     → profiles.last_login_at 갱신 → 진입 판정으로 이어진다
```

- 응답 지연이 계정 존재 여부를 흘리지 않도록 자격 증명 검증 경로의 비용을 실패·성공에서 같게 유지한다.
- 로그인 성공·실패, 비밀번호 변경, 재설정 시도는 security_events에 시각·IP·user agent를 기록하되 **비밀번호 원문·해시를 남기지 않는다**(REQ-AUT-14).

## 진입 판정

인증 컨텍스트가 생긴 뒤 **어느 표면에 들어갈 수 있는가**와 **어느 사업장으로 들어가는가**를 순서대로 판정한다. 앞은 표면 판정(REQ-AUT-23), 뒤는 멤버십 라우팅(REQ-AUT-24)이다.

```plain
표면 판정
├─ 직원 앱      → STAFF 이상 ACTIVE 멤버십 보유 여부
├─ 관리자 웹    → OWNER 또는 MANAGER ACTIVE 멤버십 보유 여부
└─ 시스템 웹    → 플랫폼 RBAC 보유 여부
                  없으면 auth.platform_forbidden/403
                  사업장 OWNER라도 플랫폼 권한은 별개다

멤버십 라우팅 (ACTIVE 멤버십 수 기준)
├─ 0개
│  ├─ PENDING 초대 있음 → 초대 수락 화면
│  └─ 없음              → 온보딩(사업장 등록 또는 초대 대기)
├─ 1개                  → 자동 선택
└─ 2개 이상             → 사업장 선택 화면
                          동일 사용자가 사업장별로 다른 역할을 가질 수 있다
```

- 선택된 사업장은 클라이언트가 활성 사업장으로 보관하고 **이후 모든 업무 요청에 포함**하지만, 서버는 매 요청 멤버십·역할을 재검증한다(REQ-WRK-20). 클라이언트가 보낸 사업장 식별자를 신뢰해 스코프를 정하지 않는다.
- 전환 차단 대상은 SUSPENDED·CLOSED 사업장(workplace.unavailable/409) · LEFT·REMOVED 멤버십 · STAFF의 관리자 웹 접근이다. 마지막 활성 사업장이 무효가 되면 선택 화면으로 되돌린다.
- 사업장 전환 시 **클라이언트 캐시를 사업장·역할 단위로 격리**해 이전 사업장 데이터가 화면에 잔존하지 않게 한다. 캐시 규약의 정본은 [04_request_data_flow.md](./04_request_data_flow.md)다.

## 라우트 보호

클라이언트 라우트 가드는 web_front의 관리자 웹 · 시스템 웹 경로 진입에만 관여한다. 공개 경로 목록과 성격의 정본은 [05_rendering_seo.md](./05_rendering_seo.md)이며 본 절은 판정 규칙만 담는다.

**가드는 세션 쿠키를 읽지 않는다.** 웹 세션 쿠키는 HttpOnly라 스크립트가 볼 수 없고, 판정 편의를 위해 그 속성을 풀거나 세션 상태를 로컬 저장소·비HttpOnly 쿠키로 복제하지 않는다. 판정 근거는 **부팅 시 1회 수행하는 진입 컨텍스트 조회의 성패**뿐이다([../06_api/03_auth.md](../06_api/03_auth.md)).

| 판정 | 동작 |
|------|------|
| 공개 경로 요청 | 통과. 인증 상태를 확인하지 않는다 |
| 보호 경로 + 진입 컨텍스트 없음(401) | 로그인으로 이동시키고 원래 경로를 복귀 대상으로 전달한다. 복귀 대상은 **내부 경로만 허용**해 오픈 리다이렉트를 차단한다 |
| 보호 경로 + 진입 컨텍스트 있음 | 통과. 역할·사업장 자격은 판정하지 않으며 화면이 여는 것은 골격뿐이다 |
| 조회 실패(네트워크 오류 등) | 통과시키지 않고 로그인으로 보낸다 — 조회 실패가 곧 권한 부여가 되지 않게 한다 |

**가드를 우회해 보호 경로 번들을 직접 로드해도 얻는 것이 없다.** 업무 데이터는 전부 API 응답이고 API는 세션·역할·사업장을 매 요청 재검증한다. 그래서 신뢰 가드는 **3계층 — 서비스 검증 → RLS → 제약·트리거**이며 클라이언트 라우트 가드는 그 앞의 **보조 장치로 계층 수에 포함하지 않는다**(정본 [../10_security/01_authn_authz.md](../10_security/01_authn_authz.md)). 이 규정을 웹 소스 주석과 본 문서에 함께 명문화한다.

## 재인증

민감 작업은 **비밀번호 재인증을 선행**한다(REQ-AUT-25). 재인증 결과는 단기 유효 토큰으로 발급하고 Redis에 둔다.

| 항목 | 계약 |
|------|------|
| 대상 작업 | 민감정보 원문 복호화(REQ-HRM-04) · 사업장 폐쇄(REQ-WRK-36) · 계정 탈퇴(REQ-AUT-20) · 민감 문서 다운로드(REQ-HRM-24) · 프로필 연락처·복구 이메일 변경(REQ-AUT-26 — 이름만 바꾸면 요구하지 않는다) |
| 유효 시간 | **5분** |
| 소비 단위 | **작업 단위 1회 소비**다. 5분 안이라도 한 번 쓴 토큰으로 다른 작업을 수행할 수 없다 |
| 저장 위치 | Redis. 회전이 잦고 법정 보존 대상이 아니라 데이터베이스에 쓰지 않는다 |
| 미충족 응답 | auth.reauth_required/401 |
| 대체 수단 | **생체 인증을 재인증 수단으로 인정하지 않는다** — 생체 등록은 기기 소유자 단위라 계정 소유자와 일치한다는 보장이 없다 |
| 동반 요구 | 복호화·민감 문서 다운로드는 재인증 외에 **사유 입력 · 감사 로그 기록 · 서버 1회성 응답**을 함께 충족해야 한다 |

- **비밀번호 변경의 현재 비밀번호 확인은 재인증 토큰을 발급·소비하지 않으므로 재인증 대상 작업 · 5회/5분 한도 축에 들어가지 않는다**(정본 [../10_security/01_authn_authz.md](../10_security/01_authn_authz.md)).

## 세션 폐기

| 트리거 | 웹 | 앱 |
|--------|-----|-----|
| 로그아웃 | 세션 키 삭제 · CSRF 토큰 폐기 | refresh 토큰 revoke · access 토큰 블랙리스트 등재 · 기기 푸시 토큰 정리 |
| 계정 정지(SUSPENDED) | 해당 사용자의 전 세션 즉시 삭제 | 전 refresh revoke + 유효 access 블랙리스트 등재 |
| 비밀번호 변경 | 사용자가 "현재 세션 유지 / 모든 기기 로그아웃"을 선택한다 | 같은 선택을 따른다 |
| 비밀번호 재설정 완료 | **전 세션 강제 폐기**(선택 없음) | **전 refresh 강제 revoke** |
| 계정 탈퇴(DELETED) | 전 세션 삭제 | 전 토큰 revoke |
| 사업장 멤버십 상실 | 세션은 유지하되 해당 사업장 스코프 요청이 거부된다 | 동일 |

- **인증이 유효한 중에 계정 상태가 바뀌면 다음 요청에서 차단된다.** 서버 가드가 계정 상태를 재조회하고 RLS 헬퍼도 프로필 상태가 ACTIVE가 아니면 거짓을 반환하므로, 정지·탈퇴가 2단 방어 양쪽에 즉시 반영된다.
- 앱 블랙리스트 항목의 TTL은 **토큰 잔여 수명**으로 맞춘다. 영구 보관하면 항목이 무한 증식한다.
- 세션·블랙리스트가 유실되면 전원 재로그인이 필요하지만 **업무 데이터는 잃지 않는다**. 이 성격이 Redis를 업무 데이터 정본으로 쓰지 않는 근거다.

## 비밀번호 재설정

| 단계 | 계약 |
|------|------|
| 요청 | recovery_email 등록 계정은 메일로 재설정 링크를 받는다. 미등록 계정은 플랫폼 지원 담당(SUPPORT 이상) 보조 재설정을 안내하며 **토큰을 발급하지 않는다** |
| 응답 통일 | **계정 존재 여부와 무관하게 같은 응답**을 반환한다. 메일 발송 실패도 사용자 응답은 성공과 동일하게 유지하고 실패 로그만 남긴다(열거 방지) |
| **은닉 위치** | **함수가 아니라 응답이 담당한다** — 발급 함수는 미존재·DELETED·복구 이메일 미등록에 **0행**을 돌려주지만 그것을 받는 것은 서버이고 사용자 응답은 어느 경우에도 202다. 수신 주소가 반환에 실려도 미인증 클라이언트는 그 값을 볼 수 없다 |
| 토큰 저장 | **해시 저장**한다. 원문 토큰을 데이터베이스에 두지 않는다 |
| 유효 시간 | 1시간. 사용 여부를 함께 검증한다 |
| 실패 응답 | 만료·사용완료·불일치는 auth.reset_token_invalid/400 |
| 성공 처리 | 새 비밀번호를 가입과 동일 정책으로 검증해 적용하고 **기존 세션·refresh 토큰을 전체 폐기**한다 |
| 반복 실패 | rate limit + 보안 이벤트 기록 |
| **발급 자리** | 서버 함수 **issue_password_reset**이 토큰과 **수신 주소를 함께** 돌려준다(정본 [../05_database/08_rls_policies.md](../05_database/08_rls_policies.md) 헬퍼 #36). 아이디로 요청해도 그 계정의 복구 이메일이 반환에 실린다 |
| **보조 재설정의 발급 자리** | 복구 이메일이 없는 계정은 위 함수가 0행으로 배제하므로 **다른 함수가 담는다** — **issue_assisted_password_reset**이 지원 담당의 대리 등록과 토큰 발급을 한 트랜잭션에 묶는다(정본 같은 문서 헬퍼 **#44** · 표면 [../06_api/14_system.md](../06_api/14_system.md) #10). **두 함수의 대상 집합은 겹치지 않는다** |

## rate limit

인증 경로는 자동화 시도의 첫 표적이다. 제한 기준을 고정하고 초과 시 common.rate_limited/429와 재시도 가능 시각을 함께 반환한다.

| 대상 | 기준 키 | 한도 |
|------|--------|------|
| 로그인 실패 | (IP, username) 조합 | **10회 / 10분**. 초과 시 해당 조합을 잠금 창 동안 차단한다 |
| 비밀번호 재설정 요청 | username 또는 recovery_email | **5회 / 1시간** |
| 아이디 중복 확인 | IP | **30회 / 1분**. 형식 검증을 통과한 요청만 조회하고 가용 여부 불리언만 반환한다 |
| 재인증 시도 | 사용자 | **5회 / 5분**. 초과 시 재인증 창을 닫고 재로그인을 요구한다 |
| 사업자 진위확인 | (사업장, 일) | **20회 / 1일**. 외부 국세청 API 호출을 동반하므로 사업장 단위로 일 한도를 건다 |
| 다운로드 토큰 발급 | (사용자, 시간) | **60회 / 1시간**. 명세서 열람·민감 문서·아바타가 같은 경로를 쓰므로 정상 사용 상한을 웃도는 값으로 잡는다(정본 [10_realtime_files.md](./10_realtime_files.md) 다운로드 절) |
| 인증 후 일반 API | 사용자 | **300회 / 1분**. 정상 사용 상한을 크게 웃도는 값이며 자동화 오남용 차단이 목적이다 |

검산: 로그인 실패 1 + 비밀번호 재설정 1 + 아이디 중복 확인 1 + 재인증 1 + 사업자 진위확인 1 + 다운로드 토큰 발급 1 + 인증 후 일반 API 1 = **7축**.

- 카운터는 Redis에 두고 창 만료를 TTL로 처리한다. 별도 정리 작업을 두지 않는다.
- **429는 인증 실패와 구분되는 상태다.** 잠금 중 올바른 비밀번호를 넣어도 401이 아니라 429가 나가야 잠금 상태가 사용자에게 드러난다.
- 수치가 바뀌면 [../03_requirements/15_nonfunctional.md](../03_requirements/15_nonfunctional.md)의 REQ-NFR 보안 비기능 항목을 같은 변경 단위에서 함께 고친다.
