insadesk의 격리는 **사업장(workplace) 단위**다. 전 업무 테이블이 workplace_id 스코프를 갖고, 같은 사용자가 사업장마다 다른 역할을 가질 수 있으며, 한 요청은 언제나 하나의 활성 사업장 안에서만 유효하다.

격리를 지키는 방법은 하나가 아니라 **둘을 겹쳐 두는 것**이다. 서비스 레이어가 멤버십·역할·사업장 스코프를 1차로 검증하고, PostgreSQL RLS가 행 단위로 2차 강제한다. 어느 한쪽만 두면 결과가 나쁘다 — 애플리케이션 검증만 두면 새 엔드포인트 하나가 스코프 검사를 빠뜨렸을 때 타 사업장 데이터가 그대로 나가고, RLS만 두면 "권한 없음"과 "데이터 없음"이 구분되지 않아 사용자에게 잘못된 안내가 나간다.

정책 본문·헬퍼 함수 시그니처의 명세 정본은 [../05_database/08_rls_policies.md](../05_database/08_rls_policies.md)와 [../05_database/09_functions_triggers.md](../05_database/09_functions_triggers.md)다. 본 문서는 **애플리케이션이 그 정책과 맺는 계약**을 고정한다.

## 3층 권한 모델

권한은 서로 다른 세 축이며 상위 축이 하위 축을 대체하지 않는다.

| 층 | 축 | 판정 대상 | 성격 |
|----|-----|----------|------|
| 1층 | 인증 경계 | 인증 여부 · 계정 상태(ACTIVE · SUSPENDED · DELETED) | 통과하지 못하면 어떤 자원에도 접근하지 못한다. 정지·탈퇴는 RLS 헬퍼가 프로필 상태를 보므로 **2단 방어 양쪽에 즉시 반영**된다 |
| 2층 | 사업장 RBAC | OWNER ⊃ MANAGER ⊃ STAFF **누적** | 사업장 안에서의 업무 권한이다. 같은 사용자가 사업장 A에서 OWNER, 사업장 B에서 STAFF일 수 있다. **사업장당 OWNER는 항상 1명**이다(D-13). ADVISOR는 v1에 두지 않는다 |
| 3층 | 플랫폼 RBAC | VIEWER(1) · SUPPORT(2) · ADMIN(3) · SUPER_ADMIN(4) **화이트리스트** | 플랫폼 운영 권한이며 사업장 RBAC와 **완전 별개**다. 사업장 OWNER라도 플랫폼 권한은 없다(REQ-AUT-23). 권한 키는 역할별 명시 화이트리스트로 평가하고 와일드카드를 두지 않는다 — 미정의 키는 기본 거부다 |

- 2층은 누적이고 3층은 화이트리스트다. 이 차이가 중요하다 — 사업장 권한은 상위 역할이 하위 권한을 포함하지만, 플랫폼 권한은 등급이 높다고 모든 키를 갖지 않는다.
- 플랫폼 역할 보유자가 사업장 데이터에 접근하는 경로는 **명시 권한 키를 통과한 조회만**이며 급여 확정·명세서 발행 같은 사업장 업무 행위를 대행하지 않는다. 상세 정본은 [../10_security/07_platform_rbac.md](../10_security/07_platform_rbac.md)다.

## 2단 방어

| 단계 | 위치 | 검증 내용 | 실패 응답 |
|------|------|----------|----------|
| 1차 | Spring Security 필터 체인·서비스 계층 | 인증 컨텍스트 존재 · 요청 사업장에 대한 ACTIVE 멤버십 · 요구 역할 충족 · 사업장 상태가 쓰기 가능 · 요청 자원이 그 사업장 소속인지 | auth.workplace_forbidden/403 · workplace.unavailable/409 등 **구분 가능한 도메인 코드** |
| 2차 | PostgreSQL RLS | 행 단위 가시성·변경 가능성. 전 업무 테이블 ENABLE + FORCE ROW LEVEL SECURITY · 기본 거부 · 명시 정책만 허용 | 행이 보이지 않거나 변경이 0행으로 끝난다. 애플리케이션은 이를 **부재가 아니라 결함 신호**로 다룬다 |

- **FORCE를 빼지 않는다.** FORCE가 없으면 테이블 소유자로 접속한 세션이 정책을 통째로 건너뛴다.
- **접속 롤을 분리한다.** 마이그레이션 소유자와 애플리케이션 롤이 다르고, 애플리케이션 롤 insadesk_app은 **테이블 소유자가 아니며 NOSUPERUSER · NOBYPASSRLS**다. 롤에는 필요한 SELECT · INSERT · UPDATE만 명시 부여하고 DELETE·DDL·소유 권한을 주지 않는다.
- **서버 전용 테이블은 롤에 직접 부여하지 않는다.** users · password_reset_tokens처럼 클라이언트가 닿을 이유가 없는 테이블은 애플리케이션 롤에 권한을 주지 않고 SECURITY DEFINER 함수로만 접근한다.
- **변경 결과 행 수를 확인한다.** RLS가 막은 UPDATE는 오류가 아니라 0행 갱신으로 끝난다. 영향 행 수를 검사하지 않으면 인가 실패가 성공으로 보인다.
- RLS 헬퍼는 전부 SECURITY DEFINER · STABLE · 검색 경로 고정으로 정의하고, 정책 안에서는 스칼라 서브쿼리로 감싸 행마다 재평가되지 않게 한다.
- **정의자 지정만으로는 정책 재귀가 끊기지 않는다.** FORCE는 테이블 소유자에게도 정책을 적용하므로, 정책이 헬퍼를 호출하고 헬퍼가 그 테이블을 읽는 구조는 강제 옵션 아래에서 무한 재귀가 된다 — 멤버십 정책 ↔ 멤버십 헬퍼가 정확히 그 구조다.
- **그래서 헬퍼 소유자를 세 번째 롤로 분리한다.** 그 롤만 정책 평가를 우회하고 **접속 경로를 갖지 않으므로**(로그인 불가) 우회 권한이 함수 본문 밖으로 나가지 않는다. 애플리케이션 롤은 함수를 실행할 뿐이고, 노출 범위는 함수의 반환 타입만큼이다. 롤 속성·소유 함수 목록의 정본은 [../05_database/08_rls_policies.md](../05_database/08_rls_policies.md)다.
- **정기작업의 읽기 경로도 이 계약의 일부다.** 서버 전용 쓰기 축만 열고 읽기 축을 닫으면 배치가 계산 입력을 얻지 못한다 — 어떤 테이블의 조회를 서버 컨텍스트로 여는지는 열거로 고정하며, 필요할 때 켜는 방식은 그 플래그가 사용자 요청 경로로 번지는 원인이 된다.

## 세션 컨텍스트 주입 계약

RLS 정책은 "지금 이 연결이 누구인가"를 알아야 평가된다. 그 값을 주입하는 방식이 격리의 성립 조건이다.

| 항목 | 계약 |
|------|------|
| 주입 지점 | **DataSource 프록시**(D-21 · ADR-28)가 **트랜잭션에 커넥션이 바인딩되는 순간 app.current_user_id를 설정**한다. 값은 바인드 파라미터로 넘기며 호출부가 주입을 책임지지 않는다. **프록시가 켜는 것은 이 하나뿐이다** |
| 나머지 4종의 자리 | 시스템 컨텍스트는 **서버 전용 진입점**이, 트랜잭션 컨텍스트 3종은 **보안 정의자 서버 함수 내부**가 각자 자기 트랜잭션 안에서 켠다 — **프록시가 대신 켜지 않는다.** 이 구분을 흐리지 않는다: "프록시가 다 켜 준다"로 읽히는 순간 **시스템 컨텍스트가 사용자 요청 경로에서 켜지는 것을 막는 근거가 사라진다**(그 플래그 하나가 users · password_reset_tokens의 정책을 통과시킨다) |
| 트랜잭션 전제 | **모든 업무 쿼리는 트랜잭션 안에서만 실행한다.** 영속성 컨텍스트를 요청 범위로 여는 설정을 끄고 서비스 계층 진입에 트랜잭션 경계를 요구한다 — 트랜잭션 밖 쿼리는 주입 지점을 지나지 않으므로 **읽기 전용 조회에도 트랜잭션 경계가 필요**하며, 대신 읽기 전용 표시를 붙인다 |
| 설정 방식 | 트랜잭션 지역 설정을 쓴다. 커넥션 풀 환경에서 연결 지속 설정을 쓰면 **다음 요청이 이전 요청의 컨텍스트를 물려받는다** |
| 우회 금지 | **프록시 밖에서 연결 · 영속성 컨텍스트 · SQL 세션을 직접 얻지 않는다.** 트랜잭션 밖 쿼리와 함께 **ArchUnit 아키텍처 테스트**가 차단한다. 두 데이터 접근 축이 같은 데이터소스를 공유하므로 주입은 한 자리에서 걸린다 |
| 미주입 동작 | 세션 변수가 비어 있으면 사용자 식별자가 NULL이 되어 **기본 거부**로 떨어진다. 주입 누락이 데이터 유출이 아니라 조회 실패로 나타난다 |

세션 변수는 **5종**이다. 검산: 사용자 1 + 시스템 컨텍스트 1 + 트랜잭션 컨텍스트 3(초대 수락 · 사업장 폐쇄 · 사업자 재검증) = **5**. **이것은 GUC 종수의 검산이지 프록시가 주입하는 개수의 검산이 아니다** — 켜는 자리로 세면 프록시 1 + 서버 전용 진입점 1 + 서버 함수 3 = **5**로 같은 수에 이른다(ADR-28).

| 세션 변수 | 값 | 용도 |
|-----------|-----|------|
| app.current_user_id | 인증된 사용자 식별자 | **DataSource 프록시가 켠다.** 전 정책의 주체 판정이며 값의 출처는 인증 컨텍스트다. 미주입 시 NULL → 기본 거부 |
| app.system_context | 켜짐 표시 | **서버 전용 진입점이 켠다.** 서버 전용 테이블·정기작업 경로이며 **사용자 요청 경로에서는 절대 켜지 않는다** |
| app.invitation_accept_context | 켜짐 표시 | 초대 수락 원자 함수 내부에서만 켠다. 클라이언트의 직접 수락 우회와 구분하는 축이다 |
| app.workplace_close_context | 켜짐 표시 | 사업장 폐쇄 함수 내부에서만 켠다. 읽기 전용 전환과 같은 트랜잭션의 멤버십 종료를 구분하는 축이다 |
| app.workplace_reverify_context | 켜짐 표시 | 사업자 재검증 정정 함수 내부에서만 켠다. **같은 트랜잭션의 진위확인 성공 기록과 함께** 요구되므로 플래그 단독으로는 아무것도 열지 않는다 |

- **뒤 셋은 같은 형태의 트랜잭션 컨텍스트다** — 서버 함수 한 곳에서만 켜고, 트랜잭션이 끝나면 사라지며, 전용 헬퍼가 읽는다. "지금이 그 트랜잭션 안인가"는 행 값으로 판정할 수 없으므로 좁은 예외를 여는 자리에는 이 축이 필요하다.
- **컨텍스트가 여는 것은 경로이지 검증 면제가 아니다.** 수락은 사업장 쓰기 가능 판정을, 재검증 정정은 같은 트랜잭션의 검증 기록을 각각 함께 요구한다.

- **활성 사업장과 역할은 세션 변수로 두지 않는다.** 정책은 행의 workplace_id 열과 멤버십 헬퍼로 평가하고, 서비스 레이어는 1차 검증에서 확정한 사업장을 쿼리 술어로 내린다. 세션 변수를 늘리면 주입 지점마다 누락 위험이 늘고, 무엇보다 **클라이언트가 보낸 사업장 식별자가 그대로 세션에 실리는 경로**가 생긴다 — 그 순간 격리의 근거가 서버 판정에서 요청 파라미터로 내려앉는다. 다른 문서가 세션 컨텍스트를 "사용자·활성 사업장·역할"로 요약해 부르더라도 **물리적으로 주입되는 변수는 위 5종이며 본 문서가 주입 계약의 정본**이다.
- 정기작업은 시스템 컨텍스트를 켜고 실행하되 **작업 단위로 사업장을 순회**하며, 한 트랜잭션이 여러 사업장을 가로질러 쓰지 않는다. **그 플래그를 서버 전용 진입점만 켤 수 있다는 것이 주입 자리를 나눠 둔 이유**다 — 프록시가 켜는 축에 섞이면 사용자 요청 경로로 번진다.

## 격리 판정 경로

```plain
요청 도착
  → 인증 컨텍스트 수립 (세션 쿠키 또는 JWT)
  → 계정 상태 확인 (ACTIVE 아니면 차단)
  → 요청 사업장에 대한 ACTIVE 멤버십·역할 조회        ← 1차 검증
  → 요구 역할 충족 여부 판정 (OWNER · MANAGER · STAFF)
  → 사업장 상태 확인 (CLOSED · SUSPENDED면 쓰기 차단)
  → 서비스 계층이 트랜잭션 개시 → DataSource 프록시가 커넥션 바인딩 시점에 app.current_user_id 주입
  → 쿼리 실행 → RLS 정책 평가 (행 단위)              ← 2차 방어
  → 변경 영향 행 수 확인 (0이면 결함 신호)
  → 응답 (에러는 도메인 코드 + HTTP 상태)
```

1차가 사용자에게 **왜 거부됐는지**를 알려주고, 2차가 1차의 누락을 **결과적으로** 막는다. 둘의 역할을 바꾸지 않는다.

## 본인 소유권 인가

명세서 · 근로계약 · 급여이력은 **멤버십이 아니라 본인 소유권**으로 인가한다(REQ-SLP-09 · REQ-HRM-15 · CMP-07). 판정 조건은 직원 행의 사용자 식별자가 요청자와 같은지 하나이며, 멤버십의 존재·상태를 요구하지 않는다.

| 상황 | 사업장 업무 접근 | 본인 귀속 법정문서 열람 |
|------|-----------------|----------------------|
| 재직 중(ACTIVE 멤버십) | 역할 범위 내 허용 | 허용 |
| 퇴사(LEFT · REMOVED) | 차단 | **보존기간 내 허용**(읽기 전용) |
| 사업장 폐쇄(CLOSED) | 신규 생성 차단 · 읽기 전용 | **허용** |
| 사업장 구독 만료(EXPIRED) | **차단하지 않는다** — 만료는 신규 사업장 등록과 유료 기능 실행만 막고 근태·급여·명세서 같은 사업장 내 업무 생성은 그대로 열린다(REQ-SUB-09) | 허용 |
| 계정 탈퇴 전 보존기간 내 | 차단 | **허용** |
| 계정 탈퇴(DELETED) | 차단 | 차단 — 법정 보존 데이터 자체는 파기하지 않는다 |

- **멤버십 조인으로 정책을 짜면 퇴사·폐쇄 순간 본인 명세서 접근이 끊긴다.** 명세서는 지급일 기준 3년 보존·교부 대상이라 그 단절 자체가 위반 소지다. 소유권 헬퍼를 별도로 두는 이유가 여기에 있다.
- 소유권 인가는 **읽기 전용**이다. 퇴사자가 자기 명세서를 재발행하거나 수정할 수 없다.
- 사업장 스코프를 함께 요구하는 테이블(근로계약 등)은 소유권 헬퍼와 사업장 소속 확인을 병용해 **테넌트 오염**을 차단한다.

## 사업장 전환 격리

사업장 전환은 인증 상태가 유지된 채 스코프만 바뀌는 조작이라 **캐시가 이전 사업장 값을 들고 남는 사고**가 가장 흔하다.

| 지점 | 규약 |
|------|------|
| 서버 | 클라이언트가 보낸 활성 사업장을 매 요청 재검증한다. 저장된 선택값을 신뢰하지 않는다(REQ-WRK-20) |
| 클라이언트 캐시 | 쿼리 키 첫 세그먼트에 활성 사업장 식별자를 포함하고 역할도 키에 반영한다. 계약 정본은 [04_request_data_flow.md](./04_request_data_flow.md) |
| 전환 시점 | 전환 성공 응답을 받은 뒤 이전 사업장 키 그룹을 무효화한다. 낙관적으로 먼저 전환하지 않는다 |
| 실시간 채널 | **재구독하지 않는다.** SSE 연결은 수신자를 고정한 단일 스트림 1개이고 사업장 단위 구독 개념이 없다 — 사업장 분리는 서버 내부 Redis 채널에만 있으며, 화면은 이벤트 payload의 사업장 식별자로 가른다(정본 [10_realtime_files.md](./10_realtime_files.md)) |
| 전환 차단 | SUSPENDED · CLOSED 사업장 · LEFT · REMOVED 멤버십 · STAFF의 관리자 웹 접근은 workplace.unavailable/409 또는 auth.workplace_forbidden/403 |
| 무효 복구 | 마지막 활성 사업장이 무효가 되면 선택 화면으로 되돌린다 |

## 정책이 없는 것이 설계인 지점

정책을 두지 않은 자리가 곧 표현 불가능한 접근이다. 아래는 누락이 아니라 의도된 부재다.

- **users · password_reset_tokens에 애플리케이션 롤 권한을 두지 않는다.** 자격 증명 원장을 클라이언트 경로에서 닿을 수 없게 만드는 것이 목적이며, 접근은 서버 전용 함수로만 한다.
- **감사 로그·보안 이벤트·위치정보 확인자료에 UPDATE·DELETE 정책을 두지 않는다.** 기록을 고칠 수 있으면 감사가 아니다. 정정이 필요하면 정정 로그를 새로 남긴다.
- **동료 직원의 연락처·민감정보를 여는 정책을 두지 않는다.** 동료 조회는 이름·역할만 반환하는 함수로만 열고, 연락처가 반환 타입에 없으므로 실릴 자리 자체가 없다.
- **초대의 클라이언트 직접 수락 정책을 두지 않는다.** 수락은 인원 한도 재검증·멤버십 생성·직원 초안 생성이 한 트랜잭션에 묶여야 하므로 서버 원자 함수 경로로만 허용한다.
- **급여 확정 결과에 UPDATE 정책을 두지 않는다.** 확정 불변은 규칙이 아니라 표현 불가능성으로 강제한다.
- **Materialized View를 쓰지 않는다.** 행 수준 보안이 적용되지 않아 집계 뷰 하나가 사업장 경계를 통째로 무력화한다.
- **업무 데이터를 Redis에 캐시하지 않는다.** RLS 판정을 거치지 않은 값이 캐시에 남으면 격리가 캐시 계층에서 뚫린다.
