이 문서가 **ADR 채번의 유일 정본**이다. 다른 문서는 번호로 인용만 하고 여기서 결정을 다시 논증하지 않는다. 각 ADR은 **맥락 · 결정 · 버린 대안 · 파급** 네 항목으로 고정하며, 대체된 결정은 그 앞에 **상태** 항목을 하나 더 갖는다.

채번 정책은 셋이다.

- **결번을 만들지 않는다.** ADR-01부터 연속이며 대체된 결정도 번호를 비우지 않는다.
- **대체된 결정은 원문을 보존하고 상태 행에 대체 관계를 표기한다.** 결정을 통째로 뒤집을 때는 원 번호의 본문을 덮어써 이력을 지우지 않고 새 결정을 다음 번호로 등재한 뒤, 원 번호에 "대체됨 → ADR-NN"을 단다. 현행 계약은 언제나 대체한 쪽이며 대체된 번호를 근거로 구현하지 않는다. 수단만 바뀌는 부분 개정은 원 번호 본문을 고치고 개정 사실을 함께 적는다.
- **번호는 등재 순서이고 배치는 주제별이다.** 01~04가 웹 구조와 렌더링, 05~08이 인증과 데이터 접근, 09~10이 저장소와 계약 공유, 11~14가 런타임 인프라, 15~16이 파일과 문서 생성, 17~19가 정확성 강제, 20~23이 배포와 운영, 24가 웹 빌드·라우팅 스택, **25~29가 백엔드 스택 전환**이다.

**ADR 총수 29건**이다(ADR-01~29 · 결번 없음). 이 중 **6건이 대체**됐고 원문은 이력으로 남는다 — **ADR-01 · ADR-03 · ADR-04는 2026-08-08 ADR-24로**, **ADR-06 · ADR-07 · ADR-19는 2026-09-06 각각 ADR-27 · ADR-28 · ADR-29로** 대체됐다. 현행 유효 결정은 **23건**이다. 검산: 29 − 대체 6 = **23**. 제품·범위 결정(D-NN)의 정본은 [../01_overview/06_design_decisions.md](../01_overview/06_design_decisions.md)이며 축이 다르다 — D는 무엇을 만들고 무엇을 안 만드는가, ADR은 그것을 어떤 기술로 어떻게 만드는가다.

## ADR-01 — 단일 웹 애플리케이션과 라우트 그룹 3분할

- **상태**: **대체됨(2026-08-08 → [ADR-24](#adr-24--웹-빌드라우팅-스택을-vite--react-router-프리렌더로-선정한다))**. 아래 본문은 이력으로 보존하며 현행 계약이 아니다 — 라우트 그룹과 서버 미들웨어는 전환 후 존재하지 않는 개념이다. **웹을 하나의 애플리케이션·하나의 배포 프로젝트로 둔다는 결론과 미들웨어에 판정을 싣지 않는다는 규정은 ADR-24가 승계**했다.
- **맥락**: 웹이 담아야 하는 표면은 셋이다 — 미인증 공개 페이지 · 사업장 운영 관리자 웹 · 플랫폼 관리 시스템 웹. 셋은 사용자도 권한도 다르지만 로그인·세션·디자인 토큰·API 클라이언트·타입 생성 파이프라인을 공유한다.
- **결정**: **하나의 Next.js 애플리케이션**이 라우트 그룹 (public) · (admin) · (system) 셋을 담고 미들웨어가 진입을 분기한다(D-01). 배포 프로젝트도 1개다. **미들웨어의 역할은 세션 쿠키 유무에 따른 라우트 보호까지**이며 권한을 판정하지 않는다 — 가드에 판정을 실으면 가드를 우회하는 경로가 곧 취약점이 된다. 판정 실패는 통과가 아니라 로그인 유도로 닫는다.
- **버린 대안**: ① 표면별 애플리케이션 분리 — 로그인·세션·에러 정제·디자인 시스템·타입 생성이 전부 여러 벌이 되고 그중 하나만 갱신되는 드리프트가 일상이 된다. ② 관리자 웹만 만드는 안 — 미인증 사용자가 요금제·약관·개인정보·위치정보 문서를 볼 자리가 사라져 상시 게시 의무를 서비스 밖에서 처리하게 된다. ③ 미들웨어에 역할·사업장 판정까지 싣는 안 — 요청마다 왕복이 늘고 그 판정이 API 서버 판정과 갈리는 순간 어느 쪽이 정본인지 알 수 없다.
- **파급**: 라우트 그룹별 렌더링 모드가 갈리므로 그 표가 별도 정본을 갖는다([05_rendering_seo.md](./05_rendering_seo.md)). 미들웨어가 판정하지 않는다는 규정이 [ADR-08](#adr-08--격리를-서비스-검증과-rls-2단으로-겹쳐-둔다)의 2단 방어를 필수로 만든다.

## ADR-02 — 서브도메인 직접 호출과 상위 도메인 세션 쿠키

- **맥락**: 웹은 Vercel, API는 EC2에 있어 오리진이 다르다. 브라우저가 API를 어떻게 부를지에 따라 지연·실시간 연결·인증 전달 방식이 전부 달라진다.
- **결정**: 커스텀 도메인 전제로 웹을 app 서브도메인, API를 api 서브도메인에 두고 **브라우저가 API를 직접 호출**한다(D-03). 세션 쿠키는 **상위 도메인 스코프 + SameSite=Lax + HttpOnly + Secure**로 두 서브도메인이 공유하고, 상태 변경 요청에는 **CSRF 토큰**을 요구한다. 실시간 연결도 직접 붙는다.
- **버린 대안**: ① 웹 서버 리라이트 프록시 — 모든 API 트래픽이 한 홉을 더 거쳐 지연·비용이 늘고 서버 전송 이벤트가 프록시의 버퍼링·타임아웃 정책에 종속된다. ② BFF 계층 신설 — 인증·권한 판정 지점이 둘로 갈라져 2단 방어의 1차 검증이 어디인지 흐려지고 에러 규격을 두 번 정제하게 된다. ③ 쿠키를 SameSite=None으로 푸는 안 — 서드파티 컨텍스트에서도 쿠키가 실려 CSRF 표면이 불필요하게 넓어진다.
- **파급**: 쿠키가 자동 전송되므로 실시간 연결이 별도 인증 헤더 없이 성립한다([10_realtime_files.md](./10_realtime_files.md)). 오리진이 다르므로 교차 출처 정책을 app 서브도메인 하나로 좁히고 자격 증명 포함을 허용한다([08_deployment_topology.md](./08_deployment_topology.md)).
- **유지 확인(2026-08-08)**: 웹 전환 후에도 **웹 산출물이 하나이고 웹 오리진도 하나**라서 쿠키 스코프와 교차 출처 허용 오리진 목록이 바뀌지 않는다(D-20). 버린 대안 ①의 리라이트 프록시는 프레임워크와 무관한 웹 호스팅 계층의 기제이며 판정은 그대로다.

## ADR-03 — 인증 후 데이터 접근을 클라이언트 조회로 단일화

- **상태**: **대체됨(2026-08-08 → [ADR-24](#adr-24--웹-빌드라우팅-스택을-vite--react-router-프리렌더로-선정한다))**. 논증의 축이던 서버 컴포넌트 셸과 서버 변이 기제가 전환 후 존재하지 않는다. **결론 — 인증 후 데이터는 클라이언트가 API를 직접 호출하고 웹 전용 서버 변이 경로를 두지 않는다 — 는 그대로 유효하며 ADR-24가 승계**했다.
- **맥락**: 인증 후 화면의 데이터를 서버 컴포넌트가 가져올지 클라이언트가 가져올지에 따라 인가 판정 지점과 캐시 무효화 축이 달라진다. 게다가 같은 업무 데이터를 앱도 봐야 한다.
- **결정**: 레이아웃과 셸만 서버 컴포넌트가 렌더하고 **업무 데이터는 클라이언트가 API를 직접 호출**한다(D-04). 조회·변이·캐시는 서버 상태 라이브러리 한 축으로 통일하고 쿼리 키 첫 세그먼트에 활성 사업장을 넣는다. **Server Actions를 채택하지 않는다.**
- **버린 대안**: ① 서버 컴포넌트 페칭 중심 — 세션 쿠키를 웹 서버로 다시 태워야 하고 인가 판정 지점이 웹 서버와 API 서버 둘로 갈라지며, 사업장 전환 시 무효화할 캐시가 서버·클라이언트로 나뉜다. ② 화면별 혼합 — 같은 데이터가 화면마다 다른 경로로 오면 사업장 스코프 격리 규칙을 화면마다 다시 지켜야 해 누락이 생긴다. ③ Server Actions로 변이 처리 — 앱은 그 경로를 쓸 수 없어 같은 업무 로직을 두 벌 유지하게 되고 REST 표면을 하나로 유지하는 이점이 사라진다.
- **파급**: 쿼리 키·무효화·낙관적 갱신 금지 목록이 별도 정본을 갖는다([04_request_data_flow.md](./04_request_data_flow.md)). 웹과 앱이 같은 표면을 쓰므로 API 계약이 단일 정본이 되고 타입 생성 파이프라인이 성립한다([ADR-10](#adr-10--클라이언트-api-타입을-openapi-문서에서-생성하고-ci가-차이를-막는다)).

## ADR-04 — 공개 페이지를 정적 생성과 증분 재생성으로 배포

- **상태**: **대체됨(2026-08-08 → [ADR-24](#adr-24--웹-빌드라우팅-스택을-vite--react-router-프리렌더로-선정한다))**. 증분 재생성과 온디맨드 재검증을 실행할 기제가 전환 후 없다. **이 결정이 막으려던 결함(게시 문안과 동의 이력의 버전이 갈리는 것)은 법정 문서를 프리렌더에서 빼고 클라이언트 조회로 두는 ADR-24의 계약이 원천 제거**한다.
- **맥락**: 공개 페이지는 검색 노출이 목적이라 첫 바이트가 빨라야 한다. 그런데 약관·개인정보·위치정보 문서는 본문의 정본이 데이터베이스의 활성 버전이라 배포 없이 개정된다.
- **결정**: 랜딩·요금제는 **빌드 시점 정적 생성**, 약관 문서 3종은 **증분 재생성**으로 둔다(D-02). 재검증은 시스템 웹의 활성 버전 전환 시점에 온디맨드로 요청하고, 실패해도 게시가 낡지 않도록 시간 기반 재검증을 함께 건다. 로그인·회원가입·재설정은 정적 셸 + 클라이언트 폼이다.
- **버린 대안**: ① 약관도 정적 생성으로 굳히는 안 — 개정 뒤에도 옛 버전이 계속 게시되어 **화면에 뜨는 약관 버전과 동의 이력의 버전이 갈린다**. ② 약관을 서버 렌더로 매 요청 조회 — 상시 게시 의무 대상인 페이지가 데이터베이스 가용성에 종속된다. ③ 별도 마케팅 사이트로 공개 페이지를 분리 — 약관 활성 버전과 동의 연동이 제품 밖으로 나가 두 곳에서 갈린다.
- **파급**: 활성 버전 전환 조작이 재검증 호출과 한 흐름이 되어 시스템 웹의 문서 관리 화면에 부수 동작이 붙는다. 렌더링 모드 표와 성능 예산이 [05_rendering_seo.md](./05_rendering_seo.md)에 고정되고 그 수치는 [../03_requirements/15_nonfunctional.md](../03_requirements/15_nonfunctional.md)와 같은 값을 쓴다.

## ADR-05 — 웹은 서버 세션 앱은 토큰으로 인증 축을 나눈다

- **맥락**: 같은 REST 표면을 브라우저와 네이티브 앱이 함께 쓴다. 두 플랫폼은 자격 증명을 안전하게 보관하는 기본 수단이 다르다.
- **결정**: **웹은 Redis에 두는 서버 세션 + HttpOnly 쿠키 + CSRF 토큰**, **앱은 접근 토큰과 갱신 토큰 2종 + 회전 재발급 + Redis 블랙리스트**다. 로그인은 자격 증명 검증 뒤 **계정 상태를 먼저 확인**하고 통과한 경우에만 컨텍스트를 발급한다. 재인증 토큰은 5분 수명으로 Redis에 두고 작업 단위로 1회 소비한다.
- **버린 대안**: ① 웹에도 토큰을 쓰는 안 — 토큰을 어느 저장소에 두든 스크립트 접근 위험이 남고, 그 위험을 없애려 쿠키에 넣으면 결국 세션 설계를 다시 하게 된다. ② 앱에 쿠키 세션을 쓰는 안 — 쿠키 저장소·CSRF·도메인 규약을 네이티브에서 재현해야 하고 실시간 연결과 재설치 복구 경로가 복잡해진다. ③ 인증 프레임워크(전략 계층 라이브러리) 도입 — 전략이 로컬 자격 증명 하나뿐인데 실제 분기인 "세션이냐 토큰이냐"가 전략 콜백 안으로 숨어 가드 코드만 보고는 어느 경로가 무엇을 신뢰하는지 읽을 수 없다.
- **파급**: 세션·블랙리스트·재인증 토큰이 전부 Redis에 모여 [ADR-11](#adr-11--redis를-세션과-중계-전용으로-쓰고-업무-캐시로-쓰지-않는다)의 채택 범위를 정한다. 계정 정지·탈퇴가 세션 삭제와 RLS 헬퍼 양쪽에 즉시 반영되므로 상태 변경이 2단 방어 모두를 지난다([02_authn_session.md](./02_authn_session.md)).
- **개정(2026-09-06)**: 구현 수단이 Spring 축으로 바뀐다 — 웹 세션은 **세션 추상화의 Redis 스토어**, 앱 토큰은 **JOSE 라이브러리 발급·검증**이다. **버린 대안 ③(전략 계층 인증 프레임워크 도입)의 판정은 그대로 유지된다** — Spring Security를 필터 체인과 인가 결정 지점으로는 쓰되 그 위에 자격 증명 전략 계층을 얹지 않는다. "세션이냐 토큰이냐"라는 표면 분기가 필터 체인에 그대로 드러나야 하며 전략 콜백 안으로 숨지 않는다(D-21).

## ADR-06 — 스키마 정본을 raw SQL에 두고 자체 마이그레이션 러너를 쓴다

- **상태**: **대체됨(2026-09-06 → [ADR-27](#adr-27--스키마-정본을-저장소-루트에-두고-flyway로-적용한다))**. 아래 본문은 이력으로 보존하며 현행 계약이 아니다 — **스키마 정본을 raw SQL에 두고 ORM이 introspection으로 따라온다는 결론, 이미 적용한 파일을 고치지 않고 보정을 새 번호로 한다는 규정은 ADR-27이 승계**했다. 뒤집힌 것은 적용 수단뿐이다. **버린 대안 ③이 표준 도구를 버린 근거("배포 이미지에 다른 언어 런타임을 하나 더 넣어야 한다")는 백엔드가 같은 런타임을 쓰게 되면서 소멸**했고, 그것이 ADR-27이 자체 러너를 버린 이유다.
- **맥락**: 이 스키마에는 ORM이 표현하지 못하는 객체가 많다 — 행 수준 보안 정책 · 기간 겹침 배제 제약 · 부분 유일 인덱스 · 상태 전이 가드 트리거 · 보안 정의자 함수다. 이것들이 격리와 무결성의 실체다.
- **결정**: **스키마 정본은 raw SQL 마이그레이션 파일**(4자리 번호 + 이름)이고 ORM은 introspection으로 그 사본을 만든다(D-05). 적용은 **자체 러너**가 한다 — 적용 이력 테이블을 조회해 미적용 파일만 번호순으로, 파일 단위 트랜잭션으로 적용하고, 실패하면 그 파일에서 멈춘다. 이미 적용한 파일은 고치지 않고 보정은 새 번호로 한다.
- **버린 대안**: ① ORM 마이그레이션 도구 사용 — 정책·배제 제약·트리거를 생성하지 못해 결국 수동 SQL을 덧붙이게 되고 그 순간 마이그레이션 이력이 두 갈래가 된다. ② ORM 스키마 파일을 정본으로 두는 안 — 표현하지 못하는 객체가 스키마 파일에서 사라지고 다음 마이그레이션이 그것들을 조용히 지운다. ③ 별도 런타임이 필요한 마이그레이션 도구 도입 — 배포 이미지에 다른 언어 런타임을 하나 더 넣어야 하고, 러너가 하는 일은 이력 조회와 순차 적용뿐이라 얻는 것에 비해 표면이 크다.
- **파급**: 배포 흐름에서 **마이그레이션이 애플리케이션 기동보다 앞서고 실패는 배포 중단**이 된다([08_deployment_topology.md](./08_deployment_topology.md)). 자동 역방향 적용을 두지 않으므로 되돌림은 되돌리는 마이그레이션을 새로 쓰는 방식이 된다.

## ADR-07 — RLS 세션 컨텍스트를 ORM 확장이 전 쿼리에 주입한다

- **상태**: **대체됨(2026-09-06 → [ADR-28](#adr-28--rls-세션-컨텍스트를-datasource-프록시가-트랜잭션-진입-시-주입한다))**. 아래 본문은 이력으로 보존하며 현행 계약이 아니다 — 논증의 축이던 ORM 클라이언트 확장이 전환 후 존재하지 않는다. **결론과 버린 대안 셋은 전부 그대로 유효하며 ADR-28이 승계**했다: 호출부가 주입을 책임지지 않는다 · 설정은 트랜잭션 지역이다 · 활성 사업장과 역할은 세션 변수로 싣지 않는다 · 주입 변수는 **5종**이다. 바뀐 것은 주입을 수행하는 자리(클라이언트 확장 → DataSource 프록시)와 우회를 막는 수단(정적 분석 규칙 → 아키텍처 테스트)뿐이다.
- **맥락**: RLS 정책은 "지금 이 연결이 누구인가"를 알아야 평가된다. 그 값을 어디서 주입하느냐가 격리의 성립 조건이다. 커넥션 풀 환경에서는 주입 방식 자체가 오염 위험을 만든다.
- **결정**: ORM 클라이언트 확장이 **모든 쿼리를 트랜잭션으로 감싸고 진입 시 세션 변수를 설정**한다(D-05). 주입 변수는 **5종**이다 — 현재 사용자 · 시스템 컨텍스트에 트랜잭션 컨텍스트 3종(초대 수락 · 사업장 폐쇄 · 사업자 재검증)을 더한다. 확장이 직접 설정하는 것은 현재 사용자·시스템 컨텍스트이고, 트랜잭션 컨텍스트 3종은 보안 정의자 서버 함수 내부에서만 켠다. 설정은 **트랜잭션 지역**으로 하고, 확장을 거치지 않는 클라이언트 인스턴스 생성을 정적 분석 규칙으로 차단한다. 활성 사업장과 역할은 세션 변수로 두지 않고 행의 사업장 열과 헬퍼로 평가한다.
- **버린 대안**: ① 컨텍스트 주입을 호출부 책임으로 두는 안 — 새 리포지토리 메서드 하나가 주입을 빠뜨리면 그 쿼리만 격리 없이 실행되고, 그 사실은 사고가 나기 전까지 드러나지 않는다. ② 연결 지속 설정으로 주입하는 안 — 풀에 반납된 연결이 이전 요청의 컨텍스트를 물려받아 **다음 사용자가 남의 데이터를 본다**. ③ 활성 사업장을 세션 변수로 싣는 안 — 클라이언트가 보낸 사업장 식별자가 그대로 세션에 실리는 경로가 생겨 격리의 근거가 서버 판정에서 요청 파라미터로 내려앉는다.
- **파급**: 주입이 누락되면 사용자 식별자가 비어 **기본 거부**로 떨어져 유출이 아니라 조회 실패로 나타난다. 정기작업은 시스템 컨텍스트를 켜고 돌되 사용자 요청 경로에서는 절대 켜지 않는다([03_multitenancy_rls.md](./03_multitenancy_rls.md) · [07_batch_scheduling.md](./07_batch_scheduling.md)).

## ADR-08 — 격리를 서비스 검증과 RLS 2단으로 겹쳐 둔다

- **맥락**: 사업장 격리를 애플리케이션에서 지킬 것인지 데이터베이스에서 지킬 것인지는 흔한 양자택일로 보이지만, 어느 한쪽만 고르면 각각 다른 방식으로 실패한다.
- **결정**: **서비스 레이어가 멤버십·역할·사업장 스코프를 1차 검증**하고 **RLS가 행 단위로 2차 강제**한다. 전 업무 테이블에 행 수준 보안을 활성화하고 **강제 옵션까지 건다**. 애플리케이션 접속 롤은 테이블 소유자가 아니며 보안 우회 속성을 갖지 않고, 서버 전용 테이블은 롤에 권한을 부여하지 않는다. 변경 쿼리는 **영향 행 수를 확인**한다.
- **버린 대안**: ① 애플리케이션 검증만 두는 안 — 새 엔드포인트 하나가 사업장 스코프 검사를 빠뜨리면 다른 사업장 데이터가 그대로 나간다. ② RLS만 두는 안 — "권한 없음"과 "데이터 없음"이 구분되지 않아 사용자에게 잘못된 안내가 나가고, 차단 사유를 알려줄 수 없어 조치 가능한 오류와 정상 상태를 구분하지 못한다. ③ 강제 옵션을 생략하는 안 — 테이블 소유자로 접속한 세션이 정책을 통째로 건너뛰어 방어가 있다는 착각만 남는다.
- **파급**: 1차가 도메인 에러 코드를, 2차가 결과적 차단을 담당하는 역할 분담이 에러 규약과 맞물린다(403과 422의 구분 — [../03_requirements/01_global_rules.md](../03_requirements/01_global_rules.md)). 명세서·근로계약은 멤버십이 아니라 본인 소유권 축으로 인가해 퇴사 후 열람이 끊기지 않게 한다.

## ADR-09 — 저장소를 3개 독립 패키지로 두고 npm을 쓴다

- **맥락**: 배포 대상이 셋(정적 호스팅 · 컨테이너 · 모바일 스토어)이고 각각 릴리스 주기가 다르다. 동시에 세 표면이 API 계약을 공유해야 한다.
- **결정**: back · web_front · app_front를 **각각 독립 패키지**로 두고(D-06) 패키지 매니저는 **npm**을 쓴다. 락 파일을 커밋하고 CI·배포는 락 파일 그대로 재현하는 설치 명령을 쓴다. **workspaces로 묶지 않는다.** 계약 공유는 코드 공유가 아니라 타입 생성으로 한다.
- **버린 대안**: ① 단일 패키지 통합 — 한 곳의 의존성 변경이 무관한 표면의 릴리스를 막고 배포 축이 서로를 끌고 다닌다. ② workspaces로 묶는 안 — 공유 코드를 담을 네 번째 패키지 폴더가 생겨 확정된 3폴더 구조가 깨지고, 루트로 호이스팅된 공용 의존성이 세 표면의 경계를 흐린다. ③ 별도 설치가 필요한 패키지 매니저 채택 — 도구 축과 버전 고정 절차가 하나 더 늘고, 심볼릭 링크 기반 의존성 배치를 모바일 번들러가 기본 해석하지 못해 앱 저장소에 예외 설정을 계속 유지해야 한다.
- **파급**: 계약 공유가 타입 생성에 전적으로 의존하므로 그 파이프라인이 없으면 세 저장소가 갈린다([ADR-10](#adr-10--클라이언트-api-타입을-openapi-문서에서-생성하고-ci가-차이를-막는다)). CI가 저장소별로 독립 실행되어 한 표면의 실패가 다른 표면의 배포를 막지 않는다.
- **유지 확인(2026-08-08)**: 웹 전환 후에도 **web_front가 한 폴더·한 패키지·한 산출물**이라 3폴더 구조와 독립 패키지 3개가 그대로 유지된다(D-20 · ADR-24). 공개 페이지를 별도 패키지로 승격하지 않는다.
- **개정(2026-09-06)**: 백엔드 폴더 이름이 back → **backend**로 바뀌고 **빌드 도구가 Gradle 단일 프로젝트**가 되어 **패키지 매니저 축이 표면별로 갈린다**(backend는 Gradle · web_front와 app_front는 npm). 저장소를 3개 독립 패키지로 두는 결정과 workspaces 미채택은 그대로이며, 오히려 **런타임이 갈려 하나로 묶을 여지 자체가 사라졌다** — 버린 대안 ②가 지목한 호이스팅 문제는 이제 웹과 앱 둘 사이에서만 성립한다. 스키마 정본 db_migration/이 저장소 루트에 추가되나 **빌드·배포 단위가 아니라 네 번째 패키지가 아니다**(D-06 · D-21 · [ADR-27](#adr-27--스키마-정본을-저장소-루트에-두고-flyway로-적용한다)).

## ADR-10 — 클라이언트 API 타입을 OpenAPI 문서에서 생성하고 CI가 차이를 막는다

- **맥락**: 저장소가 셋이고 서버 계약이 자주 바뀐다. 요청·응답 타입을 손으로 쓰면 서버가 바뀌어도 클라이언트가 컴파일을 통과한다.
- **결정**: 서버의 검증 스키마에서 **OpenAPI 문서를 생성**하고, 그 문서에서 **클라이언트 요청·응답 타입을 생성**한다. 생성물은 각 클라이언트 저장소에 커밋하고, **CI가 재생성 후 차이를 검사해 다르면 실패**시킨다. 생성물을 손으로 수정하지 않고 손으로 쓴 타입과 병행하지 않는다.
- **버린 대안**: ① 타입을 손으로 유지 — 계약 위반이 런타임에야 드러나고, 그 지점이 금액 필드면 화면에 값이 비어 표시된다. ② 생성물을 커밋하지 않고 빌드 때마다 만드는 안 — 클라이언트 빌드가 서버 소스를 필요로 하게 되어 프론트 배포가 백엔드 저장소 상태에 묶인다. ③ 차이 검사 없이 생성만 두는 안 — 서버 계약이 바뀌어도 낡은 생성물이 그대로 남아 컴파일이 통과하며, 드리프트를 잡을 자동 지점이 사라진다.
- **파급**: 생성 타입은 **형태**만 담고 권한·페이지네이션·에러 코드 계약은 API 규약과 에러 코드 정본이 갖는다. 저장소를 나눈 결정([ADR-09](#adr-09--저장소를-3개-독립-패키지로-두고-npm을-쓴다))이 감당 가능해지는 근거가 이 파이프라인이다.
- **개정(2026-09-06)**: 서버측 생성 축이 **검증 스키마 → 애노테이션 기반 OpenAPI 생성기**로 바뀐다. 결정과 버린 대안 셋은 그대로다. 다만 **검증 애노테이션이 곧 문서 스키마가 되므로 선언과 생성물이 갈리지 않게 할 책임이 DTO 한 곳에 모인다** — 손으로 쓴 스키마를 병행하지 않는 규정이 그 지점에 그대로 적용된다. 클라이언트측 생성 도구와 차이 검사 게이트는 불변이다(D-21).

## ADR-11 — Redis를 세션과 중계 전용으로 쓰고 업무 캐시로 쓰지 않는다

- **맥락**: 세션·토큰 폐기·재인증 토큰·실시간 팬아웃·정기작업 락은 전부 **수명이 짧고 만료가 내장돼야 하는 상태**다. 이것을 업무 데이터베이스에 두면 요청마다 업무 부하가 늘고 만료 정리 작업이 따로 필요해진다.
- **결정**: Redis를 채택하고 용도를 **5종**으로 한정한다 — 웹 세션 스토어 · 토큰 블랙리스트 · 재인증 토큰 · 실시간 채널 팬아웃 · 정기작업 분산락. 검산: 세션 1 + 블랙리스트 1 + 재인증 1 + 채널 1 + 락 1 = **5**. 만료는 전부 수명 설정으로 처리하고, 지속화를 켜되 **업무 데이터의 정본으로 쓰지 않는다**. 업무 데이터 조회 캐시로도 쓰지 않는다.
- **버린 대안**: ① 세션을 업무 데이터베이스에 두는 안 — 요청마다 업무 데이터베이스에 부하가 걸리고 만료 정리 작업이 하나 더 생긴다. ② 세션을 프로세스 메모리에 두는 안 — 배포할 때마다 전원이 로그아웃되고, 정기작업 재기동이 사용자 세션을 끊는다. ③ 업무 데이터 조회 결과를 캐시하는 안 — RLS 판정을 거치지 않은 값이 캐시에 남으면 격리가 캐시 계층에서 뚫린다.
- **파급**: Redis가 비어도 서비스는 재로그인으로 복구되고 데이터는 잃지 않으므로 백업 대상에서 제외된다([ADR-22](#adr-22--백업을-일일-논리-백업으로-두고-시점-복구를-채택하지-않는다)). 팬아웃 용도가 [ADR-14](#adr-14--실시간을-sse-단방향으로-두고-redis-채널로-팬아웃한다)를, 락 용도가 [ADR-13](#adr-13--정기작업-중복-실행은-redis-락-업무-경합은-트랜잭션-잠금)을 성립시킨다.

## ADR-12 — 정기작업을 시각 트리거로 등록하고 작업 큐를 두지 않는다

- **맥락**: v1 정기작업은 **8건**이고 전부 저빈도다(30분 주기 2건 · 일 1회 6건). 이 정도 규모에 어떤 실행 인프라가 맞는지가 문제다.
- **결정**: 애플리케이션 프로세스 안에서 **시각 표현식으로 등록**해 실행한다. 중복 실행은 분산락이, 재실행의 중복 부수효과는 멱등키가, 영구 실패는 재시도 상한과 종결 처리가 막는다. **별도 작업 큐 인프라를 두지 않는다.** 정기 실행을 배포 플랫폼의 스케줄 기능으로 옮기지도 않는다.
- **버린 대안**: ① 작업 큐 도입 — 워커 프로세스 분리·재시도 정책·대시보드 운영이 따라오는데 얻는 것은 8건에 대한 재시도뿐이다. ② 호스트 스케줄러로 컨테이너를 따로 띄우는 안 — 애플리케이션 코드와 실행 환경이 갈려 도메인 서비스를 재사용하지 못하고 설정이 두 곳에 생긴다. ③ 배포 플랫폼의 정기 실행 기능 사용 — 웹 플랫폼이 API 서버의 작업을 호출하는 형태가 되어 인증 경로가 하나 더 생기고 실행 시간 제한을 받는다.
- **파급**: 작업은 프로세스에 붙어 있으므로 **배포 재기동이 실행 창과 겹칠 수 있다**. 그래서 각 작업이 기준일을 인자로 계산해 재실행이 같은 대상을 잡게 하고, 순서 의존을 두지 않는다([07_batch_scheduling.md](./07_batch_scheduling.md)).

## ADR-13 — 정기작업 중복 실행은 Redis 락 업무 경합은 트랜잭션 잠금

- **맥락**: 잠금이 필요한 자리가 두 종류다. 하나는 같은 정기작업이 두 번 도는 것을 막는 일이고, 다른 하나는 급여 확정 중 근태 수정 같은 업무 데이터 경합을 막는 일이다. 성격이 다르다.
- **결정**: **정기작업 중복 실행 차단에만 Redis 락**을 쓴다. 작업 이름별 키에 소유자와 만료를 함께 걸고 소유자 확인 후 해제한다. **업무 데이터 경합은 데이터베이스 트랜잭션 잠금**으로 막는다 — 같은 근태 건의 동시 승인 · 급여 확정 중 해당 기간 수정 · 같은 사업장 귀속월의 동시 확정 · 연차 원장 동시 차감 · 초대 수락 시 인원 한도 재검증 · 사업장 등록 시 소유 한도 재검증이다.
- **버린 대안**: ① 업무 경합까지 Redis 락으로 막는 안 — 락 서버가 잠깐 끊긴 사이에 급여 확정 불변식이 함께 무너지고, 잠금과 트랜잭션의 경계가 달라 커밋되지 않은 상태에서 락이 풀린다. ② 정기작업 중복도 데이터베이스 권고 잠금으로 막는 안 — 작업이 도는 동안 데이터베이스 연결을 하나 점유해야 하고, 장주기 작업이 연결 풀을 잠식한다. ③ 잠금을 아예 생략하는 안 — 인스턴스가 하나여도 배포 중 겹침과 수동 재실행이 있어 중복 실행이 실제로 일어난다.
- **파급**: 락은 실행 경로 수에 대한 방어이지 인스턴스 수에 대한 방어가 아니므로 단일 인스턴스에서도 생략하지 않는다. 업무 불변식이 Redis 가용성에 의존하지 않게 되어 [ADR-11](#adr-11--redis를-세션과-중계-전용으로-쓰고-업무-캐시로-쓰지-않는다)의 "업무 데이터 정본이 아니다"가 유지된다.

## ADR-14 — 실시간을 SSE 단방향으로 두고 Redis 채널로 팬아웃한다

- **맥락**: v1의 실시간 요구는 **인앱 알림 배달 하나**이며 **서버에서 클라이언트로 가는 단방향**이다. 클라이언트가 실시간으로 보낼 것은 없고, 배달 실패가 알림 자체의 유실이 되어서도 안 된다.
- **결정**: **SSE**를 쓴다. 이벤트 생산자는 Redis 채널에 발행하고 각 인스턴스의 핸들러가 구독해 자신이 보유한 연결에만 전달한다. 이벤트에 식별자를 부여해 재연결 시 이후 발생분을 재전송하되, **유실 보충의 정본 경로는 재접속 후 목록 조회**로 둔다. 페이로드에 금액·개인정보를 싣지 않고, 클라이언트는 이벤트를 받으면 캐시를 무효화하고 재조회한다. **WebSocket을 채택하지 않는다.**
- **버린 대안**: ① WebSocket 채택 — 양방향 프로토콜·핸드셰이크·하트비트·프록시 설정을 관리하면서 절반만 쓴다. ② 폴링으로 대체 — 알림 지연과 서버 부하가 사용자 수에 비례해 늘고, 명세서 발행·승인 결과처럼 즉시성이 의미 있는 알림에서 체감이 나쁘다. ③ 이벤트 페이로드를 캐시에 직접 병합하는 안 — 수신 시점 권한과 조회 시점 권한이 다를 수 있어 삭제·권한 변경 이벤트에서 격리가 깨진다.
- **파급**: 프록시가 SSE 경로의 버퍼링을 끄고 타임아웃을 길게 잡아야 한다([ADR-21](#adr-21--nginx를-단일-진입점으로-두고-lets-encrypt로-tls를-종단한다)). 쿠키가 자동 전송되는 웹은 별도 인증 헤더 없이 붙고 앱은 헤더를 쓴다([ADR-02](#adr-02--서브도메인-직접-호출과-상위-도메인-세션-쿠키)).

## ADR-15 — PDF를 HTML 템플릿과 헤드리스 브라우저로 렌더한다

- **맥락**: 임금명세서는 법정 필수항목 6호를 담은 표 레이아웃이고 항목 수가 사업장·직원마다 다르다. 게다가 관리자 웹 미리보기와 실제 교부본이 같아야 한다.
- **결정**: 서버 **HTML 템플릿을 헤드리스 브라우저가 렌더해 PDF로 출력**한다. 미리보기와 교부본이 같은 템플릿을 공유한다. 한글 폰트는 컨테이너 이미지에 포함하고 렌더 시점에 외부에서 내려받지 않는다. 브라우저 인스턴스는 풀로 관리하고 **동시 실행 수에 상한**을 둔다. 대량 생성은 요청 응답 경로가 아니라 일괄 실행 경로에서 수행한다.
- **버린 대안**: ① 좌표·셀 폭을 코드로 조립하는 PDF 라이브러리 — 항목이 늘 때마다 레이아웃을 다시 맞춰야 하고 한글 폰트 임베딩과 줄바꿈을 라이브러리 규약대로 따로 해결해야 한다. ② 외부 PDF 변환 서비스 — 명세서에는 급여·인적사항이 담기므로 국외 전송과 위탁 고지 부담이 생긴다. ③ 요청마다 브라우저를 새로 띄우는 안 — 대량 발행 시 메모리가 인스턴스 한도를 넘어 컨테이너가 죽고 그 실패가 급여 확정 직후에 일어난다.
- **파급**: 이미지에 브라우저와 폰트가 포함되어 이미지 크기와 기동 시간이 늘어난다. **PDF 생성 실패가 급여 확정을 롤백하지 않고** 명세서만 실패 상태로 남으며 재시도 정기작업이 이어받는다([10_realtime_files.md](./10_realtime_files.md)).

## ADR-16 — 파일을 서울 리전 비공개 버킷에 두고 서버가 스트리밍한다

- **맥락**: 저장 대상에 주민번호·계좌가 담긴 문서, 명세서, 근로계약서가 포함된다. 저장 위치와 접근 경로가 곧 법적 요건이다.
- **결정**: **서울 리전 비공개 버킷**에 두고 국외 복제를 켜지 않는다. 키의 첫 세그먼트는 사업장 식별자다. **클라이언트에 서명 URL을 내려주지 않는다** — 법정 문서와 민감 문서는 **1회용 다운로드 토큰 + 서버 스트리밍**으로만 내려주고 서버의 저장소 접근에 쓰는 수명 제한 서명은 서버 안에 머문다. 업로드는 인가 → 크기 → 선언 형식 → **매직넘버** → 해시 → 저장 → 메타 순으로 검증한다.
- **버린 대안**: ① 서명 URL을 클라이언트에 전달하는 안 — URL이 전달되는 순간 수명 안에서 누구에게나 열리고 서버는 그 접근을 기록할 수도 막을 수도 없다. ② 공개 버킷 + 추측 불가능한 경로 — 링크 하나가 유출되면 인증 없이 명세서가 열리며, 유출 사실을 알 방법도 없다. ③ 클라이언트가 저장소로 직접 업로드하는 안 — 인가·형식·매직넘버 검증을 우회할 수 있고 우회한 파일이 메타 없이 버킷에 남는다.
- **파급**: 다운로드가 서버를 통과하므로 열람·다운로드 기록이 자연스럽게 남아 교부 의무 증빙이 된다. 본인 소유권 인가와 맞물려 퇴사·폐쇄 후에도 본인 열람이 유지된다([03_multitenancy_rls.md](./03_multitenancy_rls.md)).

## ADR-17 — 시각은 UTC로 저장하고 일 경계는 KST로 판정한다

- **맥락**: 근무일·급여 귀속월·기준값 효력일은 전부 **날짜 경계**에 걸린다. 이 경계가 하루 밀리면 급여 귀속월 전체가 틀어진다.
- **결정**: 시각은 **UTC로 저장**하고 일 경계 판정과 표시는 **KST**로 한다. 근무일·급여월·효력일 같은 날짜 값은 **문자열로 다루고** 날짜 객체로 파싱하지 않는다. 조회는 저장된 날짜 열을 범위 술어로 직접 비교하고 열에 변환을 씌우지 않는다. 프로세스 시간대는 **Asia/Seoul 고정**이며 브라우저 로컬 시간대에 의존하는 표시를 두지 않는다.
- **버린 대안**: ① 날짜 값을 날짜 객체로 역직렬화하는 안 — 자정 기준으로 해석돼 **KST 일자가 하루 밀린다**. ② 조회 시 열에 시간대 변환을 씌우는 안 — 인덱스를 쓰지 못하고 세션 시간대에 결과가 의존한다. ③ 브라우저 시간대로 표시하는 안 — 해외 접속자가 다른 근무일을 보게 되어 같은 데이터를 두 사람이 다르게 읽는다.
- **파급**: 날짜 값의 역직렬화 결과를 기동 시 스모크 테스트로 검증한다([ADR-18](#adr-18--계산-결정론을-순수-함수-격리와-정적-분석-규칙으로-강제한다)). 정기작업의 대상 일자도 실행 시각에서 역산하지 않고 기준일을 인자로 받는다([07_batch_scheduling.md](./07_batch_scheduling.md)).
- **개정(2026-09-06)**: **날짜 값을 문자열로 다룬다는 수단만 바뀐다.** 버린 대안 ①이 지목한 실패(날짜 객체가 자정 기준으로 해석돼 KST 일자가 하루 밀린다)는 **시간대를 갖지 않는 날짜 타입에서 성립하지 않으므로**, 문자열 우회 대신 **시간대 없는 날짜 타입 하나로 고정**한다. 대신 **시간대를 끌고 들어오는 구형 날짜·시각 타입의 사용을 금지**하는 계약을 새로 둔다 — 이것이 파급의 파서 고정을 대신하며 기동 스모크 테스트의 검증 대상이 된다. UTC 저장 · KST 경계 판정 · 프로세스 시간대 고정 · 열에 변환을 씌우지 않는 조회는 전부 불변이다(D-21).

- **개정(2026-09-10)**: **「UTC로 저장」의 대상은 timestamptz 이며 시간대 없는 열(time · date)은 그 문장의 대상이 아니다.** timestamptz 는 오프셋을 함께 실어 보내 데이터베이스가 스스로 정규화하므로 **드라이버·ORM 의 시간대 달력 설정에 기대지 않고**, 시간대 없는 열은 **달력을 지나지 않아야 저장값이 곧 뜻하는 값**이다. 그 달력 설정을 이 결정의 이행으로 읽으면 **시간대 없는 열의 값이 통째로 밀린다.** **실측 근거(2026-09-10)** — ORM 시간대 달력이 UTC로 걸려 근무 편성의 시각 열이 9시간 밀렸고, **읽을 때 같은 달력으로 되돌려 API 왕복은 일관해 보였다.** 저장값을 그대로 보는 것은 데이터베이스 안의 가드뿐이라 연소자 주간 09:00 편성이 00:00으로 읽혀 **전건 차단**되고 진짜 야간 22:00은 13:00으로 읽혀 **가드를 통과했다** — **막아야 할 것을 통과시키고 통과시킬 것을 막는** 형태다. **버린 대안 ①이 지목한 하루 밀림이 date 에서 성립하지 않게 된 것과 별개로, 같은 실패가 time 열에서 드라이버 설정 경로로 되살아났다** — 성립 조건을 없앤 축(타입 선택)과 다시 열린 축(달력 설정)이 달라서 앞선 개정이 이것을 막지 못했다. **파급** — 왕복 검증은 이 형태를 잡지 못하므로 **쓴 값을 원 SQL로 되읽어 대조**하는 축을 검증에 둔다([ADR-29](#adr-29--백엔드-테스트를-junit과-testcontainers로-두고-웹과-앱-러너를-유지한다)). UTC 저장 · KST 경계 판정 · 프로세스 시간대 고정 · 열에 변환을 씌우지 않는 조회는 전부 불변이다.

## ADR-18 — 계산 결정론을 순수 함수 격리와 정적 분석 규칙으로 강제한다

- **맥락**: 같은 입력에 항상 같은 금액이 나와야 한다는 규칙은 문서로만 두면 지켜지지 않는다. 위반 지점이 너무 많고, 위반이 드러나는 시점은 명세서 교부 뒤다.
- **결정**: 급여 계산을 **값 객체만 주고받는 순수 함수 계층**으로 격리해 데이터베이스·현재 시각·난수에 접근할 수 없게 만든다. 그 위에 프로젝트 고유 **정적 분석 규칙 4종**을 둔다 — 금액·비율 경로의 부동소수점 변환 차단 · 계산 계층의 시각·난수 접근 차단 · RLS 컨텍스트 확장 우회 클라이언트 생성 차단 · 클라이언트 번들의 서버 전용 환경변수 참조 차단. 검산: 부동소수점 1 + 시각 의존 1 + 확장 우회 1 + 시크릿 노출 1 = **4**. **네 번째 규칙의 판정 축은 클라이언트 노출 접두 VITE_다**(2026-08-08 개정 — D-20) — 그 접두가 없는 환경변수를 웹 클라이언트 코드가 참조하면 차단한다.
- **버린 대안**: ① 규칙을 문서와 코드 리뷰로만 지키는 안 — 위반 지점이 너무 많아 한 번의 놓침이 조용히 틀린 금액을 만들고, 그 오차는 재출력 시점에야 드러난다. ② 런타임 검사로 잡는 안 — 검사 자체가 실행 시각에 의존하고, 프로덕션에서 처음 걸리면 이미 계산이 진행된 뒤다. ③ 계산 계층에 데이터베이스 접근을 허용하되 규약으로 제한하는 안 — 접근이 가능한 한 언젠가 쓰이며, 그 순간 재현성은 규칙이 아니라 운에 달린다.
- **파급**: 골든 케이스가 HTTP·데이터베이스를 거치지 않고 순수 함수를 직접 호출할 수 있게 된다([ADR-19](#adr-19--테스트-러너를-vitest로-통일하고-앱만-jest를-유지한다)). 기준 시각·기준일이 전부 인자로 흐르므로 미리보기와 확정 계산이 같은 코드 경로를 공유한다([06_payroll_engine.md](./06_payroll_engine.md)).
- **개정(2026-09-06)**: **규칙 4종의 구성은 그대로이고 판정 축만 언어에 맞게 옮긴다.** ① 부동소수점 차단 — 금액·비율 경로의 float · double 사용과 십진 타입을 부동소수점으로 생성하는 호출을 막는다. ② 시각·난수 접근 차단 — 불변이다. ③ **RLS 우회 차단의 대상이 "컨텍스트 확장을 거치지 않는 클라이언트 생성"에서 "주입 프록시 밖에서 연결·영속성 컨텍스트·SQL 세션을 직접 얻는 것"으로 바뀐다**([ADR-28](#adr-28--rls-세션-컨텍스트를-datasource-프록시가-트랜잭션-진입-시-주입한다)). ④ 클라이언트 노출 접두 규칙 — 웹 축이라 불변이다. 집행 도구는 백엔드에서 **아키텍처 테스트 + 컴파일 시점 정적 분석**이고 웹·앱에서 기존 축 그대로이며, **검산 4는 유지**된다(D-21).

## ADR-19 — 테스트 러너를 Vitest로 통일하고 앱만 Jest를 유지한다

- **상태**: **대체됨(2026-09-06 → [ADR-29](#adr-29--백엔드-테스트를-junit과-testcontainers로-두고-웹과-앱-러너를-유지한다))**. 아래 본문은 이력으로 보존하며 현행 계약이 아니다 — **러너를 하나로 통일한다는 결론이 뒤집혔다**(백엔드가 다른 언어가 되어 통일 대상 자체가 사라졌다). **골든 케이스 계약은 전부 그대로 유효하며 ADR-29가 승계**했다: 순수 함수 계층 직접 호출 · 기대값을 정수 원으로 명시 · **근사 비교 금지** · 기준값 누락의 부정 케이스 검증 · 기동 시 타입 스모크 테스트 · 앱 종단 테스트 미채택. 버린 대안 ①이 지목한 실패(트랜스폼 비용이 실행 시간을 지배한다)는 JVM 러너에서 성립하지 않는다.
- **맥락**: 저장소가 셋이고 각각 기본 스캐폴드가 권하는 러너가 다르다. 급여 골든 케이스는 케이스 수가 많아 트랜스폼 비용이 실행 시간을 지배한다.
- **결정**: back과 web_front는 **Vitest**로 통일하고 **앱만 Jest**를 유지한다. 급여 골든 케이스는 순수 함수 계층을 직접 호출하고 기대값을 정수 원으로 명시하며 **근사 비교를 쓰지 않는다**. 기준값 누락 시 계산이 **차단되는지**를 부정 케이스로 검증하고, 기동 시 타입 파서 설정을 타입 단언으로 확인하는 스모크 테스트를 둔다. 웹 핵심 흐름에 브라우저 자동화 테스트를 두되 **앱 종단 테스트는 v1에 두지 않는다**.
- **버린 대안**: ① 세 저장소를 전부 Jest로 통일 — 골든 케이스의 트랜스폼 비용이 실행 시간을 지배해 회귀 실행이 느려지고 결국 자주 돌리지 않게 된다. ② 앱까지 Vitest로 통일 — 모바일 프리셋과 번들러 트랜스폼이 Jest에 묶여 있어 통일 비용이 러너를 하나로 맞춘 이득보다 크다. ③ 골든 케이스에 허용 오차를 두는 안 — 오차를 허용하는 순간 부동소수점 회귀가 테스트를 통과하고, 그 오차가 드러날 때는 이미 명세서가 교부된 뒤다.
- **파급**: 러너가 둘이라 설정·모킹 관례가 저장소마다 갈리지 않도록 웹과 서버가 같은 관례를 쓴다. 골든 케이스 목록과 기대값의 정본은 인수 기준 문서가 갖는다([../03_requirements/16_acceptance_criteria.md](../03_requirements/16_acceptance_criteria.md)).

## ADR-20 — 배포를 GitHub Actions 게이트와 이미지 레지스트리 경유로 만든다

- **맥락**: 배포 대상이 정적 호스팅과 컨테이너 둘로 나뉜다. 각각 배포 수단이 다르지만 품질 게이트는 하나여야 한다.
- **결정**: GitHub Actions가 **공통 품질 게이트**를 담당한다 — 락 파일 그대로 설치 → 타입 검사 → 정적 분석 → 테스트 → API 타입 재생성 후 차이 검사. web_front는 배포 플랫폼의 저장소 연동이 배포하고 **Actions는 배포 명령을 갖지 않는다**. back은 Actions가 이미지를 빌드해 레지스트리에 올리고 EC2가 그것을 받아 **마이그레이션 후 Compose를 재기동**한다. 게이트 실패 시 이미지를 만들지 않는다. **무중단 배포를 v1에 두지 않는다.**
- **버린 대안**: ① EC2에서 소스를 받아 직접 빌드하는 안 — 빌드 자원이 운영 인스턴스를 잠식하고 빌드 실패가 운영 중단으로 이어지며, 무엇이 배포됐는지 이미지 태그로 특정할 수 없다. ② Actions가 배포까지 수행하도록 웹 플랫폼 배포 명령을 넣는 안 — 플랫폼의 프리뷰·롤백 기능과 배포 주체가 이원화되어 어느 배포가 정본인지 흐려진다. ③ 게이트 없이 배포부터 하고 사후 검증하는 안 — 계약 드리프트와 회귀가 운영에서 처음 드러나며, 급여 계산 회귀는 그 시점이 마감 직후다.
- **파급**: 재기동이 순간 중단을 동반하므로 배포 창을 업무 시간 밖으로 잡는다. 마이그레이션이 기동보다 앞서는 순서가 배포 절차에 고정된다([ADR-06](#adr-06--스키마-정본을-raw-sql에-두고-자체-마이그레이션-러너를-쓴다) · [08_deployment_topology.md](./08_deployment_topology.md)).
- **개정(2026-08-08)**: web_front의 빌드 명령은 **react-router build**이며 한 번의 빌드가 프리렌더 정적 HTML과 SPA 번들을 함께 만든다(ADR-24). **약관 게시가 클라이언트 조회로 바뀌어 활성 버전 전환 시 콘텐츠 갱신 배포를 개시할 필요가 없어졌다** — 저장소 연동이 유일한 배포 개시 경로라는 원 결정이 예외 없이 유지된다.
- **개정(2026-09-06)**: backend의 게이트가 **락 파일 설치 → 타입 검사** 대신 **의존성 해석 → 컴파일 → 정적 분석 → 테스트**가 된다(빌드 도구는 Gradle — [ADR-09](#adr-09--저장소를-3개-독립-패키지로-두고-npm을-쓴다) 개정). 마이그레이션이 기동보다 앞서는 순서는 유지되나 **적용 주체가 애플리케이션 프로세스 밖의 선행 스키마 적용 단계**이므로([ADR-27](#adr-27--스키마-정본을-저장소-루트에-두고-flyway로-적용한다)) 자체 러너 실행 단계가 표준 도구의 적용 단계로 바뀌고, **적용 실패로 애플리케이션이 뜨지 않는 것이 곧 배포 중단**이 된다. 웹 배포 축과 무중단 미채택은 불변이다(D-21).

## ADR-21 — nginx를 단일 진입점으로 두고 Let's Encrypt로 TLS를 종단한다

- **맥락**: EC2 한 대에 애플리케이션·데이터베이스·캐시가 함께 있다. 외부에서 무엇이 보이는가가 곧 공격 표면이다.
- **결정**: **nginx 하나만 외부에 노출**하고 데이터베이스·캐시는 호스트 포트로 노출하지 않는다. nginx가 TLS를 종단하고 인증서는 **Let's Encrypt**로 발급·갱신하며 갱신 후 설정을 다시 읽게 한다. 평문 포트는 리다이렉트 전용이고 전송 보안 헤더를 적용한다. SSE 경로는 버퍼링을 끄고 타임아웃을 길게 잡으며, 요청 본문 크기 상한을 nginx와 애플리케이션 양쪽에 건다.
- **버린 대안**: ① 애플리케이션이 TLS를 직접 종단하는 안 — 인증서 갱신·재적재·헤더 정책이 애플리케이션 배포 주기에 묶이고, 프록시 수준 설정(버퍼링·크기 제한)을 애플리케이션 코드로 재현하게 된다. ② 관리형 로드밸런서를 두는 안 — 인스턴스가 한 대인데 고정 비용이 매출보다 먼저 발생하고 얻는 가용성 이득이 없다. ③ 데이터베이스·캐시를 호스트 포트로 노출하고 방화벽 규칙으로 막는 안 — 보안 그룹 규칙 하나가 데이터베이스를 인터넷에 여는 사고 경로가 된다.
- **파급**: 인증서 갱신 실패가 서비스 중단으로 직결되므로 갱신 확인이 운영 점검 항목이 된다. 업로드 크기 상한이 두 곳에 있어 값을 바꿀 때 함께 고친다([08_deployment_topology.md](./08_deployment_topology.md)).

## ADR-22 — 백업을 일일 논리 백업으로 두고 시점 복구를 채택하지 않는다

- **맥락**: 데이터가 소실되면 근태·급여·명세서가 함께 사라진다. 그런데 시점 복구를 켜면 베이스 백업·아카이브 보존·복구 리허설을 함께 운영해야 한다.
- **결정**: **논리 백업 일 1회 → 서울 리전 S3 업로드**로 둔다. 실행은 애플리케이션이 아니라 호스트 스케줄이며 백업 객체도 서버 측 암호화 대상이다. **시점 복구를 v1에 채택하지 않고** 그 결과인 **RPO 최대 24시간 · RTO 4시간**을 인정해 문서에 남긴다. 보존 일수는 운영 비용 확정 전까지 **미확인**으로 두고 임의 값을 고정하지 않는다. **업로드 성공을 백업 성공으로 간주하지 않고** 복원 가능 여부를 정기 확인한다.
- **버린 대안**: ① 시점 복구 채택 — 아카이브 스토리지·베이스 백업 주기·복구 리허설이 함께 따라오는데, 타깃 규모에서 하루치 재입력이 감당 가능한 수준이다. ② 백업을 애플리케이션 정기작업으로 두는 안 — 애플리케이션이 죽으면 백업도 함께 멈춰 가장 필요한 순간에 없다. ③ 복원 검증 없이 백업만 두는 안 — 손상된 덤프가 쌓이는 것을 장애 순간에야 알게 되고 그때는 복구할 것이 없다.
- **파급**: 복구 절차에 **손실 구간 파악과 재입력 안내**가 필수 단계로 들어간다 — 24시간 RPO를 인정한 이상 사용자에게 무엇이 사라졌는지 알리는 것이 절차의 일부다([08_deployment_topology.md](./08_deployment_topology.md)). Redis는 업무 정본이 아니므로 백업 대상에서 제외된다([ADR-11](#adr-11--redis를-세션과-중계-전용으로-쓰고-업무-캐시로-쓰지-않는다)).

## ADR-23 — 관측을 구조화 로그와 에러 추적으로 좁힌다

- **맥락**: 단일 프로세스·단일 인스턴스 운영이다. 관측 스택을 세우면 그 자체가 운영 대상이 되는데, 정작 필요한 것은 "무엇이 왜 실패했는가"다.
- **결정**: **구조화 JSON 로그를 표준 출력**으로 내보내고 컨테이너 로그 드라이버가 회전·보관한다(호스트 **30일**). 에러 추적은 **Sentry를 채택**하되 스택 트레이스와 에러 코드만 보내고 **요청 본문·주민번호·계좌·금액·개인 식별 정보를 전송하지 않으며** 사용자 식별은 내부 식별자로만 한다. 인프라는 인스턴스 기본 지표 알람과 외부 가동 확인으로 본다. **APM·지표 수집 대시보드·로그 집계 서비스를 v1에 채택하지 않는다.**
- **버린 대안**: ① 지표 수집기와 대시보드를 세우는 안 — 컨테이너가 둘 늘고 그것들이 운영 대상이 되는데, 단일 프로세스라 추적할 서비스 경계가 없어 얻는 정보가 적다. ② 로그 집계 서비스에 전량 전송하는 안 — 개인정보를 남기지 않더라도 외부 전송 표면을 하나 더 만들고 비용이 로그량에 비례해 늘어난다. ③ 에러 추적 없이 로그만 두는 안 — 예외가 로그 더미에 묻혀 반복 발생 여부와 영향 범위를 알 수 없고, 운영자가 사용자 문의로 처음 알게 된다.
- **파급**: 로그에 개인정보를 남기지 않는 규칙이 로거 설정 수준의 강제 사항이 된다. 감사 로그는 운영 로그와 별개 축이며 데이터베이스에 남아 회전 대상이 아니다([../10_security/04_pii_protection.md](../10_security/04_pii_protection.md)). 에러 추적 서비스는 개인정보 위탁 대상 판단이 필요하므로 개인정보 처리방침의 수탁 고지와 함께 관리한다([../10_security/03_secrets_keys.md](../10_security/03_secrets_keys.md)).
- **개정(2026-09-06)**: 구조화 JSON 로그는 **로깅 파사드 + JSON 인코더**로, 에러 추적은 **프레임워크 연동 SDK**로 구현한다. 전송 금지 항목 · 내부 식별자만 사용 · 호스트 30일 보관 · APM과 지표 대시보드 미채택은 전부 불변이다(D-21).

## ADR-24 — 웹 빌드·라우팅 스택을 Vite + React Router 프리렌더로 선정한다

- **맥락**: 웹이 담아야 하는 표면은 셋이다 — 미인증 공개 페이지 · 사업장 운영 관리자 웹 · 플랫폼 관리 시스템 웹. 셋은 사용자도 권한도 다르지만 로그인·세션·디자인 토큰·API 클라이언트·타입 생성 파이프라인을 공유한다. 이 구조를 서버 렌더 프레임워크 위에 얹으면 서버 컴포넌트·서버 변이·서버 미들웨어라는 쓰지 않기로 한 기제가 계약 안으로 딸려 들어오고, 정작 필요한 것은 **공개 2본의 검색 노출**과 **인증 후 화면의 클라이언트 렌더** 둘뿐이다([ADR-01](#adr-01--단일-웹-애플리케이션과-라우트-그룹-3분할) · [ADR-03](#adr-03--인증-후-데이터-접근을-클라이언트-조회로-단일화) · [ADR-04](#adr-04--공개-페이지를-정적-생성과-증분-재생성으로-배포)의 재검토 결과다).
- **결정**: 웹 빌드·라우팅 스택을 **Vite(Rolldown) + React 플러그인 + React Router framework mode + Tailwind 플러그인**으로 확정한다(D-20). 라우터 설정에서 서버 렌더를 끄고 **랜딩과 요금제만 프리렌더 목록에 넣어** 빌드 시점 정적 HTML을 굽는다. **법정 문서는 프리렌더하지 않고** 클라이언트가 활성 버전을 조회해 표시한다. 미인증 인증 화면 4본을 포함한 나머지 전 경로는 SPA fallback으로 서빙한다. **산출물 하나 · 배포 프로젝트 1개 · web_front 한 폴더 · 웹 오리진 하나**이며, 클라이언트 노출 환경변수 접두는 **VITE_**다. 정확한 버전 정본은 [../08_tech_stack/01_frontend_web.md](../08_tech_stack/01_frontend_web.md)다.
- **버린 대안**: ① 서버 렌더 프레임워크 유지 — 서버 미들웨어·서버 컴포넌트·서버 변이라는 미채택 기제를 계약에 남긴 채 "쓰지 않는다"를 문서로 반복해야 하고, 증분 재생성에 얹힌 약관 게시가 활성 버전 전환마다 재검증 성공에 의존한다. ② 다른 파일 기반 라우터 채택 — 프리렌더 기능이 없어 공개 페이지의 검색 노출을 별도 도구로 해결해야 하고, 공급망 침해 이력이 있어 인증 자산을 담는 표면의 의존으로 두기 어렵다. ③ 공개 페이지만 별도 정적 사이트로 분리 — 디자인 토큰·폰트·API 타입이 이중화되고 약관 게시 경로가 둘이 되어 [ADR-04](#adr-04--공개-페이지를-정적-생성과-증분-재생성으로-배포)가 막던 위험이 되살아난다. ④ 0.x 세대 프리렌더 플러그인 조합 — 유지보수가 끊긴 도구에 공개 표면의 빌드를 의존하게 된다.
- **파급**: 렌더링 모드 표와 라우트 보호 계약이 [05_rendering_seo.md](./05_rendering_seo.md)에 재고정된다. **서버 미들웨어가 없어 진입 판정 계층이 사라지므로** 클라이언트 라우트 가드는 UX 보조로만 두고 최종 강제를 서버 검증과 RLS가 진다 — [ADR-08](#adr-08--격리를-서비스-검증과-rls-2단으로-겹쳐-둔다)의 2단 방어가 더 강하게 요구된다([02_authn_session.md](./02_authn_session.md)). 배포 축은 [ADR-20](#adr-20--배포를-github-actions-게이트와-이미지-레지스트리-경유로-만든다)이 승계하며 빌드 명령만 바뀐다. ## ADR-25 — 백엔드를 Java 25와 Spring Boot로 두고 패키지를 3축으로 나눈다

- **맥락**: 백엔드 한 프로세스가 REST · SSE · 정기작업 8건 · PDF 렌더링 · 급여 계산을 전부 담당하고 도메인은 13개다. 프레임워크가 도메인 경계와 트랜잭션 경계를 강제하지 않으면 13개 도메인이 각자 다른 관례를 갖고, 그 차이가 인가 판정과 확정 불변식처럼 틀리면 되돌릴 수 없는 자리에서 드러난다.
- **결정**: **Java 25 · Spring Boot 4.1.1** 단일 프로세스 모놀리식이다(D-21). **실행 모델은 서블릿 스택으로 고정한다** — [ADR-28](#adr-28--rls-세션-컨텍스트를-datasource-프록시가-트랜잭션-진입-시-주입한다)의 세션 컨텍스트 주입이 **스레드에 바인딩된 트랜잭션**을 전제하고 쓰기 축이 블로킹이므로, 두 축을 섞으면 **주입 지점이 하나라는 보장이 깨진다**. 패키지는 **common · core · modules 3축**이며 검산은 core 9 + modules 13 = **22**다. **common**은 응답 봉투 · 에러 코드 · 페이지네이션 · 멱등키 · 금액과 시간 값 객체 · 검증 애노테이션 같은 횡단 공통을 담고 **도메인 지식과 인프라 의존을 갖지 않는다**. **core**는 인프라 관심사 9종이다 — 설정 · 데이터소스 · 캐시 · 저장소 · 메일 · 실시간 · PDF · 스케줄러 · 감사. **modules**는 문서 도메인 13과 1:1이고 각 모듈이 **controller · dto · service · repository 4계층**을 갖는다. **도메인 모듈은 다른 도메인 모듈의 repository를 직접 부르지 않으며** 협력은 공개 서비스 인터페이스로만 한다. 모듈 안에는 **다섯째 계층을 이름으로 열어 둔다** — 순수 함수 계층(calc)과 필터 체인 계층(security) 둘이며, **어느 모듈이 그 계층을 두는지는 세지 않는다.** 닫는 축이 모듈 목록이 아니라 계층 이름이므로 이름을 맞춰 지으면 구조 검사가 자동으로 따라붙는다 — 목록을 세면 새 계산 계층이 생길 때마다 규약을 고쳐야 하고 고치기 전까지 그 계층이 검사 밖에 놓인다([ADR-18](#adr-18--계산-결정론을-순수-함수-격리와-정적-분석-규칙으로-강제한다) · 실행 규약 정본은 저장소 .claude/rules/backend-architecture.md). **마이크로서비스를 채택하지 않는다.**
- **버린 대안**: ① **프레임워크 없이 얇은 HTTP 계층만 조립** — 인가 필터 · 트랜잭션 경계 · 모듈 경계를 프로젝트마다 새로 설계하게 되고, "이 REQ가 어느 계층에서 판정되는가"가 도메인마다 다른 답을 갖는다. ② **패키지를 계층 우선으로 나누는 안**(controller 전부를 한 패키지에, service 전부를 다른 패키지에) — 한 도메인의 변경이 최상위 패키지 전부를 건드리고, **도메인 경계가 패키지 구조에 드러나지 않아 모듈 간 직접 호출을 구조로 막을 수 없다.** ③ **마이크로서비스 분할** — 급여 확정처럼 근태 · 인사 · 기준값을 한 트랜잭션으로 묶어야 하는 연산이 분산 트랜잭션이 되어, 확정 불변식과 계산 결정론을 지키는 비용이 타깃 규모 대비 과하다. ④ **common을 두지 않고 core에 합치는 안** — 인프라 의존이 없는 값 객체와 인프라 어댑터가 한 패키지에 섞이면 **순수 함수 계층이 인프라를 의존하지 않는다는 보장이 패키지 구조에서 사라진다.** ⑤ **리액티브 스택 채택** — 타깃 규모(상시 근로자 1~30인 사업장)에서 얻을 처리량 이득이 없는데, **주입 누락이 조회 실패가 아니라 격리 없는 조회로 나타날 경로**가 생긴다. ADR-28이 기대는 안전 실패 방식이 그 순간 무너지므로 비용이 이득을 압도한다.
- **파급**: 모듈 경계가 문서 도메인 13과 1:1이라 요구사항 문서와 코드가 같은 축으로 읽힌다. **도메인 모듈 간 repository 직접 호출 금지와 4계층 건너뛰기 금지가 아키텍처 테스트의 검사 항목**이 되며 [ADR-28](#adr-28--rls-세션-컨텍스트를-datasource-프록시가-트랜잭션-진입-시-주입한다)의 우회 차단과 같은 도구를 쓴다. 정확한 버전과 모듈 목록의 정본은 [../08_tech_stack/03_backend.md](../08_tech_stack/03_backend.md)다.

## ADR-26 — 데이터 접근을 JPA 쓰기와 MyBatis 읽기 2축으로 나눈다

- **맥락**: 쓰기 경로와 읽기 경로의 성격이 다르다. 쓰기는 확정 불변 · 정정 체인 · 상태 전이 가드처럼 **엔티티 상태 변화가 곧 규칙**이고, 읽기는 관리자 웹 누적 조회의 동적 정렬·필터 · 급여 결과 1:N 중첩 · 재귀 CTE · 대량 집계처럼 **발행 SQL이 그대로 보여야** 한다. 한 도구가 둘을 다 잘하지 못한다.
- **결정**: **쓰기와 단순 조회는 JPA 단일 축**이고 **복잡 조회만 MyBatis 읽기 전용**이다(D-21). **MyBatis를 쓰기 경로에 두지 않는다 — 이것이 이 결정의 핵심이다.** 엔티티는 수기로 작성하고 **스키마 생성을 금지하고 검증만 수행**해 데이터베이스가 정본인 축을 지킨다([ADR-27](#adr-27--스키마-정본을-저장소-루트에-두고-flyway로-적용한다)). 두 축은 **같은 데이터소스와 같은 트랜잭션을 공유**하며 별도 세션 팩토리·별도 데이터소스를 두지 않는다 — 그래야 세션 컨텍스트 주입이 한 자리에서 걸린다([ADR-28](#adr-28--rls-세션-컨텍스트를-datasource-프록시가-트랜잭션-진입-시-주입한다)). 금액은 정수, 비율은 십진 타입으로 받고 두 축 모두 부동소수점 변환 경로를 두지 않는다.
- **버린 대안**: ① **경계 없이 도메인마다 편한 도구를 고르는 안** — 영속성 컨텍스트가 아직 반영하지 않은 변경을 직접 SQL이 보지 못하고, 반대로 직접 갱신을 컨텍스트가 모른 채 낡은 엔티티를 들고 있다. 이것을 호출 순서 규율로 막으면 **위반이 리뷰에 걸리지 않는 종류의 결함**이 되고 가장 비싸게 드러나는 자리가 급여 확정이다. 쓰기를 한 축으로 좁히면 **그 문제의 성립 조건 자체가 사라진다.** ② **JPA 단일 축** — 동적 정렬·필터와 1:N 중첩을 쿼리 DSL로 조립하면 **발행 SQL이 코드에서 보이지 않아** 173개 정책 위에서 어느 정책이 어느 조회를 막는지 추적할 수 없고, 재귀 CTE와 범위 겹침 배제 제약을 쓰는 조회는 결국 네이티브 쿼리로 빠져 축이 도로 둘이 된다. ③ **MyBatis 단일 축** — 61테이블의 매핑을 손으로 유지해야 하고, 상태 전이가 규칙인 쓰기 경로에서 변경 추적과 낙관적 잠금을 매번 다시 만들게 된다. ④ **읽기 축을 프레임워크 내장 SQL 클라이언트로 두는 안** — 의존성 축은 하나 줄지만 동적 SQL과 중첩 결과 매핑을 코드로 조립하게 되어 ②의 문제가 읽기 경로에 그대로 재발한다.
- **파급**: **쓰기 경로가 하나라 감사 기록 · 낙관적 잠금 · 변경 영향 행 수 확인을 한 자리에 둘 수 있다**([ADR-08](#adr-08--격리를-서비스-검증과-rls-2단으로-겹쳐-둔다)). 대량 삽입도 쓰기 축에 남으므로 배치 크기 조정이 한 설정으로 끝난다. **읽기 축이 읽기 전용이라는 사실은 아키텍처 테스트가 검사한다** — 매퍼에 삽입·수정·삭제 구문이 등장하면 실패시킨다. **다만 그 검사가 보는 것은 읽기 전용 하나뿐이다** — **매퍼 SQL의 도메인 경계 침범은 보지 못한다.** 구조 검사는 자바 패키지 참조를 읽는데 **매퍼의 조인 대상은 문자열 안의 테이블 이름**이라 참조 그래프에 나타나지 않는다. 그래서 **모듈 간 직접 호출 금지가 리포지토리 축에서는 강제되고 읽기 축 매퍼에서는 강제되지 않는다** — 같은 규칙이 두 축에서 강제 수준이 다르다는 사실 자체를 여기 남긴다. 경계를 넘을지의 판정 기준은 저장소 규약(.claude/rules/backend-architecture.md §2)이 갖는다.

## ADR-27 — 스키마 정본을 저장소 루트에 두고 Flyway로 적용한다

- **맥락**: [ADR-06](#adr-06--스키마-정본을-raw-sql에-두고-자체-마이그레이션-러너를-쓴다)이 자체 러너를 고른 근거는 셋이었다 — 이력 테이블 형식과 번호 규약이 도구에 종속되지 않는 것, 러너가 하는 일이 이력 조회와 순차 적용뿐이라는 것, 그리고 **표준 도구를 쓰면 배포 이미지에 다른 언어 런타임을 하나 더 넣어야 한다**는 것이었다. 백엔드가 JVM으로 바뀌면서 셋째 근거가 사라졌고 나머지 둘은 도구 설정으로 지킬 수 있다.
- **결정**: 스키마 정본은 **저장소 루트 db_migration/의 raw SQL**이고 적용은 **Flyway**가 **애플리케이션 프로세스 밖의 선행 실행 단계**에서 수행한다(D-21) — 같은 이미지·같은 런타임을 쓰되 **프레임워크의 기동 시 자동 적용에 맡기지 않는다.** **ADR-06에서 그대로 승계하는 계약**: 파일명 V{NNNN}\_\_{name}.sql · 번호 구간 21 · 체크섬 · 번호 재사용 금지 · **이미 적용한 파일을 고치지 않고 보정은 다음 미사용 번호로** · 되돌리기 스크립트 없음 · **같은 번호가 둘이면 적용을 시작하지 않고 단계를 실패시킨다**(그 결과 애플리케이션도 시작되지 않는다 — **번호가 이력의 동일성 축이라 이 검사는 도구의 기본 동작이며, 자체 러너가 쓰던 파일명 키 규약은 승계하지 않는다**) · 마이그레이션 롤과 애플리케이션 롤 분리 · 적용이 기동보다 앞서고 실패는 배포 중단. **새로 고정하는 계약 셋**: ① **적용 이력 테이블을 업무 스키마 밖에 둔다** — 기본값대로 두면 public 테이블 수 검수 기준 **60이 즉시 깨진다**. ② **db_migration/은 backend/ 밖이라 클래스패스가 아니므로 파일 시스템 위치로 지정**하고 배포 이미지가 그 경로를 담는다. ③ **하위 폴더 provisioning/ 과 seed/ 는 적용 대상이 아니다** — 롤 생성은 환경 준비 절차이고 기준값 시드는 확인 절차를 동반하므로 기동 경로에 두지 않는다. ④ **소유자 자격 증명을 애플리케이션 프로세스에 두지 않는다** — 적용 단계만 마이그레이션 롤로 접속하고 끝나면 종료하며, 애플리케이션은 애플리케이션 롤 자격만 갖고 기동한다. 이것이 ADR-06에서 승계한 롤 분리를 **자격 증명 보관 위치까지** 지키는 형태다.
- **버린 대안**: ① **자체 러너 유지** — 러너가 하는 일이 표준 도구의 기본 동작과 같은데 같은 런타임 안에서 기동 전에 도는 경로를 직접 만들 이유가 없고, 직접 만든 러너는 체크섬 · 정렬 · 부분 실패의 경계 사례를 스스로 검증해야 한다. ② **엔티티에서 스키마를 생성하는 안** — ADR-06이 이미 버린 대안이며 도구가 바뀌어도 판정은 같다. 정책 · 배제 제약 · 부분 인덱스 · 가드 트리거 · 보안 정의자 함수가 엔티티에서 사라지고 **다음 적용이 그것들을 조용히 지운다.** ③ **적용 이력을 업무 스키마에 두는 안** — 검수 기준의 테이블 수가 도구가 만든 테이블 하나 때문에 어긋나고, 그 어긋남을 예외 1건으로 문서에 적으면 도구가 테이블을 하나 더 만들 때마다 예외가 쌓여 검수 자체가 무뎌진다. ④ **db_migration/을 backend/ 안에 두는 안** — 클래스패스에 들어가 위치 지정이 간단해지지만 **스키마 정본이 애플리케이션 저장소의 하위 폴더가 되어 "데이터베이스가 정본"이라는 축이 배치에서 흐려진다.** ⑤ **프레임워크의 기동 시 자동 적용에 맡기는 안** — 설정 한 줄로 끝나 가장 편하지만 **애플리케이션 프로세스가 소유자 자격 증명을 상주 보유**하게 된다. 그러면 애플리케이션 결함 하나가 정책을 지우거나 강제 옵션을 끌 수 있어 **2단 방어의 두 번째 층이 애플리케이션 결함에 종속된다** — 이는 시크릿 인벤토리가 롤 분리를 첫 항목으로 두는 바로 그 근거다([../10_security/03_secrets_keys.md](../10_security/03_secrets_keys.md)). 적용을 프로세스 밖으로 한 단계 떼는 비용이 그 종속을 없애는 값보다 싸다.
- **파급**: 적용이 애플리케이션보다 앞선 실행 단계라 **적용 실패면 애플리케이션이 시작되지 않고 그것이 배포 중단**이다([ADR-20](#adr-20--배포를-github-actions-게이트와-이미지-레지스트리-경유로-만든다) 개정). **애플리케이션은 마이그레이션 자격 증명을 갖지 않는다는 시크릿 인벤토리의 계약이 그대로 유지**되며, 업무 커넥션 풀은 애플리케이션 롤로만 연다. 로컬 개발에서도 같은 선행 단계를 거치므로 기동 절차가 운영과 한 형태다. 구간 배치 · 시드 정책 · 적용 후 검수 기준의 정본은 [../05_database/10_migrations_seed.md](../05_database/10_migrations_seed.md)다.

## ADR-28 — RLS 세션 컨텍스트를 DataSource 프록시가 트랜잭션 진입 시 주입한다

- **맥락**: [ADR-07](#adr-07--rls-세션-컨텍스트를-orm-확장이-전-쿼리에-주입한다)의 결론(호출부가 주입을 책임지지 않는다)은 그대로 유효한데 그것을 실현하던 ORM 클라이언트 확장이 전환 후 존재하지 않는다. 커넥션 풀 환경에서 **주입 방식 자체가 오염 위험을 만든다**는 조건도 그대로다.
- **결정**: **데이터소스 프록시가 트랜잭션에 커넥션이 바인딩되는 순간 세션 변수를 설정**한다(D-21). 세션 변수는 **5종**이고 값은 바인드 파라미터로 넘기며 설정은 **트랜잭션 지역**이다 — ADR-07의 계약 그대로다. **다만 프록시가 켜는 것은 그중 하나뿐이다** — 프록시는 app.current_user_id만 설정하고, 시스템 컨텍스트는 **서버 전용 진입점**이, 트랜잭션 컨텍스트 3종은 **보안 정의자 서버 함수 내부**가 각자 자기 트랜잭션 안에서 켠다. 검산: 프록시 1 + 서버 전용 진입점 1 + 서버 함수 3 = **5**. **이 구분을 흐리지 않는다** — "프록시가 다 켜 준다"로 읽히는 순간 **시스템 컨텍스트가 사용자 요청 경로에서 켜지는 것을 막는 근거가 사라진다**(그 플래그 하나가 users와 password_reset_tokens의 정책을 통과시킨다). **새로 고정하는 것 넷**: ① **모든 업무 쿼리는 트랜잭션 안에서만 실행한다** — 영속성 컨텍스트를 요청 범위로 여는 설정을 끄고 서비스 계층 진입에 트랜잭션 경계를 요구하며, 트랜잭션 밖 쿼리는 아키텍처 테스트가 막는다. ② **값의 출처는 인증 컨텍스트 하나**이고 요청 스레드 밖(비동기 · 실시간 팬아웃 · 정기작업)으로는 전파되지 않는 것이 기본이므로 서버 전용 경로는 **명시적 진입점 한 곳**을 쓴다. ③ **커넥션 풀의 연결 초기화 구문을 쓰지 않는다** — 풀 생성 시 1회만 실행돼 사용자별 값을 담을 수 없고 전역 설정은 다음 요청으로 샌다. ④ **두 데이터 접근 축이 같은 데이터소스를 공유**하므로 주입이 한 번에 걸린다([ADR-26](#adr-26--데이터-접근을-jpa-쓰기와-mybatis-읽기-2축으로-나눈다)). 프록시 밖에서 연결 · 영속성 컨텍스트 · SQL 세션을 직접 얻는 코드는 아키텍처 테스트가 차단한다.
- **버린 대안**: ① **서비스 메서드마다 주입을 호출하는 안** — ADR-07이 버린 그대로다. 새 메서드 하나가 빠뜨리면 그 쿼리만 격리 없이 실행되고 **사고가 나기 전까지 드러나지 않는다.** ② **연결 초기화 구문이나 전역 설정으로 주입하는 안** — 풀에 반납된 연결이 이전 요청의 컨텍스트를 물려받아 **다음 사용자가 남의 데이터를 본다.** ③ **영속성 계층의 쿼리 가로채기 지점에 주입하는 안** — 그 지점은 쿼리 단위라 트랜잭션 경계와 맞지 않아 같은 트랜잭션에서 중복 주입되거나 첫 쿼리 앞에만 걸리고, 무엇보다 **다른 데이터 접근 축의 쿼리를 가로채지 못해 읽기 경로 전체가 컨텍스트 없이 나간다.** ④ **활성 사업장을 세션 변수로 싣는 안** — ADR-07이 버린 그대로다. 클라이언트가 보낸 식별자가 세션에 실리는 경로가 생겨 격리의 근거가 서버 판정에서 요청 파라미터로 내려앉는다.
- **파급**: 주입 지점이 하나라 **주입 누락이 유출이 아니라 조회 실패로 나타난다**는 안전 실패 방식이 유지된다. "모든 업무 쿼리는 트랜잭션 안"이라는 전제가 새로 생겨 **읽기 전용 조회에도 트랜잭션 경계가 필요**해지며, 대신 읽기 전용 표시를 붙여 불필요한 반영을 막는다. 주입 계약의 정본은 [03_multitenancy_rls.md](./03_multitenancy_rls.md)이고 세션 변수 목록의 정본은 [../05_database/08_rls_policies.md](../05_database/08_rls_policies.md)다.

## ADR-29 — 백엔드 테스트를 JUnit과 Testcontainers로 두고 웹과 앱 러너를 유지한다

- **맥락**: [ADR-19](#adr-19--테스트-러너를-vitest로-통일하고-앱만-jest를-유지한다)가 러너를 하나로 맞춘 이유는 설정·모킹 관례가 갈리지 않게 하는 것이었는데, 백엔드가 다른 언어가 되면서 **통일 대상 자체가 사라졌다.** 남은 문제는 급여 골든 케이스와 RLS 격리 테스트를 어디서 어떻게 도는가다.
- **결정**: 백엔드는 **JUnit 5 + 단언 라이브러리**를 쓰고 통합 테스트는 **컨테이너로 띄운 실제 PostgreSQL 18**에 붙는다. web_front는 Vitest, app_front는 Jest 그대로다. **ADR-19에서 그대로 승계하는 골든 케이스 계약**: 순수 함수 계층 직접 호출 · 기대값을 **정수 원으로 명시** · **근사 비교 금지** · 기준값 누락 시 계산이 차단되는지를 부정 케이스로 검증 · 기동 시 타입 스모크 테스트 · 웹 브라우저 자동화 테스트 유지 · **앱 종단 테스트 미채택**. **RLS 격리 테스트는 실제 데이터베이스에서만 성립한다** — 정책 · 강제 옵션 · 롤 분리가 검증 대상이므로 다른 데이터베이스로 대체하지 않는다.
- **버린 대안**: ① **인메모리 데이터베이스로 통합 테스트를 도는 안** — 행 수준 보안 · 배제 제약 · 부분 유일 인덱스 · 보안 정의자 함수가 없거나 다르게 동작해 **2단 방어의 2단째가 실제로 도는지를 검증할 수 없다.** 통과하는 테스트가 방어가 있다는 착각만 남긴다. ② **통합 테스트를 공용 개발 데이터베이스에 붙이는 안** — 테스트가 서로의 데이터를 보고 실행 순서에 결과가 의존하며, **격리 테스트가 격리되지 않은 환경에서 돈다.** ③ **골든 케이스를 HTTP 경유로 도는 안** — [ADR-18](#adr-18--계산-결정론을-순수-함수-격리와-정적-분석-규칙으로-강제한다)의 순수 함수 격리를 검증에서 활용하지 못하고 실행 시간이 케이스 수에 비례해 늘어 결국 자주 돌리지 않게 된다. ④ **웹과 앱까지 러너를 다시 맞추려는 안** — 각 표면이 자기 생태계의 표준을 따르는 편이 유지 비용이 낮고, 러너가 셋이어도 **CI 워크플로의 단계 이름을 같게 두면 게이트는 한 벌로 유지된다.**
- **파급**: 러너가 셋이 되어 ADR-19가 지키려던 관례 통일은 러너가 아니라 **CI 단계 이름과 게이트 구성**이 담당한다([ADR-20](#adr-20--배포를-github-actions-게이트와-이미지-레지스트리-경유로-만든다) 개정). 통합 테스트가 컨테이너를 띄우므로 CI 실행 시간이 늘고, 그래서 **골든 케이스는 데이터베이스를 거치지 않는 단위 테스트로 남긴다.** 케이스 목록과 기대값의 정본은 [../03_requirements/16_acceptance_criteria.md](../03_requirements/16_acceptance_criteria.md)다.
