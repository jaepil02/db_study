# 04 요청·데이터 흐름

> **대상**: 조회 흐름과 쿼리 키 규약 · 변이 흐름과 낙관적 갱신 금지 목록 · 에러 규격의 전달 경로 · 직원 앱의 동일 축 · SSE 수신 흐름
> **작성일**: 2026-08-03
> **개정일**: 2026-09-06 — 백엔드 스택 전환(D-21 · ADR-25~29) 반영 — 조회 흐름 펜스의 1차 검증 주체를 **Spring Security 필터 체인·서비스 계층**으로, 주입 줄을 **서비스 트랜잭션 개시 + DataSource 프록시 세션 변수 주입**으로 재작성하고 변이 흐름 펜스 ④의 가드 어휘를 같은 축으로 치환. 쿼리 키·무효화·낙관적 갱신 금지 목록은 불변
> **개정일**: 2026-08-08 — 활성 사업장 전달 축을 경로 포함으로 정정(헤더 전달 문구 삭제), 웹 프론트엔드 전환(D-20) 어휘 반영, SSE 수신 스코프를 수신자 고정 단일 스트림으로 정정
> **개정일**: 2026-08-27 — 웹 목록을 200건 단위 누적 조회로 전환하고 오프셋·커서 이어읽기, 쿼리 키에서 page·size 제외, 첫 묶음 메타데이터, 자동 연쇄 재조회 차단, 첫 묶음 초기화와 오프셋 정합성 한계를 명문화
> **원천**: docs_ref2/requirements_p0.md(REQ-GLB-19 에러 규약 · REQ-WRK-20 캐시 격리 · REQ-NTF-02 실시간 배달) · docs_ref2/features.md(낙관적 업데이트 금지 · 멱등성 · 동시성) · 확정 결정 D-03 · D-20 · **D-21**([../01_overview/06_design_decisions.md](../01_overview/06_design_decisions.md)) · [09_decision_records.md](./09_decision_records.md) **ADR-28**

인증 후 업무 데이터의 경로는 **하나**다 — 클라이언트가 TanStack Query로 API 서브도메인을 직접 호출한다(D-03 · D-20). 웹 호스팅 계층을 경유하는 경로도, 웹 전용 서버 변이 경로도, 화면별 예외도 두지 않는다. 경로를 하나로 고정하는 목적은 성능이 아니라 **규칙을 한 곳에서만 지키게 만드는 것**이다 — 사업장 스코프 격리·에러 정제·낙관적 갱신 금지는 경로가 둘이 되는 순간 두 번 지켜야 한다.

직원 앱(app_front)도 같은 축을 쓴다. 조회·변이·에러 정제·실시간 수신의 규약이 동일하고 인증 헤더만 다르다. 이 동일성이 REST 표면을 하나로 유지하는 이유다.

## 조회 흐름

```plain
화면 훅 → 쿼리 키 조립(활성 사업장 · 역할 · 서버 필터 축)
        → fetch 래퍼(자격 증명 포함 · 활성 사업장을 경로에 포함한 요청 조립)
        → api.{domain} → nginx → Spring Security 필터 체인·서비스 계층 1차 검증
        → 서비스 트랜잭션 개시 + DataSource 프록시 사용자 컨텍스트 주입 → RLS 2차 평가
        → 응답 → 에러 정제 계층 통과 → 도메인 타입 매핑 → 캐시
```

| 항목 | 규약 |
|------|------|
| 조회 주체 | 클라이언트 전용이다. 웹 호스팅 계층이 업무 데이터를 미리 가져오지 않는다 |
| 활성 사업장 전달 | **경로 변수가 유일한 전달 축**이다 — /v1/workplaces/{workplaceId}/… 다. 헤더·쿠키·서버 세션에 담아 암묵 전달하지 않으며 인가 판정도 경로 값 그대로가 아니라 매 요청 멤버십 재검증으로 한다(정본 [../06_api/01_conventions.md](../06_api/01_conventions.md)) |
| 재시도 | 4xx는 재시도하지 않는다. 인가 실패·전제 미충족을 반복 호출로 덮지 않는다. 5xx·네트워크 오류만 제한 횟수로 재시도한다 |
| 로딩·빈·오류·권한 거부 | 모든 데이터 화면이 네 상태를 갖춘다. 표준 정본은 [../07_screen/01_standards.md](../07_screen/01_standards.md) |
| 대량 목록 | 근태 원본 · 급여 대장 · 감사 로그 · 알림 등 서버 목록은 **200건 단위로 이어 읽는다**. 현재 필요한 묶음만 서버에서 받고 전량 로드 경로를 두지 않는다 |
| 집계 | 합계·평균은 서버가 계산한 값을 표시한다. 행을 받아 클라이언트가 합산하지 않는다(REQ-GLB-01) |
| 민감정보 | 마스킹 값만 캐시에 들어간다. 복호화된 원문은 서버 1회성 응답으로 화면에 표시하고 캐시·전역 상태에 보관하지 않는다 |

### 쿼리 키 규약

쿼리 키는 캐시 적중 범위이자 **격리 경계**다. 키 설계를 느슨하게 두면 사업장을 전환했는데 이전 사업장 데이터가 화면에 남는다.

1. **첫 세그먼트는 활성 사업장 식별자**다. 사업장에 매이지 않는 조회(본인 프로필 · 알림 · 소속 목록)만 예외이며 그 경우 사용자 식별자를 첫 세그먼트에 둔다.
2. **역할을 키에 포함한다.** 같은 엔드포인트가 역할에 따라 다른 행 집합을 돌려주는 자리(근태 목록 · 급여 이력 · 문서함)가 있어 역할이 빠지면 STAFF 캐시가 MANAGER 응답으로 갱신된다.
3. **결과 집합을 바꾸는 축은 전부 키에 넣는다** — 기간 · 급여 귀속월 · 상태 필터 · 정렬 · 검색어. 무한 목록의 page · size · cursor는 같은 결과 집합 안의 이어읽기 위치이므로 키에 넣지 않고 queryFn의 pageParam으로만 전달한다.
4. **대상자 식별자는 키의 마지막 자리**에 둔다. 접두 일치로 무효화 범위를 잡기 위해서다.
5. **원소 수를 축마다 고정한다.** 본인 조회도 대상자 자리를 비우지 않고 채운다 — 길이가 다른 키가 섞이면 접두 일치 무효화가 서로를 덮는다.

### 웹 누적 목록 흐름

```plain
목록 조건(workplaceId · 역할 · 검색 · 필터 · 정렬)으로 쿼리 체인 생성
  → 첫 200건 요청
  → DataTable 표시
  → 스크롤 센티널 도달 또는 “다음 200건 불러오기”
  → 오프셋 pageParam+1 또는 커서 nextCursor로 다음 200건 요청
  → 안정 식별자 중복 제거 후 items만 뒤에 추가
```

| 항목 | 규약 |
|------|------|
| API 방식 | 오프셋 · 커서 · 범위 조회의 기존 분류를 유지한다. 오프셋 화면도 UI만 이어읽기이며 API를 커서로 가장하지 않는다 |
| 요청 단위 | 웹 DataTable은 정확히 200건씩 요청한다. 오프셋은 page=1, 2, … + size=200, 커서는 nextCursor + size=200이다 |
| 누적 대상 | items만 응답 순서대로 누적하고 안정 식별자로 중복 제거한다. summary · range · employees · registrationNumbers · totalUnfiltered 등 부가 메타데이터는 첫 묶음을 고정해 쓴다 |
| 추가 조회 | 자동 센티널과 키보드로 도달 가능한 수동 버튼을 함께 둔다. 요청 중복을 막고 추가 조회 실패 시 기존 행을 유지한 채 같은 위치에서 재시도한다 |
| 자동 재조회 | 창 포커스·네트워크 재연결로 누적된 N개 묶음을 연쇄 재조회하지 않는다. 전체 최신화는 명시적 “처음부터 새로고침”으로 새 체인을 만든다 |
| 초기화 | 검색·필터·정렬·사업장·역할 변경은 쿼리 키를 바꿔 첫 200건부터 시작한다. 관련 변이 성공은 기존 체인을 reset해 첫 묶음부터 다시 읽는다 |
| 제외 | 범위 조회 · 작은 모달 선택 목록 · 로컬 계산 표는 공용 누적 목록 대상이 아니다. 직원 앱의 화면별 조회 단위도 웹 변경으로 강제하지 않는다 |

오프셋 이어읽기에는 스냅샷 일관성이 없다. 조회 중 외부 삽입·삭제가 앞쪽에서 일어나면 안정 식별자 중복 제거는 같은 행의 재등장만 막고 **건너뛴 행은 복원하지 못한다**. 사용자가 “처음부터 새로고침”으로 현재 모집단을 다시 읽을 수 있게 하고, 완전한 일관성이 필요한 표면은 커서 또는 스냅샷 토큰을 별도 API 결정으로 다룬다.

### 무효화 전략

| 범위 | 시점 | 대상 |
|------|------|------|
| 도메인 키 그룹 | 변이 **성공 응답을 받은 뒤** | 일반 조회는 관련 키를 무효화하고, 누적 목록은 저장된 모든 묶음을 다시 읽지 않도록 reset해 첫 200건부터 시작한다. 근태 승인은 근태 목록·일 집계·마감 가능 여부를 함께 갱신한다 |
| 사업장 전 범위 | 사업장 전환 성공 후 | 이전 사업장 접두를 가진 전 키. 전환 전에 미리 지우지 않는다 |
| 전체 무효화 | 세션 경계에서만 | 로그인 · 로그아웃 · 초대 수락 · 계정 상태 변경 감지. 사용자가 바뀌었는데 이전 캐시가 남는 사고를 원천 차단한다 |
| 실시간 수신 | SSE 이벤트 도착 | 일반 조회는 해당 도메인 키를 무효화하고 누적 목록은 첫 묶음부터 다시 시작한다. **이벤트 본문을 캐시에 그대로 반영하지 않는다** |

## 변이 흐름

```plain
① 사용자 조작 → ② 클라이언트 형식 검증(사용성 보조)
  → ③ 변이 요청(멱등키 필요 시 동봉) → ④ 필터 체인·서비스 1차 검증
  → ⑤ 서비스 업무 규칙 판정 · 상태 전이 가드 · 트랜잭션 잠금
  → ⑥ RLS 2차 평가 · 영향 행 수 확인 → ⑦ 감사 기록(대상 액션)
  → ⑧ 성공 응답 → ⑨ 관련 쿼리 키 무효화 → ⑩ 화면 반영
```

- **⑩이 ⑧보다 앞설 수 있는 경우와 없는 경우를 구분한다.** 되돌리기 쉬운 1행 갱신은 낙관적으로 먼저 반영해도 되지만, 아래 목록은 서버 확정 후에만 화면에 반영한다.
- 멱등키가 필요한 변이는 클라이언트가 재시도해도 부수효과가 한 번만 나도록 서버가 (사업장, 멱등키) 부분 유일 제약으로 흡수한다(REQ-GLB-14). **멱등성은 같은 요청의 중복만 막고 서로 다른 요청의 경합은 막지 못하므로** 경합 대상은 트랜잭션 잠금으로 따로 막는다(REQ-GLB-15).

### 낙관적 갱신 금지 목록

되돌리기 어렵거나 되돌림 자체가 새로운 사실이 되는 작업이다. **화면이 먼저 성공을 보여준 뒤 서버가 거부하면, 사용자는 이미 끝났다고 믿은 일을 다시 확인할 방법이 없다.**

| 작업 | 금지 사유 |
|------|----------|
| 급여 확정 | 확정은 불변이며 되돌림이 취소가 아니라 무효화 + 정정본 생성이다. 낙관 반영 후 실패하면 확정 여부가 화면과 서버에서 갈린다 |
| 급여 무효화·정정본 발행 | 감사 대상 행위이며 OWNER 전용이다. 실패한 시도가 성공처럼 보이면 정정 이력이 어긋난다 |
| 근태 마감·재오픈 | 마감은 급여 계산의 확정 입력이다. 마감된 줄 알고 급여를 돌리는 경로가 생긴다 |
| 근태 수정 요청 승인·반려 | 본인 승인 차단·잠금 기간 검사가 서버 판정이라 클라이언트가 결과를 예측할 수 없다 |
| 휴가 승인·반려 | 연차 원장 차감이 함께 일어난다. 잔여 일수가 화면과 원장에서 갈린다 |
| 명세서 발행·재발급·정정본 | 교부 시점이 법적 사실이다. 발행되지 않은 명세서를 발행됨으로 표시할 수 없다 |
| 사업장 폐쇄 | 재인증·차단 조건 검사가 선행하며 되돌릴 수 없다 |
| 초대 수락 | 인원 한도 재검증이 서버 원자 함수 안에서 일어난다 |
| 임포트 확정 | 다행 커밋이며 부분 반영이 없다 |
| 역할 변경·멤버 제외 | 마지막 OWNER 보호 가드가 서버 판정이다 |
| 신고자료 생성 | 멱등키 대상이며 생성 실패가 재시도로 이어진다 |

허용되는 낙관 반영은 알림 읽음 처리 · 목록 정렬·필터 같은 표시 축 조작 · 개인 설정 저장처럼 **역연산이 명확하고 실패해도 사실관계가 바뀌지 않는** 것뿐이다.

## 에러 규격 흐름

```plain
서버 판정 실패
  → {domain}.{snake_case} 코드 + HTTP 상태 + details(선택)
  → 응답 본문은 code · message 단일 규격 (내부 식별자 · 원문 오류 미포함)
  → 클라이언트 fetch 래퍼가 코드를 파싱
  → 에러 정제 계층이 코드 → 한국어 문안 · 후속 행동을 매핑
  → 화면 표시 (필드 오류는 폼 필드에 · 그 외는 알림 영역에)
```

| 계층 | 책임 |
|------|------|
| 서버 | 코드와 HTTP 상태를 정한다. **403(적용 대상 아님 — 정상 상태)과 422(전제 미충족 — 조치 가능)를 구분**한다. 차단 사유가 여럿이면 details 배열로 전부 반환한다 |
| fetch 래퍼 | 상태 코드와 본문을 하나의 오류 객체로 정규화한다. 네트워크 실패도 같은 형태로 감싼다 |
| 정제 계층 | 코드 → 문안 매핑을 **한 곳에서만** 관리한다. 매핑에 없는 코드는 도메인 기본 문안으로 떨어뜨리되 코드 문자열을 그대로 노출하지 않는다 |
| 화면 | 문안 표시와 후속 행동(재시도 · 로그인 유도 · 보완 항목 안내)을 수행한다. 서버 원문 메시지를 그대로 띄우지 않는다 |

- **details를 안내로 바꾸는 것이 정제 계층의 핵심 역할**이다. 근태 마감 차단은 사유 배열을, 명세서 필수항목 누락은 보완 항목 목록을, 임포트 검증 실패는 행 번호·필드·사유를 담아 오므로 문안 하나로 접으면 사용자가 무엇을 고쳐야 하는지 알 수 없다.
- 코드 채번·전수 정본은 [../09_glossary/02_error_codes.md](../09_glossary/02_error_codes.md)이고 [../06_api/02_errors.md](../06_api/02_errors.md)는 미러다. **정제 계층에서 코드를 신설·개명하지 않는다.**
- 계산 차단(기준값 누락 · 스냅샷 누락 · 최저임금 미달)은 오류가 아니라 **정상 동작**이다. 문안도 실패가 아니라 "무엇을 채우면 진행되는가"로 쓴다.

## 직원 앱의 동일 축

| 항목 | 웹과 같은 것 | 앱만 다른 것 |
|------|-------------|-------------|
| 조회·변이 경로 | 같은 REST 표면 · 같은 쿼리 키 규약 · 같은 무효화 전략 | 인증이 Authorization 헤더다 |
| 에러 처리 | 같은 코드 체계 · 같은 정제 계층 구조 | 네트워크 단절 표시가 더 잦아 재시도 안내를 화면에 상시 둔다 |
| 낙관적 갱신 | 같은 금지 목록 | 체크인·체크아웃도 금지 대상이다 — 지오펜스·순서 판정이 서버에 있어 클라이언트가 결과를 예측할 수 없다 |
| 캐시 | 활성 사업장·역할 키 격리 동일 | **디스크에 영속하지 않는다.** 분실 기기에서 급여 이력이 읽히지 않게 메모리 캐시만 쓴다 |
| 오프라인 | — | **오프라인 기록 큐를 두지 않는다.** 체크인 시각과 기록 시각이 갈리면 지오펜스·지각 판정·마감 잠금의 기준 시각이 요청마다 달라진다 |

## SSE 수신 흐름

```plain
서버 이벤트 발생 (알림 생성 — 승인 결과 · 급여 확정 · 명세서 발행 등)
  → 저장 먼저 · 발행 나중 (저장 실패 시 발행하지 않는다)
  → 서버 내부 Redis 채널 발행 (사용자 스코프 · 사업장 스코프 — 서버 안에서만 갈린다)
  → SSE 핸들러가 자신이 보유한 연결(수신자 고정)에만 전달
  → 클라이언트 수신 → 해당 도메인 쿼리 키 무효화 → 재조회
```

| 항목 | 규약 |
|------|------|
| 반영 방식 | **무효화 후 재조회**를 기본으로 한다. 이벤트 본문을 캐시에 직접 병합하지 않는다 — 수신 시점의 권한과 조회 시점의 권한이 다를 수 있고, 재조회가 가시성을 다시 판정한다 |
| 유실 보충 | 미연결 중 발생분은 재접속 시 목록 조회로 보충한다(REQ-NTF-02). 실시간 채널을 유일한 배달 경로로 삼지 않는다 |
| 실패 격리 | 알림 생성 실패가 원 이벤트를 롤백하지 않는다. 급여 확정이 알림 실패로 되돌아가서는 안 된다 |
| 스코프 | 스트림은 **수신자 고정 단일 스트림 1개**다. 클라이언트가 사업장 채널을 구독·해제하지 않으며 사업장 전환도 재연결을 요구하지 않는다 — 화면은 이벤트 payload의 사업장 식별자로 가르고 캐시는 사업장 키 그룹 무효화로 격리한다. 연결·재연결·이벤트 계약의 정본은 [10_realtime_files.md](./10_realtime_files.md) |
