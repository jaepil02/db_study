명세서 교부는 **근로기준법 §48② 법정 의무**이며 미교부는 최대 500만원 과태료 대상이다. 전자교부는 적법하되 **교부 시점 판정이 중요**하다 — 사내 전산망·앱 게시는 근로자가 열람할 수 있는 상태로 입력된 때, 이메일·메신저는 발송된 때가 교부다. **교부(DELIVERED)와 실제 열람(VIEWED)은 별개 이벤트**로 구분 기록한다.

인가의 핵심 원칙은 **본인 소유권**이다. 명세서·근로계약·급여이력은 사업장 멤버십이 아니라 employees.user_id가 요청자와 같은지로 인가한다 — 사업장 RBAC로만 막으면 퇴사 순간 본인 명세서 접근이 끊기는데, 명세서는 지급일 + 3년 보존·교부 대상이라 그 자체가 위반 소지다.

**정정은 재발급이 아니다.** 재발급은 동일 원본의 재교부라 새 행을 만들지 않고, 정정은 원본을 보존한 채 supersedes_id로 연결된 정정본을 새로 발행한다. 상태 전이 정본은 [../09_glossary/03_enums_state_machines.md](../09_glossary/03_enums_state_machines.md)다. 전역 계약은 [01_global_rules.md](./01_global_rules.md)를 전제한다.

| REQ-SLP-07 | 전자교부·교부 시점 | **명세서 전자교부는 적법하다.** 교부 시점 판정은 **사내 전산망·앱 게시는 근로자가 열람할 수 있는 상태로 입력된 때**, **이메일·메신저는 발송된 때**다. payslip_deliveries(payslip_id · delivery_type ∈ ISSUED·VIEWED·DOWNLOADED · delivered_at · channel · ip · user_agent)에 기록한다. **교부는 전자 게시 완료 시점**이고 **직원의 실제 열람(VIEWED)은 별개 이벤트**로 구분 기록한다. **교부 성립 시점이 채널마다 다르므로 ISSUED의 유일성 축은 (명세서, 채널)이다** — 명세서당 1행으로 묶으면 인앱 게시가 그 자리를 소진해 이메일 교부 사실을 남길 수 없다. | REQ-SLP-08 | 열람·다운로드 통제 | STAFF는 본인 명세서 목록과 PDF를 **1회용 다운로드 토큰 + 서버 스트리밍**으로 열람한다. 토큰은 단기 만료·1회 사용이며 세션·IP·user agent 보조 바인딩으로 복사 재사용을 차단한다 — 만료·재사용은 **payslip.download_token_expired/410**. 열람·다운로드 시각·IP·기기를 기록한다. 미존재·타인 명세서는 **payslip.not_found/404**로 **행 존재 자체를 숨긴다**(403이 아니다). 권한 밖 관리 액션 시도는 **payslip.forbidden/403**. **열람 기록 INSERT는 대상 명세서의 소유권과 테넌트를 다시 검증한다** — 기록 행의 user_id가 요청자인지만 보면 대상 명세서 식별자를 임의로 채운 기록이 통과해 법정 증거 원장이 오염되고, **참조 성립 여부가 곧 명세서 존재 신호가 되어 행 존재 은닉이 무너진다** | 본인 · MANAGER | P1 |
| REQ-SLP-09 | 본인 소유권 인가 | 명세서·근로계약·급여이력의 열람 인가는 **사업장 멤버십이 아니라 본인 소유권**으로 판정한다 — 인가 조건은 payslips.employee_id를 통해 얻은 employees.user_id가 요청자와 같은지이며 **workplace_members의 존재·상태를 요구하지 않는다**. 따라서 **① 퇴사(LEFT·REMOVED) 후 ② 사업장 폐쇄(CLOSED) 후 ③ 계정 탈퇴 전 보존기간 내** 모두 본인 열람이 가능하다. **사업장 RBAC로만 인가하면 퇴사 순간 본인 명세서 접근이 끊기는데, 명세서는 지급일 + 3년 보존·교부 대상이라 그 자체가 위반 소지다.** 읽기 전용이며 쓰기·재발행은 불가능하다 | 본인 | P1 |

| 요구사항ID | 요구사항명 | 설명 | 접근 권한 | 우선순위 |

| REQ-SLP-13 | 발행 알림·대체 경로 | 발행 완료 시 직원에게 인앱 알림을 생성한다(타입 payslip_issued). **알림 본문에 금액 상세를 포함하지 않고 명세서 화면 링크만 포함**한다(REQ-NTF-01). **앱 미설치·미로그인 직원에게는 이메일 등 대체 교부 경로를 제공**하고 그 발송 사실도 **채널을 달리하는 ISSUED 이력으로 기록**한다(REQ-SLP-07) — 이메일은 발송된 때가 교부이므로 인앱 게시와 별개의 교부 사건이며, 두 사건이 각각 남아야 어느 채널로 언제 의무가 이행됐는지 답할 수 있다 | 시스템 | P1 |
| REQ-SLP-14 | 법정 교부 우선 | 직원이 알림 수신을 거부해도 **법정 교부 인앱 알림과 명세서 목록 생성은 생략하지 않는다**. 필수 알림 수신 거부 시도는 **notification.mandatory_pref/409**다. v1은 알림 설정 기능 자체를 두지 않으므로 이 코드의 실제 발생 지점이 없으나 불변식을 명시하기 위해 예약한다 | 시스템 | P1 |

## SLP-07 명세서 재발급/정정  P2

| 요구사항ID | 요구사항명 | 설명 | 접근 권한 | 우선순위 |
|-----------|-----------|------|----------|----------|
| REQ-SLP-15 | 재발급 | MANAGER 이상과 본인은 동일 급여 결과의 명세서를 재발급(재다운로드)할 수 있다. **재발급은 동일 원본의 재교부이며 payslips 행을 새로 만들지 않는다** — 부분 유니크가 원본 1건을 보장한다. 재발급 이력은 **행위자에 따라 원장이 갈린다** — **본인(토큰 주체가 명세서 소유자)** 다운로드만 payslip_deliveries의 **DOWNLOADED 행**(시각·IP·기기)으로 남고, **관리자 다운로드는 audit_logs의 document.download_sensitive**로 남는다([../06_api/09_payslip.md](../06_api/09_payslip.md) #11). **두 원장의 성격이 다르다** — payslip_deliveries는 **근로기준법 §48② 교부 이행의 법정 증적**이고 audit_logs는 운영 감사 원장이라, 관리자의 업무상 다운로드를 법정 교부 원장에 섞으면 **그 원장이 무엇을 증명하는지가 흐려진다.** **이력이 사라지는 것이 아니라 옮겨 적히는 것이다.** **버전 개념은 재발급이 아니라 정정본 체인(supersedes_id)이 담당**한다 | 본인 · MANAGER | P2 |
| REQ-SLP-16 | 정정본 발행 | 급여 정정 시 원본 급여 실행은 VOIDED로 **보존**하고 supersedes_id로 연결된 새 실행과 명세서 정정본(버전·정정사유)을 발행한다. **정정본 발행은 OWNER 전용**이며 MANAGER 시도는 **payslip.correct_forbidden/403**이다. **이 제한과 정정 사유 필수는 서비스 검증만으로 두지 않는다** — 정정본은 상태 전이가 아니라 새 행 생성이라 상태 전이 가드가 닿지 않고 쓰기 정책은 서버 경로만 열 뿐 역할을 판별하지 못하므로, **정정본 생성 시점에 요청자의 OWNER 여부·정정 사유 존재·대상 원본의 상태를 재검증하는 가드**와 **정정 대상이 지정된 행은 사유가 비어 있을 수 없다는 제약**을 함께 둔다. 발행은 멱등키로 보호하며 **같은 정정 건의 멱등키 충돌은 payslip.bulk_conflict/409**로 되돌린다 — 일괄 발행과 같은 멱등 규약을 쓰므로 코드를 나누지 않는다. **원본 급여 실행 VOID 시점에 PENDING·FAILED 상태인 명세서는 생성을 중단하고 FAILED(사유 = 원본 VOID)로 고정**한다 — 이 연쇄는 서비스 코드의 순서 준수에 맡기지 않고 **급여 실행이 VOIDED로 전이한 트랜잭션의 트리거가 수행**하며, 누락되면 무효 급여의 명세서가 정기작업으로 재큐잉된다. 정정본은 새 실행이 확정된 뒤 이 경로로만 발행한다 — CORRECTED 체인은 GENERATED·DELIVERED 명세서에 한한다. 직원 화면에 **최신본과 원본 이력**을 함께 표시하고 정정 사유·새 명세서 링크를 알리며 교부 이력을 별도 기록한다. **원본은 폐기하지 않는다** | OWNER | P2 |

## 관련 테이블

| 테이블 | 역할 |
|--------|------|
| payslips | 명세서 — payroll_run_id · employee_id · document_id · status · issued_at · supersedes_id · correction_reason · failure_detail. 원본 1건 부분 유니크 · **정정 대상 지정 시 사유 필수 제약**(REQ-SLP-01·02·06·16) |
| payslip_deliveries | 교부·열람·다운로드 이력 — ISSUED·VIEWED·DOWNLOADED · channel · ip · user_agent. **채널별 ISSUED 1회 유일**(REQ-SLP-07·13·15) |
| batch_jobs | 일괄 발행 작업 — 전체·성공·실패 건수와 실패 사유. **명세서 일괄은 대상 급여 실행 식별자 필수**(REQ-SLP-11) |
| documents | PDF **실체·파일 해시의 정본**(REQ-SLP-02·10). 보존기한은 payslips와 documents가 같은 산식에서 각각 파생해 **발행 시점에 대조**하며 어느 쪽도 상대의 사본이 아니다. 명세서 보존 목록 조회의 대상은 payslips다 |
| payroll_runs · payroll_employee_results · payroll_employee_result_items | 스냅샷 원천 — 확정 결과와 동결된 계산방법(REQ-SLP-02·05) |
| employees | 본인 소유권 인가의 판정 대상 — employees.user_id(REQ-SLP-09) |
| notifications | 발행 알림 payslip_issued(REQ-SLP-13·14) |

|-----------|:--:|----------|
