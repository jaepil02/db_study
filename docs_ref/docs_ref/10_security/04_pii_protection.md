이 제품은 **주민등록번호와 급여계좌를 다룬다.** 근로계약·임금대장·근로자명부·임금명세서가 법정 필수 기재사항으로 그 값을 요구하기 때문이며, 다루지 않는 선택지가 없다. 그래서 보호는 "가능하면 한다"가 아니라 **구조로 강제**한다.

**평문 컬럼을 두지 않는다.** 주민번호·계좌는 암호문(bytea) + HMAC blind index + 마스킹 표시값 **3축으로 분리 저장**하며 원문은 응답·로그·감사 전후값 어디에도 남지 않는다. 컬럼 명세의 정본은 [../05_database/03_hr.md](../05_database/03_hr.md)이며 본 문서와 어긋나면 그쪽이 우선한다.

본 문서는 컬럼을 다시 정의하지 않고 **접근 통제·마스킹·감사·파기의 보안 규약**을 고정한다. 위치정보는 성질과 근거 법령이 달라 [05_location_privacy.md](./05_location_privacy.md)가 따로 담는다.

## 핵심 원칙

**1. 평문은 저장하지 않고 열람만 한다.** 저장 형태는 암호문뿐이고 평문은 4요건을 통과한 요청에 대해 **1회성 응답으로만** 존재한다. 평문 컬럼이 없으면 조회 한 줄이 실수로 평문을 흘릴 자리가 없다.

**2. 중복 검출은 복호화가 아니다.** blind index가 존재하는 이유가 이것이다 — 같은 주민번호가 이미 등록됐는지 확인하려고 매 등록마다 4요건을 통과할 수는 없다. HMAC 비교는 원문을 되살리지 않는다.

**3. 조회 권한과 열람 권한을 분리한다.** RLS는 **행 가시성만** 담당하고 서비스는 마스킹 컬럼만 투영한다. 정책이 열려 있어도 암호문 컬럼이 응답에 실리지 않으며, 이 분리가 없으면 정책 하나를 넓히는 순간 원문이 따라 열린다.

**4. 접근 사실 자체가 기록이다.** 복호화는 되돌릴 수 없는 열람이므로 사전 통제만으로 부족하다. 사유 필수 감사가 사후 통제를 맡고, **데이터베이스 트리거가 사유 없는 감사 행을 거부**해 애플리케이션 우회 경로를 없앤다.

**5. 보존과 파기는 둘 다 의무다.** 파기하지 않으면 개인정보 위반이고 보존기간 내에 파기하면 근로기준법 위반이다. **기산일 없이 파기 배치를 돌리는 것 자체가 위반**이며, 두 의무가 충돌할 때는 보존이 우선한다.

**6. 국내에 두고 국외로 내보내지 않는다.** 파일·백업은 서울 리전에 두고 국외 복제를 켜지 않는다. 국외 이전은 고지·동의 절차를 추가로 요구하며, **절차 없이 저장하는 것 자체가 위반**이다.

## 보호 대상 인벤토리

| 데이터 | 저장 위치 | 보호 방식 |
|--------|----------|----------|
| **주민등록번호** | employee_personal_infos.resident_no_enc · resident_no_blind_index · resident_no_masked | **AES-GCM 암호문 + HMAC blind index + 마스킹 표시값**. 평문 컬럼 없음. 복호화는 4요건 통과 시 1회성 응답. 외국인등록번호 등 대체 식별자를 같은 컬럼으로 다룬다 |
| **급여계좌** | employee_personal_infos.bank_account_enc · bank_account_masked | AES-GCM 암호문 + 마스킹 표시값. **blind index를 두지 않는다** — 계좌는 중복이 정상(가족 계좌 공유 등)이라 중복 검출 축이 성립하지 않는다 |
| 성명·연락처·주소·비상연락처·**이력** | employees(career_history 포함) · profiles | 암호화 대상이 아니다. **행 단위 격리(RLS)와 목록 응답 제한**으로 보호한다 — 멤버 목록 응답에 급여·주민번호·계좌·상세 주소·이력을 포함하지 않는다. 이력은 근로자명부 법정 기재사항(REQ-HRM-25)이라 보유하되 명부 출력과 관리자·본인 축에서만 읽는다 |
| 부양가족 수·자녀 수 | **employees.tax_dependents_count · employees.children_under_20_count** | 세액 산출 입력이며 **부양가족 수는 간이세액표 조회 키 · 자녀 수는 조회 후 차감 축**이다. 암호화 대상은 아니나 관리자·본인 축으로만 열린다 |
| **급여액·공제 내역** | payroll_employee_results · payroll_employee_result_items | 관리자 + **본인 소유권** 축으로만 열린다. 알림 본문·푸시·로그·에러 추적에 **금액을 싣지 않는다** |
| **임금명세서 PDF** | S3 비공개 버킷 + payslips 메타 | 본인 소유권 축(멤버십 비의존) + **1회용 다운로드 토큰 + 서버 스트리밍**. 클라이언트에 서명 URL을 내려주지 않는다(ADR-16) |
| **근로계약서 PDF·전자서명 이미지** | S3 비공개 버킷 + contracts · contract_signatures 메타 | 상동. 서명 삽입은 **본인만 INSERT** 가능하며 트리거가 계약 상태·서명자 일치·PDF 해시를 재검증한다 |
| **민감 문서(documents.is_sensitive)** | S3 비공개 버킷 + documents 메타 | 관리자에게도 **권한 + 사유 + 감사 + 1회용 토큰**을 요구한다(REQ-HRM-24). 직원은 본인 공개 문서만 본다 |
| 위치정보 좌표 | attendance_records의 in_lat · in_lng · out_lat · out_lng · in_accuracy_m · out_accuracy_m **6컬럼** | 목적 달성 즉시 파기(coords_purged_at 세팅 + 6컬럼 NULL). 상세는 [05_location_privacy.md](./05_location_privacy.md) |
| 위치정보 확인자료 | location_usage_records | 정보주체 본인 전용. 관리자에게 열지 않는다 |
| 비밀번호 | users.password_hash | **argon2id 적응형 해시**. **원문·해시를 로그·응답·감사 전후값에 남기지 않는다** |
| 비밀번호 재설정 토큰 | password_reset_tokens.token_hash | **해시만 저장**한다. 원문 토큰은 발송 채널에만 존재한다 |
| 논리 백업 | S3 서울 리전 | **마스킹되지 않은 원본이 담긴다.** 서버 측 암호화 + 백업 전용 자격 분리. PII 암호화 키는 백업에 담기지 않는다 |

검산: 암호화 대상 2 + 격리 대상 3 + 파일 대상 3 + 위치 2 + 자격 증명 2 + 백업 1 = **13항**.

- **주민번호와 계좌의 보호 방식이 다른 것은 중복 검출 요구가 다르기 때문이다.** 같은 사업장에 같은 주민번호가 두 번 등록되면 그것은 오류지만, 같은 계좌가 두 번 등록되는 것은 오류가 아니다.
- **급여액이 인벤토리에 있는 이유**는 그것이 근로자에게 가장 민감한 값이기 때문이다. 암호화 대상은 아니지만 **알림·로그·외부 전송 표면에서 배제**되는 규칙은 주민번호와 같다.
- 개인정보 원문·금액·자격 증명·토큰을 **애플리케이션 로그에 남기지 않는다**(REQ-NFR-16). 에러 추적 서비스에는 스택 트레이스와 에러 코드만 보내고 사용자 식별은 내부 식별자로만 한다(ADR-23).

## 평문 접근 통제

민감정보 원문 복호화는 **네 요건을 모두 충족해야 수행된다**(REQ-HRM-04). 넷 중 하나라도 빠지면 복호화하지 않으며 hr.decrypt_forbidden/403으로 거부한다.

| # | 요건 | 강제 지점 |
|:-:|------|----------|
| ① | **재인증** — 5분 단기 · 작업 단위 1회 소비 | 서비스 가드. 미충족은 auth.reauth_required/401 |
| ② | **사유 입력** | 서비스 가드 + **audit_logs의 guard_audit_reason_required() 트리거** |
| ③ | **audit_logs 기록**(reason 필수) | 트리거가 사유 없는 감사 행을 거부하므로 기록 없이 복호화가 성립하지 않는다 |
| ④ | **서버 1회성 응답 envelope** | 응답에만 실리고 저장·캐시·재조회 경로가 없다 |

검산: 신원 축 1 + 근거 축 1 + 기록 축 1 + 전달 축 1 = **4요건**.

| 통제 지점 | 규약 |
|-----------|------|
| 수행 주체 | **OWNER · MANAGER 한정**이다. STAFF는 본인 것도 복호화하지 않고 마스킹 값만 본다 |
| 플랫폼 관리자 | **v1 범위 밖이다.** 어느 레벨에서도 열리지 않으며 열어 줄 방법도 없다 — 권한 키 화이트리스트에 PII 계열 키가 없고 employee_personal_infos 정책에 플랫폼 축 자체가 없어 **접근이 표현되지 않는다**. 지원 목적의 원문 열람 경로를 v1에 두지 않는다([07_platform_rbac.md](./07_platform_rbac.md)) |
| 저장 경로 | 앱 롤이 평문을 직접 넣는 경로가 없다 — 암호화 컬럼의 INSERT·UPDATE 정책이 **서버 컨텍스트 결합**이라 서버 암호화를 반드시 경유한다 |
| 부분 저장 | 누락 필드를 NULL로 덮지 않고 **기존 값을 보존**한다. 키 버전 메타가 깨질 요청은 hr.personal_info_key_version_conflict/409 |
| 응답 투영 | 서비스는 **마스킹 컬럼만 투영**한다. RLS가 행을 열어도 암호문 컬럼이 응답 타입에 없다 |
| 민감 문서 다운로드 | 재인증 + 사유 + 감사 + **1회용 토큰**을 요구한다(REQ-HRM-24). 서버가 객체를 읽어 스트리밍하며 클라이언트에 저장소 서명 URL을 넘기지 않는다 |
| 재인증의 한계 | **재인증은 인가를 대체하지 않는다.** 통과해도 역할과 RLS 판정을 그대로 지난다 |

- **플랫폼 축을 v1 범위 밖으로 두는 것이 "권한을 안 준다"보다 강한 통제다.** 키를 신설하고 정책에 플랫폼 축을 더하지 않는 한 판정 함수가 참을 반환할 방법이 없다. 나중에 지원 업무를 위해 열려면 권한 키 채번과 정책 개정이 함께 필요하므로 그 변경이 눈에 띈다.
- **③이 넷 중 가장 강한 요건이다.** 사유 없는 감사 행이 데이터베이스에서 거부되므로, 애플리케이션이 감사를 건너뛰도록 고쳐도 복호화 트랜잭션 자체가 실패한다.
- **재인증의 작업 단위 소비가 없으면 4요건이 사실상 3요건이 된다** — 5분 창 안에서 한 번의 재인증으로 여러 직원의 주민번호를 연속 열람할 수 있게 된다.

## 마스킹 규약

화면·목록·내보내기에는 마스킹 표시값만 쓴다. 마스킹은 암호문에서 그때그때 생성하지 않고 **저장된 표시값 컬럼을 읽는다** — 생성 경로가 있으면 그 경로가 곧 복호화 경로다.

| 대상 | 표시 형식 | 비고 |
|------|----------|------|
| 주민등록번호 | 생년월일 6자리와 성별 자리 1자리까지 표시하고 나머지를 가린다 | resident_no_masked에 저장한다. 동명이인 구분과 성별·연령 확인이라는 실무 용도를 충족하는 최소 노출이다 |
| 급여계좌 | 은행명은 그대로 표시하고 계좌번호는 뒤 일부만 남긴다 | bank_account_masked에 저장한다. 이체 대상 확인이 목적이므로 뒷자리가 남는다 |
| 휴대폰 번호 | 중간 자리를 가린다 | 목록 응답에서의 표시 규약이며 암호화 대상은 아니다 |
| 급여액 | 마스킹하지 않는다 | 관리자·본인에게는 정확한 값이 필요하다. 보호는 마스킹이 아니라 **접근 축 제한과 전송 표면 배제**로 한다 |
| 알림·푸시 본문 | 금액·주민번호·계좌를 넣지 않는다 | 잠금화면·미리보기에 그대로 노출된다. 본문은 사건 종류와 진입 유도까지만 담는다 |
| 감사 로그 전후값 | **PII 원문 금지** — 마스킹값·참조 식별자·변경 분류만 남긴다 | before_value · after_value 공통 규율이다 |
| 시스템 웹 사용자 목록 | 민감정보를 마스킹한다 | REQ-SYS-06 |

- **정확한 마스킹 자릿수는 화면 표준이 아니라 저장 규약이다.** 표시값이 컬럼에 저장되므로 자릿수를 바꾸면 기존 행의 표시값을 재생성해야 하고, 재생성은 복호화를 요구한다. **자릿수는 최초 등록 시 확정하고 이후 바꾸지 않는다.**
- 마스킹 값은 그 자체가 개인정보다 — 마스킹했다는 이유로 로그·외부 전송에 실어도 되는 값이 아니다.

## 접근 감사

기록 구조의 정본은 [../05_database/15_system.md](../05_database/15_system.md)(audit_logs)이며 요구사항 정본은 REQ-SYS-10 · REQ-GLB-17이다.

| 대상 행위 | 기록 항목 |
|-----------|----------|
| **PII 복호화** | 행위자 · 행위 시점 역할 · 액션 · 대상 유형·식별자 · 사업장 · **사유(필수)** · IP · 클라이언트 · 시각 |
| 민감 문서 다운로드 | 상동 |
| 계정·사업장 제재 · **사업장 폐쇄**(자발·강제) | 상동 + 전후 상태 |
| 역할 변경 | 상동 + 전후 역할 |
| 급여 확정 · VOID · 정정 | 상동 + 전후 상태와 참조 식별자 |
| 근태 마감 · 재오픈 · 무효화 | 상동 |
| 상시근로자 스냅샷 확정 · 정정 | 상동 |
| 최저임금 미달 강행 확정 | 상동 |
| 기준값 변경 | 상동 + 전후값과 발효일 |
| 임포트 확정 | 상동 |
| **감사 내보내기** | 상동 — 내보내기 다운로드 이력 자체를 별도 감사 로그로 남긴다 |
| 원좌표 파기 실행 | 상동([05_location_privacy.md](./05_location_privacy.md)) |

| 규약 | 내용 |
|------|------|
| 기록 방식 | **INSERT 전용**이다. UPDATE·DELETE 정책이 없고 prevent_mutation() 트리거가 다시 막는다 |
| 정정 | 기존 행을 고치지 않고 **새 정정 로그를 추가**한다 |
| 사유 강제 | guard_audit_reason_required()가 고위험 액션(전수 정본 15_system)의 reason을 NOT NULL·공백 불가로 강제한다. **민감 문서 다운로드와 원좌표 파기 실행이 그 목록에 포함되므로** 위 표의 두 행이 요구하는 사유가 애플리케이션 규약이 아니라 데이터베이스 강제다. 전수 정본은 [../05_database/15_system.md](../05_database/15_system.md)다 |
| 전후값 규율 | **PII 원문을 저장하지 않는다** — 마스킹값·참조 식별자·변경 분류만 남긴다. 이 규율이 사업장 관리자에게 자기 사업장 감사 행을 여는 정책의 전제다 |
| 역할 동결 | **행위 시점 역할을 함께 저장**한다. 사후 역할 변경과 무관하게 "그때 무슨 권한으로 했는가"에 답하기 위해서다 |
| 보존 | 법정 보존 대상이며 로그 회전 대상이 아니다. 운영 로그와 축이 다르다 |
| 조회 권한 | 전체 감사는 플랫폼 audit:view 권한이다. 사업장 관리자는 **자기 사업장 행 중 도메인 이력 액션만** 본다 |

- **조회(SELECT) 자체는 감사에 남지 않는다.** 원시 조회는 함수 호출이 없어 데이터베이스가 가로챌 수 없다. 그래서 감사가 필요한 접근(복호화 · 민감 문서 다운로드 · 감사 내보내기)은 **전부 서버 경유 함수·스트리밍 경로로 설계**해 기록이 남게 한다 — 마스킹 값 조회에는 감사를 걸지 않는다.
- **감사 로그를 지울 수 없다는 성질이 없으면 감사가 아니다.** 침해 행위자가 자기 흔적을 지우는 경로가 없어야 사후 통제가 성립한다.

## 전송·저장 경계

| 경계 | 규약 |
|------|------|
| 전송 구간 | 전 구간 TLS다. 평문 포트는 리다이렉트 전용이며 전송 보안 헤더를 적용한다(ADR-21) |
| 파일 저장 | **서울 리전 비공개 버킷**이며 국외 복제를 켜지 않는다. 키의 첫 세그먼트는 사업장 식별자다 |
| 파일 접근 | **클라이언트에 서명 URL을 내려주지 않는다.** 1회용 다운로드 토큰 + 서버 스트리밍이며 서버의 저장소 접근 서명은 서버 안에 머문다 |
| 업로드 검증 | 인가 → 크기 → 선언 형식 → **매직넘버** → 해시 → 저장 → 메타 순서다. 클라이언트 직접 업로드를 허용하지 않는다 — 우회한 파일이 메타 없이 버킷에 남는다 |
| 백업 저장 | 서울 리전 S3. 서버 측 암호화 대상이며 **백업 전용 자격**을 쓴다 |
| 데이터베이스 노출 | 데이터베이스·캐시를 호스트 포트로 노출하지 않는다 |
| 외부 전송 | v1의 외부 전송 대상은 국세청 사업자등록 API · 메일 발송 · 에러 추적 **3곳**이다. 국세청 호출에는 사업자등록번호만 실리고 개인정보를 싣지 않는다. 메일에는 교부 대상 문서가 실리므로 **수신자 본인 고정**을 지킨다 |
| PDF 생성 | **외부 변환 서비스를 쓰지 않는다.** 명세서에는 급여·인적사항이 담기므로 국외 전송과 위탁 고지 부담이 생긴다(ADR-15) |
| 개발 환경 | **주민번호·계좌가 담긴 데이터를 개발 환경에 두지 않는다.** 개발 환경은 접근 통제·감사·암호화가 운영 수준이 아니라 그 자체가 유출 경로다 |
| 국외 이전 | **v1은 개인정보의 국외 이전을 하지 않는다.** 이전이 생기면 고지·동의 절차가 선행해야 하므로, 그 절차 없이 국외 리전·국외 서비스를 도입하지 않는다 |

- 에러 추적 서비스는 개인정보 위탁 대상 판단이 필요하므로 **개인정보 처리방침의 수탁 고지와 함께 관리**한다.
- **위탁 고지 문서의 정본은 terms_documents의 활성 버전**이며 처리 위탁이 늘면 문서 개정과 재동의 흐름이 함께 돈다(REQ-SYS-15 · REQ-SYS-16).

## 파기와 보존기간 충돌 규칙

개인정보는 목적 달성 시 파기해야 하고 법정 서류는 보존기간까지 남겨야 한다. **두 의무가 같은 데이터에 걸릴 때 보존이 우선한다.**

| 유형 | 보존 기산일 | 파기 시점 |
|------|------------|----------|
| 근로계약서 | **근로관계 종료일 + 3년** | 기산일 도래 후. **재직 중 만료되지 않도록** 종료 시점에 보존기한을 확정·연장한다 |
| 임금대장 | **마지막 기입일 + 3년** | 기산일 도래 후 |
| 근로자명부 | **퇴직일 + 3년** | 기산일 도래 후 |
| 임금명세서 | **지급일 + 3년** | 기산일 도래 후 |
| 위치정보 원좌표 | 해당 없음 | **목적 달성 즉시 파기** — 시점은 해당 귀속월 근태 마감 확정이다([05_location_privacy.md](./05_location_privacy.md)) |
| 위치정보 확인자료 | 이용·제공일 기준 법정 보존기간 | 보존 만료 후 |
| 감사 로그 | 법정 보존 대상 | 보존 만료 후 |
| 탈퇴 계정의 잔여 개인정보 | 보존 대상 데이터와 분리 | 보존기간 만료 후 파기 절차가 정리한다 |

| 충돌 규칙 | 내용 |
|-----------|------|
| **보존기간 내 파기 금지** | 개인정보 파기 요구가 있어도 법정 보존 대상은 파기하지 않는다. 요구자에게 보존 근거와 만료 시점을 안내한다 |
| **기산일 없는 파기 금지** | 유형별 기산일이 다르므로 일괄 연 단위 파기를 돌리지 않는다. **기산일 없이 파기 배치를 돌리는 것 자체가 위반**이다(REQ-GLB-18) |
| 탈퇴와 보존의 관계 | 탈퇴는 계정 상태 전이와 프로필 비식별화이며 **법정 보존 대상(급여 · 근태 · 근로계약 · 명세서 · 임금대장)을 삭제하지 않는다** |
| 사업장 폐쇄와 보존의 관계 | 폐쇄는 신규 생성을 막을 뿐 보존 데이터를 지우지 않는다. 폐쇄 후에도 **본인 소유권 열람이 보존기간 내 유지**된다(CMP-07) |
| 파기 실행의 기록 | 파기 실행은 audit_logs에 남긴다. 무엇이 언제 어느 근거로 지워졌는지가 남지 않으면 파기 이행을 증명할 수 없다 |
| 자동 파기 배치 | **v1은 보존기한 만료 대상의 자동 파기 배치를 두지 않는다.** 보존기한 관리(CMP-04)가 만료 대상을 식별하고 파기는 담당자 확인 후 수행한다 — 잘못된 자동 파기는 되돌릴 수 없다. **위치정보 원좌표만 예외**이며, 목적 달성 시점이 근태 마감 확정으로 특정되므로 마감 트랜잭션의 자동 후속 처리가 수행한다([05_location_privacy.md](./05_location_privacy.md)) |

## 잔여 위험

| # | 위험 | 근거 | 판단 |
|:-:|------|------|------|
| 1 | 관리자는 4요건을 충족하면 소속 직원의 주민번호·계좌 원문을 볼 수 있다 | 근로계약·신고자료 작성에 실제로 필요한 값이라 사전 차단이 불가능하다 | **수용** — 사전 통제가 아니라 **사유 필수 감사**가 통제를 맡는다. 감사 조회는 열람 대상 보호의 근거가 된다 |
| 2 | 조회(SELECT) 자체는 감사에 남지 않는다 | 원시 조회는 함수 호출이 없어 데이터베이스가 가로챌 수 없다 | **구조적 한계** — 감사 대상 접근을 전부 서버 경유 경로로 설계해 우회 조회를 남기지 않는다 |
| 3 | 마스킹 표시값을 저장하므로 자릿수 변경이 사실상 불가능하다 | 재생성이 전 행 복호화를 요구한다 | **의식적 선택** — 실시간 마스킹 생성 경로를 두면 그것이 곧 복호화 경로가 된다. 자릿수를 최초에 확정한다 |
| 4 | 논리 백업에 마스킹되지 않은 원본이 담긴다 | 덤프는 컬럼을 그대로 옮긴다 | **등재** — 서버 측 암호화 + 백업 전용 자격 분리. **PII 암호화 키는 백업에 담기지 않으므로** 백업 단독으로는 주민번호·계좌 원문이 복원되지 않는다 |
| 5 | 자동 파기 배치가 없어 만료 대상이 방치될 수 있다 | v1은 담당자 확인 후 수동 파기다 | **의식적 선택** — 잘못된 자동 파기는 되돌릴 수 없다. 보존기한 관리(CMP-04)가 만료 대상을 식별하고 알린다 |
| 6 | 정보주체 권리행사(열람·정정·삭제) 처리 경로가 제품 기능으로 없다 | PRV-03이 v1.1 이월이다 | **이월** — v1은 담당자 지정 + 수동 처리 절차로 대응한다. 처리 기한이 있는 법정 의무이므로 운영 문서를 출시 전에 갖춘다 |
| 7 | 데이터 반출·파기 기능이 제품 기능으로 없다 | PRV-04가 v1.1 이월이다 | **이월** — 상동. 반출 요구는 감사 내보내기 경로와 달리 정보주체 축이라 별도 설계가 필요하다 |
| 8 | 급여액이 암호화 대상이 아니다 | 계산·집계·정렬 대상이라 암호화하면 급여 엔진이 성립하지 않는다 | **의식적 선택** — 보호는 접근 축 제한(관리자 + 본인 소유권)과 전송 표면 배제로 한다 |
