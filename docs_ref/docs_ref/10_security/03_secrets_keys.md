시크릿 관리는 세 가지를 강제한다. **어떤 시크릿도 클라이언트 번들과 앱 번들에 들어가지 않는다.** **키는 버전을 갖고 회전 가능하다.** **미설정은 통과가 아니라 부팅 실패다.**

보관 위치의 정본은 [../08_tech_stack/05_tooling_devops.md](../08_tech_stack/05_tooling_devops.md)다 — 운영 back은 EC2 호스트 환경 파일, web_front는 Vercel 프로젝트 환경변수(빌드 시점 주입), app_front는 빌드 시 주입이며 저장소에는 **키 이름만 담은 예시 파일**을 둔다. 본 문서는 **시크릿의 종류·노출 범위·회전 절차**를 고정한다.

**정확한 환경변수 이름은 구현 착수 시 backend/.env.example · web_front 환경변수 목록이 정본이 된다.** 본 문서는 그 목록이 담아야 할 항목과 각 항목의 보안 등급을 규정한다.

## 핵심 원칙

**1. 노출 여부는 이름이 선언한다.** 웹은 **VITE_ 접두**가 붙은 변수만 빌드 시점에 클라이언트 번들로 치환된다. 접두 없는 변수를 클라이언트 코드에서 참조하면 값이 비어 규약 위반이 런타임에 드러나며, 그 이전에 **정적 분석 규칙이 참조 자체를 차단**한다(ADR-18 개정 · D-20).

**2. 앱 번들에는 시크릿이 없다.** 모바일 번들은 리버스 엔지니어링이 가능하므로 "앱에만 넣은 키"라는 개념이 성립하지 않는다. 앱에는 API 기본 주소처럼 **노출돼도 무해한 값만** 둔다.

**3. 미설정은 fail-closed다.** 기동 시 환경변수 스키마를 검증해 필수 값이 없으면 부팅을 실패시킨다. 런타임에 처음 발견되는 설정 오류를 만들지 않으며, **키가 없을 때 암호화를 건너뛰고 평문으로 저장하는 경로를 두지 않는다.**

**4. 키는 버전을 갖는다.** 암호화 키와 blind index 키를 회전하려면 어느 행이 어느 키로 처리됐는지 알아야 한다. 그래서 키 버전이 데이터 컬럼에 함께 저장되며, **버전 없는 키 회전은 데이터 유실이다.**

**5. 응답·로그에 시크릿의 그림자도 싣지 않는다.** 실패 응답은 code와 message 둘뿐이며 내부 식별자·원문 오류를 담지 않는다. 로그·에러 추적에는 **변수 이름만** 남기고 값을 남기지 않는다.

**6. 백업은 시크릿과 같은 등급이다.** 데이터베이스 백업에는 마스킹되지 않은 원본이 담긴다 — 백업 객체 접근 자격을 애플리케이션 자격과 분리하고 서버 측 암호화를 건다.

## 시크릿 인벤토리

**v1 운영에 필요한 시크릿은 13종**이다. 검산: 데이터 계층 3 + 인증 계층 3 + 암호화 계층 2 + 외부 연동 3 + 운영 2 = **13**.

| 시크릿 | 위치 | 노출 범위 | 미설정 시 |
|--------|------|----------|----------|
| 애플리케이션 DB 접속 자격(insadesk_app) | EC2 호스트 환경 파일 | 서버 전용 | **부팅 실패**. NOSUPERUSER · NOBYPASSRLS · 비소유자 롤이며 DELETE·DDL 권한이 없다 |
| 마이그레이션 롤 접속 자격 | 배포 환경 · **스키마 적용 선행 단계** | 서버 전용 · **애플리케이션과 분리** | 적용 실패 → **애플리케이션이 시작되지 않고 배포 중단**. **애플리케이션 프로세스는 이 자격을 갖지 않는다** — 적용 단계만 이 자격으로 접속하고 끝나면 종료한다(ADR-27) |
| Redis 접속 자격 | EC2 호스트 환경 파일 | 서버 전용 | **부팅 실패**. 세션·블랙리스트·재인증 토큰·채널·정기작업 락이 전부 여기에 있다 |
| 웹 세션 서명·암호화 키 | EC2 호스트 환경 파일 | 서버 전용 | **부팅 실패**. 유출 시 임의 세션 위조가 가능하므로 최고 등급이다 |
| 앱 JWT 서명 키 | EC2 호스트 환경 파일 | 서버 전용 | **부팅 실패**. 유출 시 임의 사용자 토큰 발급이 가능하다 |
| **초기 SUPER_ADMIN 부트스트랩 자격(username · password 해시)** | EC2 호스트 환경 파일 | 서버 전용 · **최고 등급** | **부팅은 계속되고 부트스트랩만 건너뛴다**(경고 로그) — 다른 시크릿과 달리 미설정이 정상 상태다. 관리자가 0명이면 시스템 웹에 진입할 계정이 없다. **평문 비밀번호를 받지 않으며** 생성 성공 후 환경변수를 제거하는 것이 운영 절차다(정본 [../05_database/10_migrations_seed.md](../05_database/10_migrations_seed.md)) |
| **PII 암호화 마스터 키(AES-GCM · 버전별)** | EC2 호스트 환경 파일 | 서버 전용 · **최고 등급** | **부팅 실패**. 인적사항 저장·복호화가 모두 불가능하다. 유출 시 주민번호·계좌 원문이 열린다 |
| **blind index HMAC 키(버전별)** | EC2 호스트 환경 파일 | 서버 전용 · **최고 등급** | **부팅 실패**. 중복 검출이 불가능해 인적사항 등록이 차단된다. 유출 시 **후보값 대입으로 주민번호 보유 여부를 확인**할 수 있다 |
| 국세청 사업자등록 API 키 | EC2 호스트 환경 파일 | 서버 전용 | 사업자 진위·상태 검증 실패 → 사업장은 PENDING_VERIFICATION으로 생성되고 급여 확정·명세서 발행이 차단된다(D-11) |
| SMTP 발송 자격 | EC2 호스트 환경 파일 | 서버 전용 | 메일 발송 실패. **명세서 교부·계약서 교부·비밀번호 재설정 링크가 나가지 않는다** — 교부 의무 이행에 직결되므로 실패를 운영 알림 대상으로 둔다 |
| S3 접근 자격(파일) | EC2 호스트 환경 파일 | 서버 전용 | 문서·명세서 PDF·임포트/익스포트 업로드·다운로드 불가. **클라이언트에 서명 URL을 내려주지 않으므로 이 자격은 서버 안에만 머문다**(ADR-16) |
| S3 접근 자격(백업) | 호스트 백업 스케줄 | 서버 전용 · **애플리케이션과 분리** | 백업 미수행. **백업에는 마스킹되지 않은 원본이 담기므로** 파일 자격과 권한 범위를 나눈다 |
| 컨테이너 레지스트리 자격 | GitHub Actions 시크릿 · EC2 | 배포 경로 전용 | 이미지 푸시·수신 실패 → 배포 중단 |

시크릿이 아닌 값과 v1 미사용 자격은 아래와 같다.

| 항목 | 성격 | 비고 |
|------|------|------|
| 웹 API 기본 주소(VITE_ 접두) | **클라이언트 노출** · 공개 정보 | 값이 공개돼도 무해하다 — 그 주소로 닿는 모든 표면이 인증·2단 방어 뒤에 있다 |
| 앱 API 기본 주소 | **앱 번들 포함** · 공개 정보 | 앱에 넣어도 되는 유일한 부류다 |
| Sentry 전송 대상 식별자 | 클라이언트·앱 포함 가능 · **시크릿 아님** | 값이 노출돼도 조회 권한이 생기지 않는다. 다만 **스택 트레이스와 에러 코드만 전송**하고 요청 본문·주민번호·계좌·금액·개인 식별 정보를 보내지 않는 규칙이 이 항목의 실질 통제다(ADR-23) |
| 앱 FCM 공개 설정 | 앱 번들 포함 · 공개 정보 | 서버 측 푸시 발송 자격은 아래를 본다 |
| 푸시 발송 서비스 계정(FCM) | **v1 미사용** | 알림 채널 범위의 정본은 [../02_features/10_notification.md](../02_features/10_notification.md)이며 **v1은 인앱 단일 채널**이다(NTF-02 이월). 따라서 v1 운영에서 발급·설정 대상이 아니며, 도입 시점에 인벤토리에 등재한다 |
| 문자 발송 사업자 자격 | **v1 미사용** | 문자 대체 발송은 v1 알림 범위 밖이다. 사업자 선정 자체가 조달 사안이므로 자격 형태를 미리 고정하지 않는다 |
| 요율·세액표 등 기준값 | **시크릿 아님** | 법령 공개 정보이며 statutory_rates에 effective date로 등재한다. **확인되지 않은 값은 시드하지 않는다** |

- **부트스트랩 자격은 인벤토리에서 유일하게 "설정된 상태가 비정상"인 항목이다.** 다른 시크릿은 상시 존재해야 하지만 이 둘은 최초 1회 관리자 생성을 위해서만 존재하고 그 뒤에는 제거된다. 생성 시도 자체가 사유 필수 감사 액션이므로 **어느 환경에서 언제 최초 관리자가 만들어졌는지가 감사 원장에 남는다.**
- **애플리케이션 롤과 마이그레이션 롤을 나누는 것이 인벤토리의 첫 항목인 이유**는, 하나로 합치면 애플리케이션이 정책을 지우거나 FORCE를 끌 수 있게 되어 2단 방어의 두 번째 층이 애플리케이션 결함에 종속되기 때문이다.
- **파일 자격과 백업 자격을 나누는 이유**도 같다. 애플리케이션 자격으로 백업 객체까지 읽을 수 있으면 애플리케이션 하나의 취약점이 전 사업장 원본 유출이 된다.
- 시크릿은 저장소에 커밋하지 않는다. 예시 파일에는 **키 이름만** 담는다.

## 키 계층과 버전 관리

민감정보는 두 개의 독립된 키를 쓴다. 컬럼 명세의 정본은 [../05_database/03_hr.md](../05_database/03_hr.md)이며 본 절은 키 운영 규약만 담는다.

| 키 | 용도 | 데이터 측 버전 컬럼 | 분리하는 이유 |
|----|------|--------------------|--------------|
| AES-GCM 마스터 키 | 주민번호·계좌 **암호문** 생성·복호화 | employee_personal_infos.enc_key_version | 복호화 능력 그 자체다 |
| HMAC blind index 키 | 복호화 없는 **중복 검출** 색인 생성 | employee_personal_infos.blind_index_key_version | 색인은 결정론적이어야 비교가 되므로 암호화 키와 성질이 다르다. 같은 키를 쓰면 **한쪽 회전이 다른 쪽을 함께 무너뜨린다** |

**두 키 버전을 별도 컬럼으로 두는 것이 회전을 가능하게 하는 조건이다.** 한 컬럼으로 합치면 색인 재생성과 암호문 재암호화를 반드시 같은 작업으로 묶어야 하고, 그 작업은 전 행 복호화를 요구한다.

| 항목 | 규약 |
|------|------|
| 저장 형태 | 키 값은 환경 주입이고 **버전 번호만 데이터 행에 저장**한다. 키 자체를 데이터베이스에 두지 않는다 |
| 기본값 | 두 버전 컬럼 모두 1에서 시작한다 |
| 암호화 키 회전 | 새 버전 키를 추가 등록해 **신규 저장은 새 버전으로** 하고, 기존 행은 서버 배치로 복호화 후 재암호화하며 버전을 올린다. 구버전 키는 재암호화 완료가 확인될 때까지 **복호화 전용으로 유지**한다 |
| 색인 키 회전 | 새 버전 키로 blind index를 재계산해 갱신한다. **원문이 필요하므로 암호화 키 회전과 같은 배치 안에서 수행할 수 있지만 버전은 각각 올린다** |
| 회전 중 상태 | 서로 다른 버전의 행이 공존하는 것이 정상이다. 조회는 행의 버전을 읽어 해당 키를 고르며, **버전 메타가 깨질 요청은 hr.personal_info_key_version_conflict/409로 거부**한다 |
| 중복 검출의 정합 | blind index 비교는 **같은 키 버전끼리만 유효**하다. 회전 중에는 부분 UQ가 버전 경계에서 중복을 놓칠 수 있으므로 회전 배치는 사업장 단위로 완결시킨다 |
| 회전 금지 사항 | 구버전 키를 회전 완료 전에 폐기하지 않는다. **폐기 순간 그 버전으로 암호화된 행은 영구히 읽을 수 없다** |
| 세션·JWT 서명 키 | 회전 시 기존 세션과 토큰이 무효가 된다. 계획된 회전은 배포 창에 맞추고 사용자에게 재로그인이 필요함을 알린다 |

- **blind index 키 유출은 암호화 키 유출보다 덜 심각하지만 무해하지 않다.** 주민번호는 후보 공간이 좁아 **키를 아는 공격자는 특정 번호의 보유 여부를 대입으로 확인**할 수 있다. 그래서 이 키를 암호화 키와 같은 등급으로 취급한다.
- 키 관리 서비스를 v1에 두지 않는다 — 단일 인스턴스 운영에서 얻는 이득보다 운영 대상이 하나 더 느는 비용이 크다. 이 선택의 결과로 **키가 호스트 환경 파일에 평문으로 존재**하며, 이를 잔여 위험으로 등재한다.

## 클라이언트 노출 규약

| 지점 | 규약 |
|------|------|
| 웹 접두 규약 | **VITE_ 접두가 붙은 변수만 빌드 시점에 클라이언트 번들로 치환된다.** 접두 없는 변수를 클라이언트 코드에서 참조하는 코드는 정적 분석 규칙이 차단한다 |
| 웹 서버 시크릿 | **web_front에 서버 시크릿을 두지 않는다.** 산출물이 정적 파일이라 서버 런타임 자체가 없고, 인증 후 데이터는 브라우저가 API를 직접 호출한다(D-20 · D-03). **빌드 시 주입한 값은 번들에 그대로 남으므로 접두 없는 값도 빌드 환경에 두지 않는다** |
| 앱 번들 | **앱에는 시크릿을 넣지 않는다.** 번들 복호화·문자열 추출로 값이 드러난다는 전제로 설계한다 |
| 앱 저장소 | 발급받은 토큰은 기기 보안 저장소(Keychain · Keystore)에 둔다. **평문 저장소를 쓰지 않는다** |
| 응답 | 실패 응답은 code와 message 단일 규격이며 내부 식별자·원문 오류·스택을 싣지 않는다(REQ-GLB-19) |
| 로그·에러 추적 | 개인정보 원문·금액·자격 증명·토큰을 남기지 않는다. 원인 안내가 필요해도 **변수 이름만** 언급하고 값은 남기지 않는다 |
| 소스 맵 | 운영 번들의 소스 맵을 공개 경로에 두지 않는다 |

### 배포 전 확인

1. 웹·앱 빌드 산출물에서 서버 전용 변수 이름과 값이 검색되지 않는지 확인한다 — 특히 데이터베이스 자격 · 세션 서명 키 · JWT 서명 키 · PII 암호화 키 · blind index 키 · 국세청 API 키 · SMTP 자격 · S3 자격.
2. 클라이언트 코드가 VITE_ 접두 없는 변수를 참조하지 않는지 확인한다.
3. 기동 시 환경변수 스키마 검증이 필수 값 누락에서 실제로 부팅을 실패시키는지 확인한다.
4. 응답 본문에 데이터베이스 원문 오류나 외부 API 원문 응답을 그대로 실은 경로가 없는지 확인한다.
5. 예시 파일(backend/.env.example)에 값이 아니라 키 이름만 담겼는지 확인한다.
6. **초기 SUPER_ADMIN 부트스트랩 환경변수 2개가 생성 성공 후 호스트 환경 파일에서 제거됐는지 확인한다.** 남겨 두면 최상위 권한을 만드는 자격이 상시 존재하게 된다.

검산: 번들 검사 2 + 기동 검사 1 + 응답 검사 1 + 저장소 검사 1 + 부트스트랩 검사 1 = **6항**.

## 회전·유출 대응 절차

### 정기 회전

| 시크릿 | 회전 시 영향 범위 |
|--------|------------------|
| 애플리케이션 DB 자격 | 재기동 필요. 업무 데이터 영향 없음 |
| Redis 자격 | 재기동 필요. **전원 재로그인**이 발생하나 업무 데이터는 잃지 않는다 |
| 웹 세션 서명 키 | **전 웹 세션 무효** |
| 앱 JWT 서명 키 | **전 앱 토큰 무효** — 앱 사용자 전원이 재로그인한다 |
| 초기 SUPER_ADMIN 부트스트랩 자격 | **재부여 불가**. 관리자가 이미 존재하면 부트스트랩이 다시 돌지 않으므로 환경변수를 다시 넣어도 효과가 없다. 자격을 잃었을 때의 복구 경로는 **감사 기록을 남기는 데이터베이스 조작**이며 그 절차를 운영 문서로 관리한다 |
| PII 암호화 키 | 전 행 재암호화 배치 필요. 완료 전 구버전 키 폐기 금지 |
| blind index 키 | 전 행 재색인 배치 필요. 회전 중 중복 검출 정합에 주의한다 |
| 국세청 API 키 | 사업장 등록 검증 경로 |
| SMTP 자격 | 명세서·계약서 교부와 비밀번호 재설정 메일 |
| S3 자격 | 파일 업로드·다운로드 전 경로 또는 백업 경로 |
| 레지스트리 자격 | 배포 경로 |

- **회전은 영향 범위를 먼저 확인하고 시행한다.** 세션·토큰 서명 키 회전은 사용자 전원의 재로그인을 뜻하므로 예고 없이 하지 않는다.
- 회전 이력은 audit_logs가 아니라 **운영 기록**에 남긴다 — 시크릿 값은 어느 원장에도 남기지 않는다.

### 유출 대응

```plain
① 유출 인지 — 어느 시크릿이 · 언제부터 · 어느 경로로 노출됐는지 확정한다
② 즉시 무효화 — 해당 시크릿을 회전하거나 폐기한다
   ├─ 세션·JWT 서명 키 → 전 세션·전 토큰 폐기
   ├─ DB·Redis 자격 → 자격 교체 후 재기동
   ├─ S3 자격 → 자격 교체 + 객체 접근 로그 확인
   └─ PII 암호화·blind index 키 → ⑤로 이어진다
③ 영향 범위 판정 — 그 시크릿으로 도달 가능한 데이터와 실제 접근 흔적을 대조한다
④ 개인정보 접근 가능성 판단 — 있으면 [05_location_privacy.md](./05_location_privacy.md)·[04_pii_protection.md](./04_pii_protection.md)의 유출 대응 절차로 넘긴다
⑤ PII 키 유출인 경우 — 새 키 버전으로 전 행 재암호화·재색인을 수행하고 구버전 키를 폐기한다
   재암호화가 끝나기 전에는 구버전 키를 살려 둬야 하므로 ②의 즉시 폐기 대상이 아니다
⑥ 재발 방지 — 노출 경로를 닫고 배포 전 확인 항목을 갱신한다
⑦ 기록 — 인지 시각 · 조치 · 영향 범위 · 후속 과제를 운영 기록에 남긴다
```

- **⑤가 다른 항목과 다른 이유는 되돌릴 수 없기 때문이다.** 다른 시크릿은 폐기가 곧 차단이지만, 암호화 키는 폐기가 곧 데이터 소실이다.
- **키 유출과 데이터 유출은 다른 사건이다.** 키가 새어도 암호문에 접근한 흔적이 없으면 개인정보 유출은 아니며, 그 판단 근거를 ③에서 남긴다. 반대로 판단이 서지 않으면 **유출로 간주하고 통지 절차를 밟는다**([06_threat_model.md](./06_threat_model.md)).

## 잔여 위험

| # | 위험 | 근거 | 판단 |
|:-:|------|------|------|
| 1 | 키가 호스트 환경 파일에 평문으로 존재한다 | 키 관리 서비스를 v1에 두지 않는다 | **의식적 선택** — 단일 인스턴스 운영에서 관리 서비스가 운영 대상을 하나 더 만든다. 호스트 접근 자체를 최소 인원으로 제한하고 파일 권한을 좁히는 것이 완화책이다 |
| 2 | 호스트 접근 권한을 가진 운영자는 전 시크릿에 접근한다 | 환경 파일을 읽을 수 있으면 키를 전부 읽는다 | **수용** — 사전 통제가 없으므로 접근 인원 최소화와 접근 기록이 사후 통제를 맡는다 |
| 3 | 백업 객체에 마스킹되지 않은 원본이 담긴다 | 논리 백업은 암호문·마스킹값·평문 컬럼을 그대로 옮긴다 | **등재** — 서버 측 암호화 + 백업 전용 자격 분리로 완화한다. **PII 암호화 키는 백업에 담기지 않으므로** 백업 단독으로는 주민번호·계좌 원문이 복원되지 않는다 |
| 4 | blind index 키 유출 시 주민번호 보유 여부를 대입으로 확인할 수 있다 | 주민번호는 후보 공간이 좁아 사전 공격에 취약하다 | **등재** — 암호화 키와 동일 등급으로 취급하고 회전 절차를 갖춘다 |
| 5 | 시크릿 값의 실제 강도·길이 규약을 v1에 고정하지 않았다 | 생성 방식은 구현 착수 시 정한다 | **이월** — 서명 키·암호화 키는 암호학적 난수 생성기로 만들고 키 길이를 알고리즘 권장값으로 고정한다는 원칙만 지금 고정한다 |
| 6 | 개발 환경과 운영 환경의 키가 물리적으로 분리돼 있는지 자동 검사되지 않는다 | 환경 파일이 사람 손으로 관리된다 | **등재** — 개발 환경에 운영 데이터를 두지 않는다는 규칙([../04_architecture/08_deployment_topology.md](../04_architecture/08_deployment_topology.md))이 피해 범위를 좁힌다 |
| 7 | 에러 추적 서비스가 외부 전송 표면이다 | 스택 트레이스에 예기치 않은 값이 실릴 수 있다 | **수용** — 전송 항목을 스택 트레이스와 에러 코드로 한정하고 개인정보 필드를 차단한다. 개인정보 위탁 대상 판단이 필요하므로 개인정보 처리방침의 수탁 고지와 함께 관리한다(ADR-23) |
