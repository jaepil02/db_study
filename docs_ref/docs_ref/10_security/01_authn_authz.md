인증 축은 표면에 따라 둘이다 — **관리자 웹·시스템 웹은 서버 세션 쿠키**, **직원 앱은 JWT**다. 두 축은 자격 증명 전달 방식만 다르고 그 뒤의 인가·격리 경로는 같다. 본 문서는 그 구조를 다시 정의하지 않고 **보안 관점의 강제 규약과 잔여 위험**만 고정한다.

## 핵심 원칙

**1. 인증 실패는 분기 없이 단일 응답으로 흡수한다.** 아이디 미존재와 비밀번호 불일치를 auth.invalid_credentials/401 하나로 되돌리고 비밀번호 재설정 요청은 계정 존재 여부와 무관하게 같은 응답을 낸다. 근거는 이 제품의 로그인 식별자가 username이라 응답이 갈리는 순간 **재직자 계정 조회 도구**가 되기 때문이다.

**2. 자격 증명 검증 통과는 인증 성립이 아니다.** 계정 상태 선검증이 컨텍스트 발급보다 앞선다(REQ-AUT-09). 정지·탈퇴 계정에 세션을 먼저 발급하면 그 세션이 살아 있는 동안 접근이 열리고, 제재의 효력이 세션 수명만큼 늦어진다.

**3. 가드는 계층이고 각 계층의 신뢰 수준이 다르다.** 신뢰 계층은 **서비스 가드 · RLS · 제약과 트리거 셋**이며 서비스 가드가 1차 통제이고 RLS가 최종 방어다. **클라이언트 라우터 가드는 계층 수에 넣지 않는다** — 웹이 정적 산출물이라 요청을 가로채는 서버 계층이 없고 브라우저 안의 판정은 언제나 우회 가능하기 때문이다(D-20 · ADR-24). 이 서열을 문서와 웹 소스 주석에 함께 명문화한다 — **클라이언트 가드에 권한 판정을 실으면 그것을 우회하는 경로가 곧 취약점**이 된다.

**4. 판정 실패는 통과가 아니라 거부다.** 쿠키 파싱 오류 · 세션 컨텍스트 미주입 · 역할 조회 실패는 전부 불통과다. RLS 헬퍼는 컨텍스트가 비면 NULL을 반환해 기본 거부로 떨어지므로, 주입 누락이 유출이 아니라 조회 실패로 나타난다.

**5. 상태 변경은 다음 요청에서 즉시 걸린다.** 계정 정지는 세션 폐기와 RLS 헬퍼 양쪽에 반영된다 — users.status 갱신이 profiles.status로 전파되고 is_workplace_member()가 그 값을 보므로, 한 컬럼 갱신이 전 사업장의 행 가시성을 닫는다.

**6. 재인증은 신원 재확인이지 기기 확인이 아니다.** 생체 인증을 재인증 수단으로 인정하지 않는다 — 생체 등록은 기기 소유자 단위라 계정 소유자와 일치한다는 보장이 없다.

## 인증 경계

계약 정본은 [../04_architecture/02_authn_session.md](../04_architecture/02_authn_session.md)이며 본 절은 **보안 속성만** 옮긴다.

| 항목 | 웹(관리자 웹 · 시스템 웹) | 직원 앱 |
|------|--------------------------|---------|
| 자격 증명 보관 | 서버 Redis 세션 스토어. 브라우저에는 세션 식별자만 | 기기 보안 저장소(Keychain · Keystore). **평문 저장소를 쓰지 않는다** |
| 쿠키 속성 | **HttpOnly · Secure · SameSite=Lax · Domain=.{domain} · Path=/** | 해당 없음 |
| 스크립트 접근 | 불가(HttpOnly) — access token을 JavaScript에 노출하지 않는다 | 앱 코드만 접근 |
| 상태 변경 보호 | **CSRF 토큰 필수**. 부재·불일치는 auth.csrf_token_invalid/403 | 불요 — 헤더 인증은 브라우저가 자동 전송하지 않는다 |
| 수명 관리 | 세션 TTL 만료 · 활동 시 연장 | access 만료 임박 시 **refresh 회전 재발급** |
| 폐기 수단 | 세션 키 삭제(즉시 반영) | refresh revoke + **access 블랙리스트 등재**(TTL = 토큰 잔여 수명) |
| 실시간 채널 인증 | 상위 도메인 쿠키가 SSE 연결에 자동 실린다 | Authorization 헤더 |

- **SameSite를 None까지 풀지 않는다.** 서드파티 컨텍스트 전송을 열면 CSRF 표면이 그만큼 넓어진다. 쿠키 도메인을 상위로 올리는 것은 웹과 API가 서로 다른 서브도메인에 있다는 D-03의 실무적 귀결이며, 그 대가로 CSRF 토큰을 필수로 둔다(ADR-02).
- **블랙리스트 항목의 TTL을 토큰 잔여 수명으로 맞춘다.** 영구 보관하면 항목이 무한 증식하고, 짧게 잡으면 폐기된 토큰이 되살아난다.
- **웹에 토큰을 쓰지 않고 앱에 쿠키를 쓰지 않는다**(ADR-05). 각 표면이 자기 플랫폼의 기본 보관 수단을 쓴다 — 웹의 토큰은 어느 저장소를 골라도 스크립트 접근 위험이 남는다.
- 세션·블랙리스트·재인증 토큰은 전부 Redis에 두고 업무 데이터베이스에 두지 않는다(ADR-11). **유실 시 전원 재로그인이 필요하지만 업무 데이터는 잃지 않는다** — 이 성격이 Redis를 백업 대상에서 제외하는 근거다.

## 가드 계층

신뢰 가드는 **3계층**이다. 그 앞에 놓이는 클라이언트 라우터 가드는 계층으로 세지 않는다 — 웹 산출물이 정적이라 요청을 가로채는 서버 계층이 없기 때문이다(D-20).

| 계층 | 위치 | 판정 | 우회 가능성 | 실패 시 |
|------|------|------|-------------|---------|
| **보조**. 클라이언트 라우터 가드 | web_front 브라우저 라우터 — 보호 경로 진입 | **세션 성립 여부만.** 유효성·역할·사업장을 판정하지 않는다 | **가능** — 브라우저 안의 판정이며 앱과 API 직접 호출은 애초에 타지 않는다 | 로그인 화면으로 보낸다. 복귀 대상은 **내부 경로만 허용**해 오픈 리다이렉트를 차단한다 |
| 1. 서비스 가드 | 보안 필터 체인·서비스 레이어 | 인증 컨텍스트 · 계정 상태 · ACTIVE 멤버십 · 요구 역할 · 사업장 쓰기 가능 여부 · 자원의 사업장 소속 | 불가 — 모든 업무 요청의 유일한 입구 | **구분 가능한 도메인 코드** — auth.workplace_forbidden/403 · auth.platform_forbidden/403 · workplace.unavailable/409 |
| 2. RLS 정책 | PostgreSQL — **61테이블** ENABLE + FORCE · 정책 **173개** · 헬퍼 **43종** | 행 단위 가시성·변경 가능성 | 불가 — 앱 롤이 NOSUPERUSER · NOBYPASSRLS이며 테이블 소유자가 아니다 | 0행 조회 또는 0행 갱신. 애플리케이션은 이를 **부재가 아니라 결함 신호**로 다룬다 |
| 3. 제약·트리거 | DB 제약 · BEFORE 트리거 가드 | 컬럼 단위 제한 · 상태 전이 · 확정 불변 · 사유 필수 | 불가 | 제약 위반으로 트랜잭션을 되돌린다 |

검산: 신뢰 계층 3(서비스 · RLS · 제약과 트리거) + 보조 1 = 표 **4행**이며 **신뢰 계층 수는 3**이다.

- **클라이언트 가드는 신뢰 경계가 아니다.** 세션 쿠키가 HttpOnly라 스크립트가 읽을 수 없으므로 판정 근거는 서버 세션 조회 응답이며, **그 결과도 화면 전환에만 쓰고 인가 근거로 쓰지 않는다.** 판정을 쉽게 하려고 세션 쿠키를 스크립트가 읽게 푸는 방향으로 해결하지 않는다 — 그 순간 13번 위협(세션 탈취)의 통제가 무너진다. 세션 유무 판정 방식의 계약 정본은 [../04_architecture/02_authn_session.md](../04_architecture/02_authn_session.md)다.
- 쿠키가 있으나 만료됐거나 계정이 정지된 경우 **화면은 열리고 첫 API 호출이 거부되는 동작이 정상**이다(REQ-AUT-12).
- **1차 가드가 있어야 하는 이유는 사용자 안내다.** RLS만 두면 "권한 없음"과 "데이터 없음"이 구분되지 않아 조치 가능한 오류와 정상 상태를 분간하지 못한다(ADR-08).
- **2차 방어가 있어야 하는 이유는 코드 결함이다.** 새 엔드포인트 하나가 사업장 스코프 검사를 빠뜨려도 남의 사업장 행에 닿지 않게 하는 것이 RLS의 목적이며, 이를 "혹시 모를 보험"으로 두지 않는다.
- **변경 결과 행 수를 확인한다.** RLS가 막은 UPDATE는 오류가 아니라 0행 갱신으로 끝나므로, 영향 행 수를 검사하지 않으면 인가 실패가 성공으로 보인다.
- 클라이언트의 화면 노출 제어는 판정이 아니다. 네비게이션에서 감춘 화면도 직접 진입하면 1·2계층이 다시 거부한다.

## 계정 생애주기 통제

| 단계 | 통제 |
|------|------|
| 가입 | 활성 버전의 **약관·개인정보 2종 문서 동의가 성립 조건**이다(REQ-AUT-03 · D-19). 필수 누락은 auth.consent_required/422. **위치정보는 별도 선택 동의**라 미동의는 가입을 막지 않고 GPS 체크인만 차단한다(privacy.location_consent_required/403). 자격 증명과 프로필은 단일 트랜잭션으로 생성하고 실패 시 전체 롤백한다 |
| 비밀번호 저장 | **argon2id**로 저장하고 **원문·해시를 로그·응답·감사 전후값 어디에도 남기지 않는다**(REQ-AUT-02). 파라미터는 **메모리 19MiB(19456KiB) · 반복 2 · 병렬 1 · salt 16바이트 · 해시 32바이트**이며 근거는 OWASP Password Storage 권고의 최소 조합이다. **프레임워크 기본값을 그대로 쓰지 않는다** — 널리 쓰이는 기본값이 메모리 16MiB라 권고 최소에 미달한다 |
| 비밀번호 변경 | **요청에 현재 비밀번호를 함께 받아 검증**하고 현재와 상이함을 확인한 뒤 security_events에 기록한다. 변경 후 현재 세션 유지와 전 기기 로그아웃 중 하나를 사용자가 고른다. **재인증 토큰을 발급·소비하지 않으므로 재인증 대상 작업에 들어가지 않는다**(아래 재인증 통제 절) |
| 재설정 | 토큰을 **해시로 저장**하고 만료(1시간)와 사용 여부를 함께 검증한다. 성공 시 **기존 세션과 refresh 토큰을 전체 폐기**하며 사용자 선택을 두지 않는다 |
| 정지(SUSPENDED) | 플랫폼 ADMIN 이상이 사유와 해제 예정일을 입력하고 **기존 세션을 즉시 폐기**한다(REQ-AUT-18). 정지 중에는 전 권한 헬퍼가 거부를 반환한다. suspended_until 경과 계정은 접근 시점과 정기작업 autoUnsuspendAccounts 양쪽에서 ACTIVE로 복귀한다 |
| 탈퇴 차단 | 재인증 선행. **OWNER로 소유한 사업장이 하나라도 있으면 차단**한다(auth.owner_must_transfer/409) — 양도는 v1에 두지 않으므로 폐쇄 경로로 안내한다. CLOSED 사업장은 소유 수에서 제외한다 |
| 탈퇴 처리 | status = DELETED · 프로필 비식별화 · 세션과 refresh 전체 폐기 · 전 멤버십 비활성화를 단일 트랜잭션으로 수행한다. **법정 보존 대상(급여 · 근태 · 근로계약 · 명세서 · 임금대장)은 삭제하지 않는다** |
| 탈퇴 후 | DELETED는 로그인·재설정·초대 수락을 모두 차단한다(auth.account_deleted/403). **DELETED에서 다른 상태로의 전이는 불가능**하다 |
| username 재사용 | 정책값으로 관리하며 **기본은 금지**다 — 재사용을 허용하면 탈퇴자에게 온 초대·알림·감사 기록이 새 사람에게 귀속될 여지가 생긴다 |
| 전이 감사 | 상태 변경은 account_status_events와 audit_logs에 전후 상태·사유·처리자를 남긴다. **마지막 SUPER_ADMIN 보유 계정의 정지·삭제는 차단**한다(system.last_super_admin/409) |

- **정지·탈퇴가 2단 방어 양쪽에 반영되는 것이 이 절의 핵심이다.** 세션 폐기만 두면 아직 만료되지 않은 앱 토큰이 남고, RLS 헬퍼만 두면 세션이 살아 있는 동안 인증 후 화면이 열린다.
- 로그인 성공·실패, 비밀번호 변경, 재설정 시도, 재인증은 security_events에 시각·IP·user agent로 남기되 **비밀번호 원문·해시를 남기지 않는다**. 프로필의 이름·연락처 변경(PROFILE_CHANGE)과 복구 이메일 변경(RECOVERY_EMAIL_CHANGE)도 같은 원장에 남는다. 기록 종류의 전수는 [../05_database/01_auth.md](../05_database/01_auth.md) security_events가 정본이며 이 테이블은 append-only다.
- **멤버십 상실은 세션을 끊지 않는다.** 세션은 유지되고 해당 사업장 스코프 요청만 거부되며, 본인 소유권으로 인가되는 법정문서 열람은 계속 열린다([02_rls_isolation.md](./02_rls_isolation.md)).

## 재인증 통제

민감 작업은 비밀번호 재인증을 선행한다(REQ-AUT-25). 계약 정본은 [../04_architecture/02_authn_session.md](../04_architecture/02_authn_session.md)다.

| 항목 | 계약 |
|------|------|
| 대상 작업 **5종** | 민감정보 원문 복호화(REQ-HRM-04) · 사업장 폐쇄(REQ-WRK-36) · 계정 탈퇴(REQ-AUT-20) · 민감 문서 다운로드(REQ-HRM-24) · **프로필 연락처·복구 이메일 변경**(REQ-AUT-26). 검산: PII 축 2 + 계정 축 2 + 사업장 축 1 = **5** |
| 유효 시간 | **5분** |
| 소비 단위 | **작업 단위 1회 소비**다. 5분 안이라도 한 번 쓴 토큰으로 다른 작업을 수행할 수 없다 |
| 저장 위치 | Redis. 회전이 잦고 법정 보존 대상이 아니라 데이터베이스에 쓰지 않는다 |
| 미충족 응답 | auth.reauth_required/401 |
| 시도 제한 | **5회 / 5분**. 초과 시 재인증 창을 닫고 재로그인을 요구한다 |
| 대체 수단 | **생체 인증을 재인증 수단으로 인정하지 않는다** |
| 동반 요구 | 복호화·민감 문서 다운로드는 재인증 외에 **사유 입력 · 감사 로그 기록 · 서버 1회성 응답**을 함께 충족해야 한다([04_pii_protection.md](./04_pii_protection.md)) |

- **작업 단위 소비가 시간 제한보다 중요하다.** 시간만 두면 복호화 한 번을 위해 받은 재인증으로 5분 안에 사업장 폐쇄까지 수행할 수 있다.
- 재인증은 **인가를 대체하지 않는다** — 재인증을 통과해도 역할과 RLS 판정을 그대로 지난다.
- **비밀번호 변경의 현재 비밀번호 확인은 재인증이 아니다.** 변경 요청 자체가 현재 비밀번호를 함께 받아 검증하는 것이며 재인증 토큰을 발급하지도 소비하지도 않는다. 따라서 대상 작업의 검산에 들어가지 않고 auth.reauth_required/401과 재인증 5회/5분 한도의 대상도 아니다.

## rate limit과 사용자 열거 차단

인증 경로는 자동화 시도의 첫 표적이다. 한도의 정본은 [../04_architecture/02_authn_session.md](../04_architecture/02_authn_session.md)이며 REQ-NFR-14가 같은 값을 인용한다.

| 대상 | 기준 키 | 한도 |
|------|--------|------|
| 로그인 실패 | (IP, username) 조합 | **10회 / 10분** |
| 비밀번호 재설정 요청 | username 또는 recovery_email | **5회 / 1시간** |
| 아이디 중복 확인 | IP | **30회 / 1분** |
| 재인증 시도 | 사용자 | **5회 / 5분** |
| 인증 후 일반 API | 사용자 | **300회 / 1분** |
| **사업자 진위확인 호출** | (사업장, 일) | **20회 / 1일** |
| **다운로드 토큰 발급** | (사용자, 시간) | **60회 / 1시간** |

검산: 인증 전 축 3 + 인증 후 축 2 + 외부 연동·파일 축 2 = **7축**.

| 열거 차단 지점 | 규약 |
|---------------|------|
| 로그인 | 아이디 미존재와 비밀번호 불일치를 **auth.invalid_credentials/401로 통일**한다(REQ-AUT-10) |
| 응답 시간 | 자격 증명 검증 경로의 비용을 실패·성공에서 같게 유지한다 — 지연 차이가 계정 존재 여부를 흘린다 |
| 비밀번호 재설정 | **계정 존재 여부와 무관하게 같은 응답**을 반환한다. 메일 발송 실패도 사용자 응답은 성공과 동일하게 유지하고 실패 로그만 남긴다 |
| 아이디 중복 확인 | 형식 검증을 통과한 요청만 조회하고 **가용 여부 불리언만** 반환한다 — 계정 상태·프로필을 노출하지 않는다 |
| 초대 | 타인 대상 초대는 **행 존재조차 노출하지 않는다**(RLS 정책 #29) |
| 사업장 | 비멤버에게 사업장 행 존재를 노출하지 않는다(정책 #20) — 사업자등록번호로 타사 사업장을 탐지하는 경로를 막는다 |
| 비소유 자원 | RLS가 0행으로 반환하므로 거부가 아니라 부재로 보인다. 앱은 **404로 통일**해 표면화한다 |

- **뒤 두 축은 인증 경로가 아니라 비용·유출 축이다.** 사업자 진위확인은 외부 API 호출 비용과 사업자등록번호 대량 조회를 억제하고, 다운로드 토큰 발급 한도는 1회용 토큰을 대량으로 찍어 내는 경로를 좁힌다.
- **429는 인증 실패와 구분되는 상태다.** 잠금 중 올바른 비밀번호를 넣어도 401이 아니라 429가 나가야 잠금 상태가 사용자에게 드러난다.
- 카운터는 Redis에 두고 창 만료를 TTL로 처리한다. 별도 정리 작업을 두지 않는다.
- **아이디 중복 확인은 열거 방지와 정면으로 충돌하는 기능이다.** 가입 사용성을 위해 남기되 IP 단위 한도와 불리언 응답으로 조회 도구화를 억제하며, 이 상충을 잔여 위험으로 등재한다.

## 인증·인가 에러 코드

전수 정본은 [../09_glossary/02_error_codes.md](../09_glossary/02_error_codes.md)(**120종 · 16네임스페이스**)이며 아래는 인증·인가 축의 auth 네임스페이스 요약이다.

| 코드 | HTTP | 발생 |
|------|:----:|------|
| auth.invalid_credentials | 401 | 아이디 미존재·비밀번호 불일치 **통일 응답** |
| auth.token_invalid | 401 | access token 만료·revoke·서명 불일치 |
| auth.reauth_required | 401 | 민감 작업 재인증 미충족 |
| auth.csrf_token_invalid | 403 | 웹 세션 채널 상태변경 요청의 CSRF 토큰 부재·불일치 — 앱 JWT 채널은 대상 아님 |
| auth.account_suspended | 403 | SUSPENDED 계정의 로그인·접근 |
| auth.account_deleted | 403 | DELETED 계정의 로그인·접근 |
| auth.workplace_forbidden | 403 | 요청 사업장과 멤버십·역할 불일치 |
| auth.platform_forbidden | 403 | 시스템 웹 진입 시 **플랫폼 권한 자체가 없음** |
| auth.consent_required | 422 | 필수 동의 또는 개정 재동의 누락 |
| auth.weak_password | 422 | 비밀번호 정책 미충족 |
| auth.password_unchanged | 422 | 새 비밀번호가 현재와 동일 |
| auth.reset_token_invalid | 400 | 재설정 토큰 만료·사용완료·불일치 |
| auth.username_taken | 409 | username 중복 |
| auth.phone_taken | 409 | 휴대폰 중복 — 부분 유니크, DELETED 제외 |
| auth.owner_must_transfer | 409 | OWNER 소유 사업장 존재로 탈퇴 차단 |

검산: 401 축 3 + 403 축 5 + 422 축 3 + 400 축 1 + 409 축 3 = **15종**. rate limit 초과는 auth 네임스페이스가 아니라 common.rate_limited/429이고, 플랫폼 권한 부족은 system.permission_denied/403이다.

- **플랫폼 권한 자체가 없는 상태와 역할 레벨이 부족한 상태를 다른 코드로 구분한다** — 전자는 시스템 웹 진입 자체가 막히고 후자는 진입 후 특정 액션만 막힌다.
- 응답 본문은 code와 message 단일 규격이며 **내부 식별자·원문 오류·스택을 싣지 않는다**(REQ-GLB-19).

| 1 | 아이디 중복 확인 API가 username 존재 여부를 그대로 알려준다 | 가입 사용성을 위해 가용 여부를 반환하는 기능이라 열거 차단과 목적이 상충한다 | **의식적 선택** — IP 단위 30회/1분 한도 · 불리언 단일 응답 · 형식 검증 통과분만 조회 |
| 2 | 클라이언트 라우터 가드를 우회한 화면 진입을 막을 수 없다 | 웹이 정적 산출물이라 요청을 가로채는 서버 계층이 없고, 브라우저 안의 판정은 우회 가능하다(D-20) | **설계** — 데이터는 서비스 가드와 RLS가 막는다. 화면이 열리고 첫 호출이 거부되는 것이 정상 동작이며, 화면 자체에는 사업장 데이터가 들어 있지 않다 |
| 3 | ~~웹 세션 TTL과 앱 access 토큰 수명의 구체 값이 확정돼 있지 않다~~ | 회전·폐기 메커니즘은 고정됐고 수치는 구현 착수 시점에 정하기로 했다 | **해소(2026-09-07)** — 웹 유휴 2시간 · 웹 절대 상한 12시간 · 앱 access 15분 · 앱 refresh 14일로 확정했고 정본은 [../04_architecture/02_authn_session.md](../04_architecture/02_authn_session.md) 컨텍스트 수명 절이다. **절대 상한은 그 확정에서 신설된 계약**이며 활동 시 연장만 두면 열어 둔 탭이 무기한 유효해지는 구멍을 닫는다 |
| 4 | 기기 도난 시 앱 refresh 토큰이 그대로 쓰인다 | 기기 보안 저장소는 OS 잠금 해제 이후를 보호하지 않는다 | **수용** — 사용자 주도 전 기기 로그아웃과 관리자 정지 시 전 토큰 revoke로 완화한다 |
| 5 | 2단계 인증을 v1에 두지 않는다 | 비밀번호 단일 요소이며 민감 작업만 재인증으로 보강한다 | **의식적 선택** — 타깃 사용자가 1~30인 사업장이라 도입 비용 대비 이탈이 크다. 재인증 대상 작업이 고위험 작업을 좁힌다 |
| 6 | 정지 직후 발급된 앱 access 토큰의 잔여 수명 동안 블랙리스트 조회가 유일한 차단점이다 | 토큰은 자체 검증형이라 폐기가 조회 의존이다 | **수용** — 블랙리스트 조회 실패를 통과가 아니라 거부로 처리하고, RLS 헬퍼가 프로필 상태를 다시 본다 |
