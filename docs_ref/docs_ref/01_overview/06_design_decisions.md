이 문서는 insadesk v1의 **제품 결정 D-NN 채번 정본**이다. 전 문서는 결정을 여기서만 채번하고 다른 자리에서는 링크로 인용한다.

**기술 구현 결정의 정본은 [../04_architecture/09_decision_records.md](../04_architecture/09_decision_records.md)(ADR-NN)다.** 두 체계는 축이 다르다 — **D는 제품·범위 결정**(무엇을 만들고 무엇을 안 만드는가 · 어떤 표면과 저장소로 나누는가 · 계산과 권한의 원칙을 어떻게 세우는가)이고, **ADR은 기술 결정**(어떤 라이브러리·스케줄러·스토리지·CI를 쓰는가 · 어떤 구현 구조를 택하는가)이다. D에서 정한 방향의 기술 세부는 여기서 재론하지 않고 ADR이 이어받는다.

**D 총수는 24건**(D-01~D-24 · 결번 없음)이다. 채번 규칙은 셋이다.

- 각 결정은 **무엇을 정했는가**와 **왜 그 대안을 버렸는가**를 함께 적는다 — 이유가 남지 않으면 나중에 같은 논의를 반복하거나 결정을 조용히 뒤집게 된다.
- **뒤집힌 결정은 지우지 않고 대체 관계를 표기한다.** 원문을 남겨야 왜 한 번 그렇게 갔다가 되돌렸는지가 보존된다. 대체된 결정의 결정 칸은 **상태 한 줄 + 보존된 원 결정문** 순서로 적으며, 구현자는 상태 줄이 지목하는 현행 결정을 따른다.
- **번호는 확정 순서이고 배치는 주제별이다.** D-01~D-06이 사용자 확정 결정과 저장소 구조, D-07~D-10이 범위 결정, D-11~D-18이 원천 문서의 구조적 판정, D-19가 검수 중 확정한 교정 결정, D-20이 웹 프론트엔드 스택 전환 결정, **D-21이 백엔드 스택 전환 결정**, **D-22가 관리자·시스템 웹의 셸 구조 결정**, **D-23이 v1 범위 확장 결정**, **D-24가 콘텐츠 영역 구조 결정**이며, 아래 절은 주제로 묶여 있어 번호가 절 사이를 건너뛴다.

| **D-24** | 관리자·시스템 웹 콘텐츠 영역 = 뷰포트 고정 | **상태: 현행(2026-09-16 확정 — D-22의 탭 워크스페이스 위에 서며 어떤 결정도 대체하지 않는다).** 폭 1024 이상에서 **콘텐츠 영역(사이드바·헤더를 뺀 자리) 자체는 스크롤하지 않는다** — 스크롤은 표 데이터 영역과 이름 붙은 구획(상세 페인 · 섹션 본문 · 카드 본문)만 갖는다. ① **표는 영역을 채운다** — 남는 가로 폭은 이름·사유 같은 글자 열이 흡수하고 숫자·상태 열은 제 폭을 지킨다. ② **건수는 표 우상단**(열 선택 왼쪽 N건 — 조건 결과 전체 건수)이고 목록은 200건씩 **무한 스크롤**로 이어 읽으며 페이지 번호·하단 안내 문구를 두지 않는다. 표 밀도 선택을 두지 않는다. ③ **툴바 필터는 검색형 콤보박스**다 — 정적 선택지는 부분 문자열·초성, 서버 선택지는 입력 중 부분 일치 조회. ④ **설명형 안내는 툴바의 안내 아이콘 팝오버**로 옮기고 차단 사유 · 법정·책임 고지만 한 줄로 남긴다. ⑤ 탭은 비활성 탭도 자기 칸을 갖는 박스형이며 프로필은 헤더 우측 한 곳에만 둔다. ⑥ 폭 1024 미만은 표가 카드로 · 분할이 위아래로 바뀌며 페이지 스크롤을 허용한다. 화면 규격의 정본은 [../07_screen/01_standards.md](../07_screen/01_standards.md) §3 · §4 · §5다 | ① **표는 내용만큼만 차지하는 규약 유지**를 버렸다 — 4행짜리 목록이 뷰포트 끝까지 늘어나지 않는 이점은 있었으나 **대부분의 목록이 화면 폭의 절반에서 멈추고 나머지가 빈 채로 남아** 표가 작은 화면에서 쓰는 것처럼 보였다. 행이 적어 표 안이 비는 편이 표 밖이 비는 것보다 읽기 흐름이 끊기지 않는다. ② **페이지 스크롤을 허용하는 안**도 버렸다 — 필터·툴바·합계 행이 스크롤과 함께 사라져 긴 목록의 아래쪽에서 조건을 바꾸려면 다시 올라가야 하고, 상세 페인과 목록이 함께 밀려 "목록을 훑으며 하나씩 처리"하는 동선이 끊긴다. ③ **페이지 번호 방식으로 돌아가는 안**을 버렸다 — 일괄 선택과 키보드 동선이 쪽 경계에서 끊긴다 |
| **D-22** | 관리자·시스템 웹 셸 = 탭 워크스페이스 | **상태: 현행(2026-09-10 확정 — D-20의 단일 앱 축 위에 서며 어떤 결정도 대체하지 않는다).** 관리자 웹과 시스템 웹의 콘텐츠 영역은 **브라우저 탭형 다중 문서 셸**이다. 화면을 열면 탭이 생기고 다른 화면으로 가도 **이전 화면이 닫히지 않는다.** ① **탭 동일성 = 화면 코드** — 같은 화면의 탭은 하나이며 **상세는 탭이 아니라 그 탭의 파라미터**다(직원 상세·퇴사가 직원 목록 탭의 페인으로 열리는 것이 그 귀결이며 **화면 코드·라우트·딥링크는 불변**이다). ② **URL은 언제나 활성 탭의 경로** — 라우터가 탭 집합의 정본이 아니라 활성 탭의 명령 버스다. 딥링크·새로고침·공유가 탭 도입 전과 같게 동작한다. ③ **비활성 탭을 DOM에 남긴다** — 필터·스크롤·펼친 행이 보존되지 않으면 탭을 유지할 이유가 없다. 상한을 넘으면 오래 쓰지 않은 탭부터 언마운트하고 탭 줄에는 남긴다. ④ **탭 스코프 위치 훅** — 화면은 라우터 위치 훅을 직접 쓰지 않는다. 라우터 훅은 언제나 활성 탭의 주소를 돌려주므로 **감춰진 탭이 남의 필터를 자기 것으로 읽어 잘못된 목록을 부른다.** ⑤ **세션 복원과 미저장 가드** — 열린 탭 집합은 브라우저 세션 동안 복원되고, 저장되지 않은 입력이 있는 탭은 닫을 때 확인을 받는다. ⑥ **적용 범위는 관리자 웹·시스템 웹뿐**이다 — 공개 페이지와 직원 앱은 대상이 아니고 768 미만에서는 탭 줄을 두지 않는다. 화면 규격의 정본은 [../07_screen/01_standards.md](../07_screen/01_standards.md) §4-4다 | ① **단일 문서 셸 유지**(한 번에 한 화면)를 버렸다 — 이 제품의 관리자 동선은 **한 화면에서 끝나지 않는다.** 근태 마감이 막히면 차단 사유를 보고 근태 현황으로 갔다가 수정 승인을 처리하고 돌아와야 하는데, 매 이동마다 기간·직원 필터와 스크롤 위치를 다시 만들면 **화면 사이를 오가는 비용이 판단 비용을 넘는다.** ② **브라우저 탭 여러 개로 대신하는 안**도 버렸다 — 탭마다 애플리케이션이 통째로 다시 뜨고 조회 캐시·세션 상태가 갈라지며, **활성 사업장을 한 탭에서 바꾸면 다른 탭이 조용히 다른 사업장을 보고 있게 된다**(D-20의 사업장 스코프 캐시 격리가 탭 하나 안에서만 성립한다). ③ **화면 안에 서브탭을 두는 안**(화면마다 자체 다중 문서)도 버렸다 — 같은 장치가 화면 수만큼 다시 만들어지고 어느 화면이 무엇을 기억하는지 사용자가 화면마다 다시 배우게 된다. ④ **탭을 라우터 히스토리로 표현하는 안**을 버렸다 — 뒤로가기가 탭 닫기인지 화면 안 이동인지 갈리지 않아, 되돌릴 수 없는 작업의 확인 단계에서 뒤로가기가 무엇을 취소하는지 사용자가 예측할 수 없다 |
| **D-20** | 웹 프론트엔드 = React · Vite · React Router 단일 앱 | **상태: 현행(2026-08-08 확정 — D-01·D-04를 대체하고 D-02의 수단을 개정한다).** web_front는 **React + Vite + React Router(framework mode) 단일 앱**이며 Next.js를 쓰지 않는다. ① **공개 페이지 프리렌더** — 라우터 설정의 사전 렌더 목록으로 랜딩(/)과 요금제(/pricing)를 빌드 시점 정적 HTML로 굽는다(검색 노출 확보). 요금제 수치는 프리렌더 셸 + 클라이언트 조회로 최신을 보장한다. ② **법정 문서는 프리렌더하지 않는다** — 약관·개인정보·위치정보 문서는 클라이언트가 활성 버전을 조회해 항상 최신을 표시한다. 활성 버전 전환(SYS-11) 시 재빌드·재검증이 불필요해지고 게시 문안과 동의 이력 버전이 갈릴 위험이 원천 제거된다. ③ **미인증 인증 화면 4본**(가입 · 로그인 · 비밀번호 재설정 · 동의)은 단일 페이지 앱 축에 속하며 프리렌더 대상이 아니다 — 화면 코드와 표면 병기는 불변이다. ④ 나머지 전 경로(관리자 웹 · 시스템 웹)는 단일 페이지 앱 fallback으로 서빙한다. **산출물 하나 · Vercel 프로젝트 1개 · web_front 1폴더 · 웹 오리진 1개**이므로 D-03 · D-06은 그대로 유지된다. ⑤ **라우트 보호** — 요청을 가로채는 서버 미들웨어 계층이 없다. 클라이언트 라우터 가드는 사용성 보조이며 최종 강제는 서버 검증 + 행 단위 보안 2차 방어다. 신뢰 가드 계층은 4 → **3계층(서비스 → RLS → 제약·트리거) + 클라이언트 보조**로 재정의한다 | ① **단일 Next.js 앱 유지(D-01)**를 버렸다 — 서버 렌더링·서버 변이 경로를 쓰지 않기로 이미 정해 둔 설계(D-03 · D-04)에서 서버 실행 런타임을 전제하는 프레임워크를 유지하면 쓰지 않는 계층이 배포·보안 경계에 남고, 그 계층이 있다는 이유로 인가 판정이 다시 흩어진다. 기술 선정의 상세 근거는 [../04_architecture/09_decision_records.md](../04_architecture/09_decision_records.md) ADR-24가 소유한다. ② **공개 페이지를 별도 정적 사이트로 분리**하는 안도 버렸다 — 디자인 토큰·폰트·에러 정제가 두 벌이 되고 약관 게시 표면이 이원화돼 활성 버전이 갈린다(D-02가 버린 대안 ②의 위험이 그대로 재발한다). ③ **법정 문서까지 프리렌더**하는 안을 버렸다 — 활성 버전을 바꿀 때마다 재빌드·재배포 트리거가 필요하고, 트리거가 실패하는 창에서 게시 문안과 동의 이력의 버전이 어긋난다 |
| **D-01** | 단일 Next.js 앱 · 라우트 그룹 분리 | **상태: 대체됨(2026-08-08 → D-20).** 아래는 보존된 원 결정문이며 현행 계약이 아니다 — 이 결정이 버린 대안 ①(앱 분리)은 D-20에서도 채택되지 않았고, 뒤집힌 것은 프레임워크와 진입 분기 수단이다. 공개 웹 · 관리자 웹 · 시스템 웹을 **하나의 Next.js 애플리케이션**에 라우트 그룹 (public) · (admin) · (system)으로 나누고 미들웨어가 진입을 분기한다. | **D-05** | ORM = Prisma · 스키마 정본은 raw SQL | **상태: 대체됨(2026-09-06 → D-21).** 아래는 보존된 원 결정문이며 현행 계약이 아니다 — **스키마 정본을 raw SQL 마이그레이션에 두고 ORM이 스키마를 소유하지 않는다는 축은 D-21이 그대로 승계**했고, 뒤집힌 것은 셋이다: ORM 제품(Prisma → Spring Data JPA + MyBatis) · 마이그레이션 적용 수단(자체 러너 → Flyway) · 행 단위 보안 주입 기제(클라이언트 확장 → DataSource 프록시). 버린 대안 ②가 지목한 실패(엔티티가 스키마 정본을 코드로 끌어와 이중화되는 것)는 **JPA에서도 그대로 성립하므로** D-21이 스키마 생성을 금지하고 검증만 두는 계약으로 막는다. **스키마 정본은 raw SQL 마이그레이션**(V{NNNN}__ 번호 체계 · 별도 러너)이고 Prisma는 introspection으로 동기화만 한다. 행 단위 보안은 클라이언트 확장으로 전 쿼리를 트랜잭션에 감싸 세션 변수를 설정해 강제하고, 큰 정수·십진 타입은 언어 타입으로 강제해 부동소수점 유입을 막는다 | ① **Drizzle**을 버렸다 — 타입·마이그레이션이 가볍지만 raw SQL 정본 + introspection 왕복 흐름의 성숙도가 낮고, 전 쿼리를 가로채 트랜잭션과 세션 변수를 강제할 확장점이 약하다. ② **TypeORM**도 버렸다 — 데코레이터 엔티티가 스키마 정본을 코드로 끌어와 raw SQL 마이그레이션과 정본이 이중화되고, 행 단위 보안 정책·트리거·함수를 표현하지 못해 결국 SQL이 따로 남는다. **ORM이 스키마를 소유하지 않는다**는 것이 이 결정의 핵심이다 |
| **D-14** | 상시근로자 수를 실수값으로 저장 | 5인 미만 여부 플래그가 아니라 **평균 근로자 수 실수값과 일자별 근로자 수 시계열**을 저장하고 경계 판정을 파생시킨다. 스냅샷은 기준일별로 보존한다 | ① **5인 미만 여부 단일 불리언**을 버렸다 — 취업규칙(10인)·성희롱 예방교육(10인)·두루누리(10인)가 5인과 다른 경계를 써서 불리언 하나로 표현되지 않는다. ② **월 평균값 하나만 저장**하는 안도 버렸다 — 시행령의 보정 규칙(일별 미달일수가 절반 미만이면 판정을 뒤집음)을 적용하려면 일자별 시계열이 필수라 평균값 하나로는 계산 자체가 불가능하다. **규모는 사업장의 속성이 아니라 기준일의 함수**이며 사유마다·날마다 판정한다 |
| **D-15** | 5인 미만 분기 = 조문 단위 화이트리스트 | 근로기준법 시행령 별표를 **적용되는 조문만 열거하는 화이트리스트**로 다룬다 — 목록에 없으면 미적용이다. 분기는 전부-아니면-전무가 아니라 **조문 단위로 분해**해 정책 테이블(CMP-02)에서 effective date로 관리한다 | ① **블랙리스트(적용 제외 목록)로 구현**하는 안을 버렸다 — 별표를 제외 목록으로 오해하면 5인 미만 분기가 통째로 뒤집혀 미적용 조문이 적용되고 적용 조문이 빠진다. ② **단일 플래그 분기**도 버렸다 — 5인 미만 확대 논의가 진행 중인데 조문 단위로 분해되어 있지 않으면 적용 확대 때 마이그레이션과 재배포가 필요하다. 정책값으로 두면 기준값 변경만으로 대응하고 과거 급여의 재현성도 지켜진다 |
| **D-16** | 단수 처리 = 항목별 1회 · 상향 통일 | **항목별 최종 금액에서 1회만** 적용하고 중간 단계에서 반올림하지 않는다. 지급 항목은 올림 · 무급공제는 절사 · 법정공제는 10원 미만 절사이며, **최저임금 환산액은 반올림하지 않는다**. 규칙 자체를 기준값으로 관리한다 | ① **지급 항목도 절사**하는 안을 버렸다 — 임금 전액 지급 원칙·최저임금법과 충돌 소지가 있어 상향으로 통일한다. ② **중간 단계마다 반올림**을 버렸다 — 항목 수만큼 오차가 누적되고 집계 순서에 따라 결과가 달라져 계산 결정론이 깨진다. ③ **최저임금 환산액 절상**도 버렸다 — 절상하면 실제 미달을 놓쳐 사용자를 최저임금법 위반에 노출시킨다. 부동소수점은 전면 금지하고 정수·고정소수점만 쓴다 |
| **D-17** | 확정 결과에 값 동결 | 확정 시점의 **기준값 행 식별자와 실제 값 · 상시근로자 스냅샷 · 규모별 정책 버전 · 통상임금 규칙 버전**을 결과에 동결 저장한다. 확정 결과는 덮어쓰지 않으며 정정은 원본 무효화 후 정정본 신규 생성 체인으로만 한다 | **effective date 이력만 두고 결과는 참조로 남기는 안**을 버렸다 — 기준값 행이 사후 정정되거나 정책 버전이 바뀌면 이듬해에 과거 명세서를 재출력할 때 값이 전부 틀어진다. 이력 조회만으로는 재현이 깨지며, 명세서는 지급일 기준 3년 보존·교부 대상이라 재출력 불일치가 그대로 분쟁이 된다. 확정 결과 덮어쓰기를 허용하는 안도 같은 이유로 버렸다 |

## 권한·보안

| # | 항목 | 결정 | 버린 대안과 이유 |
|---|------|------|-----------------|
| **D-11** | WRK-01 국세청 게이트 유지 + 검증 대기 상태 도입 | 사업자 진위·상태 검증 통과를 사업장 생성 조건으로 **유지**하되, 개업 준비 중과 국세청 API 장애는 **PENDING_VERIFICATION** 상태로 생성을 허용한다. 검증 대기에서는 근태·인사 입력을 허용하되 **급여 확정·명세서 발행을 차단**하고 일정 기간 미검증 시 자동 정지한다 | ① **게이트 폐지**(무검증 등록)를 버렸다 — 무등록 급여 운영을 조력하는 리스크가 크고 사업장 신뢰 축이 사라진다. ② **예외 없는 현행 게이트 유지**도 버렸다 — 부가가치세법상 사업 개시 후 20일 내 신청이라 등록 전 근로는 정상 발생하는데 오픈 첫 달 급여를 넣을 수 없고, 외부 API 가용성에 법정 의무 이행이 종속된다. **이 게이트는 법이 요구한 것이 아니라 제품이 선택한 신뢰 장치**임을 명시한다 |
| **D-12** | 휴업과 폐업 분리 | 사업장 검증 상태에서 **휴업과 폐업을 분리**해 폐업만 신규 등록을 차단하고 휴업은 경고 후 허용한다 | **휴폐업을 한 상태로 묶어 동일하게 차단**하는 안을 버렸다 — 휴업 중에도 근로관계·휴업수당·퇴직금 의무가 존속하므로 차단이 과도하고, 휴업 사업장의 사용자가 법정 의무를 이행할 수단을 잃는다 |
| **D-13** | 사업장당 OWNER 단일성 | **사업장당 OWNER는 항상 1명**이다. 마지막 OWNER의 강등과 본인 권한의 자기 제거를 차단하고, MANAGER는 다른 OWNER·MANAGER의 역할을 바꾸지 못한다. 역할 회수 후에도 그 사람이 만든 데이터는 유지되고 감사 로그에 행위자로 남는다 | ① **복수 OWNER 허용**을 버렸다 — 폐쇄·구독·한도·급여 무효화·명세서 정정처럼 되돌릴 수 없는 행위의 책임 주체가 흐려지고, "마지막 OWNER 보호" 가드 자체가 성립하지 않는다. ② **OWNER 없이 MANAGER만 두는 안**도 버렸다 — 구독과 등록 한도가 계정 단위인데 소유자가 없으면 과금 주체를 특정할 수 없다. 양도(OWNER 이전)는 v1.1이라 v1의 이탈 경로는 폐쇄뿐이다 |
| **D-18** | 복수 사업장 허용 + 사업 단위 판정 요구 | **1개 사업자등록번호로 복수 사업장 등록을 허용**한다(동일 사업자번호 + 동일 사업장명의 완전 중복만 차단하고 같은 사업자번호는 그룹으로 연결). 대신 복수 사업장 등록 시 **사업 단위 판정(CMP-08)을 요구**해 독립성 체크리스트를 사용자가 선언하게 하고, 통합 운영으로 선언되면 상시근로자를 합산 산정하며 선언 근거를 감사 보존한다 | ① **사업자번호당 사업장 1개 제한**을 버렸다 — 부가가치세법이 사업자단위과세·종사업장을 허용하고 구독 등급이 복수 사업장을 파는데 등록을 막으면 유료 사용자가 제품을 쓸 수 없다. ② **사업장별로만 상시근로자 산정**을 버렸다 — 3인 매장 2개를 사장이 직접 관리하면 실질은 6인이라 5인 이상 규정이 적용되는데, 사업장별 산정은 5인 미만으로 잘못 판정해 **사용자를 법 위반에 노출시킨다**. ③ **자동 합산**도 버렸다 — 독립성 판단은 법적 판단이라 제품이 자동으로 내릴 수 없어 선언 + 경고 방식으로 처리한다 |
| **D-19** | 위치정보 동의 분리 — 가입 요건 아님 | **위치정보 동의는 가입 성립 요건이 아니다.** 가입 필수 동의는 약관·개인정보 2종이고, 위치정보는 **별도 선택 동의**로 두어 **GPS 체크인 사용 전에** 받는다 — 미동의여도 가입·웹 이용은 가능하고 체크인만 차단되며, 철회하면 체크인이 다시 차단된다 | ① **가입 시 3종 필수(원천 서술)**를 버렸다 — 위치 기능을 쓰지 않는 관리자·웹 전용 사용자에게 개인위치정보 동의를 강제하면 선택 동의를 서비스 이용 조건으로 삼는 것이 되어 동의의 임의성이 무너지고, 위치정보법 §18의 별도 동의 취지(이용 시점 동의)와도 어긋난다. ② **동의 없이 체크인 허용**은 논외다 — §18 위반이다. 화면 설계(07_screen)는 처음부터 이 방향이었고 요구사항 서술만 원천을 따라 3종 필수로 남아 있었다 |
