insadesk가 무엇이고 누구를 위한 것이며 어떤 흐름으로 쓰이는지를 한 장에 담는다. 기능 단위 명세는 [../02_features/README.md](../02_features/README.md), 화면은 [../07_screen/README.md](../07_screen/README.md), 동작 계약은 [../03_requirements/README.md](../03_requirements/README.md)가 정본이다.

## 무엇인가

**insadesk**는 상시 근로자 **1~30인** 규모의 소상공인이 노무사·세무사 없이 **근태 → 급여 자동계산 → 명세서 교부 → 법정 신고 자료**까지 한 달치를 스스로 마감하도록 돕는 SaaS다. 사장이 사업장을 만들고 직원을 초대하면, 직원이 앱으로 찍은 출퇴근이 근태 마감을 거쳐 급여 계산의 입력이 되고, 확정된 급여가 임금명세서로 교부되며, 퇴사가 발생하면 금품청산·이직확인서·4대보험 상실 신고자료까지 같은 원장 위에서 이어진다. 제품의 단위 성과는 기능 하나가 아니라 **한 주기의 마감이 끊기지 않고 끝나는 것**이다.

계산은 전부 **서버 전용 · 결정론**이다. 동일 입력이면 언제 돌려도 동일 결과가 나오도록 룰 기반으로만 산출하며 AI 추론·실행 시각 의존·부동소수점 누적을 쓰지 않는다. 요율·세액표·최저임금·비과세 한도·단수 규칙은 코드에 박지 않고 **귀속 기준일로 조회하는 기준값 테이블**에서만 읽으며, 필요한 기준값이 하나라도 없으면 임의 기본값으로 메우지 않고 계산 자체를 차단한다. 확정 시점에는 기준값 행 식별자와 실제 값 · 상시근로자 스냅샷 · 정책 버전을 결과에 **동결 저장**한다 — 이력 조회만으로는 이듬해에 과거 명세서를 재출력할 때 값이 어긋난다.

법정 의무를 안내문이 아니라 **제품 구조로 내장**한다. 임금명세서 교부 · 근로조건 서면 명시 · 휴게시간 부여 · 금품청산 14일 · 퇴직금 · 근로자명부와 서류 보존 · 연소자 서류 비치는 전 규모 의무이고, 연차 · 가산수당 · 관공서 공휴일 유급 · 해고 서면통지는 5인 이상 의무다. 이 경계를 사업장의 고정 속성으로 두지 않고 **상시근로자 스냅샷이라는 기준일의 함수**로 계산하며, 규모별 적용 조항은 조문 단위 정책값으로 버전 관리해 법이 바뀌어도 재배포 없이 대응한다.

**아닌 것**을 분명히 한다. insadesk는 **세무사·노무사를 대체하지 않는다** — 계산 결과는 참고자료이며 신고·납부의 최종 책임은 사업주에게 있음을 제품이 고지한다. **홈택스·4대보험 EDI로 신고서를 직접 전송하지 않는다** — v1이 만드는 것은 신고 자료의 산출이며 제출은 사용자가 각 기관 채널에서 수행한다. 가사사용인·동거친족만 사용하는 사업은 근로기준법 적용 대상이 아니라 계산 결과가 적용되지 않으며, 이 사실을 온보딩에서 고지한다.

v1의 범위는 **마감 완결선**이다(D-07). 근태부터 명세서까지 끝까지 도는 최소 집합인 필수 94기능에, 혼자 운영하는 사장이 매일 서비스 밖으로 새는 일을 막는 **운영 요약·편의 4기능**(프로필 관리 · 오늘 출근 현황 · 인건비 추이 · 목록 내보내기 — D-23)을 더한 **98기능**을 만들고, 통계 분석·대시보드 전반·연 1회 이하 빈도의 신고는 v1.1로 미루거나 두지 않는다. 미룬 것의 유일한 등재처는 [02_goals_scope.md](./02_goals_scope.md)의 Out 범위 표다.

## 누구를 위한 것인가

| 사용자 | 역할 | 주요 목적 |
|--------|------|-----------|
| 사장 | OWNER | 사업장을 등록·검증하고 직원을 초대한다. 급여 기준을 정하고 확정하며 명세서 정정본을 발행한다. 구독 등급·인원 한도·사업장 폐쇄를 결정하는 유일한 주체다 |
| 매니저 | MANAGER | 사장이 운영을 위임한 관리자. 인사·근로계약·근태 승인과 마감·급여 계산과 확정·명세서 발행·신고 자료 산출을 수행한다. 다른 OWNER·MANAGER를 제외하거나 역할을 바꾸지 못한다 |
| 직원 | STAFF | 앱으로 출퇴근을 찍고 휴게를 기록하며 근태 수정과 휴가를 신청한다. 본인 급여 이력·명세서를 열람하고 근로계약에 전자서명한다. 열람·수정 범위는 **본인 데이터뿐**이다 |
| 플랫폼 운영자 | VIEWER · SUPPORT · ADMIN · SUPER_ADMIN | 사업장·사용자 조회와 제재 · 구독 등급 수동 조정 · 기준값·약관 관리 · 감사 로그 운영을 담당한다. **사업장 RBAC와 완전히 별개의 축**이며 사업장 업무 데이터의 소유자가 아니다 |

- 사업장 역할은 OWNER ⊃ MANAGER ⊃ STAFF의 **누적** 관계다. 사업장당 OWNER는 항상 1명이다(D-13).
- 외부 세무사·노무사를 위한 읽기 전용 ADVISOR 역할은 **v1에 두지 않는다**(WRK-13 이월). 상세는 [03_personas_roles.md](./03_personas_roles.md)를 따른다.

## 핵심 흐름

```
가입(약관·개인정보 동의 — 위치정보는 별도 선택) → 로그인
  → 사업장 등록 · 국세청 진위·상태 검증(통과 또는 PENDING_VERIFICATION)
    → 직원 초대 · 기존 사업장은 일괄 임포트(연차 잔액 기초값 포함)
      → 인적사항·고용형태·근로조건 등록 → 근로계약서 작성·전자서명·교부
        → 근무 스케줄 편성 → 출퇴근 체크인(지오펜스 서버 재검증) · 휴게 기록
          → 지각·조퇴·결근 판정 · 연장·야간·휴일 집계 · 수정 요청 승인
            → 상시근로자 산정 · 휴게 준수 검증 통과 → 근태 마감(잠금)
              → 급여 기준 적용 → 법정수당·4대보험·소득세 계산 → 최저임금 검증
                → 급여 미리보기 → 급여 확정(잠금 · 멱등키) → 임금대장 기록
                  → 명세서 자동 생성·일괄 발행 → 교부 알림 → 직원 열람
                    → 퇴사 처리 → 퇴직금 판정·개산액 → 금품청산 14일 시계
                      → 4대보험 상실 신고자료 · 이직확인서 → 신고 기한 캘린더
```

- 각 단계는 앞 단계의 확정을 입력으로 받는다 — 근태가 마감되지 않으면 급여 계산이 차단되고, 급여가 확정되지 않으면 명세서가 생성되지 않는다.
- 확정된 결과는 덮어쓰지 않는다. 정정은 원본 무효화 후 정정본을 신규 생성해 연결하는 체인으로만 한다.
- 퇴사 이후에도 본인 명세서·근로계약·급여이력의 열람은 끊기지 않는다 — 멤버십이 아니라 **본인 소유권**으로 인가하기 때문이다(CMP-07).

## 제품 표면

| 표면 | 대상 | 저장소 |
|------|------|--------|
| 직원 앱 | STAFF 본인 데이터 — 체크인·휴게·근태 수정 요청·휴가·급여 이력·명세서 열람·계약 서명·알림 | app_front (React Native) |
| 관리자 웹 | OWNER · MANAGER의 사업장 운영 — 인사·근태·급여·명세서·신고 자료·구독 | web_front — 단일 페이지 앱 경로 |
| 시스템 웹 | 플랫폼 운영자 — 사업장·사용자·구독·기준값·약관·감사 로그 | web_front — 단일 페이지 앱 경로 |
| 공개 웹 | 미인증 — 랜딩·요금제(프리렌더 정적) · 약관·개인정보·위치정보 문서(클라이언트 조회) · 가입·로그인·비밀번호 재설정·동의(단일 페이지 앱) | web_front |
| 백엔드 | 전 표면의 단일 API·계산·배치·파일 서버 | back |

- 웹 3표면은 **하나의 산출물**이다 — 단일 Vite 빌드가 랜딩·요금제를 빌드 시점에 정적 HTML로 굽고 나머지 전 경로를 단일 페이지 앱으로 서빙한다. Vercel 프로젝트도 1개이며 별도 사이트로 쪼개지 않는다(D-20).
- 공개 웹 안에서도 렌더링이 갈린다 — 랜딩·요금제만 프리렌더 + 검색 최적화 대상이고, **법정 문서(약관·개인정보·위치정보)는 프리렌더하지 않고 클라이언트가 활성 버전을 조회**해 게시 문안과 동의 이력 버전이 갈리지 않게 한다. 인증 이후 화면은 클라이언트 렌더링이다(D-02 · D-20).
- 진입 분기를 담당하는 서버 미들웨어 계층은 없다 — 클라이언트 라우터 가드는 사용성 보조이고 최종 강제는 서버 검증과 행 단위 보안이다(D-20).
- 저장소는 back · web_front · app_front 3분할이다(D-06 — 전환 후에도 불변).

## 기술 스택 요약

웹은 **React · Vite · React Router**로 만들어 **Vercel**에 배포하고(공개 페이지는 빌드 시점 프리렌더 · 나머지는 단일 페이지 앱), 백엔드는 **Java · Spring Boot + PostgreSQL 18**을 **AWS EC2**의 Docker 컨테이너로 운영하며, 직원 앱은 **React Native**(CLI bare)로 만든다. 웹은 app 서브도메인, API는 api 서브도메인으로 **커스텀 도메인 아래 직접 호출**하며 프록시 계층을 두지 않는다(D-03) — 세션 쿠키는 상위 도메인 스코프로 공유한다. 데이터 접근은 **쓰기와 단순 조회를 JPA 한 축**으로, **복잡 조회만 MyBatis 읽기 전용**으로 나누되 스키마 정본은 저장소 루트 db_migration/의 raw SQL이고 적용은 Flyway가 하며, 행 단위 격리는 전 쿼리를 트랜잭션으로 감싸 세션 변수를 설정하는 데이터소스 프록시로 강제한다(D-21).

인증은 표면별로 갈린다 — 웹은 서버 세션 쿠키, 앱은 토큰 기반이다. 실시간 알림은 서버 전송 이벤트와 Redis 발행·구독으로, 정기작업은 분산 락 + 멱등키로 다중 인스턴스 중복 실행을 막는다. 파일(명세서 PDF·문서함·임포트)은 서울 리전 객체 스토리지에 두고 1회용 다운로드 토큰 + 서버 스트리밍으로만 내보낸다. **정확한 버전·구성·선정 근거의 정본은 [../08_tech_stack/README.md](../08_tech_stack/README.md)**이며, 이 절은 요약이므로 값이 어긋나면 정본을 따른다.
