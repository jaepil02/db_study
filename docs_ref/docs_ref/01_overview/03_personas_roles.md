insadesk의 사용자 유형·권한 계층·접근 경계를 확정한다. 본 문서가 **페르소나와 3층 권한 구조의 정본**이며, 역할 × 기능 단위의 판정 상세는 [../02_features/14_permission_matrix.md](../02_features/14_permission_matrix.md)가, 상태 전이의 정의는 [../09_glossary/03_enums_state_machines.md](../09_glossary/03_enums_state_machines.md)가 이어받는다.

## 페르소나

**사장(OWNER)** — 사업장을 만든 사람이다. 사업자등록번호로 진위·상태 검증을 통과해 테넌트를 생성하고, 직원을 초대하며, 급여 기준과 지급일을 정한다. 구독 등급·사업장 등록 한도·사업장당 인원 한도가 걸리는 지점이 전부 이 페르소나이고, 되돌릴 수 없는 행위(급여 무효화·명세서 정정본 발행·근태 마감 취소·임포트 확정·사업장 폐쇄)의 최종 승인자다. 사업장당 OWNER는 **항상 1명**이며, 마지막 OWNER를 강등하거나 스스로 권한을 내려 OWNER가 0명이 되는 경로는 차단한다.

**매니저(MANAGER)** — 사장이 운영을 위임한 관리자다. 인사 등록·근로계약·근태 승인과 마감·급여 계산과 확정·명세서 발행·신고 자료 산출까지 일상 운영 전부를 수행하지만, 다른 OWNER·MANAGER를 제외하거나 그 역할을 바꾸지 못한다. 본인이 대상자로 포함된 급여는 자기거래이므로 **MANAGER는 확정할 수 없고 OWNER만 확정한다**(자기포함 표시·감사 기록 병행). 직원 겸 관리자인 소상공인 현실에서 이 페르소나는 STAFF 권한을 함께 갖는다.

**직원(STAFF)** — 앱으로 출퇴근을 찍는 근로자다. 열람·수정 범위는 **본인 데이터뿐**이며, 휴게 기록·근태 수정 요청·휴가 신청·근로계약 전자서명·본인 급여 이력과 명세서 열람이 전부다. 본인이 낸 요청을 본인이 승인하는 경로는 차단한다. 퇴사해 멤버십이 끝난 뒤에도 본인 귀속 법정문서(명세서·근로계약서·급여이력)는 보존기간 내 계속 열람할 수 있다 — 명세서는 지급일 기준 3년 보존·교부 대상이라 접근을 끊는 것 자체가 위반 소지이기 때문이다(CMP-07).

**플랫폼 운영자** — 서비스 운영사 소속이며 사업장의 구성원이 아니다. 사업장·사용자 조회와 제재 · 구독 등급 수동 조정 · 기준값·약관 문서 관리 · 감사 로그 열람을 담당한다. v1은 등급 조정이 수동 처리라 이 페르소나 없이는 유료 전환 자체가 불가능하고, 기준값 등록이 없으면 급여 계산이 시작조차 되지 않는다. 권한 키는 명시적 화이트리스트로 부여하고 **미정의 키는 기본 거부**한다.

## 3층 권한

권한은 세 층위로 분리한다. **사업장 RBAC와 플랫폼 RBAC는 완전히 별개**이며 서로를 승계하지 않는다 — 플랫폼 ADMIN이라고 해서 특정 사업장의 급여를 확정할 수 없고, 사업장 OWNER라고 해서 다른 사업장을 조회할 수 없다.

| 층위 | 식별 | 적용 범위 | 값 |
|------|------|-----------|-----|
| 인증 경계 | 인증 사용자 식별자 유무 | 미인증은 공개 경로(랜딩·요금제·약관·가입·**가입 동의**·로그인·비밀번호 재설정 — 화면 축 PUB 7본, 정본 [../07_screen/01_standards.md](../07_screen/01_standards.md))만 | — |
| 사업장 RBAC | 사업장 멤버십의 역할 | 활성 사업장 내 업무 전반. 요청마다 활성 사업장 식별자를 함께 실어 스코프를 고정한다 | OWNER · MANAGER · STAFF |
| 플랫폼 RBAC | 시스템 관리자 레코드의 역할 | 플랫폼 운영 — 사업장·사용자·구독·기준값·약관·감사 로그 | VIEWER(1) · SUPPORT(2) · ADMIN(3) · SUPER_ADMIN(4) |

플랫폼 역할은 레벨 누적이다.

| 역할 | 레벨 | 권한 요약 |
|------|:----:|-----------|
| VIEWER | 1 | 사업장·사용자·구독·요금제·기준값 조회만 |
| SUPPORT | 2 | VIEWER + 지원 액션 · 보조 비밀번호 재설정 |
| ADMIN | 3 | SUPPORT + 계정·사업장 정지/해제 · 구독 등급 조정 · 기준값 갱신 · 약관 관리 · 감사 로그 |
| SUPER_ADMIN | 4 | ADMIN + 역할 임명/회수 · 계정 강제 삭제 |

- 제재·강제 폐쇄·재검증·민감정보 접근은 사유 입력과 감사 로그를 함께 요구한다.
- 플랫폼 역할 임명/회수 기능(SYS-02)은 **v1에 두지 않는다** — 초기 SUPER_ADMIN은 시드가 아니라 **서버 기동 시 환경변수 1회성 부트스트랩**으로 만든다(정본: [../05_database/10_migrations_seed.md](../05_database/10_migrations_seed.md)).
- 권한 강제는 **2단 방어**다. 서비스 레이어가 1차로 멤버십·역할·사업장 스코프를 검증하고, 데이터베이스 행 단위 보안 정책이 2차 심층방어로 행 격리를 보장한다. 클라이언트 가드는 보조이며 최종 판단은 항상 서버다. 상세는 [../04_architecture/03_multitenancy_rls.md](../04_architecture/03_multitenancy_rls.md)가 정본이다.

## 역할 누적 체계

사업장 역할은 **OWNER ⊃ MANAGER ⊃ STAFF의 누적** 관계다. 기능 명세의 섹션 제목에 붙는 역할은 그 기능을 수행할 수 있는 **최소 역할**을 뜻하며, 상위 역할은 하위 역할의 기능을 전부 수행한다.

| 역할 | 범위 | 하지 못하는 것 |
|------|------|---------------|
| OWNER | 전체. 폐쇄·구독·한도·역할 관리·급여 무효화·명세서 정정본이 전용이다 | 마지막 OWNER의 강등·자기 권한 제거 |
| MANAGER | 근태·급여·인사·명세서·신고 운영 전반 | 다른 OWNER·MANAGER 제외 및 역할 변경 · OWNER 전용 액션 |
| STAFF | 본인 근태·급여·명세서·휴가·계약 | 타인 데이터 열람 · 본인 요청의 본인 승인 |

OWNER 전용 액션은 기능ID를 갖지 않지만 MANAGER가 수행할 수 없는 행위이며, 서비스 레이어와 행 단위 정책 양쪽에서 OWNER를 강제한다 — 사업장 폐쇄 · 멤버 역할 변경 · 근태 마감 취소(급여 미확정 기간 한정) · 데이터 임포트 확정 · 급여 무효화와 정정 · 명세서 정정본 발행 · 구독과 등록 한도 관리.

**ADVISOR 역할은 v1에 두지 않는다**(WRK-13 이월). 외부 세무사·노무사에게 읽기 전용 권한을 주는 경로가 v1에 없으므로, 사업장 역할 값은 OWNER · MANAGER · STAFF **3종뿐**이다. 다른 문서는 ADVISOR를 현행 역할처럼 인용하지 않는다. 이 역할이 없는 동안 사업주가 계정을 공유하면 감사 추적과 권한 분리가 무너지므로, 세무사 협업 요구가 실제로 발생하면 v1.1에서 최우선으로 검토한다.

## 계정·멤버십 수명주기

계정과 멤버십은 **별개의 수명주기**를 갖는다. 계정이 살아 있어도 멤버십은 끝날 수 있고, 멤버십이 끝나도 본인 소유권 기반 열람은 이어진다.

| 축 | 단계 | 요지 |
|----|------|------|
| 계정 | 가입 → 활성 → 정지 → 삭제 | 가입 시 **약관·개인정보 동의(필수 2종)**를 버전과 함께 기록하고, **위치정보 동의는 가입 요건이 아니라 GPS 체크인 사용 전에 받는 별도 선택 동의**다(D-19). 정지·해제 주체는 플랫폼 운영자이며 정지 만료는 정기작업이 복귀시킨다. 탈퇴 시 개인정보는 파기하되 법정 보존 데이터는 유지하고, OWNER는 **사업장 폐쇄가 선행**해야 한다 |
| 멤버십 | 초대 → 수락·거절·만료 → 활성 → 제외 | 초대 재발송은 새 토큰을 발급하며 직전 토큰을 무효화한다. 인원 한도는 발송 시점과 **수락 시점에 재검증**한다. 제외 전에 마지막 OWNER · 급여 확정 진행 중 대상자 · 진행 중 승인의 필수 승인자를 먼저 해소하도록 요구한다 |
| 사업장 | 등록 → 검증(또는 검증 대기) → 활성 → 정지 → 폐쇄 | 검증 대기 상태에서는 근태·인사 입력을 허용하되 급여 확정·명세서 발행을 차단한다. 폐쇄 후에는 신규 업무 생성을 막고 읽기 전용으로 전환하되 법정 보존 데이터는 유지한다 |

- 상태 값·전이 조건·차단 사유의 정본은 [../09_glossary/03_enums_state_machines.md](../09_glossary/03_enums_state_machines.md)다. 이 절은 요약이므로 값이 어긋나면 정본을 따른다.
- 제외 후에도 근태·급여·명세서·근로계약은 법정 보존되며 **본인은 보존기간 내 계속 열람**한다(CMP-07). 재초대는 자발적 이탈 이력만 재활성화하고 강제 제외·정지 이력자는 차단한다.

## 사업자등록 요건 분류

권한 설계에 앞서 **사업자등록이 근로관계의 요건이 아니라는 점**을 고정한다. 근로기준법의 사용자 정의에 등록 여부가 들어가지 않고, 상시 5명 이상을 사용하는 "모든 사업 또는 사업장"이 적용 대상이며, 원천징수의무자는 "소득을 지급하는 자"다. 4대보험 사업장관리번호는 사업자등록번호와 별도로 부여될 수 있다. 따라서 **무등록 사업주도 임금·주휴·최저임금·명세서 교부·4대보험·원천징수 의무를 전부 진다** — 등록이 없다고 의무가 면제되지 않는다.

기능은 등록번호 의존도에 따라 세 갈래다.

| 분류 | 기능 수 | 성격 |
|------|:------:|------|
| (A) 사업자등록번호가 반드시 필요 | 15 | 테넌트 등록 클러스터(WRK-01 · WRK-02 · WRK-03 · WRK-14 · SYS-06)와 대외 신고 클러스터(TAX 전 기능) 두 곳뿐이다 |
| (B) 근로관계만으로 적용되는 법정 의무 | 69 | 등록과 무관하게 사용자라면 지는 의무 — HRM · ATT · LEV · PAY · SLP · CMP · PRV와 멤버 제외 |
| (C) 순수 제품 편의·인프라 | 54 | 법령과 무관한 제품 기능 — AUT · WRK 나머지 · ATT 체크인 계열 · NTF · DSH · SUB · SYS · 신고 캘린더 |

검산: 15 + 69 + 54 = **138**(원천 features.md 채택 목록 기준).

**급여 계산·명세서 교부·임금대장 어디에도 사업자등록번호는 법정 기재사항이 아니다.** 그럼에도 v1은 사업장 등록 시 국세청 진위·상태 검증 통과를 생성 조건으로 유지한다 — **이 게이트는 법이 요구한 것이 아니라 제품이 선택한 신뢰 장치**이며, 무등록 급여 운영을 조력하는 리스크를 피하려는 결정이다(D-11). 다만 게이트가 정상 사용자를 막는 세 경우는 고친다.

| 세그먼트 | 처리 |
|---------|------|
| 개업 준비 중(등록 전 채용·교육) | 검증 대기 상태로 생성을 허용한다. 등록 전 근로는 정상 발생하며, 막으면 오픈 첫 달 급여를 넣을 수 없다 |
| 휴업 중 사업장 | 폐업과 분리해 경고 후 허용한다. 휴업 중에도 근로관계·휴업수당·퇴직금 의무가 존속한다(D-12) |
| 국세청 API 장애 | 검증 대기 상태로 생성을 허용한다. 외부 API 가용성에 법정 의무 이행이 종속되지 않게 한다 |
| 가사사용인 · 동거친족만 사용하는 사업 | 차단이 타당하다 — 근로기준법 적용 제외라 계산 결과가 적용되지 않는다. 적용 제외 사실을 온보딩에서 고지하고 근로자 아닌 자로 구분한다(HRM-16) |
| 무등록 사업주(등록 회피) | 차단이 타당하다. 등록 안내는 제공한다 |

검증 대기 상태에서는 근태·인사 입력을 허용하되 **급여 확정·명세서 발행은 차단**하고, 일정 기간 미검증 시 자동 정지한다.
