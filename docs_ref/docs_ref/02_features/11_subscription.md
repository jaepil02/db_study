# SUB — 구독

> **대상**: 구독·요금제(SUB) 기능 명세
> **작성일**: 2026-08-03
> **개정일**: 2026-08-08 — DB 커버리지 감사 반영 — 등급별 활성 요금제 1행·발효일 유일·참조 요금제 불변을 제약·가드 계약으로 명시 · 구독 미설정 계정의 FREE 판정 규칙 · 사업장 등록 한도의 DB 백스톱
> **원천**: docs_ref2/features_p0.md §5 · §6 · docs_ref2/features.md §5 · §6 · docs_ref2/requirements_p0.md SUB 절 · 2026-08-08 DB 커버리지 감사

SUB는 **한도를 정의하고 강제하는 도메인**이다. 요금제(SUB-01)가 한도를 정의하고 구독(SUB-02)이 계정에 등급을 붙이며, 게이팅(SUB-03)과 이용 한도(SUB-04)가 사업장 등록과 초대 시점에 그 한도를 강제한다. 5기능이 모두 플랫폼요건 태그인 이유는 이것이 없으면 서비스 운영 자체가 성립하지 않기 때문이다.

**구독은 사업장이 아니라 계정 단위**다. 한 계정이 여러 사업장을 소유할 수 있으므로 등급을 사업장에 붙이면 같은 사장이 사업장마다 다른 등급을 갖는 이상한 상태가 된다. **직원으로 소속되는 경우(OWNER 아닌 멤버십)는 본인 구독과 무관하게 무료·무제한**이며 한도는 OWNER 측의 두 축에만 적용된다 — 소유 사업장 수와 사업장당 활성 멤버 수다.

**한도 초과는 권한 부족과 다른 축이다.** 권한 부족은 403이고 한도 초과는 402이며, 후자에는 현재 사용량·필요 등급·업그레이드 경로를 함께 반환한다. 사용자가 취할 조치가 다르기 때문이다.

**v1의 유료 전환은 수동 처리다.** 업그레이드 요청 워크플로(SUB-06)와 PG 결제 연동(SUB-07)이 영구 제외이므로 등급 조정은 플랫폼 관리자(SYS-05)가 수행하고 사용자에게는 문의 경로를 안내한다. 따라서 **SYS-05가 없으면 유료 전환 자체가 불가능**하다.

**구독 만료가 법정 의무 이행을 막지 않는다.** 만료는 신규 사업장 등록과 유료 기능 실행을 차단하되 **기존 급여·명세서 등 법정 보존 데이터의 조회·교부는 차단하지 않는다** — 구독료 미납을 이유로 명세서 교부를 막으면 사용자가 위반 상태에 놓인다.

## 기능 목록

| 기능ID | 기능명 | 설명 | 우선순위 |
|--------|--------|------|:--------:|
| **SUB-01** | 요금제 정의 | 등급별 한도를 정의한다. 필드는 코드·이름·**소유 가능 사업장 수**·**사업장당 최대 인원**·가격·기능 플래그·버전·유효 시작일·표시 순서·활성 여부다. 사업장당 인원 한도는 OWNER·MANAGER·STAFF를 모두 포함한 활성 멤버 수이며 **어떤 등급도 30을 초과할 수 없다**(상품 전역 상한). 기본 시드는 **FREE(사업장 1 · 인원 5) · PRO(3 · 15) · ULTRA(5 · 30)** 3등급이고 가격은 운영 설정값이다. 요금제 변경은 덮어쓰기가 아니라 **새 버전 + 유효 시작일**로 관리해 과거 구독에 적용된 한도를 추적할 수 있게 한다. **이미 참조된 요금제는 삭제하지 않는다** — 삭제하면 과거 구독이 어떤 한도로 운영됐는지 알 수 없어진다. 관리 주체는 플랫폼 관리자다 | **P0** |
| **SUB-02** | 구독 등급(계정) | 계정 단위 구독 레코드를 관리한다. 사용자·요금제 코드·상태·시작일·만료일·메모를 두고 상태는 체험·활성·연체·만료·해지로 전이한다. **미설정 계정은 FREE로 간주**해 별도 레코드 없이도 동작하게 한다. **만료 상태는 신규 사업장 등록을 차단**한다. 본인은 등급·한도·현재 사용량·상태·만료일을 조회하고 플랫폼 관리자는 사용자별 구독을 검색한다. **게이팅과 화면 표시가 동일한 사용량 산출 헬퍼를 공유**해 "화면에는 여유가 있는데 실행하면 막히는" 상태를 만들지 않는다. v1의 등급 조정은 수동 처리이므로 실제 변경 주체는 플랫폼 관리자(SYS-05)다 | **P0** |
| **SUB-03** | 사업장 등록 게이팅 | 사업장 등록 시 **소유 사업장 수가 요금제 한도 미만인지 서버에서 강제**한다. 초과하면 현재 사용량·필요 등급·업그레이드 안내를 함께 반환하고, **권한 부족(403)과 한도 초과(402)를 분리**해 사용자가 무엇을 해야 하는지 구분되게 한다. **동시 다중 생성 요청은 사용자 행 잠금으로 직렬화**해 한도 우회를 막는다 — 두 요청이 동시에 검사를 통과하면 한도를 1개 넘겨 생성된다. 등급 강등·사업장 폐쇄 시 등록 가능 수를 즉시 재계산하되 **초과 상태가 되어도 기존 사업장을 자동 폐쇄하지 않고 신규 등록만 차단**한다 | **P0** |
| **SUB-04** | 이용 한도 | 사업장당 활성 멤버 수 한도를 강제한다. 모든 사업장은 **30명을 절대 상한**으로 하고 요금제별 한도는 그 이하다. 검사는 **초대 발송 시점과 수락 시점 양쪽**에서 수행한다 — 발송 시점에만 검사하면 대기 초대가 여럿 쌓인 사이에 한도가 차서 초과 수락이 성립한다. 판정 기준은 **OWNER의 구독 등급**이며 초대받는 사람의 구독과 무관하다. **동시 다중 수락은 사업장 행 잠금으로 직렬화**한다. 임포트(WRK-16) 확정 직전에도 활성 멤버 수를 재검증한다. 사업장·계정 화면에 사용량 대비 한도를 표시하고 임박·초과 시 경고한다 | P1 |
| **SUB-05** | 구독 상태 점검 | 체험 종료·구독 만료·수동 부여 종료일을 정기작업(checkSubscriptionExpiry)이 점검해 상태를 전이한다. 작업은 **멱등해야 하고 분산락으로 중복 실행을 방지**한다. 만료 예정·만료·한도 초과는 OWNER와 플랫폼 관리자에게 알린다. 만료는 **신규 사업장 등록과 유료 기능 실행을 차단**하되 **기존 급여·명세서 등 법정 보존 데이터의 조회·교부는 차단하지 않는다** — 구독 만료를 이유로 법정 의무 이행을 막으면 제품이 사용자를 위반 상태로 밀어 넣는다 | P1 |

**5기능이다** — SUB-01 · 02 · 03 · 04 · 05. 우선순위 분포는 P0 3(SUB-01 · 02 · 03) · P1 2(SUB-04 · 05)이며 3 + 2 = 5다. **SUB-06(업그레이드 요청) · SUB-07(PG 결제 연동)은 영구 제외**이며 등급 조정은 플랫폼 관리자 수동 처리(SYS-05)로 운영한다.

## 요금제 한도 개요

값의 정본은 [../03_requirements/12_subscription.md](../03_requirements/12_subscription.md)이고 저장 구조는 [../05_database/14_subscription.md](../05_database/14_subscription.md)가 정본이다.

| 등급 | 소유 가능 사업장 | 사업장당 최대 인원 |
|------|----------------|-----------------|
| FREE | 1개 | 5명 |
| PRO | 3개 | 15명 |
| ULTRA | 5개 | 30명 |

- **직원으로 소속되는 경우는 한도에 포함되지 않는다.** OWNER 아닌 멤버십은 본인 구독과 무관하게 무료·무제한이다.
- **동일 사업자번호라도 별도 사업장으로 등록하면 각각 한도 1개를 소진**한다. 사업자번호가 아니라 사업장 행이 한도의 단위다.
- 사업장당 인원 한도는 **OWNER·MANAGER·STAFF 전원**을 세며, 상품 전역 상한 30명을 어떤 등급도 넘지 못한다.
- 한도 축소로 기존 사용량이 초과되어도 **기존 데이터를 삭제하거나 사업장을 폐쇄하지 않고 신규 생성·초대만 제한**한다.
- **두 한도 축 모두 서비스 검증과 DB 가드가 2단으로 강제한다** — 인원은 guard_member_cap()이, 소유 사업장 수는 guard_workplace_cap()이 받친다. 동시 요청이 검사를 함께 통과하는 경로를 잠금만으로 막지 않는다.
- **이미 참조된 요금제의 한도·가격은 고칠 수 없다** — 고치면 기존 가입자의 한도가 소급 변경되므로 새 버전 행으로만 바꾸며, 파괴적 변경 시도는 가드가 거부한다.

## 구독 상태 개요

상태 머신의 정본은 [../09_glossary/03_enums_state_machines.md](../09_glossary/03_enums_state_machines.md)다.

| 상태 | 의미 | 제한 |
|------|------|------|
| TRIAL | 체험 기간 | 등급 한도를 그대로 적용한다 |
| ACTIVE | 정상 구독 | 제한 없음 |
| PAST_DUE | 연체 | 만료 예정 안내 대상 |
| EXPIRED | 만료 | **신규 사업장 등록·유료 기능 차단. 법정 보존 데이터 조회·교부는 유지** |
| CANCELLED | 해지 | 만료와 동일한 차단 범위 |

**레코드가 없는 계정은 FREE로 간주**한다 — 가입 시 구독 행을 반드시 만들어야 한다는 제약을 두면 가입 트랜잭션이 불필요하게 커지고, 없는 상태와 FREE 상태를 구분할 실익도 없다. 이때 한도 판정이 적용하는 것은 **활성 FREE 요금제 행**이며, **등급별 활성 행이 정확히 1개**여야 그 판정이 결정론적이 된다(정본 [../05_database/14_subscription.md](../05_database/14_subscription.md)).

## 에러 코드

| 코드 | HTTP | 발생 조건 |
|------|:----:|----------|
| subscription.workplace_limit_exceeded | 402 | OWNER 소유 사업장 등록 수 한도 초과. 현재 사용량·필요 등급을 함께 반환한다(SUB-03 · WRK-01 · WRK-11) |
| subscription.staff_limit_exceeded | 402 | 사업장 활성 멤버 수 한도 초과 — 초대 발송·수락·임포트 확정 세 지점에서 발생한다(SUB-04 · WRK-04 · WRK-05 · WRK-16) |
| subscription.expired | 402 | 구독 만료로 기능 차단. **법정 보존 데이터 조회는 이 코드로 막지 않는다**(SUB-05) |
| subscription.plan_not_found | 404 | 요금제 미존재(SUB-01 · SUB-02) |
| subscription.upgrade_required | 402 | 기능 플래그·한도로 업그레이드가 필요한 실행(SUB-04) |
| system.plan_in_use | 409 | 이미 참조된 요금제의 파괴적 변경·삭제 시도(SUB-01) — 정본 네임스페이스는 system이며 등재는 [12_system.md](./12_system.md)다 |

- **402를 쓰는 이유는 403과 구분하기 위해서다.** 권한이 없는 것이 아니라 등급이 모자란 상태이며 업그레이드라는 조치가 가능하다. 두 상태를 403으로 뭉개면 사용자는 관리자에게 문의해야 할지 등급을 올려야 할지 알 수 없다.
- 전수 정본은 [../09_glossary/02_error_codes.md](../09_glossary/02_error_codes.md)다.
