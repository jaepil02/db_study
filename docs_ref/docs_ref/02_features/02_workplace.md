# WRK — 사업장·멤버·온보딩

> **대상**: 사업장·멤버·데이터 온보딩(WRK) 기능 명세
> **작성일**: 2026-08-03
> **개정일**: 2026-09-16 — **DSH-06 리포트 내보내기를 이 파일에 등재한다**(D-23 · v1.1 이월 해제). 사업장 단위 목록 전반에 걸리는 기능이라 테넌트 도메인 파일에 둔다. 파일 행 13 → **14**(WRK 13 · DSH 1)
> **개정일**: 2026-08-08 — DB 커버리지 감사 반영 — 대표 연락처 저장 축 명시 · MANAGER 초대 제한과 대표 사업장 유일성의 강제 축 등재 · 폐쇄의 멤버십 종료 구성 동작 명문화 · 검증 대기 차단 축 정정 · 임포트 한도 판정 축 정정(활성 멤버 → **활성 직원**)
> **원천**: docs_ref2/features_p0.md §2 · §4-1 · §5 · docs_ref2/features.md §4-1 · §5 · docs_ref2/requirements_p0.md WRK 절

WRK는 **테넌트의 생성·구성·종료**를 담당한다. 사업장(workplaces)이 곧 멀티테넌트 격리의 단위이며, 전 업무 테이블이 사업장 식별자 스코프로 잠긴다. 따라서 이 도메인의 계약이 틀리면 격리 자체가 무너지고 다른 도메인의 권한 설계는 무의미해진다.

사업장 생성은 **국세청 진위확인 통과를 전제**로 한다. 이 게이트는 법이 요구한 것이 아니라 제품이 선택한 신뢰 장치이며, 그대로 두면 정상 사용자를 막는 세 구멍이 생긴다 — 개업 준비 중(등록 전 채용·교육) · 휴업 중 사업장 · 국세청 API 장애다. 셋 다 근로관계와 임금 의무가 실재하는데 등록만 불가능해지는 상태다. WRK-14가 **휴업과 폐업을 분리**하고 **PENDING_VERIFICATION 상태**를 도입해 이 구멍을 메운다 — PENDING에서는 근태·인사 입력을 허용하되 급여 확정·명세서 발행만 차단한다.

**1개 사업자등록번호로 복수 사업장을 등록할 수 있다**(부가가치세법 §8 사업자단위과세·종사업장). 차단은 동일 사업자번호 + 동일 사업장명의 완전 중복뿐이며, 같은 사업자번호 사업장들은 그룹으로 연결하고 그중 하나를 **대표 사업장(site_role=PRIMARY)** 으로 지정한다 — 그룹당 대표는 **정확히 1개**이며 2개 이상은 DB 제약이, 0개는 등록 트랜잭션이 막는다. **v1의 과세 단위는 개별과세(tax_unit_type=GENERAL) 고정**이며 사업자단위과세(BUSINESS_UNIT)는 v1에 두지 않는다. 다만 사업장 분리가 5인 미만 회피 수단이 되어서는 안 되므로 복수 등록 시 **CMP-08 사업 단위 판정**을 요구한다.

**WRK-13(ADVISOR 초대) · WRK-12(업종 프리셋) · WRK-15(다중 근무지)는 v1에 두지 않는다.** ADVISOR 역할이 없으므로 사업장 역할은 OWNER ⊃ MANAGER ⊃ STAFF 3종 누적 체계뿐이고, 근무지는 사업장당 단일이며 지오펜스 판정도 사업장 좌표 하나를 쓴다. WRK-10은 **폐쇄만 v1 범위**이며 양도(OWNER 이전)는 v1.1이다.

## 기능 목록

| 기능ID | 기능명 | 설명 | 우선순위 |
|--------|--------|------|:--------:|
| **WRK-01** | 사업장 등록 | 테넌트 생성이다. 입력 필드는 아홉이다 — **사업자등록번호**(10자리 · 형식과 체크섬 검증) · **상호**(1~100자) · **대표자명** · **개업일** · **주소** · **업종** · **사업장 식별명**(지점명) · **근무지 좌표**(위도·경도) · **지오펜스 반경**(50~500미터 · 기본 100미터)이며 위치정확도 한계값을 함께 둔다. 등록 트랜잭션 진입 전에 등록자 계정이 활성인지와 **소유 사업장 수 한도**(WRK-11)를 선검사하고, 진위확인(WRK-02) 통과 후 단일 트랜잭션에서 사업장과 등록자 OWNER 멤버십을 함께 만든다. 같은 트랜잭션이 기본 근무정책·알림 설정·휴가 유형·급여 기준 초안을 시드한다. **진위 미통과 입력으로는 사업장이 생성되지 않는다** | **P0** |
| **WRK-02** | 사업자 진위/상태 검증 | 국세청 사업자등록정보 진위확인·상태조회 API를 **서버에서만** 호출한다. API 키를 클라이언트에 노출하면 그 자체가 유출이므로 서버 비밀로만 보관한다. 진위확인은 사업자번호·대표자명·개업일 일치를 판정하고, 상태조회는 계속사업자·휴업·폐업과 과세유형·폐업일자를 확인한다. **폐업만 신규 등록을 차단하고 휴업은 경고 후 허용**한다 — 휴업 중에도 근로관계·휴업수당·퇴직금 의무가 존속하기 때문이다. 요청 요약·응답 요약·판정 결과·지연 시간을 검증 로그에 남기되 원문 민감 데이터는 최소 보관한다. timeout·재시도 정책을 두고, 장애 시에는 등록을 막는 대신 PENDING_VERIFICATION 생성 경로(WRK-14)를 제시한다 | **P0** |
| **WRK-03** | 사업장 정보 관리 | 상호·주소·업종·**대표 연락처**·기본 근무시간과 **근무지 좌표·지오펜스 반경·위치정확도 한계**를 수정한다. 대표 연락처는 사업장 행이 직접 보유하며 개인 연락처와 별개 축이다. 좌표와 반경이 없으면 출퇴근 판정(ATT-02)이 성립하지 않으므로 제품성립 축이다. **사업자번호·대표자명·개업일은 재검증 없이 변경할 수 없다** — 이 셋이 사업장 아이덴티티의 앵커라 자유 변경을 허용하면 검증 이력과 실체가 어긋난다. **반경 변경은 변경 시각 이후 체크인부터 적용하고 과거 판정을 소급하지 않는다**. 변경은 전후값·유효시작일·변경자를 이력으로 남기며, 좌표·정책은 출퇴근에 필요하므로 STAFF도 조회한다 | **P0** |
| **WRK-04** | 직원 초대 | 직원이 사업장에 들어오는 경로를 만든다. 아이디 또는 휴대폰번호로 역할(STAFF·MANAGER)·고용 시작 예정일·메시지를 지정해 발송하며 **MANAGER는 STAFF만 초대할 수 있다** — 이 제한은 서비스 판정과 DB 가드 양쪽에서 강제한다. 관리자 권한만 보는 판정으로는 OWNER와 MANAGER가 구분되지 않아 **MANAGER가 관리자를 스스로 늘리는 경로**가 열리기 때문이다. 토큰은 **해시로만 저장**하고 기본 만료는 7일이며 초대 유형은 멤버 초대 하나다. 가입자에게는 인앱 알림, 미가입자에게는 1회용 공유 코드로 전달한다. 동일 대상의 대기 초대는 중복 생성하지 않고, 이미 활성 멤버인 대상은 거부한다. **만료·거절 초대를 재발송하면 새 토큰을 발급하고 직전 토큰을 즉시 무효화**한다 — 무효화를 빠뜨리면 취소된 초대로도 수락이 성립한다. **인원 한도는 발송 시점과 수락 시점 양쪽에서 재검증**한다(대기 중 다른 초대가 수락되어 한도가 찰 수 있다) | **P0** |
| **WRK-05** | 초대 수락/거절 | 직원 측 경로다. 본인에게 온 대기 초대만 조회하며 **타인 초대는 행 존재 자체를 노출하지 않는다**. 수락은 단일 트랜잭션에서 활성 멤버 한도 재검증 · 멤버십 생성 또는 재활성화 · 인사 레코드 초안 생성 · 초대 상태 전이 · 관리자 알림을 수행하고, **동시 수락 경합은 사업장 행 잠금으로 직렬화**해 한도 우회를 막는다. 재활성화는 **자발적 이탈(LEFT) 이력에만 허용**하고 강제 제외·정지 이력자는 차단해 관리자가 사유를 확인하도록 한다. 공유 코드는 1회용이며 초대 대상 연락처·아이디 일치 검증을 필수로 한다. **사업장이 정지·폐쇄 상태면 수락 자체를 막는다** — 폐쇄만 보는 판정으로는 정지 사업장의 수락이 통과하므로 두 상태를 함께 보는 쓰기 가능 판정을 수락 경로에 건다 | **P0** |
| **WRK-06** | 사업장 선택/전환 | 1계정 ↔ N사업장 전제를 성립시킨다. 본인의 활성 멤버십 목록(사업장명·역할·사업장 상태·마지막 선택 시각)을 조회하고 활성 사업장을 전환한다. 클라이언트는 선택된 사업장 식별자를 모든 업무 요청에 포함하지만 **서버는 매 요청 멤버십·역할을 재검증**한다 — 클라이언트가 보낸 값을 신뢰하면 격리가 클라이언트 측 변수로 내려앉는다. 정지·폐쇄 사업장, 이탈·제외된 멤버십, STAFF의 관리자 웹 접근은 전환 대상에서 차단한다. **클라이언트 캐시는 사업장 식별자 + 역할 단위로 격리**해 전환 후 타 사업장 데이터가 잔존하지 않게 한다 | **P0** |
| **WRK-07** | 멤버 역할 관리 | **OWNER만** MANAGER와 STAFF 사이의 역할을 바꾼다. MANAGER에게는 역할 변경 권한이 없고 다른 OWNER·MANAGER를 건드릴 수도 없다. **사업장당 활성 OWNER는 항상 정확히 1명**이라는 불변식을 서비스 레이어와 DB 제약 양쪽에서 강제하며, 마지막 OWNER 강등 · 본인 권한을 스스로 제거해 OWNER가 0명이 되는 조작을 차단한다. OWNER 권한의 이전은 역할 직접 변경이 아니라 양도 경로로만 가능한데 **양도는 v1.1 이월이므로 v1에서 OWNER는 고정**이다. 변경은 전후 역할·처리자·사유를 이력으로 남기고 대상자에게 알리며 권한 캐시를 즉시 무효화한다. **역할을 회수해도 그 사람이 만든 근태·급여 데이터는 유지되고 감사 로그에 행위자로 남는다** | P1 |
| **WRK-08** | 멤버 목록·검색 | 대상자 선택의 전제다. OWNER·MANAGER는 이름·역할·멤버 상태·입사일·고용형태·재직 상태·연락처 일부를 페이지네이션 조회하고, 이름·아이디·연락처 뒤 4자리·역할·상태로 검색한다. **목록 응답에 급여·주민번호·계좌·상세 주소를 포함하지 않는다** — 목록은 가장 넓게 열리는 표면이라 여기에 민감정보를 실으면 마스킹·복호화 통제(HRM-01)가 우회된다. STAFF에게는 공개 최소 정보만 반환한다 | **P0** |
| **WRK-09** | 멤버 제외 | 소속 종료다. OWNER는 MANAGER·STAFF를, MANAGER는 STAFF만 제외할 수 있고 **OWNER 본인은 제외할 수 없다**. 사유와 적용일 입력을 필수로 한다. 차단 선행조건이 넷이다 — 마지막 OWNER · **급여 확정이 진행 중인 대상자** · **진행 중 승인의 필수 승인자** · 제외로 사업장 필수 인원이 미달하는 경우이며, 각각 양도·확정 취소 또는 완료·승인자 재배정을 먼저 요구한다. 퇴사에 따른 제외는 퇴사 처리(HRM-04)와 연동해 4대보험 상실·정산을 트리거한다. 멤버십은 **본인 이탈은 LEFT, 강제 제외는 REMOVED**로 갈라 기록하고, **제외 후에도 근태·급여·명세서·계약은 법정 보존되며 본인은 보존기간 내 계속 열람**한다(CMP-07) | P1 |
| **WRK-10** | 사업장 폐쇄 | **v1 범위는 폐쇄뿐이며 양도는 v1.1이다.** 폐쇄가 v1에 들어온 이유는 편의가 아니라 데드락 해소다 — AUT-09 탈퇴가 "OWNER 소유 사업장 정리"를 선행 조건으로 요구하는데 폐쇄 경로가 없으면 OWNER는 영원히 탈퇴할 수 없고 이는 개인정보 파기 요구권과 정면 충돌한다. 선행조건은 다섯이다 — 진행 중 급여 확정 없음 · 미발행 명세서 없음 · 미처리 승인 없음 · **법정 보존 안내 확인** · **비밀번호 재인증**. 폐쇄는 신규 업무 생성을 차단하고 **읽기 전용으로 전환**하되 법정 보존 데이터는 유지하며, 폐쇄 후에도 본인 귀속 법정문서 열람은 끊기지 않는다. **남은 멤버십 종료는 폐쇄의 부가 처리가 아니라 구성 동작이다** — 같은 트랜잭션에서 끝내지 않으면 읽기 전용 전환이 그 멤버십을 영구히 잠가 OWNER 탈퇴 교착이 되살아난다. 플랫폼 관리자의 강제 폐쇄(SYS-03)와는 **별개 경로**다 | P2 |
| **WRK-11** | 사업장 등록 한도 | 구독 게이팅의 실행 지점이다. 등록 시 소유 사업장 수가 요금제 한도 미만인지 서버에서 강제하고, 초과하면 현재 사용량·필요 등급·업그레이드 경로를 함께 반환한다. **권한 부족(403)과 한도 초과(402)를 분리**해 사용자가 무엇을 해야 하는지 구분되게 한다. **동시 다중 생성 요청은 사용자 행 잠금으로 직렬화**해 한도 우회를 막는다. **STAFF·MANAGER로서의 타 사업장 소속은 본인 구독과 무관하게 무제한**이며, 한도는 OWNER 측의 소유 사업장 수와 사업장당 인원 수 두 축에만 적용된다. 동일 사업자번호라도 별도 사업장으로 등록하면 각각 한도 1개를 소진한다 | **P0** |
| **WRK-14** | 사업장 검증 상태 관리 | PENDING_VERIFICATION · ACTIVE · SUSPENDED · CLOSED 전이를 관리한다. **PENDING_VERIFICATION은 국세청 API 장애와 개업 준비 중(사업자등록 신청 전) 두 경우에 생성**하며, 이 상태에서는 근태·인사 입력을 허용하되 **급여 확정·명세서 발행만 차단**한다 — 외부 API 가용성에 법정 의무 이행이 종속되지 않게 하되 확정 결과가 미검증 사업장에서 나가지도 않게 하는 절충이다. **차단은 사업장 단위 쓰기 금지가 아니라 두 동작에 건 개별 판정**이다 — 사업장을 통째로 잠그면 근태·인사까지 멈춰 절충 자체가 무너진다. 정책값 기간 내에 검증되지 않으면 자동으로 정지 전이하고 **필수 알림(사업장 정지)으로 OWNER에게 통보**한다 — 사업장이 멈추면 근태·급여가 함께 멈추므로 사용자가 반드시 알아야 한다. **휴업과 폐업을 분리**해 폐업만 신규 등록을 차단한다. 이 기능이 없으면 정상 사용자가 등록조차 못 하므로 제품성립 축이다 | P1 |
| **WRK-16** | 데이터 온보딩·일괄 임포트 | 기존 사업장이 옮겨오는 **유일한 경로**다. 직원 10명을 하나씩 입력하게 하면 온보딩이 무너진다. CSV·Excel 템플릿으로 인적사항·고용형태·근로조건·입사일을 올리고, **전환 시점 이전의 근태·급여·연차 잔액 기초값**도 함께 적재한다. 작업 유형은 **직원 등록(EMPLOYEES)과 기초값 적재(OPENING_BALANCE) 2종**이며 각 작업은 전체·성공·실패 건수와 오류 리포트를 원장에 남긴다 — **이미 사용한 연차를 넣을 경로가 없으면 잔액이 0부터 시작해 연차 계산이 처음부터 틀린다**. 흐름은 미리보기 → 확정 2단계이고 미리보기 단계에서는 아무것도 커밋하지 않는다. **확정은 OWNER 전용**이며 검증 통과 행만 커밋하고 실패 행은 건너뛴 뒤 상세 리포트를 준다. 중복은 **파일 내 행간 중복**과 **기존 직원과의 중복** 두 종류로 분리 검출하고, 주민번호 판정은 복호화 없이 blind-index로 한다. 인원 한도 재검증의 기준은 **활성 직원 수 + 커밋 예정 행 수**다 — 임포트가 만드는 것은 직원 레코드이지 멤버십이 아니므로 멤버 수로 재면 적재량이 한도에 잡히지 않는다. 적재 데이터는 임포트 출처로 표시해 **기산 기준으로만 쓰고 명세서 자동 생성 대상에서 제외**하며, 민감정보는 임포트 즉시 암호화한다 | P1 |
| **DSH-06** | 리포트 내보내기 | 관리자 웹 · 시스템 웹의 목록 표를 **화면에 걸린 검색 · 필터 · 정렬 · 표시 열 그대로** XLSX로 내려받는다 — 세무사·노무사에게 넘기거나 사장이 따로 보관하려는 수요다. **파일은 서버가 만들고** 1회용 토큰 + 서버 스트리밍으로 전달하며 서명 URL을 주지 않는다. 연락처 · 금액처럼 민감정보가 든 목록은 **사유 입력이 필수**이고, 모든 내보내기를 감사 로그에 남긴다. 주민등록번호는 원문도 마스킹 값도 열에 싣지 않는다. 권한은 그 목록의 조회 권한을 그대로 따른다. 이미 있는 전용 내보내기(임금대장 · 근로자명부 · 신고자료 · 감사 로그)는 법정 서식이나 별도 계약을 가지므로 **이 기능이 대체하지 않는다** | **P2** |

**14행이다** — WRK 13기능(WRK-01 · 02 · 03 · 04 · 05 · 06 · 07 · 08 · 09 · 10 · 11 · 14 · 16)과 **DSH-06** 1기능이다. 우선순위 분포는 P0 8(WRK-01 · 02 · 03 · 04 · 05 · 06 · 08 · 11) · P1 4(WRK-07 · 09 · 14 · 16) · P2 2(WRK-10 · DSH-06)이며 8 + 4 + 2 = 14다. **WRK-12(업종 프리셋) · WRK-13(ADVISOR 초대) · WRK-15(다중 근무지)는 결번**이며 v1.1 이월이다.

## 멤버십과 초대 상태 개요

멤버십은 사업장과 계정을 잇는 행이며 역할·상태 두 축을 갖는다. 역할은 OWNER ⊃ MANAGER ⊃ STAFF 누적 3종이고 **ADVISOR는 v1에 두지 않는다**. 상태는 ACTIVE · LEFT(자발적 이탈) · REMOVED(강제 제외) · SUSPENDED로 갈리며, **재초대 수락은 LEFT 이력에만 허용**한다 — 강제 제외·정지 이력자를 자동 재활성화하면 제외 사유가 무력화된다. 허용 전이는 열거이고 **그 밖의 전이는 전부 거부**다.

초대는 PENDING → ACCEPTED · REJECTED · CANCELLED · EXPIRED로 전이한다. 만료 전이는 정기작업 expireInvitations(30분 주기)가 수행한다. 재발송은 **새 토큰 발급 + 직전 토큰 무효화**가 한 쌍이며, 이미 응답한 초대의 재수락·재거절은 거부한다. 상세 계약의 정본은 [../03_requirements/03_workplace.md](../03_requirements/03_workplace.md)다.
