정기작업은 **기능ID를 갖지 않는 서버 실행 항목**이므로 기능 집계에 들어가지 않는다. v1 필수는 **8건**이며 원천이 정의한 13건 중 5건은 v1.1로 미뤘다.

작업은 세 부류다 — **상태 전이**(초대 만료 · 계정 정지 해제 · 구독 만료) · **집계 산출**(일별 근태 롤업 · 연차 적립·소멸 · 상시근로자 스냅샷) · **경보·재시도**(법정 기한 감지 · 명세서 재생성)다. 앞의 둘은 데이터가 스스로 낡는 것을 막고, 뒤의 하나는 사용자가 놓치는 것을 잡는다.

**모든 일(日) 경계 판정은 KST 기준이고 스케줄러 프로세스의 시간대는 Asia/Seoul로 고정한다.** 작업은 실행 시각이 아니라 **기준일 파라미터로 동작**해 재실행 시 동일한 결과를 낸다 — 실행 시각에 의존하면 지연 실행과 재시도가 서로 다른 결과를 만든다.

**수동 재실행의 표면은 운영 API 하나이며 정본은 [../06_api/14_system.md](../06_api/14_system.md) #34다.** 정기작업 자체가 기능ID를 갖지 않으므로 **그 표면도 기능ID를 갖지 않고 새로 채번하지도 않는다** — 화면 자리는 SYS-RATES 운영 절이며 화면 채번 정본은 [../07_screen/README.md](../07_screen/README.md)다.

**분산락으로 다중 인스턴스 중복 실행을 막고 모든 작업이 멱등하다.** 멱등성은 같은 작업의 중복 실행을 무해하게 만들고 분산락은 애초에 동시 실행을 막는다 — 둘은 대체재가 아니라 보완재다.

## 작업별 동작

작업마다 대상 선정 조건 · 멱등 근거 · 실행 시각을 그 시각에 둔 이유를 함께 적는다. 주기와 관련 기능은 위 작업 목록 표가 정본이며 아래는 그 표가 담지 못하는 판정 규칙을 서술한다.

### expireInvitations

대기 상태로 남은 초대 중 만료 시각이 지난 것을 만료 상태로 전이한다. 주기가 30분인 것은 만료 판정의 지연이 사용자 경험에 직접 닿기 때문이다 — 만료된 초대를 수락하려 할 때 "만료됨"이 아니라 "무효"로 응답하면 원인을 알 수 없다. 전이는 상태 조건을 함께 걸어 이미 응답된 초대를 건드리지 않으며 **재발송으로 무효화된 직전 토큰은 이 정기작업과 무관하게 즉시 무효**다. 만료 전이 자체가 멱등이라 중복 실행이 상태를 흔들지 않는다.

### autoUnsuspendAccounts

정지 만료일이 지난 계정을 활성으로 복귀시키고 권한 캐시를 무효화한다. **접근 시점 복귀와 이 정기작업은 이중 경로**다 — 정지 만료 후 로그인하면 접근 경로에서 즉시 복귀하지만, 로그인하지 않는 계정도 상태가 정확해야 관리자 화면과 통계가 어긋나지 않는다. 복귀는 상태가 정지인 행만 대상으로 하므로 삭제 계정을 되살리지 않는다. **마지막 SUPER_ADMIN 보호 규칙은 정지 시점에 이미 적용**되므로 이 정기작업이 다시 판정하지 않는다.

### checkSubscriptionExpiry

체험 종료·구독 만료·수동 부여 종료일을 점검해 상태를 전이하고 만료 예정·만료를 OWNER와 플랫폼 관리자에게 알린다. **만료 전이가 법정 보존 데이터의 조회·교부를 막지 않는다** — 차단 범위는 신규 사업장 등록과 유료 기능 실행이며, 이 경계를 정기작업이 아니라 기능 게이팅이 판정한다. 알림은 만료 임박 구간에서 중복 발송되지 않도록 발송 이력으로 억제한다.

### rollupAttendanceDaily

전일 근태 원본을 읽어 일별 집계를 UPSERT한다. 판정(ATT-04)과 8버킷 분해(ATT-05)의 결과가 여기서 확정 형태로 저장된다. **판정 입력으로 근무 편성과 승인 휴가(유형의 유급 여부 포함)를 함께 읽는다** — 편성이 없으면 기록 없는 평일을 결근으로, 승인 휴가가 없으면 휴가일을 ON_LEAVE로 판정할 수 없다(읽기 축 정본 [../05_database/08_rls_policies.md](../05_database/08_rls_policies.md)). **마감된 기간은 건너뛴다** — 마감은 급여의 확정 입력이므로 정기작업이 사후에 다시 계산하면 확정 급여의 근거가 조용히 바뀐다. 자정 경과 근무는 출근 일자 기준 레코드를 실제 시간대로 분할 귀속하며, 분할 전후의 총 분 합이 일치하는지를 불변식으로 검증한다.

### accrueAndExpireLeave

연차 발생을 적립하고 만료된 발생분을 소멸시킨다. 적립은 입사일 기준 발생 조건을 판정해 원장에 발생 행을 쌓고, 소멸은 만료일이 지난 미사용 잔량을 소멸 행으로 기록한다. **요약 잔액은 원장에서 재계산**하며 정기작업이 요약만 고치는 경로를 두지 않는다. **5인 미만 기간은 산정하지 않고 스냅샷이 없으면 발생을 차단**한다. 판정에 쓰는 것은 **전일 기준 스냅샷**이므로 이 정기작업은 당일 스냅샷 산정(recomputeEmployeeCountSnapshot · 02:20)을 기다리지 않고 그 **이전 시각(00:40)** 에 둔다 — 작업 목록 표의 시각이 정본이다. **연차 사용촉진 판정은 v1에 없다**(LEV-07 이월).

### recomputeEmployeeCountSnapshot

상시근로자 스냅샷을 산정하고 5인·10인 경계 변동을 감지해 알린다. **이 작업이 없으면 근태 마감·급여 확정·연차 발생이 모두 차단 상태로 멈춘다** — 스냅샷 부재가 세 도메인의 공통 차단 사유이기 때문이다. 산정은 일자별 근로자 수 시계열을 모아 제1항 기본식과 제2항 보정을 적용하며 **경계 판정은 정수 비교**로 한다. 저장은 **(사업장, 기준일, 산정 범위) 단위 멱등 UPSERT**이고 — 같은 기준일에 사업장 단위 산정과 합산 단위 산정(CMP-08)이 각각 한 행씩 공존하므로 2열로 잡으면 합산 판정 행을 저장할 수 없다 — **확정된 과거 스냅샷을 자동으로 덮어쓰지 않는다** — 정정은 관리자 재계산 경로로만 반영된다. 새벽 02:20에 두는 이유는 전일 근태 롤업(00:20) 이후여야 그날의 근로자 수 시계열이 완성되기 때문이다. **기준일은 당일이다** — 전일을 대상으로 삼는 것은 00시대 작업 넷뿐이고 이 작업은 그 열거 밖이다([../04_architecture/07_batch_scheduling.md](../04_architecture/07_batch_scheduling.md) 작업별 기준일). D일 02:20이 D일 스냅샷을 만들어야 다음 날 00:40 연차 적립이 요구하는 **전일 기준 스냅샷**이 실제로 존재한다 — 전일로 두면 최신 스냅샷이 늘 하루 뒤처져 연차 발생 판정이 그만큼 밀린다.

### checkComplianceDeadlines

**열려 있는 기한 과제 전부**의 임박과 경과를 감지해 경보한다 — 금품청산 14일 · 퇴직급여 지급 14일 · 이직확인서 10일 · 4대보험 취득·상실 신고 · 원천징수이행상황신고가 그것이며 **놓치면 곧바로 과태료 또는 민원**이 되므로 사용자가 스스로 세는 데 의존할 수 없다.

**대상 축은 유형 목록이 아니라 원장이다.** 이 작업은 status가 OPEN이고 기한이 임계 안에 든 행을 유형과 무관하게 읽는다 — **유형을 열거해 거르면 새 유형이 생길 때마다 배치가 조용히 그것을 빠뜨린다**(실제로 4대보험 취득 과제가 2026-09-10에 생겼고 종전 서술은 그것을 세지 않았다). 유형 전수의 정본은 [../05_database/12_compliance.md](../05_database/12_compliance.md)이며 이 문서는 세지 않는다. 정기작업은 실행 시각이 아니라 **기준일 파라미터**로 동작해 재실행 시 동일 결과를 내고, 같은 과제·같은 임박 구간에서 알림이 반복되지 않도록 발송 이력으로 억제한다. 08:30에 두는 이유는 업무 시작 시점에 알림이 도착해야 그날 조치할 수 있기 때문이다.

**읽는 것이 과제만이 아니다 — 수신자도 읽는다.** compliance_tasks에는 workplace_id · employee_id 뿐이고 **수신자 축이 없어**, 알림을 보내려면 그 사업장의 관리자를 workplace_members에서 열거해야 한다. **이 읽기가 막히면 배치는 과제를 정상 감지하고 정상 종료하며 알림만 0건**이라 실행 이력이 SUCCEEDED + 정상 target_count로 남고, 드러나는 자리가 **"법정 신고 기한을 아무도 통보받지 못했다"**이며 그것은 기한이 지난 뒤다(보정 V0727 · 정본 [../05_database/08_rls_policies.md](../05_database/08_rls_policies.md) 읽기 축 절).

**임박 판정의 일수는 이 문서가 정하지 않는다 — 기준값이 갖는다.** 위 "같은 임박 구간"과 REQ-TAX-04의 "(과제, 임박 구간) 단위로 1회"가 억제 키의 둘째 축으로 임박 구간을 요구하는데 **며칠 남았을 때 DUE_SOON인지를 정한 자리가 2026-09-09 전수 확인에서 어디에도 없었다.** 값은 사용자 확정 2026-09-10으로 **남은 일수 3일 이하**가 됐고 정본은 기준값 테이블의 **FILING_DEADLINE / due_soon_window**(제품 파라미터 · rule days_before_due · 흡수 근거 [../03_requirements/01_global_rules.md](../03_requirements/01_global_rules.md) §1.3)다 — **코드에 상수로 두지 않는다.** 억제 키는 그래도 임박 구간이 아니라 **(과제, dueState)**로 잡는다 — dueState 3값이 이미 구간을 담으므로 임계가 정해져도 새 축이 필요하지 않고, 그 파생 계약의 정본은 [../06_api/11_compliance.md](../06_api/11_compliance.md) #8이다.

**임계 기준값이 없으면 이 실행을 시작하지 않는다.** 대상 판정의 구간 자체가 그 값에서 나오므로 **항목 하나의 실패가 아니라 실행이 성립하지 않는 상태**이고, 처분은 실행 이력의 실패 기록이다(사용자 표면의 차단 payroll.missing_reference_value/422에 대응하는 자리). **임의 기본값으로 돌지 않는다** — 경보가 나가는 날이 조용히 달라지고, 억제 키가 파생 상태를 담으므로 같은 기준일 재실행이 다른 구간으로 다시 경보할 수 있다.

### retryPayslipAndPush

**대상이 둘이다** — ① 급여 확정이 만든 **미렌더(PENDING) 명세서를 렌더해 GENERATED로 올리고** ② 실패 상태의 명세서 PDF를 재생성 큐에 넣으며 알림 전송을 재시도한다. ①이 이 작업의 첫 대상인 것은 **확정 트리거가 렌더를 직접 하지 않고 큐에 올리기 때문**이며(브라우저 풀 대기 중에 급여월 잠금을 쥐고 렌더 실패가 확정을 되돌리는 것을 막는 분리다), 그 자리를 두지 않으면 **큐에 소비자가 없어 확정한 명세서가 PENDING에서 멈춘다**(2026-09-11 실측 259건). 명세서 생성 실패는 **급여 확정을 롤백하지 않고** 실패 상태로 남기므로, 이 정기작업이 없으면 실패분이 영구히 미교부 상태가 된다. 15분 주기인 것은 교부 지연이 곧 법정 의무 미이행 시간이기 때문이다. **교부(DELIVERED)까지 밀지는 않는다** — 그 전이의 주체는 관리자의 게시 행위 하나뿐이고, 이미 렌더·교부된 건은 대상에서 빠져 교부 이력을 중복 생성하지 않는다. **v1은 인앱 알림 단일 채널**이므로 이 작업의 재전송 대상도 인앱 알림이며 푸시는 포함하지 않는다(NTF-02 이월).

## 공통 규약

| 항목 | 내용 |
|------|------|
| 분산락 | 다중 서버 인스턴스의 중복 실행을 막는다. 락 획득 실패는 오류가 아니라 정상 종료로 처리하며 **실행 이력에 SKIPPED로 남긴다** — 락 경합과 미실행은 다른 사건이다 |
| **실행 이력 저장처** | **scheduled_job_runs**(테이블 60). 시작·종료 시각 · 기준일 · 대상 수 · 성공/실패 수 · 재시도 회차 · dead_letter_at · 실패 사유 요약을 남긴다. **"돌지 않음"은 행 부재이고 "돌았으나 대상 0건"은 SUCCEEDED + target_count 0**이며, 이 구분이 없으면 멈춘 배치가 드러나지 않는다(REQ-NFR-16) |
| **읽기 권한** | 정기작업이 참조하는 업무 테이블의 조회 축은 **서버 컨텍스트로 명시 열거**된다 — 쓰기만 열고 읽기를 닫아 두면 계산 입력을 얻지 못한다. 대상 목록의 정본은 [../05_database/08_rls_policies.md](../05_database/08_rls_policies.md)의 서버 배치 읽기 축 절이다 |
| 멱등성 | 모든 작업은 같은 기준일로 여러 번 실행해도 결과가 같다. 재시도가 값을 두 번 반영하지 않는다 |
| 기준일 파라미터 | 실행 시각이 아니라 기준일로 동작한다. 지연 실행·수동 재실행이 동일 결과를 내야 한다. **작업별 전일·당일 규칙의 전수 표는 [../04_architecture/07_batch_scheduling.md](../04_architecture/07_batch_scheduling.md) 작업별 기준일 절**이다 |
| **수동 재실행** | 기준일을 지정해 다시 돌리는 **운영 표면**이 있다 — [../06_api/14_system.md](../06_api/14_system.md) **#34** · 플랫폼 ADMIN. **분산락은 우회하지 않고**(경합은 SKIPPED 로 남는다) **백오프 대기와 dead letter 는 건너뛴다** — 뒤 둘은 시각 트리거가 같은 실패를 되풀이하지 않게 막는 문이고, 재개를 담당자의 명시 조작으로만 두는 계약이 그 문까지 막으면 재개 경로가 없어진다. **미래 기준일은 거부한다** — 아직 오지 않은 날의 대상은 성립하지 않는다 |
| 시간대 | 모든 일 경계 판정은 **KST**다. 스케줄러 프로세스 시간대를 Asia/Seoul로 고정한다 |
| 마감 존중 | 마감된 근태 기간과 확정된 급여는 정기작업이 재계산하지 않는다. 확정 입력이 사후에 바뀌면 재현성이 깨진다 |
| 재시도 | 상한을 두고 초과하면 실패 상태를 유지한다 |
| dead letter | 재시도 상한 초과 건은 실패 상태를 유지한 채 dead letter로 기록하고 **운영 통보**를 수행한 뒤 재시도 대상에서 제외한다. 재개는 담당자의 명시 조작이며 **조용한 성공 처리를 하지 않는다** |
| 운영 통보 수단 | **운영 통보는 관측 채널(에러 추적·로그 경보 — ADR-23)이며 인앱 알림이 아니다.** 수신자가 사용자가 아니라 운영자이고 알림 테이블은 수신자 사용자 축이라 운영자 집단을 담을 수 없다. **사용자의 업무가 멈추는 사건(사업장 자동 정지)만 인앱 필수 알림(workplace_suspended)을 함께 보낸다** |
| 실행 이력 상세 | 작업 간 실행 순서에 의존하지 않는다. 같은 (작업, 기준일)의 성공 실행은 1건이며 실패 행은 재시도 회차만큼 쌓인다. **하루에 여러 번 도는 작업의 이력이 최신 1행으로 접히는 결과**의 정본은 [../04_architecture/07_batch_scheduling.md](../04_architecture/07_batch_scheduling.md) 실행 이력 절이다 |
| 알림 중복 억제 | 경보성 작업은 같은 과제·같은 구간의 재발송을 발송 이력으로 억제한다 |
| 권한 | 정기작업은 사용자 세션이 아니라 서버 전용 경로로 실행한다. 사업장 스코프는 작업 내부에서 명시 필터로 강제한다 |

## v1.1 이월 5건

원천이 정의한 13건 중 아래 5건은 v1에 두지 않는다. 이월 사유와 추가 시점의 정본은 [../01_overview/05_priorities_roadmap.md](../01_overview/05_priorities_roadmap.md)다.

| 작업 | v1에 두지 않는 이유 |
|------|-------------------|
| recomputePayrollMonthlyStats | 월별 통계 재계산은 대시보드(DSH) 소비처가 v1 범위 밖이라 산출할 대상이 없다 |
| checkStatutoryRateCoverage | 기준값 누락 자동 점검. **아래 운영 주의 참조** |
| sendPayrollClosingReminder | 미마감 귀속월 안내. 첫 마감 주기에는 관리자가 직접 인지할 수 있는 규모다 |
| purgeExpiredData | 보존만료 데이터 비식별화·파기. **기산일 관리(CMP-04)가 먼저 안정화되어야 한다** — 기산일이 틀린 상태로 파기 정기작업을 돌리면 그 자체가 위반이다 |
| checkLeavePromotion | 연차 사용촉진 판정. 촉진 기능(LEV-07)이 v1.1 이월이라 판정 대상이 없다 |

### 운영 주의 — 기준값 누락 점검은 수동 절차로 대체한다

**checkStatutoryRateCoverage를 v1에 두지 않는 것이 이 목록에서 가장 위험한 이월이다.** 요율·세액표·최저임금이 비어 있으면 급여가 통째로 틀리거나 계산 자체가 차단되는데, 자동 점검이 없으면 그 사실을 급여 확정 당일에야 알게 된다.

- **배포 전 수동 확인 절차를 필수 운영 항목으로 둔다.** 귀속월과 지급일에 필요한 기준값이 전부 등록되어 있는지, 유효기간이 겹치거나 비어 있지 않은지 확인한다.
- **확인자 필드가 비어 있는 행은 미확인으로 간주해 계산이 차단**되므로, 점검 항목에 "값이 있는가"뿐 아니라 **"확인자가 채워져 있는가"** 를 포함한다.
- 연도 경계와 **7월 경계**(국민연금 기준소득월액 상하한)를 별도 점검 시점으로 잡는다. 연 1회 점검으로는 7월 경계를 놓친다.
- **미확인 기준값은 확인 전까지 시드하지 않는다** — 추정값을 넣으면 차단이 풀려 틀린 값으로 계산이 진행된다. **목록과 건수의 정본은 [../01_overview/05_priorities_roadmap.md](../01_overview/05_priorities_roadmap.md) 미확인 절**이다.
